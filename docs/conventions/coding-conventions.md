## 1. 기본 원칙

- 모든 작업은 **브랜치 기반으로 진행**하며 `main` 및 `develop` 브랜치에 직접 push 하지 않습니다.
- 신규 작업은 **최신 `develop` 브랜치를 pull**한 뒤 시작합니다.
- 작업을 작은 기능·수정 단위로 나누고 **PR을 통해 코드 리뷰 후 병합**합니다.
- 작성자는 본인의 변경 사항과 확인 방법을 설명할 수 있어야 합니다.
- 공통 설정·의존성·DB·API 변경은 영향을 받는 팀원과 먼저 공유합니다.
- 기술적 의견이 다를 경우 **근거 기반으로 논의 후 결정**합니다.

## 2. Branch

### 브랜치 역할

| 브랜치         | 역할                 | 생성 기준        | PR 대상                     |
| ----------- | ------------------ | ------------ | ------------------------- |
| `main`      | 배포 가능한 안정 버전       | 초기 저장소 구성    | —                         |
| `develop`   | 개발 결과 통합 및 연동 확인   | `main`       | 배포 시 `main`               |
| `feature/*` | 기능 추가·개선           | 최신 `develop` | `develop`                 |
| `fix/*`     | 개발 중 발견한 오류 수정     | 최신 `develop` | `develop`                 |
| `chore/*`   | 설정·의존성·문서 등 유지 작업  | 최신 `develop` | `develop`                 |
| `hotfix/*`  | 현재 배포 버전의 긴급 오류 수정 | 최신 `main`    | `main`, 이후 `develop`에도 반영 |

### 브랜치 이름

```text
브랜치종류/이슈번호-도메인-작업내용
```

- 영문 소문자·숫자·하이픈을 사용합니다.
- 공백과 개인 이름 대신 작업 목적을 적습니다.
- 도메인은 `auth`, `notice`, `preparation`, `admin` 등 담당 기능 영역을 의미합니다.
- 공통 작업은 `common`, 문서 작업은 `docs` 등을 사용할 수 있습니다.

예시:

```text
feature/12-preparation-save-state
fix/27-preparation-missing-status
chore/31-common-lint-config
chore/35-docs-local-setup
hotfix/42-auth-login-error
```

### 작업 시작·동기화

1. 신규 작업을 시작하기 전에 로컬 미커밋 변경 사항을 확인합니다.
2. 로컬 `develop`을 원격의 최신 상태로 갱신합니다.
3. 최신 `develop`에서 작업 브랜치를 만듭니다.
4. 기존 작업 브랜치를 계속 사용하는 경우, 필요한 시점에 최신 원격 `develop`을 작업 브랜치로 병합합니다.
5. 충돌이 발생하면 관련 코드 담당자와 변경 의도를 확인합니다.

공유 브랜치의 이력을 임의로 변경하거나 force push하지 않습니다. 충돌을 해결할 때 다른 사람의 변경을 일괄 삭제하지 않습니다.

### 병합 방식

- 작업 브랜치 → `develop`: **Create a merge commit**
- `develop` → `main`: **Create a merge commit**
- 긴급 수정: `main` 반영 후 수정 사항이 포함된 `main`을 `develop`에 PR로 병합해 동기화합니다.

작업 브랜치는 병합 후 삭제하지 않고 다음 작업에는 새 브랜치를 만듭니다. `main`과 `develop`은 유지합니다. 긴급 수정 브랜치에서 작업 후에는 양쪽 반영을 확인합니다.

## 3. Code Style

### 적용 도구

- **Prettier:** 들여쓰기·줄바꿈·따옴표 등 코드 형식 통일
- **ESLint:** JavaScript·TypeScript의 오류 가능성과 코드 규칙 검사
- 개인 편집기 설정보다 저장소에 공유된 설정을 우선합니다.
- ESLint와 Prettier의 형식 규칙이 충돌하지 않도록 구성합니다. [Prettier 공식 안내](https://prettier.io/docs/integrating-with-linters)

### 기본 스타일

| 항목         | 규칙                               |
| ---------- | -------------------------------- |
| 들여쓰기       | 공백 4칸                            |
| 세미콜론       | JavaScript·TypeScript에서 사용       |
| 문자열        | JavaScript·TypeScript에서 싱글 쿼트 우선 |
| 줄바꿈        | LF                               |
| 파일 끝       | 개행 유지                            |
| 사용하지 않는 코드 | 불필요한 변수·import·임시 코드 제거          |

JSON과 JSX 속성 등은 언어 문법과 포맷터 설정을 따릅니다. Java 문자열은 더블 쿼트를 사용합니다. Java는 **IntelliJ 내장 포맷터**, React·TypeScript는 **VS Code의 Prettier·ESLint**를 사용합니다. Java에도 공백 4칸·LF·파일 끝 개행을 적용합니다.

Java 코드 스타일은 저장소의 `backend/config/intellij-java-style.xml`과 루트 `.editorconfig`로 공유합니다. IntelliJ에서 같은 스타일 XML을 가져오고, 자동 검사는 Spotless의 `idea()`로 같은 XML을 참조합니다. 공유 XML과 로컬 CLI 검증은 완료했습니다. 팀 IDE·CLI·CI의 동일 버전·결과·실행 시간 확인과 필수 검사 연결은 후속 작업입니다. [IntelliJ 코드 스타일 공유](https://www.jetbrains.com/help/idea/configuring-code-style.html), [Spotless IntelliJ 연동](https://github.com/diffplug/spotless/tree/main/plugin-gradle#intellij-idea)

### Prettier 설정안

```json
{
    "tabWidth": 4,
    "useTabs": false,
    "semi": true,
    "singleQuote": true,
    "endOfLine": "lf",
    "overrides": [
        {
            "files": ["*.yml", "*.yaml"],
            "options": {
                "tabWidth": 2
            }
        }
    ]
}
```

YAML은 공백 2칸을 사용하도록 예외를 둡니다. 그 외 지원 파일은 위 설정과 포맷터의 언어별 처리 결과를 따릅니다. [Prettier 옵션 문서](https://prettier.io/docs/options)

### 이름과 주석

- 변수·함수는 역할이 드러나는 이름을 사용합니다.
- JavaScript·TypeScript의 변수·함수는 `camelCase`를 기본으로 합니다.
- 클래스·타입·UI 컴포넌트는 해당 언어와 프레임워크의 관례를 따릅니다.
- `data1`, `temp2`처럼 의미가 불분명한 이름을 피합니다.
- 주석은 코드만으로 알기 어려운 이유·제약·계산 근거를 설명합니다.
- 해결하지 않은 TODO는 관련 이슈를 연결합니다.
- 의미 있는 운영 로그는 유지하되, 임시 디버깅 출력과 민감한 정보 출력은 제거합니다.

React·Java의 이름 규칙은 아래 기술별 항목을 따릅니다. 이전 ‘확정 기술 스택 및 스택별 개발 규칙’의 모노레포·기능별 계층 구조를 채택합니다. 현재 프로젝트 루트는 `jibro-housing/`, 백엔드 기본 패키지는 `org.jibro`입니다. 기본 공통 설정은 구성했으며 도메인별 계층은 실제 기능 구현 시 추가합니다.

## 4. Commit

### 형식

```text
type: 작업 내용
```

예시:

```text
feat: 신청 준비 상태 저장 추가
fix: 조건 미확인 항목의 준비도 반영 수정
docs: 로컬 실행 방법 작성
refactor: 준비도 계산 로직 분리
test: 다른 사용자의 준비 건 접근 차단 검증 추가
```

### 타입 목록

| 타입         | 설명                                   |   |
| ---------- | ------------------------------------ | - |
| `feat`     | 새로운 기능 및 화면, 사용자 동작 추가               |   |
| `fix`      | 잘못된 동작, 화면, 버그 수정                    |   |
| `docs`     | 코드 변경 없이 설명 문서만 수정                   |   |
| `style`    | 논리 및 동작 변화 없는 코드 형식 수정 (포맷팅, 세미콜론 등) |   |
| `refactor` | 논리 및 동작을 유지한 구조 개선                   |   |
| `test`     | 테스트 코드 추가·수정                         |   |
| `chore`    | 빌드·의존성·공통 설정 등 유지 작업                 |   |
| `comment`  | 필요한 주석 추가 및 변경                       |   |
| `!HOTFIX`  | 긴급한 버그 수정                            |   |

- 파일 수정이나 삭제 시 변경 목적에 맞춰 `refactor`, `chore` 등 사용
- UI 추가는 `feat`, 잘못된 UI 수정은 `fix`

### 작성 원칙

- 한 커밋에는 가능한 한 하나의 목적을 담습니다.
- ‘수정’, ‘작업 완료’ 대신 무엇을 바꿨는지 적습니다.
- 기능 변경과 전체 파일 포맷 변경을 한꺼번에 섞지 않습니다.
- 생성 파일·빌드 결과·비밀 정보가 포함되지 않았는지 확인합니다.

## 5. Pull Request

### PR 생성 기준

- 검토 가능한 기능·수정 단위가 되면 생성합니다.
- 설계나 방향에 대한 조기 의견이 필요하면 **Draft PR**을 사용합니다.
- 일반 작업의 대상 브랜치는 `develop`입니다.
- 하나의 PR에는 가능한 한 하나의 목적을 담습니다.
- 기능 연동에 필요한 프론트엔드·백엔드·API 문서 변경은 같은 PR에 담을 수 있습니다. 작업량이 크면 연결된 PR로 나누고 선행 작업·API 호환성과 통합 확인 순서를 적습니다. 관련 없는 작업은 함께 넣지 않습니다.
- PR 작성자는 먼저 변경 내용을 직접 확인합니다.
- 의미 있는 변경은 [프로젝트 작업 기록](../history/README.md)에 문제·고려한 선택지·결정 이유·검증·기여·한계를 기록하고 PR에서 해당 기록을 연결합니다. 커밋 파일 목록만으로 원인이나 테스트 성공을 추정하지 않습니다.

### PR 제목

```text
[타입] #이슈번호 작업 내용
```

예시:

```text
[feat] #12 신청 준비 상태 저장 API 구현
[fix] #27 조건 미확인 상태 표시 수정
```

### 이슈 연결·종료

일반 PR 본문에는 다음처럼 관련 이슈를 표시합니다.

```text
Refs #12
```

`#12`는 이슈 참조이며, 위 표기 자체로 이슈가 자동 종료되지는 않습니다.

**기본 브랜치가 `main`인 경우, `develop` 대상 PR에 `Closes #12`를 적어도 자동 종료되지 않습니다.** 개발 작업 이슈는 `develop` 병합과 완료 조건 확인 후 담당자가 종료합니다. 배포까지 필요한 작업은 해당 조건을 확인할 때까지 유지합니다. [GitHub 공식 안내](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue)

```markdown

## 변경 목적
<!-- 어떤 문제를 해결했는지 작성해주세요. -->
- 

## 작업 내용
<!-- 주요 변경 사항을 작성해주세요. -->
<!-- 예:

- 요청 DTO에 Jakarta Bean Validation 적용

## 확인 방법 및 결과
<!--

- 화면 변경은 필요한 스크린샷을 첨부합니다.
- 수동 확인은 재현 순서, 기대 결과, 실제 결과를 적습니다.

-->

## 리뷰 포인트
<!-- 리뷰어가 집중해서 봐주었으면 하는 부분이 있다면 작성해주세요. -->

- 저장 트랜잭션과 소유자 확인 위치가 적절한지 확인 부탁드립니다.
-->

## 영향 및 후속 작업
<!--
- API·DB·환경변수·의존성 변경 여부
- 다른 팀원이 수행해야 할 설정 또는 작업
- 남은 문제와 연결된 이슈
- 해당 사항이 없으면 ‘없음’으로 작성합니다.

## 체크리스트

- [ ] 커밋 메시지 컨벤션을 준수했습니다.
- [ ] 변경에 필요한 검사·빌드·테스트를 수행하고 결과를 적었습니다.
- [ ] 임시 코드와 불필요한 디버깅 출력(console.log)을 정리했습니다.
- [ ] 비밀 정보가 포함되지 않았습니다.
- [ ] 필요한 문서와 실행 안내를 갱신했습니다.
```

## 6. PR 리뷰와 병합

### 승인 기준

- 작성자를 제외한 **최소 1명이 검토하고 승인**합니다.
- 필수 수정 의견과 변경 요청을 해결한 후 병합합니다.
- 의견을 반영하지 않을 경우 이유를 설명하고 합의합니다.
- 승인 이후 동작에 영향을 주는 변경을 추가하면 재검토를 요청합니다.
- 설정된 필수 자동 검사가 있다면 통과해야 합니다.

### 리뷰 의견 구분

| 표시     | 의미                             |
| ------ | ------------------------------ |
| `[필수]` | 병합 전에 해결해야 하는 오류·요구사항 누락       |
| `[제안]` | 개선 의견. 논의 후 현재 PR 또는 후속 작업에 반영 |
| `[질문]` | 구현 의도나 동작 확인                   |

취향 차이를 필수 수정으로 요구하지 않습니다. 코드 형식은 공통 도구로 처리하고, 리뷰에서는 동작·이해 가능성·예외 처리를 중심으로 확인합니다.

### 초보 팀원과의 리뷰

- 함께 실행하거나 작성자의 설명을 들으며 검토할 수 있습니다.
- 리뷰어는 직접 확인한 범위와 추가 확인이 필요한 부분을 남깁니다.
- 계산·인증·DB 변경처럼 영향이 큰 부분은 이해 가능한 담당자와 함께 검토합니다.
- 이해하지 못한 변경을 승인 조건 충족만을 위해 승인하지 않습니다.

### 병합 담당

조건을 충족한 일반 작업 PR은 작성자가 병합하는 것을 기본으로 합니다. 배포 PR은 지정한 배포 담당자가 확인 후 병합합니다.

검토가 지연되면 팀 채팅에서 요청하고 검토자를 조정합니다. 승인 없이 직접 push하는 방식으로 우회하지 않습니다.

### 저장소 설정 제안

`main`과 `develop`에는 다음을 설정합니다.

- PR을 통한 변경
- 최소 1명 승인
- force push·브랜치 삭제 제한
- 실제 구성된 자동 검사의 통과 요구

설정 지원 범위는 저장소 공개 여부와 GitHub 요금제에 따라 확인합니다. [GitHub 보호 브랜치 안내](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)

## 8. 실행 환경과 의존성

- 실행에 필요한 언어·런타임·패키지 매니저 버전을 공유합니다.
- 같은 프로젝트에서 여러 패키지 매니저를 혼용하지 않습니다.
- 사용하는 패키지 매니저의 잠금 파일을 저장소에 포함합니다.
- 새 라이브러리는 도입 목적·대안·영향을 PR에 적습니다.
- `.env`와 실제 키·비밀번호는 커밋하지 않습니다.
- 필요한 환경변수 이름은 값 없는 예시 파일로 공유합니다.
- README에는 설치·실행·검사·테스트·초기 데이터 준비 방법을 기록합니다.

검사·빌드 스크립트와 CI workflow 파일은 기본 구성했습니다. 실행 방법은 [개발 환경 안내](../getting-started.md), 실제 통과 범위는 [초기 설정 검증 기록](../verification.md)을 따릅니다. 원격 Actions 실행과 보호 브랜치 설정은 후속 작업입니다. AWS 배포 자동화는 이번 문서에서 확정하지 않습니다.

### 백엔드: IntelliJ IDEA 설정

- 백엔드 개발은 **IntelliJ IDEA**에서 진행합니다. 팀과 CI가 사용하는 포맷터의 IntelliJ 버전은 동일하게 고정합니다.
- `backend/build.gradle`을 기준으로 Gradle 프로젝트로 연결합니다. 의존성·소스 경로는 IDE에서만 수동 추가하지 않고 Gradle 설정에서 관리합니다.
- Project SDK와 Gradle JVM은 **Eclipse Temurin 17**, Java 언어 수준은 **17**로 맞춥니다. Temurin은 JDK 배포판으로 IDE와 별개입니다. IntelliJ 자체 실행 런타임과 프로젝트 JDK 설정은 구분합니다.
- Gradle 배포판은 저장소의 **Wrapper**를 사용하고, `Build and run using`과 `Run tests using`은 **Gradle**로 설정합니다.
- Querydsl Q 클래스는 Gradle annotation processing으로 생성합니다. IDE에서 인식되지 않으면 빌드·동기화와 생성 소스 경로를 확인하며 생성 파일을 직접 작성하거나 커밋하지 않습니다.

### Java 포맷 적용·검사

- Java 포맷 엔진은 **IntelliJ 내장 포맷터**를 사용합니다. 일반 들여쓰기는 공백 4칸이며, 줄바꿈 등 상세 스타일은 공유 XML과 EditorConfig를 기준으로 합니다.
- IntelliJ의 Editor → Code Style에서 공유 XML을 가져오고 프로젝트에 적용합니다. EditorConfig와 XML의 겹치는 설정은 일치시킵니다.
- 편집 중에는 IntelliJ의 `Reformat Code`를 사용합니다. 다른 Java 포맷터 플러그인이 해당 동작을 덮어쓰지 않도록 설정합니다.
- Java 포맷 엔진은 `idea()`를 활용합니다. 공유 XML 경로와 IntelliJ 실행 파일 경로를 설정하며, 대상은 직접 작성한 main·test Java 소스로 제한합니다. 생성된 Q 클래스는 제외합니다.
- 자동 적용·검사 명령은 `spotlessApply`·`spotlessCheck`를 유지합니다. 명령행 포맷터에는 IntelliJ 실행 환경이 필요하며 실행 중인 IDE와 충돌할 수 있으므로 로컬에서 해당 명령을 사용할 때는 IntelliJ를 종료합니다. 편집 중 적용은 IDE의 Reformat Code로 진행합니다.
- CI에는 같은 버전의 IntelliJ 명령행 포맷터를 준비합니다. 설치·실행 경로, 실행 시간, IDE와 CLI의 동일 결과를 확인한 뒤 PR 필수 검사로 연결합니다. 실행 환경이 없거나 실패하면 검사 성공으로 처리하지 않습니다.
- 개인 IDE 상태·로컬 경로·비밀값은 커밋하지 않습니다. 공통 스타일 XML과 EditorConfig만 기준 설정으로 공유합니다.

[IntelliJ Gradle 설정](https://www.jetbrains.com/help/idea/gradle-settings.html), [IntelliJ 명령행 포맷터](https://www.jetbrains.com/help/idea/command-line-formatter.html), [Spotless IntelliJ 연동](https://github.com/diffplug/spotless/tree/main/plugin-gradle#intellij-idea)

### 프론트엔드: VS Code 설정

- 프론트엔드 개발은 **VS Code**에서 진행하고 `frontend`를 작업 폴더로 엽니다.
- **Prettier - Code formatter**(`esbenp.prettier-vscode`)와 **ESLint**(`dbaeumer.vscode-eslint`) 확장을 사용합니다.
- TypeScript·TSX 등의 기본 포맷터를 Prettier로 지정하고 저장 시 포맷을 적용합니다. Java 파일에는 해당 설정을 적용하지 않습니다.
- 확장에 포함된 기본값보다 프로젝트에 설치된 Prettier와 저장소 설정을 기준으로 합니다. 공백 4칸·세미콜론·싱글 쿼트 등 기존 규칙을 유지합니다.
- ESLint는 코드·Hook 규칙을 검사하며 포맷 규칙은 Prettier와 충돌하지 않게 구성합니다.
- 실행·검사는 공통 npm 스크립트로 수행합니다. 공통 `frontend/.vscode/settings.json`·`extensions.json`을 공유하며 로컬 경로·비밀값을 넣지 않습니다.

[VS Code Prettier 확장](https://github.com/prettier/prettier-vscode)

### 모노레포 운영 원칙 — 2026.10.20 확정

**GitHub 저장소는 하나로 유지하고, 프론트엔드·백엔드는 별도 프로젝트로 실행·빌드·배포합니다.** 소규모 팀에서 연동 변경·이슈·문서를 함께 확인하기 위한 선택입니다. Java와 TypeScript의 의존성을 하나로 합치거나 두 애플리케이션을 항상 함께 배포한다는 뜻은 아닙니다.

| 구분 | 프론트엔드 | 백엔드 |
| --- | --- | --- |
| 작업 폴더·IDE | `frontend/` · VS Code | `backend/` · IntelliJ IDEA에서 Gradle 프로젝트로 연결 |
| 의존성 관리 | 해당 폴더의 `package.json`·`package-lock.json`, npm | 해당 폴더의 Gradle 설정·Wrapper, JDK 17 |
| 로컬 실행 | Vite 개발 서버를 별도로 실행 | Spring Boot를 별도로 실행 |
| 빌드·검사 | 프론트엔드 npm 스크립트 | 백엔드 Gradle Wrapper 작업 |
| 배포 산출물 | React 정적 빌드 파일 | Spring Boot 실행 산출물 |

- 프론트엔드·백엔드의 설치·실행·검사·빌드 명령은 각 작업 폴더에서 수행합니다. 예를 들어 `npm ci`는 `frontend/`, Gradle Wrapper 명령은 `backend/`를 기준으로 합니다. 개발 서버 실행 스크립트와 API 연결 주소·방법은 구성했으며 각 README와 개발 환경 안내에서 확인합니다.
- 루트에서 한 번에 실행하는 편의 명령은 필요할 때 추가합니다. 두 프로젝트를 독립적으로 실행·검사할 수 있는 방법은 유지합니다. 초기에는 별도 모노레포 관리 도구나 루트 npm workspace를 도입하지 않습니다.
- 이슈·브랜치는 기능 또는 수정 목적 단위로 관리합니다. 프론트 전용·백엔드 전용 장기 통합 브랜치를 추가하지 않고 기존 `main`·`develop` 정책을 따릅니다. 한쪽만 바뀌는 작업도 허용하며, 양쪽 변경이 필요하면 담당자와 검토 범위를 함께 적습니다.
- API 변경은 요청·응답·오류 형식과 연결 화면의 영향을 함께 검토합니다. 양쪽 코드가 같은 PR에 있어도 실제 연결 확인을 생략하지 않습니다. 포맷·빌드 등 독립 검사와 사용자 흐름의 통합 확인은 구분합니다.
- 루트 공통 설정이나 같은 파일을 수정할 때는 관련 작업자와 먼저 조율합니다. 변경 목적과 무관한 전체 포맷 변경을 섞지 않습니다. 필요한 문서·설정 변경도 해당 PR에서 함께 검토합니다.
- 배포는 프론트엔드·백엔드별 산출물·버전·적용 및 복구 절차를 구분합니다. 변경 없는 구성요소의 재빌드·재시작을 필수로 묶지 않습니다. API·DB 변경으로 호환성이 달라지면 배포 순서·호환 가능한 조합·통합 확인과 복구 제약을 함께 정합니다.
- **배포 분리는 서버 대수 분리가 아닙니다.** 기존 EC2 1대의 Nginx·Spring Boot 구성과 같은 출처의 `/api/` 연결을 유지할 수 있습니다. 실제 파일 교체·컨테이너 갱신·복구 방법과 자동화는 후속 배포 설계에서 정합니다.

#### 폴더별 책임

| 위치 | 책임 | 집으로 적용 예시 |
| --- | --- | --- |
| `app` | 앱 진입·라우팅·공통 Provider 구성 | QueryClient와 AuthProvider 연결, 페이지 경로 구성 |
| `pages` | 경로별 화면과 기능 컴포넌트 조합 | 공고 상세 화면에서 공고 정보와 준비 시작 동작 연결 |
| `features/{domain}/api` | 도메인별 API 요청·응답 처리 | 공통 fetch로 공고 검색·준비 상태 저장 API 호출 |
| `features/{domain}/hooks` | 기능별 상태 로직·TanStack Query·쿼리 키 | 검색 조건별 조회, 준비 상태 변경 후 관련 캐시 무효화 |
| `features/{domain}/types` | 해당 기능의 API DTO·화면 자료형 | 검색 필터·공고 응답·준비 상태 타입 |
| `features/{domain}/components` | 특정 기능에 속하는 UI | 공고 카드·검색 필터·서류 체크리스트·신청 여정 |
| `features/auth/context` | 공유 로그인 상태와 인증 Provider | 메모리 Access Token·현재 사용자·로그인 복원 상태 |
| `shared` | 특정 기능에 의존하지 않는 요청 함수·UI·유틸·스타일 | 공통 버튼·레이아웃·날짜 표시·HTTP 오류 처리 |
| `src/test` | 테스트 환경의 공통 설정 | Vitest·React Testing Library 초기 설정 |

`user`·`admin`도 필요한 `api`·`hooks`·`types`·`components`를 같은 방식으로 구성합니다. 준비도·조건 안내의 정책 계산은 서버에서 수행하며 프론트엔드는 응답을 표시합니다.

#### 배치·참조 규칙

- 일반적인 참조 방향은 `app → pages → features → shared`입니다. 필요한 하위 영역은 직접 참조할 수 있지만 `shared`가 기능·페이지를 참조하거나, 기능이 페이지·앱 구성을 참조하지 않도록 합니다.
- 기능 간 참조가 필요하면 책임과 순환 참조 여부를 먼저 검토합니다. 공통으로 쓰인다는 이유만으로 업무 규칙을 `shared`에 옮기지 않습니다.
- `pages`는 화면을 조합합니다. 재사용할 기능 UI와 조회·저장 로직은 해당 `features`에 둡니다.
- API 함수는 React Hook과 분리합니다. `noticeApi.ts`가 공통 fetch를 호출하고 `useNoticeList.ts`가 해당 함수를 TanStack Query에 연결합니다. 공통 요청 함수에서 인증 기능을 직접 import하지 않고 필요한 토큰을 인자·설정으로 전달합니다.
- 쿼리 키는 기능별로 관리하며 응답에 영향을 주는 필터·페이지·정렬·개인 사용자 식별값을 반영합니다. 검색 조건의 기준은 URL이며, API 파라미터와 쿼리 키가 같은 값을 사용합니다. [TanStack Query 쿼리 키](https://tanstack.com/query/latest/docs/framework/react/guides/query-keys)
- 로컬 UI는 useState, 공유 인증 상태는 AuthProvider·Context, 서버 데이터는 TanStack Query로 관리합니다. 공고·준비 상태를 인증 Context에 중복 저장하지 않습니다.
- CSS Modules는 컴포넌트 옆에 `NoticeCard.module.css`처럼 둡니다. 전역 스타일만 `shared/styles`에 두고 컴포넌트·Hook·변수 이름은 아래 이름 규칙을 따릅니다.
- 테스트는 대상 파일 가까이에 `NoticeCard.test.tsx`, `noticeApi.test.ts`처럼 둡니다. `src/test/setup.ts`는 공통 초기 설정용이며 모든 테스트를 한곳에 모으는 폴더가 아닙니다.
- 코드에서 사용하는 이미지·폰트는 `src/shared/assets`, 고정 파일명으로 제공해야 하는 파일은 `public`에 둡니다. `public` 파일은 `/파일명`으로 참조합니다. [Vite 정적 파일](https://vite.dev/guide/assets.html)
- 예시의 모든 폴더·파일을 미리 만들지 않습니다. TypeScript·Vite·테스트·VS Code 기본 설정 파일은 실제 버전에 맞춰 생성했습니다. 계정 관리 등 미확정 기능도 폴더 예시만으로 MVP에 추가하지 않습니다.

### 컴포넌트 원칙

- 함수형 컴포넌트를 사용합니다.
- 한 컴포넌트가 데이터 조회·복잡한 계산·여러 UI 영역을 모두 담당하면 역할을 분리합니다.
- 같은 UI가 반복되거나 독립적으로 검증할 가치가 있을 때 공통 컴포넌트로 분리합니다.
- 서버에서 받은 데이터를 화면에서 임의로 다른 의미로 해석하지 않습니다.
- 로딩·빈 결과·오류·정상 상태를 구분해 처리합니다.
- 리스트를 렌더링할 때 배열 순서보다 데이터의 안정적인 식별자를 `key`로 사용합니다.
- 상태를 직접 변경하지 않고 새 값으로 갱신합니다.
- 폼의 필수값·오류 메시지·제출 중 상태를 사용자에게 표시합니다.

### Hook 원칙

- Hook은 컴포넌트 또는 커스텀 Hook의 최상위에서 호출합니다.
- 반복문·조건문·중첩 함수·이벤트 처리 함수 안에서 Hook을 호출하지 않습니다.
- 여러 컴포넌트가 공유하는 상태 로직은 커스텀 Hook 분리를 검토합니다.
- `useEffect`는 외부 시스템과 동기화할 필요가 있을 때 사용하고, 계산 가능한 값을 저장하기 위한 용도로 남용하지 않습니다.
- Hook 규칙은 ESLint로 검사합니다.

React는 Hook을 컴포넌트와 커스텀 Hook의 최상위에서 호출하도록 규정합니다. [React 공식 Hook 규칙](https://react.dev/reference/rules/rules-of-hooks)

### TypeScript·API 연동 추가 규칙

- TypeScript의 엄격한 타입 검사(`strict`)를 사용합니다. `any`를 임의로 사용하지 않고, 외부 응답처럼 확인이 필요한 값은 타입·검증 근거를 작성합니다.
- API 요청·응답 타입은 API 계약과 맞추며, TypeScript 타입만으로 서버 응답의 런타임 검증이 끝났다고 보지 않습니다.
- API 요청은 공통 fetch 함수와 기능별 API 모듈로 분리합니다. HTTP 오류를 공통 함수에서 처리하고 TanStack Query의 오류 상태로 전달합니다.
- 서버 조회·캐시·저장 후 재조회는 TanStack Query v5로 관리합니다. 검색 조건·페이지를 쿼리 키에 포함하고 준비 상태 변경 후 관련 쿼리를 무효화합니다.
- 로컬 UI 상태는 useState, 여러 화면이 공유하는 로그인 상태는 Context로 관리합니다. 서버 데이터를 Context에 중복 저장하지 않습니다.
- 로그아웃·사용자 전환 시 이전 사용자의 개인 데이터 캐시를 제거합니다. 개인 조회의 쿼리 키와 활성화 조건에 인증 상태를 반영합니다.
- 상태는 필요한 컴포넌트 가까이에 둡니다. 여러 화면이 공유해야 할 필요를 확인한 뒤 공통 상태로 올립니다.
- 로딩·빈 결과·오류·정상 상태 외에 비로그인·접근 권한 부족 상태도 구분합니다.
- 서버에 저장된 준비 상태·준비도·조건 안내 결과를 기준으로 화면을 표시합니다. 프론트엔드에 별도의 정책 판정 로직을 중복 구현하지 않습니다.
- 화면을 숨기는 것만으로 접근 권한이 보장되지 않습니다. API에서 권한을 검증합니다.

## 12. Spring Boot·Spring MVC·Java 규칙

### 패키지 구조 예시

기능 영역을 기준으로 구성하고, 각 영역 안에서 계층을 나눕니다. 집으로의 도메인은 `auth`, `user`, `notice`, `preparation`, `admin`, `global`로 정합니다.

```text
org.jibro
├─ auth
├─ user
├─ notice
│  ├─ controller
│  ├─ service
│  ├─ repository
│  ├─ dto
│  └─ entity
├─ preparation
├─ admin
└─ global
   ├─ config
   ├─ error
   └─ common
```

`org.jibro`는 생성한 백엔드의 실제 기본 패키지입니다. 아래 기능별 구성은 구현 시 확장할 예시이며 현재 모두 생성된 구조는 아닙니다. 다른 기능 영역도 필요한 계층을 같은 방식으로 구성하며 빈 패키지를 미리 만들 필요는 없습니다. `user`는 사용자 정보, `auth`는 로그인 수단·인증·토큰을 담당합니다. Entity 관련 규칙은 채택한 Spring Data JPA에 적용합니다.

### 계층별 책임

| 계층 | 책임 |
|---|---|
| Controller | 요청 수신, 입력 검증, HTTP 응답 변환 |
| Service | 비즈니스 규칙, 작업 순서, 트랜잭션 경계 |
| Repository | 데이터 조회·저장 |
| DTO | API 요청·응답 데이터 |
| Entity | DB에 저장되는 도메인 상태 |
| Global | 공통 설정, 오류 처리, 공통 응답 |

### 기본 원칙

- Controller에 비즈니스 로직을 작성하지 않습니다.
- Entity를 API 응답으로 직접 반환하지 않고 응답 DTO로 변환합니다.
- 입력값은 요청 DTO에서 검증하고, 중요한 비즈니스 조건은 Service에서 다시 확인합니다.
- 의존성은 생성자 주입을 사용합니다.
- 여러 데이터 변경이 하나의 작업으로 함께 성공하거나 실패해야 한다면 Service에서 트랜잭션 경계를 설정합니다.
- 예외를 Controller마다 반복 처리하지 않고 공통 예외 처리 구조를 사용합니다.
- 오류 원인을 노출할 필요가 없는 내부 예외와 사용자가 수정할 수 있는 입력 오류를 구분합니다.
- 사용자 입력·인증 정보·개인정보를 로그에 그대로 남기지 않습니다.

Spring MVC는 Servlet 기반 웹 프레임워크로, 요청 처리·데이터 바인딩·오류 응답·CORS 등의 기능을 제공합니다. [Spring MVC 공식 문서](https://docs.spring.io/spring-framework/reference/web/webmvc.html)

Spring은 JDBC·JPA 등 여러 데이터 접근 기술에 일관된 트랜잭션 추상화를 제공합니다. [Spring 트랜잭션 공식 문서](https://docs.spring.io/spring-framework/reference/data-access/transaction.html)

### Gradle·Java 환경과 프로젝트 추가 규칙

- 실행·빌드는 저장소의 Gradle Wrapper를 사용합니다. `gradlew`, `gradlew.bat`, Wrapper 설정과 JAR을 함께 관리하며 개인 전역 Gradle 버전에 의존하지 않습니다.
- Java Toolchain을 17로 지정합니다. Gradle 8.14.x와 Groovy DSL, Eclipse Temurin 17을 사용합니다. 공통 설정에서 실제 빌드에 사용되는 JDK를 확인합니다.
- 클래스는 `PascalCase`, 메서드·변수는 `camelCase`, 상수는 `UPPER_SNAKE_CASE`, 패키지는 영문 소문자를 사용합니다.
- 서버의 오류 응답에 SQL·스택 추적·내부 비밀값을 노출하지 않습니다.
- 정책 조건·준비도 계산은 별도 로직으로 분리하고, 미확인 상태와 공고 버전 변경 사례를 검증합니다.

## 13. REST API 규칙

### URL

```text
/api/v1/{resources}
/api/v1/{resources}/{id}
```

- 경로에는 명사를 사용합니다.
- 컬렉션 자원은 복수형을 기본으로 합니다.
- 동작은 URL의 동사보다 HTTP 메서드로 표현합니다.
- URL에 화면명이나 프런트엔드 컴포넌트명을 넣지 않습니다.

예시:

```text
GET    /api/v1/notices
GET    /api/v1/notices/{id}
POST   /api/v1/notices
PATCH  /api/v1/notices/{id}
DELETE /api/v1/notices/{id}
```

### HTTP 상태 코드

| 코드 | 사용 상황 |
|---|---|
| `200 OK` | 조회·수정 성공 |
| `201 Created` | 생성 성공 |
| `204 No Content` | 응답 본문이 필요 없는 삭제 성공 |
| `400 Bad Request` | 형식·입력값 오류 |
| `401 Unauthorized` | 인증 필요 또는 인증 실패 |
| `403 Forbidden` | 인증되었지만 권한 없음 |
| `404 Not Found` | 대상 자원을 찾을 수 없음 |
| `409 Conflict` | 중복·현재 상태와 충돌 |
| `500 Internal Server Error` | 예상하지 못한 서버 오류 |

### 공통 오류 응답안

```json
{
    "code": "NOTICE_NOT_FOUND",
    "message": "공고를 찾을 수 없습니다.",
    "fieldErrors": [],
    "timestamp": "2026-10-04T12:00:00Z"
}
```

- `code`: 프런트엔드가 오류 종류를 구분하는 안정적인 코드
- `message`: 사용자 또는 개발자가 이해할 수 있는 설명
- `fieldErrors`: 입력 필드별 오류. 해당하지 않으면 빈 배열
- `timestamp`: 오류가 발생한 시각

성공 응답은 응답 DTO를 직접 반환하며 공통 성공 래퍼를 사용하지 않습니다. 빈 검색 결과도 오류가 아닌 200 응답으로 반환하고 목록 필드는 빈 배열로 표현합니다. 204 응답에는 본문을 넣지 않습니다.

## 14. 프런트엔드·백엔드 API 계약

백엔드 구현 전에 다음 항목을 합의합니다.

- HTTP 메서드와 URL
- 요청 필드명·자료형·필수 여부
- 응답 필드명·자료형·`null` 가능 여부
- 날짜·금액 단위
- 성공·오류 상태 코드
- 빈 결과의 표현
- 페이지네이션 방식
- 요청·응답 예시

JSON 필드명은 `camelCase`를 사용합니다.

API가 변경되면 관련 PR에 다음을 작성합니다.

- 변경 전·후 형식
- 프런트엔드에 미치는 영향
- 기존 데이터와의 호환 여부
- 적용 순서
- API 문서 갱신 여부

프런트엔드는 오류 응답의 문구 전체를 비교해 분기하지 않고 안정적인 오류 코드를 사용합니다.

### 집으로의 확정 계약과 후속 명세

| 항목 | 확정 계약 |
| --- | --- |
| 초기 검색 조건 | 지역·지원 유형·마감 상태·키워드 |
| 조건 결합 | 서로 다른 필터는 AND, 동일 필터의 여러 선택값은 OR |
| 공개 대상 | 기본 정보 검증·공개 완료 공고를 일반 검색에 포함. 준비 안내 보완·미지원 공고도 포함하며 개인별 준비 기능은 별도 검수·공개 상태로 제한 |
| 검색 상태 | URL query parameter에 보관해 새로고침·뒤로가기 시 복원 |
| 페이지네이션 | page는 0부터 시작, size 기본 20·최대 100 |
| 성공 응답 | 응답 DTO 직접 반환, 공통 성공 래퍼 사용 안 함 |
| 빈 검색 결과 | 정상 성공 응답(200), 목록 필드는 빈 배열 |
| 오류 응답 | code, message, fieldErrors, timestamp의 공통 형식 |
| 실제 시각 | UTC로 저장·전송, 한국 시간대(Asia/Seoul)로 화면 표시 |
| 날짜만 있는 값 | 시각과 분리해 날짜로 표현. 공식 공고의 마감 기준·포함 여부 명시 |

필터별 허용 값, 키워드 검색 대상 필드, 정렬의 기준·동률 처리, 페이지 응답 DTO의 필드 명세는 공식 공고 구조화와 API 설계에서 구체화합니다. 공고 수는 검증 표본 수로 제한하지 않습니다. 검색 필터만을 위해 미검증 기관·지원 유형의 준비 규칙을 추가하지 않으며, 동일한 규칙을 적용할 수 있는 범위는 검증 후 확대를 검토합니다.

#### 권한·업무 상태 계약

- 공고 안내 결과와 실제 기관의 자격·당첨 판단을 구분합니다. 미입력·모름을 자동으로 자격 충족 또는 불충족으로 변환하지 않습니다.
- 공개 공고 조회, 로그인한 사용자의 준비 건 관리, 관리자 공고 수정의 권한을 각각 정의합니다. 기본 정보 공개와 준비 안내 제공을 구분하며, 로그인 여부만으로 미검수 준비 규칙에 접근하거나 신규 준비 건을 만들 수 없습니다.
- 토큰 만료·접근 권한 부족·공고 버전 변경·재확인 필요 상태의 코드와 화면 동작을 함께 기록합니다.
- 준비도·조건 안내·지금 할 일의 기준과 공고 버전을 응답 계약에 명시합니다.

### 공고 자동 수집·구조화·검수 계약

| 항목 | 확정 방향 | 적용 범위 |
| --- | --- | --- |
| 수집 | 한 기관의 공식 API 우선 자동 수집 | 신규 공고·기본 정보·원문 및 첨부 링크. 실제 제공 항목을 먼저 확인 |
| 검증 표본 | 첫 구현용 대표 공고 1건과 차이를 대표하는 추가 표본 | 추가 2∼3건은 시작점이며 조건·서류·절차·예외 차이를 검증할 수 있도록 조정. 수집량·지역·유형의 상한이 아님 |
| 구조화 | 반복 항목부터 추출 자동화, 사람이 조건·서류·예외 검토 | 사용자 질문·개인별 준비 규칙으로 변환하는 정확성 확인 |
| 검수·공개 | 공고 정보와 준비 안내를 동일 검수 과정에서 확인하되 결과·공개 상태는 구분 | 기본 정보 검증·공개 완료 공고는 검색·상세 제공. 개인별 준비 안내는 해당 규칙 검수·공개 완료 후 제공 |
| 수정 공고 | 변경 자동 감지 후 영향 검토 | 기존 공개 규칙·사용자 준비 상태를 자동으로 덮어쓰지 않음 |
| 초기 범위·확장 | 한 기관을 우선 조사하되 지역·지원 유형은 미리 제한하지 않음 | 공통 데이터 구조·규칙 재사용성·추가 준비 규칙·검수 및 사용자 검증 작업량으로 초기 범위 선정. 다른 기관 도입은 별도 평가 |

#### 동시 검수와 공개 상태 분리

공고 기본 정보와 준비 안내는 공고·원문 버전별 동일 검수 과정에서 함께 확인합니다. 공통 출처·버전·공식 일정은 한 번 확인한 근거를 공유하며, 검수 결과와 공개 상태는 각각 기록합니다. 동시 검수가 두 영역의 동시 통과·공개를 강제하지 않습니다. 최초 검수 전에는 기본 정보도 공개하지 않습니다.

| 동일 검수의 결과 | 공고 목록·기본 상세 | 개인별 준비 안내 |
| --- | --- | --- |
| 기본 정보·준비 안내 모두 통과 | 공개 | 제공 |
| 기본 정보 통과·준비 안내 보완 필요 | 공개 | 보완 완료까지 제공 보류 |
| 기본 정보 통과·준비 안내 미지원 | 공개 | 미제공 표시 |
| 공고 식별·출처 등 기본 정보 검증 실패 | 공개 보류 | 제공 보류 |

- 기본 정보는 공식 출처·공고 식별·기관·제목·지역과 유형의 의미·신청 단계별 기간·원문 및 첨부 링크를 대조합니다. 모르는 값은 확인 필요로 남기고 제한 없음·상시 모집으로 추정하지 않습니다.
- 준비 안내는 질문·조건·예외·공통 및 조건부 서류·신청 단계·기한·근거를 별도로 대조합니다. 보완 사유·미지원 여부·검토자·확인 시각·기준 버전·공개 이력을 기록합니다.
- 기본 정보의 공개 상태와 현재 준비 안내의 검수·제공 상태를 단일 공개 플래그로 합치지 않습니다. 일반 응답에는 공고 버전·기본 정보 확인일·준비 안내 상태·기준 버전·확인일·신규 준비 시작 가능 여부를 전달하며, 실제 DTO 필드명·상태 코드·오류 코드는 API 명세에서 확정합니다.
- 사용자 상태는 `준비 안내 제공 중`, `준비 안내 검수 중`, `준비 안내 미제공`, `준비 안내 변경 검토 중`으로 구분합니다. 원시 초안·검수 코멘트와 미검수 조건·서류·개인화 규칙은 일반 응답에 노출하지 않습니다.
- 신규 준비 건 생성·조건 질문·개인별 안내 API에서 서버가 기본 정보 공개, 적용 준비 규칙의 검수·공개, 버전 유효성 및 접근 권한을 검사합니다. 버튼 노출만으로 제한하지 않고 직접 요청과 조회 이후의 상태 변경도 검사합니다. 준비 안내가 없는 공고에 빈 규칙·가짜 준비도를 생성하지 않습니다.
- 수정 공고도 한 검수 과정에서 함께 확인합니다. 기본 정보는 해당 검증을 마친 버전으로 갱신할 수 있으나, 영향받는 준비 규칙은 변경 검토 중으로 표시하고 해당 신규 안내·준비 시작을 보류합니다. 기존 사용자의 과거 준비 기록은 버전과 함께 보존·조회하며 최신 안내로 오인시키지 않습니다. 검토 결과로 영향이 없는 범위는 확인 근거를 기록해 유지할 수 있습니다.

#### 수집과 규칙 관리

- 공식 API를 우선 사용합니다. API가 제공하지 않는 원문·첨부 링크는 공식 사이트의 제공 방식에 맞춰 확보합니다. 기관·API·대상 공고·요청 한도·수집 주기는 초기 연동에서 확인하며 API 키는 백엔드에서 관리합니다.
- 기관과 외부 공고 식별자를 연결해 중복을 방지합니다. 제공자가 요구하는 복합 식별자·코드·페이지 기준은 별도 매핑하고, 같은 데이터의 반복 수집·재시도로 중복 공고나 중복 버전이 생기지 않게 합니다.
- 원본 응답, 원문·첨부 주소, 수집·확인 시각, 출처와 버전·변경 근거를 기록합니다. 수집 시각처럼 내용과 무관한 값은 변경 비교에서 제외합니다. 첨부 주소가 같아도 내용이 바뀔 수 있으므로 첨부 식별자·해시 또는 원문 비교로 확인합니다.
- 수집 결과와 구조화 초안은 내부 검수 대상입니다. API 제공 필드나 자동 추출값을 검토 없이 사용자 질문·조건부 서류 규칙으로 확정하지 않습니다.
- 조건·서류·기한마다 공식 근거를 연결합니다. 제출 대상·예외·발급 기준 등은 별도 확인하며 확인되지 않은 항목은 검수 대기·추가 확인 필요로 남깁니다.
- 수정 공고는 새 검수 대상 버전으로 기록합니다. 공개 버전과 사용자 준비 건의 연결을 보존하고, 영향받는 안내는 재확인 필요·변경 검토 중으로 표시하거나 필요 시 일시 비공개 처리합니다. 새 버전 적용과 준비 상태 변경을 하나의 자동 덮어쓰기로 처리하지 않습니다.
- 외부 요청 실패·누락은 수집 실행 기록에 남기고 제한된 재시도로 처리합니다. 실패한 수집을 이유로 기존 공고를 삭제하거나 원문 삭제로 단정하지 않습니다.
- 공개 공고와 사용자 증빙은 구분합니다. 사용자 증빙 원본 업로드는 제외하지만 공식 공고 첨부파일 확보·분석은 허용합니다. 원본 보관 위치·기간·파일 용량 및 S3 필요성은 후속 배포 설계에서 정합니다.

#### 구현·검증 순서

1. 후보 기관의 여러 지역·지원 유형 공고를 비교해 공통 필드와 조건·서류·절차·예외 차이를 기록하고, 첫 구현용 대표 공고 1건의 정답 사례 작성
2. 인터뷰와 병행해 한 기관의 공식 API 연동·신규 공고 및 기본 정보 수집 검증
3. 추가 공고 2∼3건을 시작점으로 주요 규칙·예외·첨부 형식·필드 누락을 대표하는 표본을 구성하고 반복 항목 추출 자동화. 차이가 빠지면 표본을 보완하고 추가 구현·검수 작업량으로 초기 지원 범위 결정
4. 관리자 화면에서 공고 정보·준비 안내를 함께 대조하고 결과·공개 상태·보완 사유를 구분 기록, 기본 목록 공개와 준비 안내 제공 조건 연결
5. 수정 감지·재시도·중복 방지·사용자 재확인 처리 검증

일반 검색은 PostgreSQL의 기본 정보 검증·공개 완료 데이터에서 처리하고 준비 안내의 제공 상태를 함께 반환합니다. 외부 API가 검색 요청마다 서비스 응답을 직접 결정하도록 결합하지 않습니다. 테스트에는 저장한 응답 예시를 사용하고 실제 제공 범위·갱신 동작은 별도 연동 확인으로 검증합니다.

공식 API 후보는 [LH 공고 조회](https://www.data.go.kr/data/15058530/openapi.do), [LH 공고별 공급정보](https://www.data.go.kr/data/15056765/openapi.do)입니다. LH 선정·활용 신청·실제 호출 성공을 확정한 것은 아닙니다. API에 없는 상세 조건·서류·예외는 공식 원문 대조가 필요합니다.

### 공식 발급 링크·캘린더·준비도 구현 계약

| 항목 | 채택한 방향 | 완료·판단 기준 |
| --- | --- | --- |
| 공식 발급 링크 | 검증된 링크를 초기 준비 흐름에 포함 | 서류·대상·발급 방식과 맞는 공식 경로 확인. 확인된 링크부터 제공 |
| 캘린더 파일 내보내기 | 푸시와 분리해 일정 정확성·가져오기 사용성을 검증한 뒤 구현 범위 별도 확정 | 검증된 일정의 .ics 생성, 실제 대상 기기의 가져오기·변경·중복 처리 확인. 기능 구현 자체는 아직 미확정 |
| 푸시·이메일 기한 알림 | 후순위로 유지하고 수요·운영 부담을 별도 판단 | 권한·구독·예약·발송·실패·기한 변경 및 취소 처리 검토 |
| 준비도(%)·집 건축 표현 | 초기 완성 범위에 포함 | 계산·집 단계 매핑·미확인/재확인 표시·저장 결과 일치와 사용자 이해도 검증 |

- 공식 발급 링크는 준비 안내 검수에서 서류·발급 대상·온라인/방문 방식·공식 출처·사용자가 확인할 발급 조건을 대조합니다. 검증된 공식 URL·기관·확인일·적용 서류·근거를 관리하고 서류별로 확인된 링크부터 제공합니다. 로그인·세션에 종속된 주소 대신 안정적인 공식 안내 경로를 사용할 수 있습니다.
- API는 링크 제공 가능 여부와 확인된 발급 방법을 구분해 전달합니다. 미검증 주소를 생성하거나 임의 입력값을 외부 이동 주소로 사용하지 않습니다. 오류·변경 링크는 해당 제공을 보류하고 확인 방법을 안내합니다. 외부 이동만으로 발급 완료·준비도·집 단계를 변경하지 않습니다.
- 캘린더는 검증된 선택 일정의 .ics 파일 생성과 실제 대상 기기의 가져오기를 평가합니다. 기본 정보에서 검증한 공식 신청 일정과 준비 규칙 검수를 거친 개인별 기한의 제공 조건을 구분합니다. 제목·단계·날짜/시각·공식 원문·기준 버전·생성 시점을 포함하고 개인 답변·민감정보는 제외합니다. 날짜만 있는 일정에 임의 시각을 추가하지 않습니다.
- 파일 생성 성공을 외부 캘린더 등록·알림 예약 성공으로 응답하거나 기록하지 않습니다. 자동 동기화·수정 반영을 약속하지 않으며 재가져오기 중복·갱신과 날짜·시간대·한글 표시를 대상 앱에서 확인합니다. 도구·라이브러리·DTO·실제 구현 범위는 검증 후 별도 확정합니다. [Google Calendar 가져오기 안내](https://support.google.com/calendar/answer/37118?hl=ko)
- 푸시·이메일 발송은 캘린더 내보내기와 별도 과제입니다. 사용자 수요와 권한·구독·예약·취소·수정·실패 처리를 확인한 뒤 채택 여부를 정하며, 현재 준비 중 진입점은 실제 예약·발송을 수행하지 않습니다.
- 준비도(%)와 집 건축 표현은 초기 완료 범위입니다. 가중치·공고별 계산 기준·집 단계 매핑은 명세로 확정하되 도입 자체를 후순위로 미루지 않습니다. 서버의 준비 상태·계산 기준 버전을 사용하고 프론트엔드는 같은 결과로 %·집·여정을 표시합니다. 필수 미확인·재확인 안내를 함께 제공하며 자격·당첨 가능성으로 해석하지 않습니다.

## 15. JPA·Querydsl·DB 변경

### JPA

- 단순 저장·조회는 JPA Repository에서 처리합니다.
- 엔티티 관계·트랜잭션·지연 로딩을 이해하고, 필요한 조회의 실행 SQL을 확인합니다.
- 공고 버전과 사용자 준비 건의 연결을 유지합니다. 수정 공고 반영 시 기존 사용자 답변·준비 상태의 처리 방침을 문서화합니다.
- 채택한 Flyway로 공유·배포 DB 구조를 마이그레이션으로 관리하고 JPA의 스키마 설정은 `validate`를 기본으로 합니다. `update`, `create`, `create-drop`으로 공유 DB를 변경하지 않습니다.

### Querydsl 적용 범위와 검증

- 초기부터 지역·지원 유형·마감 상태·키워드를 조합하는 검색이 필요하므로 OpenFeign 계열 Querydsl을 도입합니다. 서로 다른 필터는 AND, 동일 필터의 여러 선택값은 OR로 결합하고 기본 정보 검증·공개 완료 공고를 조회합니다. 준비 안내 미제공·검수 중을 목록 제외 조건으로 사용하지 않습니다.
- 공고별 자격 조건 안내와 준비도 계산은 업무 규칙입니다. Querydsl로 처리하는 검색 조건과 혼동하지 않습니다.
- 복합 조회를 별도 Repository 구현에 분리하며 단순 CRUD 전체를 Querydsl로 바꾸지 않습니다.
- 원본 Querydsl과 OpenFeign 계열 의존성을 혼용하지 않습니다. JDK·Spring Boot·Hibernate·Jakarta JPA와의 호환성을 확인한 한 계열의 버전을 고정합니다.
- Q 클래스는 Gradle의 annotation processing으로 생성합니다. 직접 작성·수정하거나 Git에 커밋하지 않습니다.
- 깨끗한 체크아웃에서도 Wrapper 빌드로 Q 클래스가 생성되고 실제 조회가 수행되는지 확인합니다.
- 조건 없음, 단일·복합 조건, 범위 경계값, 정렬, 페이지 이동과 중복 결과 여부를 검증합니다.

원본 Querydsl의 유지보수가 둔화되었으며 Spring Data는 OpenFeign 포크를 최선의 노력 수준으로 지원한다고 안내합니다. OpenFeign Querydsl 7.7로 Q 클래스 생성과 테스트 PostgreSQL의 복합 조회를 검증했습니다. 실제 공고 모델·검색 API의 업무 검증은 후속 작업입니다. [Spring Data Querydsl 안내](https://docs.spring.io/spring-data/jpa/reference/repositories/core-extensions.html)

### Flyway

- SQL 변경 파일은 `V1__init.sql`, `V2__add_notice_version.sql`처럼 버전과 목적을 표시합니다.
- 공유 DB에 적용한 파일은 덮어쓰지 않고 후속 변경 파일을 추가합니다.
- 샘플·테스트 데이터와 운영 데이터를 구분합니다. 기존 데이터 영향, 적용 순서, 오류 발생 시 복구 방법을 PR에 기록합니다.
- PostgreSQL 전용 동작 검증은 PostgreSQL에서 수행합니다. H2 결과만으로 동일한 동작을 보장하지 않습니다.

## 16. PostgreSQL 규칙

### 이름 규칙

| 대상 | 규칙 | 예시 |
|---|---|---|
| 테이블 | 영문 소문자 `snake_case`, 복수형 | `housing_options` |
| 컬럼 | 영문 소문자 `snake_case` | `monthly_rent` |
| 기본키 | `id` | `id` |
| 외래키 | `{단수형_테이블명}_id` | `user_id` |
| 생성 시각 | `created_at` | `created_at` |
| 수정 시각 | `updated_at` | `updated_at` |

PostgreSQL 예약어와 혼동할 수 있는 단어를 테이블·컬럼명으로 사용하지 않습니다.

### 자료형

- 정수형 금액은 원 단위 `BIGINT` 사용을 우선 검토합니다.
- 소수점이 필요한 금융 값은 정밀도와 소수 자릿수를 정한 `NUMERIC(p, s)`를 사용합니다.
- 정확성이 필요한 금액에 `REAL`이나 `DOUBLE PRECISION`을 사용하지 않습니다.
- 날짜만 필요하면 `DATE`를 사용합니다.
- 실제 발생 시각을 저장할 때는 `TIMESTAMP WITH TIME ZONE` 사용을 우선 검토합니다.
- 긴 문자열이라는 이유만으로 길이 제한 없는 타입을 자동 선택하지 않고 데이터 의미를 먼저 정의합니다.
- 필수 데이터에는 `NOT NULL` 제약조건을 적용합니다.
- 값의 범위가 분명하면 `CHECK` 제약조건을 검토합니다.
- 중복되면 안 되는 값에는 `UNIQUE` 제약조건을 검토합니다.
- 외래키 관계와 삭제 정책을 명시합니다.

PostgreSQL은 정확성이 필요한 금액 등에 `numeric` 사용을 권장하며, `real`과 `double precision`은 부정확한 부동소수점 형식입니다. [PostgreSQL 숫자 자료형 문서](https://www.postgresql.org/docs/current/datatype-numeric.html)

### 시간 처리

- 실제 시각은 UTC 기준으로 저장·전송하고 서버·DB의 시간대 설정을 문서화합니다.
- API의 시각 값은 타임존을 포함한 ISO 8601 형식으로 전달합니다.
- 프런트엔드는 표시할 때 한국 시간대(`Asia/Seoul`)로 변환합니다.
- ‘날짜’와 ‘시각’을 구분합니다. 생년월일·공고 마감일처럼 업무상 날짜가 중요한 값에 무조건 타임스탬프를 사용하지 않습니다.
- 마감 시각에는 포함 여부와 기준 시간대를 함께 정의합니다.

[PostgreSQL 날짜·시간 자료형 문서](https://www.postgresql.org/docs/current/datatype-datetime.html)

### 스키마 변경

- 공용 DB를 수동으로만 수정하지 않습니다.
- 모든 스키마 변경은 마이그레이션 파일로 재현 가능하게 관리합니다.
- 한 번 공유되거나 배포된 마이그레이션을 임의로 수정하지 않고 새로운 마이그레이션을 추가합니다.
- 컬럼 삭제·자료형 변경·`NOT NULL` 추가 전에는 기존 데이터에 미치는 영향을 확인합니다.
- 초기 데이터와 테스트 데이터는 운영 데이터와 구분합니다.
- PR에 적용 방법과 되돌리기 어려운 변경 여부를 작성합니다.

마이그레이션 도구는 Flyway로 확정합니다. 위 스키마 변경 원칙과 15절을 함께 적용합니다.

## 17. Spring Security·JWT

### 확정 인증 정책

| 항목 | 확정 정책 |
| --- | --- |
| 로그인 수단 | 이메일·비밀번호 + Google + 카카오 |
| 인증 구성 | Spring Security + JWT, 소셜 로그인은 Spring Security OAuth2 Login |
| 서비스 토큰 | 세 로그인 경로 모두 자체 Access Token·Refresh Token 발급 |
| Access Token | JWT, 유효기간 15분 |
| Access Token 보관·전송 | React 메모리 보관, Authorization: Bearer 헤더로 전송 |
| Refresh Token | 불투명한 난수 토큰, 유효기간 7일, HttpOnly·Secure 쿠키 |
| Refresh Token 서버 관리 | PostgreSQL에 해시·만료 시각·폐기 상태 저장, 재발급 시 교체 |
| 비밀번호 | Spring Security PasswordEncoder로 단방향 해시 저장 |
| 로그아웃 | Refresh Token 폐기, 쿠키 삭제, 메모리 Access Token·개인 데이터 캐시 제거 |
| 비회원 | 공개 공고 목록·상세 조회 가능 |
| 회원 | 개인 답변·준비 건·준비 상태 저장에는 로그인 필요 |
| 관리자 | 별도 역할로 서버에서 검사. 공개 회원가입 요청으로 관리자 권한 부여 불가 |
| 계정 식별·연결 | 사용자와 로그인 수단을 분리. 이메일이 같아도 자동 병합하지 않으며 기존 계정 인증 후 연결 |
| JWT 검증 | Spring Security Resource Server JWT 기능 활용 |

- JWT 검증과 별개로 회원가입·로그인·토큰 발급·재발급·로그아웃 API를 구현합니다. 소셜 제공자의 토큰을 자체 서비스 API 인증 토큰으로 사용하지 않습니다.
- 구현 순서는 이메일·비밀번호와 JWT 흐름 → Google → 카카오 → 계정 관리입니다. 세 로그인 방식 모두 제공 범위에 포함합니다.
- 서버는 서명·만료·허용 알고리즘과 서비스에서 정한 발급자·대상을 검증합니다. 키는 저장소와 로그에 남기지 않습니다.
- 개인 신청 준비 건은 JWT로 확인한 사용자와 소유자가 일치하는지 검증합니다. 요청 본문의 사용자 ID만 신뢰하지 않습니다.
- 관리자 권한은 서버에서 검사합니다. 클라이언트에서 관리자 화면을 숨기는 것으로 대체하지 않습니다.
- 쿠키로 인증하는 재발급·로그아웃 요청에는 CSRF 대응을 포함합니다. JWT 사용만을 이유로 전체 API의 CSRF 보호를 일괄 해제하지 않습니다.
- 쿠키의 SameSite·Path·Domain 및 개발 환경 설정은 실제 주소 구성에 맞춰 별도로 확정합니다. Refresh Token은 재발급 시 교체하고 이미 사용·폐기된 토큰의 재사용을 차단합니다.
- 새로고침으로 메모리 Access Token이 사라지면 유효한 Refresh Token으로 재발급해 로그인 상태를 복원합니다. 실패 시 비로그인 상태로 전환합니다.
- 로그아웃 후에도 이미 발급한 Access Token은 만료까지 유효할 수 있습니다. 즉시 폐기가 필요하다면 별도 무효화 설계를 검토합니다.
- Authorization 헤더·쿠키·토큰·비밀번호·개인 조건 답변을 디버깅 출력에 남기지 않습니다.

**후속 정책:** 이메일 인증, 비밀번호 재설정, 계정 연결 화면·해제, 탈퇴·데이터 삭제, 관리자 계정 생성 절차는 별도로 확정합니다. Google·카카오 앱 등록·redirect URI·제공 정보·동의 설정도 초기 인증 작업에서 구성합니다.

[Spring Security JWT 안내](https://docs.spring.io/spring-security/reference/servlet/oauth2/resource-server/jwt.html), [SPA·CSRF 안내](https://docs.spring.io/spring-security/reference/servlet/exploits/csrf.html)

- Service의 핵심 비즈니스 규칙을 우선 검증합니다.
- Controller의 요청 검증·상태 코드·응답 형식을 확인합니다.

- 정상값뿐 아니라 경계값·중복값·`null`·잘못된 외래키를 확인합니다.

### 구성한 검사 명령과 실행 범위

다음 npm 스크립트와 Gradle 작업은 새 프로젝트에 등록했습니다. npm 명령은 `frontend/`, Gradle 명령은 `backend/`에서 실행합니다. 상세 환경 변수·실행 절차는 개발 환경 안내를 따릅니다. `build`의 단위 테스트와 DB가 필요한 `integrationTest`는 구분합니다. Java 포맷 검사는 IntelliJ CLI 환경이 필요하며 현재 원격 CI 필수 검사에는 연결하지 않았습니다.

| 범위 | Windows 로컬 | CI·Linux |
| --- | --- | --- |
| 프론트엔드 설치 | `npm ci` | `npm ci` |
| 포맷·린트·타입 | `npm run format:check`, `npm run lint`, `npm run typecheck` | 동일 |
| 프론트엔드 테스트·빌드 | `npm run test:run`, `npm run build` | 동일 |
| Java 포맷 검사 | `./gradlew.bat spotlessCheck` | `./gradlew spotlessCheck` |
| 백엔드 단위 검사·빌드 | `./gradlew.bat clean build` | `./gradlew clean build` |
| PostgreSQL 통합 검사 | `./gradlew.bat integrationTest` | `./gradlew integrationTest` |

- npm의 `package-lock.json`을 커밋합니다. `npm ci`는 잠금 파일을 준비한 뒤 사용합니다.
- TypeScript 타입 검사와 Vite 빌드를 구분해 구성합니다.
- GitHub Actions workflow 파일은 PR의 프론트엔드 포맷·린트·타입·테스트·빌드와 백엔드 단위 테스트·빌드·PostgreSQL 통합 테스트를 각각 수행하도록 구성했습니다. 원격 Actions 실행은 후속 확인 대상입니다. Java 포맷은 같은 IntelliJ CLI 환경을 준비·검증한 뒤 CI에 연결하며, 실제로 구성·검증한 검사만 필수 조건으로 지정합니다.
- 프론트엔드와 백엔드는 실행 폴더·의존성 설치·검사·빌드 결과를 구분한 별도 CI 작업(job)으로 구성합니다. 초기에는 PR에서 두 작업을 모두 실행하며, 파일 경로에 따른 실행 생략은 필요성이 확인되면 공통 설정·API 변경의 영향을 포함해 후속 검토합니다.
- DB 통합 테스트가 있으면 독립적인 PostgreSQL 테스트 환경을 준비합니다. 공용 RDS에서 테스트 데이터를 삭제하지 않습니다.
- 테스트 도구 버전은 Spring Boot의 관리 버전 및 프론트엔드 런타임과 맞춥니다. JUnit의 세부 버전을 임의로 혼용하지 않습니다.

### 프리티어·접근 범위 검토

- EC2는 크레딧 예산·계정의 대상 사양·실제 메모리 사용량을 확인해 선택합니다. 새 Free 플랜에서 대상인 `t3.small`도 후보로 검토할 수 있지만, 무료 기간이 보장된 고정 무료 서버라는 뜻은 아닙니다.
- RDS는 계정 플랜에서 이용 가능한 PostgreSQL의 `db.t3.micro` 또는 `db.t4g.micro`를 후보로 확인합니다. 채택한 Single-AZ 한 대 구성을 기준으로 저장공간·백업·실제 크레딧 소모를 함께 확인합니다.
- RDS는 외부에 공개하지 않고 EC2에서 접근하도록 구성합니다. 실제 네트워크 구성과 개발자의 관리 접속 방식은 후속 설계 대상입니다.
- 인스턴스의 프리티어 대상 표시만으로 전체 비용이 0원이라고 확정하지 않습니다. 계정 생성 시점·Free/Paid 플랜·크레딧·종료 시점을 확인합니다.

[AWS EC2 프리티어 조건](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ec2-free-tier-usage.html), [RDS 프리티어 안내](https://aws.amazon.com/rds/free/), [RDS PostgreSQL 기능](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/CHAP_PostgreSQL.html), [RDS 네트워크 안내](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_VPC.WorkingWithRDSInstanceinaVPC.html)

### 후속 배포 논의에서 확정할 사항

다음은 추후 배포 논의에서 확인합니다.

- AWS 계정 생성 시점, Free/Paid 플랜, 남은 크레딧과 이용 종료 시점
- EC2·RDS 사양·저장공간, PostgreSQL 패치 버전, 서울 리전 내 네트워크·HTTPS 구성
- 비밀값 관리, 프론트·백엔드별 산출물·버전·배포 절차·자동화, API·DB 호환성에 따른 적용 순서와 백업·복구·로그 관리
- 프로젝트 종료 후 서비스·데이터 유지 또는 정리 계획

프리티어 대상 표시만으로 전체 배포 비용이 항상 0원이 되는 것은 아닙니다. 무료 이용 가능 여부는 실제 계정 조건과 구성으로 추후 확인합니다. [AWS 프리티어 조건](https://docs.aws.amazon.com/awsaccountbilling/latest/aboutv2/free-tier.html)

### 범위 제한의 적용과 추가 검토

한 기관을 우선 조사하되 지역·지원 유형은 미리 제한하지 않습니다. 공통 구조로 처리되고 규칙·검수·사용자 검증 작업량을 감당할 수 있는 공고는 초기 범위에 함께 포함합니다. 대표 한 건으로 첫 흐름을 구현하는 순서와 서비스 지원 범위를 구분하며, 표본은 주요 차이를 검증하도록 구성합니다. 자동 수집·개발 환경·작은 기술 실험은 사용자 조사와 병행할 수 있습니다. 공개 계약은 동시 검수와 기본 정보·준비 안내의 결과 및 공개 상태 분리 정책으로 개정하며 개인정보·권한 기준은 유지합니다. 검증된 공식 발급 링크는 초기 구현에 포함하며 캘린더 파일 내보내기는 푸시와 분리해 검증 후 실제 구현 범위를 결정합니다. 준비도(%)·집 건축 표현은 초기 완성에 포함하고 단계적 후도입 제안은 기각합니다. 자세한 결정 상태는 [기획안의 범위 제한 재검토](../planning/project-proposal.md#범위-제한-재검토와-개선-방향)를 따릅니다.
