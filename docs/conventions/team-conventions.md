## 1. 우리가 지향하는 프로젝트

- 구체적인 사용자 문제와 근거를 바탕으로 기획합니다.
- 학기 안에 구현하고 검증할 수 있는 범위를 선택합니다.
- 각 팀원이 설명할 수 있는 결과물과 학습 경험을 남깁니다.
- 진행 상황과 어려움을 일찍 공유합니다.
- 팀원 간 실력 차이를 고려해 작업을 나누고, 특정인에게 일이 몰리지 않도록 조정합니다.

**모르는 것은 괜찮습니다. 막힌 사실을 공유하고 해결 과정에 참여하는 것을 중요하게 생각합니다.**

## 2. 역할과 책임

### 역할 분담 원칙

- 모든 작업에는 **주 담당자 1명**을 정합니다.
- 필요하면 도움을 주는 사람과 검토자를 별도로 정합니다.
- 담당자는 구현뿐 아니라 진행 공유·결과 확인·관련 기록까지 책임집니다.
- 도움을 받더라도 담당자가 결과를 이해하고 설명할 수 있어야 합니다.
- 역할은 고정하지 않고 작업량과 학습 상황에 따라 조정합니다.

| 역할        | 주요 책임                           |
| --------- | ------------------------------- |
| 팀 리더      | 일정·우선순위 조율, 회의 진행, 의사결정 정리      |
| 작업 담당자    | 작업 수행, 진행 공유, 문제 제기, 결과 확인      |
| 검토자       | 요구사항 충족 여부와 결과 확인, 개선 의견 전달     |
| 회의 기록 담당자 | 결정 사항·후속 작업·미결 사항 기록. 회의별 순환 가능 |

**리더는 모든 미완료 작업을 대신 수행하는 사람이 아닙니다.** 일정이 어려워지면 범위 축소·작업 분할·공동 작업·재배정 순으로 해결 방법을 논의합니다.

### 초보 팀원의 참여

- 처음에는 작고 결과가 명확한 작업부터 맡습니다.
- 백엔드는 IntelliJ IDEA의 JDK 17·Gradle Wrapper 연결, 프론트엔드는 VS Code의 Prettier·ESLint 설정과 기본 협업 방법을 함께 실습합니다. 실제 빌드·검사는 공통 Gradle·npm 명령을 기준으로 확인합니다.
- React·TypeScript 화면 수정, Gradle Wrapper 실행, API 요청 확인을 작은 예제로 함께 익힙니다. 공고 데이터 교차 검토와 사용자 테스트도 독립적인 작업으로 배정합니다.
- 문서와 발표도 필요한 기여로 인정하되, 관심과 수업 목표에 맞춰 작은 구현·테스트 경험을 확보합니다.
- 숙련자가 대신 완성하기보다 담당자가 수정하고 마무리할 수 있도록 돕습니다.

## 3. 소통과 기록

| 도구       | 용도                         |
| -------- | -------------------------- |
| 팀 단체 채팅방 | 빠른 질문, 일정 조율, 긴급 공유        |
| Notion   | 기획, 근거 자료, 회의록, 결정 사항, 일정  |
| GitHub   | 코드, 개발 작업, 변경 이력, 코드 검토    |
| 디자인 도구   | 화면 흐름과 UI 협업. 사용 도구는 추후 결정 |

### 기본 원칙

- 일정이나 작업에 영향을 주는 내용은 팀 전체가 확인할 수 있는 곳에 남깁니다.
- 개인 대화에서 결정된 사항도 관련 페이지나 작업에 기록합니다.
- 답변에 시간이 걸리면 확인 여부와 답변 가능한 시점을 먼저 알립니다.
- 채팅에서 논의한 최종 결정은 Notion 또는 해당 GitHub 작업에 옮깁니다.

### 연락 기준 제안

- 평일에는 원칙적으로 24시간 안에 확인 또는 답변합니다.
- 수업·시험·아르바이트 등으로 대응이 어려운 일정은 미리 공유합니다.
- 야간이나 주말의 즉각적인 응답을 기본으로 요구하지 않습니다.
- 팀 일정에 영향을 주는 긴급 사항에는 영향과 필요한 응답 시점을 함께 적습니다.

## 4. 회의 운영

### 정기회의 제안

- 주 1회, 30\~45분 진행합니다.
- 회의 전에 각자 작업 상태와 논의할 문제를 갱신합니다.
- 설명이나 디버깅이 길어지는 사안은 필요한 인원끼리 별도 시간을 잡습니다.

### 기본 안건

1. 지난주 결과물 확인
2. 막힌 작업과 일정 위험 공유
3. 교수님 피드백·사용자 조사 결과 검토
4. 이번 주 목표와 담당자 결정
5. 결정되지 않은 사항과 다음 확인 일정 정리

### 회의록 필수 항목

**일시 / 참석자 / 논의 내용 / 결정 사항 / 후속 작업·담당자·기한 / 미결 사항**

회의를 마칠 때 각 팀원이 **다음 회의까지 무엇을 완료해야 하는지** 확인합니다.

불참 시 가능한 한 사전에 알리고 진행 상황을 남깁니다. 이후 회의록을 확인하고 본인 작업에 영향을 주는 결정에 대해 필요한 의견을 전달합니다.

## 5. 작업 관리

### 작업을 만들 때 적을 내용

| 항목    | 내용                |
| ----- | ----------------- |
| 작업명   | 무엇을 완료할지 구체적으로 작성 |
| 목적    | 사용자 문제·요구사항과의 연결  |
| 담당자   | 주 담당자 1명          |
| 완료 조건 | 어떤 상태가 되면 완료인지    |
| 목표일   | 담당자와 협의한 일정       |
| 선행 작업 | 먼저 필요한 자료·설계·기능   |
| 검토자   | 결과를 확인할 사람        |
| 참고자료  | 관련 문서·화면·근거 링크    |

‘프런트엔드 개발’처럼 큰 작업은 화면이나 기능 단위로 나눕니다.

예: **‘서류 준비 상태를 변경하고 저장 결과와 오류를 화면에 표시하기’**

### 작업 상태

**할 일 → 진행 중 → 검토 요청 → 완료**

진행이 막힌 작업에는 상태와 별개로 **막힌 이유와 필요한 도움**을 표시합니다.

### 운영 원칙

- 처음에는 1인당 핵심 작업 1개를 진행하는 것을 기본으로 합니다.
- 작업량을 예측하기 어려우면 조사·실험부터 별도 작업으로 나눕니다.
- 일정은 담당자와 협의해 정하며, 처음 예상이 틀리면 근거를 남기고 조정합니다.
- 같은 작업의 자세한 진행 상태를 여러 도구에 중복 작성하지 않습니다. 개발 작업은 GitHub를 기준으로 관리하고 Notion에서 연결합니다.

## 6. 막혔거나 일정이 늦어질 때

### 질문할 때 함께 남길 내용

- 하려던 작업과 기대한 결과
- 실제로 발생한 현상
- 확인한 오류 메시지 또는 화면
- 이미 시도한 방법
- 필요한 도움과 다른 작업에 미치는 영향

혼자 같은 시도를 반복하고 있다면 진행 상황을 공유합니다. **30\~60분 정도 진전이 없는 경우를 초기 공유 기준으로 제안**하며, 시간 자체보다 막힌 내용을 설명하는 데 집중합니다.

### 일정 변경 절차

1. 지연 가능성을 알게 되면 담당자가 공유합니다.
2. 남은 작업과 예상 소요를 확인합니다.
3. 필수 범위 축소, 작업 분할, 도움 요청, 재배정을 논의합니다.
4. 변경된 담당자·완료 조건·목표일을 기록합니다.

야근이나 특정 팀원의 대체 작업을 기본 해결책으로 삼지 않습니다.

## 7. 기획·근거 자료 컨벤션

### 사실과 가설 구분

- **확인된 사실:** 공식 자료, 실제 인터뷰, 관찰 결과 등 근거가 있는 내용
- **문제 가설:** 아직 확인하지 않은 사용자 불편이나 행동
- **해결 가설:** 제안 기능이 문제를 개선할 것이라는 예상
- **팀 결정:** 조사와 제약을 고려해 선택한 방향

### 자료를 남길 때

**출처 / 작성·발표 시점 / 확인일 / 핵심 내용 / 프로젝트와의 관련성**을 기록합니다.

- 통계는 조사 대상·기간·범위를 확인합니다.
- 인터뷰 몇 건을 전체 타깃의 의견으로 확대하지 않습니다.
- 사용자의 말과 팀의 해석을 구분합니다.
- 반대 사례와 기존 서비스로 충분히 해결되는 사례도 기록합니다.
- 인터뷰 녹음은 사전 동의를 받고, 공유 기록은 필요한 범위에서 익명화합니다.

### 교수님 피드백 처리

피드백마다 **해석한 내용 / 반영 여부 / 반영 방법 또는 보류 이유 / 담당자**를 남깁니다. 의미가 불명확하면 임의로 기능을 추가하기 전에 확인합니다.

### 공고 수집·구조화·검수 협업

**한 기관의 자동 수집 + 차이를 대표하는 표본의 규칙 검증 + 검수 후 준비 안내 공개**를 채택합니다. 한 기관을 우선 조사하되 지역·지원 유형은 미리 제한하지 않습니다. 첫 구현용 대표 공고 1건과 추가 2∼3건을 시작점으로 표본을 구성하고, 주요 조건·서류·절차·예외가 빠지면 보완합니다. 표본 수는 전체 수집량이나 지원 범위의 상한이 아닙니다.

| 업무 | 주 담당 역할 | 검토·완료 기준 |
| --- | --- | --- |
| 공식 API·원문·첨부 제공 범위 조사 | 개발 + 데이터 담당 | 필요한 필드·첨부 형식·활용 조건·갱신 동작 확인 |
| 자동 수집·중복 방지·재시도 | 개발 담당 | 반복 실행·부분 실패 기록·수집 누락 검증 |
| 대표 공고 정답 사례·조건 구조화 | 데이터·정책 담당 | 조건·서류·예외·기한과 공식 근거 연결 |
| 추출 결과·수정 공고 대조 | 별도 검토자 | 동일 작업에서 공고 정보·준비 안내 원문 대조, 영역별 통과·보완 사유·영향 항목·재확인 필요 기록 |
| 공개·기존 준비 건 반영 | 관리자 작업 담당 | 기본 정보 검증 후 목록 공개, 준비 규칙 검수 후 안내 제공. 각 상태·버전·확인일과 기존 준비 건 연결 보존 |

- 자동 추출 결과를 확정 사실로 취급하지 않습니다. 구조화 담당자와 검토자를 분리하며 미확인 조건은 확인 필요로 남깁니다.
- 공식 공고 첨부 수집은 사용자 증빙서류 업로드와 구분합니다. 실제 사용자 증빙 원본은 수집·공유하지 않습니다.
- 수집·검수 작업을 하나의 대형 개발 작업으로 묶지 않습니다. 원문 대조·정답 작성·예외 검증도 독립 작업으로 분담합니다.
- 수집 성공·실패·중복·필드 누락·변경 감지·검토 시간을 기록해 자동화 효과를 확인합니다.

## 8. 기능 범위와 의사결정

### 새 기능을 추가할 때 확인할 질문

1. 누구의 어떤 문제를 해결하는가?
2. 인터뷰나 자료에서 필요성이 확인됐는가?
3. 현재 핵심 흐름에 반드시 필요한가?
4. 구현·검증·유지에 얼마나 작업이 필요한가?
5. 추가하려면 무엇을 미루거나 줄여야 하는가?

추가 제안은 즉시 개발하지 않고 우선순위 목록에 남깁니다. 합의된 방향 안의 작은 기술·수집 실험은 사용자 조사와 병행할 수 있으며, 학습한 결과로 본격 구현 범위를 판단합니다.

### 결정 기준

**사용자 가치 → 수업 목표·평가와의 연결 → 구현·검증 가능성 → 일정·운영 부담**

쉽게 되돌릴 수 있는 세부 구현은 담당자가 합의된 기준 안에서 결정합니다. 사용자 흐름·데이터 구조·공통 기술·마감에 영향을 주는 변경은 관련 팀원과 논의합니다.

의견이 갈리면 선택지와 장단점을 기록하고, 가능하면 작은 실험으로 판단합니다.

### 범위 제한을 재검토할 때

- 초기 표본·운영 범위·유지할 정확성 및 개인정보 기준을 구분합니다. 표본 공고 수를 영구 데이터 상한으로 쓰지 않습니다.
- 한 기관을 우선 조사하고 여러 지역·지원 유형 공고를 처음부터 비교합니다. 초기 범위는 지역·유형 수가 아니라 공통 데이터 구조, 새 질문·조건부 서류·예외·신청 단계, 검수 시간·오류·수집 운영 및 사용자 검증 작업량으로 선정합니다. 공통 구조와 규칙으로 처리되는 공고는 함께 포함하고, 대표 한 건의 첫 구현 순서를 서비스 범위의 상한으로 삼지 않습니다.
- 공고 정보·준비 안내는 같은 검수 과정에서 확인하고 결과·공개 상태를 구분하는 정책을 채택했습니다. 기본 정보 검증 완료 공고는 준비 안내 보완·미지원 상태여도 공개할 수 있습니다. 검증된 공식 발급 링크는 초기 구현에 포함하고 캘린더 내보내기는 푸시와 분리해 검증 후 범위를 결정합니다. 준비도(%)·집 건축 표현은 초기 완성에 포함하며 단계적 후도입 제안은 기각합니다.
- 개선 제안마다 사용자 가치·추가 작업량·완료 조건·미룰 작업을 기록합니다. [기획안의 범위 제한 재검토](../planning/project-proposal.md#범위-제한-재검토와-개선-방향)를 공동 안건으로 사용합니다.

## 9. 개발 협업 기본 규칙

React + TypeScript, Spring Boot 기반 Spring MVC, JDK 17, Gradle, PostgreSQL, Spring Security + JWT, AWS EC2 + RDS 사용 방향을 반영합니다. 채택한 TanStack Query·Spring Data JPA·Querydsl·Flyway와 이메일·Google·카카오 로그인 등의 상세 기준과 후속 작업은 [코드 및 기술 규칙](coding-conventions.md)을 기준으로 관리합니다. 같은 설정을 여러 문서에서 따로 변경하지 않습니다.

### GitHub

- 하나의 GitHub 저장소 안에 `frontend/`·`backend/`·`docs/`를 두는 모노레포를 유지합니다. 프론트·백엔드의 실행·빌드·배포는 각각 관리합니다.
- `main`은 배포 가능한 안정 버전, `develop`은 개발 통합과 연동 확인을 위한 브랜치로 유지합니다. 두 브랜치에 직접 push하지 않습니다.
- 작업별 브랜치를 만들고 Pull Request(PR)로 변경을 검토합니다.
- 프론트 전용·백엔드 전용 장기 통합 브랜치는 만들지 않습니다. 기능·수정 목적을 기준으로 담당자를 배정하며 한쪽만 수정하는 작업도 가능합니다.
- 하나의 PR에는 가능한 한 하나의 목적을 담습니다.
- 기능 연동에 필요한 프론트·백엔드·API 문서 변경은 한 PR에서 검토할 수 있습니다. 규모가 크면 연결된 PR로 나누고 선행 작업·호환성·통합 확인 순서를 공유합니다. 담당자 한 명에게 양쪽 구현을 모두 맡긴다는 뜻은 아닙니다.
- PR에는 **변경 이유 / 변경 내용 / 확인 방법 / 남은 문제**를 적습니다.
- 공통 구조·DB·API 변경은 관련 담당자와 먼저 공유합니다.
- 검토자가 이해하기 어려운 큰 변경은 나누거나 함께 설명합니다.

브랜치명 예: `feature/12-preparation-save-state`, `fix/27-preparation-missing-status`

병합 방식, 작업 브랜치 보존, 최소 1명 승인 기준은 코드 및 기술 규칙을 따릅니다. 이 문서에서 별도의 브랜치 정책을 만들지 않습니다.

커밋 메시지는 변경 목적이 드러나게 작성합니다.

예: `feat: 신청 준비 상태 저장 추가`

### 검토 원칙

- 초반에는 함께 화면을 보며 검토하는 방식도 허용합니다.
- 검토자는 가능한 사람이 분담하고, 중요한 설계·계산 변경은 관련 이해가 있는 사람이 확인합니다.
- 작성자는 검토 결과를 반영하거나 반영하지 않은 이유를 설명합니다.
- 이해하지 못한 변경을 형식적으로 승인하지 않습니다.

### 실행·빌드·배포 분리 원칙

- 프론트엔드는 VS Code에서 `frontend/`, 백엔드는 IntelliJ IDEA에서 `backend/`를 열어 작업합니다. npm 의존성과 Gradle 의존성은 각 프로젝트에서 따로 관리합니다.
- 각 폴더의 README에 설치·실행·검사·빌드를 기록하고 루트 README에서 전체 실행 순서·연동 확인 방법을 연결합니다. 새 팀원은 두 프로젝트를 각각 실행한 뒤 API 연결까지 확인합니다.
- PR 자동 검사는 프론트·백엔드별 작업으로 구성하고 초기에는 양쪽을 모두 실행합니다. 개별 검사 통과와 실제 화면·API 연동 완료를 구분합니다. 공통 설정·같은 파일 변경은 관련 작업자와 먼저 조율합니다.
- 배포 산출물·버전·적용·복구 절차를 구분하며 변경 없는 쪽의 재빌드·재시작을 필수로 묶지 않습니다. API·DB 변경이 있으면 관련 담당자가 호환성·배포 순서·통합 확인을 함께 계획합니다.
- 배포 분리는 EC2를 프론트·백엔드별로 추가한다는 뜻이 아닙니다. 기존 EC2 1대 구성을 유지하며 구체적인 배포·복구 절차와 자동화는 추후 정합니다.
- 초기에는 별도 모노레포 관리 도구를 추가하지 않습니다. 상세 명령·CI·저장소 운영 기준은 [코드 및 기술 규칙](coding-conventions.md#모노레포-운영-원칙--20261020-확정)을 따릅니다.

## 10. 완료 기준과 AI 활용

### 개발 작업 완료 기준

- 합의한 완료 조건을 충족합니다.
- 관련 기능과 연결했을 때 동작합니다.
- 정상 입력뿐 아니라 빈 값·잘못된 값 등 주요 예외를 확인합니다.
- 계산·조건 분기 등 오류 영향이 큰 부분은 검증 사례를 남깁니다.
- 개인정보를 다루는 작업은 본인 데이터만 조회·수정할 수 있는지 확인합니다. 인증·관리자 기능은 정상 동작뿐 아니라 권한 부족·만료·오류 사례를 확인합니다.
- 해당 작업에 필요한 실제 구성된 린트·타입 검사·Gradle 빌드·테스트를 수행하고, 결과 또는 확인하지 못한 이유를 PR에 남깁니다.
- 변경된 API·사용 방법·주의 사항이 있으면 문서를 갱신합니다.
- 검토를 완료하고, 남은 문제는 별도 작업으로 기록합니다.

‘코드를 작성했다’와 ‘사용할 수 있는 기능을 완성했다’를 구분합니다.

### AI 활용 원칙

- 아이디어 정리, 개념 학습, 코드 초안, 오류 분석 등에 활용할 수 있습니다.
- 제출하는 코드와 문서는 담당자가 이해하고 검증합니다.
- AI가 제시한 통계·출처·정책·계산 결과는 원자료와 대조합니다.
- 주요 설계나 핵심 계산에 AI를 활용했다면 검토 과정에서 공유합니다.
- API 키·비밀번호·사용자의 민감한 정보는 입력하거나 저장소에 올리지 않습니다.
- 강의의 별도 AI 활용 지침이 있다면 따릅니다.

## 11. 기여 기록과 회고

기여는 코드 양이나 커밋 수만으로 판단하지 않습니다.

**문제 조사, 인터뷰, 기획, 설계, 구현, 테스트, 검토, 문서화, 발표, 팀원 지원**을 작업과 결과물로 남깁니다.

주간 회의에서 다음을 짧게 확인합니다.

- 이번 주 완료한 일과 배운 점
- 도움이 필요했던 부분
- 다음 주 바꿀 협업 방식

기여나 참여 문제가 반복되면 구체적인 작업·일정 기록을 바탕으로 먼저 대화합니다. 팀 안에서 해결하기 어렵거나 수업 수행에 영향을 주면 교수님께 상황과 조정 시도를 설명하고 도움을 요청합니다.

### 확정 서비스 계약

백엔드는 IntelliJ IDEA와 내장 Java 포맷터, 프론트엔드는 VS Code와 Prettier·ESLint를 사용합니다. Java의 공유 스타일 XML·EditorConfig와 Spotless idea() 검사 절차는 코드 및 기술 규칙의 8절을 따릅니다. CI의 IntelliJ 실행 환경·버전 고정은 후속 설정 작업이며 아직 검사가 구성되었다는 뜻은 아닙니다.

- 공고 검색은 지역·지원 유형·마감 상태·키워드를 조합합니다. 필터 간 AND, 동일 필터의 여러 선택값은 OR로 처리합니다.
- 기본 정보 검증·공개 완료 공고를 일반 검색에 포함하고 준비 안내 제공 상태를 함께 표시합니다. 개인별 안내는 해당 준비 규칙의 검수·공개 완료 후 제공합니다. 검색 조건은 URL에 보관하며 page는 0부터 시작, size 기본 20·최대 100입니다.
- 성공 응답은 DTO 직접 반환, 오류는 code·message·fieldErrors·timestamp 형식입니다. 실제 시각은 UTC 저장·전송, 한국 시간 표시로 통일합니다.
- 공개 공고 목록·상세는 비회원도 조회할 수 있으며 개인 답변·준비 상태 저장에는 로그인이 필요합니다.
- Access JWT는 15분·React 메모리·Bearer 헤더, Refresh는 불투명 난수 토큰 7일·HttpOnly/Secure 쿠키·서버 해시 저장·재발급 시 교체로 정합니다.
- 사용자와 로그인 수단을 분리하고 이메일 일치만으로 자동 병합하지 않습니다. 기존 계정 인증 후 연결하며 관리자 역할은 공개 회원가입으로 부여하지 않습니다.
- 도메인 패키지는 auth·user·notice·preparation·admin·global로 나누고 각 기능 안에 계층을 구성합니다.

#### 동시 검수·공개 운영

공고·원문 버전별 하나의 검수 작업에서 공통 근거 확인 → 기본 정보 확인 → 준비 규칙 확인 → 영역별 결과·보완 사유·공개 결정 순서로 진행합니다. 공통 출처·버전·일정은 같은 검증 값을 공유합니다. 두 영역을 같은 담당자가 동시에 통과시키거나 반드시 함께 공개해야 한다는 뜻은 아니며, 기존의 구조화 담당자와 별도 검토자 역할을 유지합니다.

| 동일 검수의 결과 | 공고 목록·기본 상세 | 개인별 준비 안내 |
| --- | --- | --- |
| 기본 정보·준비 안내 모두 통과 | 공개 | 제공 |
| 기본 정보 통과·준비 안내 보완 필요 | 공개 | 보완 완료까지 제공 보류 |
| 기본 정보 통과·준비 안내 미지원 | 공개 | 미제공 표시 |
| 공고 식별·출처 등 기본 정보 검증 실패 | 공개 보류 | 제공 보류 |

공개 담당자는 검토자·확인 시각·기준 버전·보완 사유와 두 영역의 공개 이력을 남깁니다. 기본 정보·준비 안내의 확인일을 구분하고 `준비 안내 검수 중`이 기관의 공고 검토 상태를 뜻하지 않도록 표현합니다. 수정 공고도 함께 검수하되 각 영역의 통과 상태로 적용하며 기존 사용자 기록을 덮어쓰지 않습니다.

자동 수집 방향은 채택했으며 대상 기관·API·수집 주기·보관 정책·실제 호출 및 검증 결과는 후속 작업입니다. 수집에 성공한 사실만으로 규칙 검수·공개 완료로 표시하지 않습니다.

공고 데이터 담당은 서류별 공식 발급 경로·대상·발급 방식·기준과 확인일을 기록하고, 별도 검토자가 대조합니다. 개발 담당은 검증된 링크 연결·미검증/오류 안내와 외부 이동 시 상태 불변을 구현합니다.

캘린더 담당은 검증된 일정의 .ics 생성·대상 기기 가져오기·날짜/시각·변경/중복 시나리오를 작은 실험으로 확인하고 사용자에게 현재 기한 기록 도구와 놓친 이유를 조사합니다. 실제 구현 범위는 그 결과로 정하며 푸시의 권한·예약·발송·실패 처리는 별도 과제로 평가합니다.

준비도(%)·집 건축 표현은 초기 시연 완료 기준에 포함합니다. 상태별 목록·필수 미확인 표시는 이 요소들과 함께 제공하며, 사용성 테스트는 계산·표현의 의미를 개선하기 위해 수행합니다. 작은 구현 순서는 가능하지만 두 요소를 초기 완성에서 제외하는 제안은 기각 상태로 유지합니다.

## 14. 집으로 프로젝트의 공동 검토 기준

- 공고 자동 수집과 조건·서류 규칙의 구조화·검수를 구분합니다. 구조화 담당자와 공식 원문 검토자를 분리합니다.
- 대표 표본으로 만든 정답 사례에 자동 추출 결과를 대조하며 수집된 초안을 바로 공개하지 않습니다.
- 수정 공고를 감지하면 영향 검토·사용자 재확인 항목을 남기고 기존 공개 규칙과 준비 상태를 자동으로 덮어쓰지 않습니다.
- 기본 정보와 조건·서류·기한을 한 작업에서 원문 대조하고 각 검수 결과·공개 상태·기준 버전·확인일·보완 사유를 기록합니다.
- 기본 정보만 공개된 공고의 조회, 준비 안내 미제공 상태의 신규 준비 차단, 양쪽 통과 시 준비 시작, 수정 검토 중 기존 기록 보존을 함께 확인합니다.
- 조건 안내 로직과 준비도 계산은 개발 담당자 혼자 확정하지 않고 데이터·기획 담당자와 사례를 맞춥니다.
- 미입력·모름·예외 조건을 구분하며 최종 자격이나 당첨을 확정하는 문구를 사용하지 않습니다.
- 회원의 조건 답변·준비 상태를 테스트할 때 가상 데이터와 테스트 계정을 사용합니다. 실제 서류 원본을 공유하지 않습니다.
- JWT·Querydsl·공고 규칙 같은 어려운 작업은 작은 구현과 검토로 나눕니다. 리더에게 모든 설정·구현·검증을 몰아서 맡기지 않습니다.
- 서비스의 핵심 가치와 무관한 기술 시연 기능은 MVP에 추가하지 않습니다. 확정한 복합 검색에 Querydsl을 사용하되, 자격 안내·준비도 계산과 검색을 구분합니다.
