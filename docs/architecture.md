# 저장소·연동·배포 운영 원칙

최종 수정일: 2026-10-29

이 문서는 구조를 빠르게 확인하기 위한 요약입니다. 상세 협업·API·DB 계약은 [코딩 컨벤션](conventions/coding-conventions.md), 제품 정책은 [기획안](planning/project-proposal.md), 실제 실행 방법은 [개발 시작 안내](getting-started.md)를 따릅니다. 전체 문서 역할은 [문서 안내](README.md)에서 확인합니다.

- GitHub 저장소 하나, React·Spring Boot 프로젝트 둘. npm·Gradle·실행·빌드·배포 산출물은 각각 관리합니다.
- `main`은 안정 버전, `develop`은 통합·연동 기준입니다. 초기 저장소 기준 커밋 이후 기능·수정·설정 작업은 작업 브랜치와 PR로 진행합니다.
- 기능에 필요한 프론트·백엔드·API 문서 변경은 같은 PR에서 검토할 수 있습니다. 큰 작업은 연결된 PR로 나누고 선행 작업·호환성·통합 확인 순서를 기록합니다.
- PR 검사는 프론트·백엔드별 job으로 실행합니다. 초기에는 경로 필터로 생략하지 않습니다. 개별 빌드 성공과 실제 화면/API 연동을 구분합니다.
- 공통 설정·같은 파일 변경은 먼저 조율하고 관련 없는 전체 포맷 수정을 섞지 않습니다.
- 공개 API는 `/api/v1/`를 기준으로 합니다. 성공 응답은 DTO를 직접 반환하고 공통 성공 래퍼를 추가하지 않습니다. 초기 health 응답은 사용자 업무 API가 아닌 접속 확인용입니다.
- 운영 스키마는 Flyway, JPA는 validate. 실제 운영 테이블은 모델 합의 후 만듭니다. Querydsl 검증용 테이블은 테스트 DB에만 둡니다.
- 배포 산출물·버전·적용·복구 절차를 각각 관리합니다. 변경 없는 쪽의 재빌드·재시작을 필수로 묶지 않습니다. API·DB 변경은 호환성·적용 순서·복구 제약을 함께 검토합니다.
- 기존 AWS 기본안은 EC2 1대의 Nginx 정적 파일 + `/api/` Spring Boot 전달, 비공개 RDS PostgreSQL입니다. 분리 원칙은 서버 대수 증가를 뜻하지 않습니다. AWS 리소스·자동 배포·비용 설정은 이번 초기 구성에 포함하지 않습니다.
- `org.jibro`는 실제 새 프로젝트의 기본 패키지로 사용합니다. `auth`·`user`·`notice`·`preparation`·`admin` 기능 영역과 필요한 계층은 실제 작업 때 추가하며 빈 전체 폴더를 만들지 않습니다.
