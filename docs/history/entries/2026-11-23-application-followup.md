## 배경·문제

준비 항목을 모두 기록해도 신청 이후 결과와 계약·입주를 남길 공간이 없었다. 준비 단계의 후속 절차 링크는 기존 일정으로만 이동했다. 사용자가 결과 대기/선정/예비/미선정, 예비 순번, 서류 제출, 계약, 입주를 홈뿐 아니라 내 준비 등에도 연결하도록 요청했다.

## 고려한 선택지

기존 일정 확인 표시를 선정 결과로 겸용하는 방식은 발표 확인과 개인 선정 결과를 혼동한다. 준비도에 후속 결과를 합치는 방식은 이미 완료한 준비도와 과거 기록을 바꾼다. 별도 개인 기록을 준비 snapshot에 추가해 기존 소유자·버전·보관 계약을 재사용하기로 했다.

## 결정·이유

`followUp`은 선택적인 개인 기록이며, 공식 선정 판정이나 기존 준비도에 영향을 주지 않는다. 선계약 후 검증 모집도 있어서 계약 여부와 선정 결과를 독립적으로 둔다. 공식 일정과 기존 저장 기록이 있는 단계만 제공하고, 날짜가 없다고 임의 날짜나 개별 안내를 생성하지 않는다. 일정은 당시 버전의 개인화된 일정에서 가져온다.

## 변경·해결 과정

신청 후 진행 카드를 준비 기록 완료 카드에 맞춰 아이콘40px, 좌우 여백14px, 상하12px, 제목18px/줄높이1.5, 설명14px, 라벨 굵기600으로 통일했다. 내용 길이에 따른 높이는 자연스럽게 늘어난다.

위치에 대한 사용자 정정으로 녹색 신청 완료 버튼도 공식 신청 오른쪽의 기존 신청 여부 기록 버튼 칸에 배치한다. 완료 전후 동일한 2열·너비·높이·여백을 공유하고 완료 색상만 바꾼다.

신청 완료 기록 후에는 개요의 별도 완료 배지를 제거하고 그 자리에 녹색 체크 ‘신청 완료’ 버튼을 배치했다. 클릭하면 기존 신청 여부 수정 팝업이 열린다. 미신청 상태에는 기존 ‘신청 여부 기록’ 버튼을 제공한다.

사용자 후속 요청으로 진행바의 후속 절차 아래 ‘전체 완료’ 문구만 제거했다. 완료 체크와 연결선은 유지하고, 미완료일 때 ‘진행 중’ 표시는 유지한다. 공통 Journey이므로 홈과 내 준비에 함께 적용한다.

후속 사용자 요청으로 공통 요약의 ‘결과를 확인한 뒤 직접 기록해 주세요. · 준비도와 별도로 관리해요.’ 문구를 제거했다. 미기록 상태의 빈 안내 영역도 남기지 않는다. 홈·개요·신청 후 화면에 같은 수정이 적용되며, 이미 저장된 기록의 ‘직접 남긴 기록’ 표시는 유지한다.

`PreparationService`의 owner/revision/보관 보호를 유지한 PUT 경로, refresh의 개인 기록 보존, ExperienceRepository/Service의 보관 당시 결과 전달을 추가했다. 체험 모드도 같은 계약을 적용했다. 공통 `followUp.ts`, `FollowUpSummary`, `FollowUpEditor`를 만들고 지연 로딩하는 ‘신청 후’ 탭, 홈/개요 요약, 일정 진입, 후속 절차 링크, 이전 기록/보관함을 연결했다.

저장 실패 시 입력을 유지하고 취소할 수 있다. 다른 화면에서 저장한 뒤 생긴 revision 충돌은 자동 덮어쓰지 않고 최신 기록을 불러온 뒤 다시 선택하도록 했다. 소유권·보관 상태·입력 오류가 차단되는지 실제 테스트 DB로 검증했다.

초기 검사에서 테스트의 인증 거부 기대값(기존 보안은 403), 비동기 홈 이동 대기, jsdom의 ResizeObserver 부재, 불완전한 타입 fixture, 테스트의 app 계층 역참조를 발견했다. 실제 계약에 맞는 assertion/fixture와 앱 계층 통합 테스트로 수정했다. 제품 보안/타입/계층 검사를 완화하지 않았다.

## 기여·한계

AI가 코드·테스트·문서를 보조했다. 기관의 개인 선정 결과를 자동 조회하는 기능은 아니며, 사용자가 공식 안내를 확인하고 기록한다. 현재 공고에 확인된 일정만 재사용하며 새 공식 자료 수집·분석 규칙을 바꾸지 않았다. 실제 사용자 기록 변경, 원격 게시·운영 배포·push는 수행하지 않았다.

## 발표·포트폴리오 메모

준비 완료와 신청 결과를 분리하고 저장·정정·보관 경계를 공유해 여러 화면에서 개인 후속 기록을 유지했다. 사용자 효과 수치나 담당자 기여는 검증되지 않아 주장하지 않는다.

## 후속 작업

### 신청 완료에 따른 탭과 단계 표시 보완 (2026-11-23)

후속 사용자 요청으로 신청 완료 기록 전에는 4개 세부 탭만 보이고, 기록 후에만 신청 후 탭을 표시한다. 기존 `showFollowUp`을 그 기준의 단일 소유자로 좁혀 홈/개요 요약·일정 진입·탭·직접 주소 접근을 맞췄다. Workspace가 동일 준비 건의 공유 query를 사용하므로 모든 준비 건의 상세를 한꺼번에 조회하지 않는다. 4개/5개 탭 너비는 CSS 자동 열로 나눈다.

진행바는 `journeyStage`에 계산을 모아 신청 완료 후 후속 절차 진행 중, 선정/예비/미선정 결과 저장 후 전체 완료를 표시한다. 대기 상태 저장은 진행 중을 유지한다. 신청 취소 시 단계/탭을 되돌리지만 기존 결과를 삭제하지 않는다. 기존 전체 준비도와 집 건축 단계는 그대로다.

관련 검사 87개 중 기존 App70·신청 기록 모달7개는 첫 실행에서 통과했다. 새 검사에서 테스트 환경의 dialog 메서드 부재와 기존 신청 기록 선택 규칙에 맞지 않는 fixture 제목을 수정한 뒤 새 화면4·단계6개 모두 통과했다. 타입·전체 lint·계층 검사 통과. 실제5173 기존 신청 완료+선정 기록에서 5개 탭·다섯 체크·전체 완료를 읽기만 해서 확인했고 PC/390px 화면을 확인했다. 사용자 결과는 변경하지 않았다. 공고 선택 펼침/스크롤 입력이 반응하지 않아 다른 준비 건의 실브라우저 4개 탭은 확인하지 못했으며, 4→5→4 전환·직접 주소·홈 반영은 화면 통합 검사로 검증했다. viewport 복원, QA 증거 `.tools/qa/application-followup-journey-20261123.jpg`. 운영 배포와 push 없음.

### 선정 결과 입력 영역 디자인 개선 (2026-11-23)

사용자 화면 피드백에 따라 결과 선택을 제목·짧은 설명이 있는 카드로 정리했다. PC는 4열, 좁은 화면은 2열이며 선택한 카드에 녹색 테두리·배경·글자를 적용한다. 기존 라디오와 접근성 이름, 키보드 선택, 예비 순번·저장·취소·충돌 복구는 유지한다. 서류 제출 대상자 발표와 최종 선정의 구분은 선택지 아래 짧은 안내로 옮겼다.

### 신청 기록과 접수 마감 연동 (2026-11-23)

사용자 요청으로 전체 일정의 신청 접수 마감에 개요와 같은 ApplicationRecordDialog를 연결했다. 같은 준비 query와 대표 일정 ID로 완료·취소를 양방향 반영하며, 기존 별도 공식 신청 기록 ID를 유지한다. 접수 시작·회차·단순 안내 및 대표 외 마감은 완료 버튼·배지·진행률에서 제외한다. canRecordSchedule/PreparationSchedules를 표시·체험 저장·서버 저장·진행률에 적용했고, 목록 진행률 경량 조회에는 날짜만 추가했다. 기존 완료값과 보관 자료는 재작성하지 않는다.

공통 JSON 계약3사례(안내 일정 제외, 신청 완료 대체 불가, 별도 신청 기록 우선)와 화면 양방향 연동·저장 거부/revision 유지 검사를 추가했다. 관련 프런트8파일192개, 서버단위2·PostgreSQL통합6 통과. 최초 표시 모델 기대값/테스트 중복 선택자를 수정하고 접수 회차를 포함하던 서버 진행률 기대값을 새 정책에 맞췄다. 타입·전체lint·계층10개·변경 Prettier·프런트 build·bootJar 통과. Java5파일 IntelliJ 서식을 적용했다(최초 DIRTY1 후 나머지 CLEAN; spotlessCheck 자체는 설정상 SKIPPED이므로 전체 Java 서식 검사 통과로 주장하지 않는다).

runtime 교체·5173 재시작 후 PC/360px의 실제 공통 신청 기록창 열기·닫기, 접수 시작·회차의 완료 버튼/배지 없음, 360px 가로 넘침 없음을 확인했다. 실 사용자 상태는 저장하지 않았고 양방향 저장은 화면통합/서버DB 검사로 검증했다. viewport 복원, 증거 .tools/qa/application-schedule-linked-20261123.jpg. 운영 배포·push 없음.
