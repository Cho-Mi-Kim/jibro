## 검토 지적

### R1 · P2 · 오래된 보관 요청이 먼저 저장한 메모를 덮어쓴다

위치: `backend/src/main/java/org/jibro/member/ExperienceService.java`, archive의 revision 검사와 UPDATE.

두 탭이 같은 준비 건의 revision을 읽고, A가 메모를 넣어 보관한 뒤 B가 같은 revision과 다른 메모로 보관 요청하면 두 요청이 모두 성공한다. UPDATE가 revision을 올리지 않고 이미 보관됐는지도 거절하지 않아 `takeaway`가 B 값으로 바뀐다. 행 잠금은 순서만 보장하고 오래된 요청을 막지 못한다. 복원 후에도 같은 revision을 재사용할 수 있다.

실제 서비스 메서드를 호출하는 임시 PostgreSQL 통합 테스트에서 첫 보관 후 동일 revision의 두 번째 호출에 예외를 기대했으나 아무 예외도 발생하지 않아 실패했다. 테스트는 트랜잭션 롤백을 사용했고 검토 후 임시 테스트 소스를 제거했다.

권장 수정: 보관·복원 상태 변경에 일관된 revision 정책을 적용하고 DB 컬럼과 JSON 스냅샷의 revision을 함께 유지한다. 이미 보관된 건의 오래된 저장은 거절한다. 두 탭 저장 및 보관→복원→오래된 저장의 회귀 테스트를 추가한다. 시연 어댑터의 동일 동작도 함께 정합화한다.

### R2 · P2 · 로그인 복귀 테스트가 시연 지연과 1초 대기에 의존한다

위치: `frontend/src/app/App.test.tsx`, ‘로그인 복귀부터 모름 응답 저장과 서류 실패 후 재시도까지’의 최초 radio 조회.

기존 코드 그대로 전체 실행과 해당 테스트 단독 실행 모두 첫 질문 radio를 찾지 못했다. 실패 당시 화면은 ‘준비 기록 확인 중…’이었다. 시연 요청마다 180ms 인위적 지연이 있고 로그인·공고 조회·목록 조회·준비 생성이 이어지므로 기본 비동기 조회 대기와 머신 속도에 영향을 받는다. 원격 CI 성공을 이번 로컬 통과로 대체 기록하지 않는다.

진단을 위해 해당 최초 radio 조회에만 임시 3초 대기를 지정하면 테스트가 끝까지 통과했다. 진단용 변경은 원복했다. 이는 제품의 로그인 실패 재현이 아니라 테스트의 대기 시간 의존 문제다.

권장 수정: 사용자 흐름을 검증하는 테스트에서 인위적 시연 지연을 제어하거나 명시적인 요청 완료 경계를 기다린다. 오류·복구·저장 여부 단정은 유지한다. 단순 대기 연장만으로 제품 결함 해결을 주장하지 않는다.

## 후속 수정 (2026-11-10)

사용자가 두 지적의 수정·테스트·PR #24 커밋·푸시·코멘트 작성을 요청했다. 이후 병합을 중단하고 디자인을 먼저 확인하겠다고 명시하여 당시 PR을 초안·미병합 상태로 유지했다. 아래 재개 요청 이전까지 병합하지 않았다.

- R1 해결: 보관 시 이미 보관된 기록과 오래된 revision을 409로 거절한다. 실제 보관·복원 때 DB revision과 JSON 스냅샷 revision을 함께 증가시키며, 반복 복원은 변경 없이 종료한다. 시연 어댑터에도 같은 정책을 적용했다.
- R1 회귀 검증: 첫 보관 메모 보존, 동일·최신 revision의 중복 보관 거절, 보관·복원 후 오래된 보관·답변 저장 거절, 최신 답변 저장 허용 및 반복 복원의 revision 유지 사례를 PostgreSQL 통합 테스트와 시연 계약 테스트에 추가했다.
- R2 해결: 시연용 180ms 지연을 `demoDelay.ts`로 분리했다. App 흐름 테스트에서만 해당 지연을 제외하며 실제 시연의 지연, 데이터·오류 처리와 기존 사용자 흐름 단정은 유지했다. 대기 시간 상향으로 해결하지 않았다.
- 회원 기능·프론트엔드·백엔드 계약에 수정된 동작과 검증 경계를 반영했다. CSS·레이아웃·화면 구성은 변경하지 않았다.

## 로컬 화면 실행과 문서 보완·병합 재개 요청

- PR 작업 브랜치의 시연 프론트엔드를 5174에서 실행했다. 사용자가 소셜 로그인 버튼을 문의해 시연 모드에서는 숨겨지고 실제 서버 모드에는 Google·카카오가 제공됨을 소스에서 확인했다. 네이버는 기존 구현 대상이 아니었다.
- 이어 기존 PostgreSQL 데이터를 유지하면서 백엔드 8080과 실제 서버용 프론트엔드 5173을 실행했다. `/login` HTTP 200, 프록시를 통한 `/api/v1/auth/providers`의 `google`, `kakao`, 프론트엔드의 `VITE_API_MODE=server`, 기존 5174 시연 HTTP 200을 확인했다. 실제 OAuth 인증 왕복을 새로 검증했다는 의미는 아니다.
- 사용자는 화면을 확인했다고 답한 뒤 시연 실행 안내 문서화·커밋·푸시·PR 코멘트와 최신 CI/변경 검토 후 develop 병합을 요청했다. 이 최신 요청으로 이전 병합 보류를 해제하되 main 반영은 요청 범위에 포함하지 않는다.
- `docs/getting-started.md`에 시연/실제 서버 비교, 루트 PowerShell 명령, 소셜 버튼 표시 조건, 직접 지정한 환경 변수 해제, 동시 실행·종료 방법을 추가했다. 루트·프론트엔드·백엔드 README에도 설명과 공통 안내 링크를 연결했다. 코드·의존성·DB 변경은 추가하지 않았다.
