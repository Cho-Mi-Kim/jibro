# 최종 검토본과 운영 사이트 일치 확인

- 기록일: 2026-11-24 (Asia/Seoul)
- 기록 상태: 근거 정리·담당자 검토 전
- 작업 상태: 운영 일치 확인·검사 코드 수정 완료 / GitHub 재검증 예정
- 유형: 운영 / 문제 해결
- 담당·검토: Codex가 실행·대조. 별도 사람 검토 미확인.
- 관련: [PR #31](https://github.com/Cho-Mi-Kim/jibro/pull/31), `0ec52419339bc9f44d9564d4944580087ac7edd3`

## 배경·문제

사용자가 충돌 정리 후 최종본을 jibro.live에도 반영하도록 요청했다. 이어 GitHub의 edge-security 검사가 실패한 이유를 질문했다.

## 고려한 선택지

새 산출물로 서비스를 교체하는 방법과 현재 실행 파일이 최종본과 같은지 먼저 비교하는 방법을 검토했다. 소스 커밋명만으로 같다고 판단하지 않고 운영 모드로 다시 빌드한 실제 파일을 대조했다.

## 결정·이유

최종 배포 파일 258개가 현재 운영 릴리스와 모두 일치했다. 실행 중인 웹 파일 245개와 백엔드 JAR도 일치하므로 서비스 재생성·DB 변경 없이 현재 실행을 유지했다. 이번 PR 충돌 통합은 테스트·문서 변경이며 `frontend/src`, `backend/src/main`, `deploy`, `scripts/ops`에는 추가 차이가 없다.

## 변경·해결 과정

- 프런트를 일반 운영 모드로 다시 빌드하고 `bootJar` 및 기존 `package_release.py`를 실행했다. Pages 시연 산출물을 운영에 사용하지 않았다.
- 새 패키지 manifest의 최종 HEAD와 현재 운영 릴리스 `/opt/jibro/release-contact-branding-20261124`의 파일별 해시를 대조했다. 서버 파일과 실제 실행 컨테이너 파일도 별도로 확인했다.
- 더한 것: 작업 기록과 무시되는 `.tools/qa`의 이번 대조·재현 자료. 뺀 제품 코드·추가 제품 코드 없음. 기존 배포 기록을 새 배포 성공으로 덮어쓰지 않았다.
- 운영 runtime, 이미지, 컨테이너, DB, OAuth, SMTP, Turnstile 설정을 변경하지 않았다. PR 병합·추가 push·DNS 변경·유료 자원 추가 없음.

## 검증·결과

### 최종본 운영 확인

- `npm --prefix frontend run build`, `backend/gradlew bootJar`: 성공. 새 패키지 258개 파일 동일.
- 실제 실행 웹 245개 파일과 백엔드 JAR 일치.
- `production_doctor.py --origin https://jibro.live`: 10항목 통과. 웹·백엔드 healthy, 재시작 0. TLS 잔여 87일.
- Opera에서 홈 → 공고 목록 117건 → 포항블루밸리 미리보기·상세, 문의 안내·개인정보처리방침 실제 표시 확인. 문의 페이지 로고와 배치도 화면으로 확인.
- 최종 파일의 `verify_edge.py`를 운영 요청과 분리한 임시 웹 컨테이너에서 root로 실행: 7항목 통과.

### edge-security 실패 원인 확인

- GitHub run `45363130175`는 `Isolated web did not start`로 실패했다. 원래 스크립트는 기동 실패 시 컨테이너 로그를 출력하지 않아 이유가 숨겨졌다.
- 운영과 분리한 동일 파일 사본을 일반 사용자 소유로 실행하고 실패 시 임시 컨테이너 로그만 확인했다. `cannot load certificate key ... privkey.pem ... Permission denied`로 같은 실패 재현.
- OpenSSL이 만드는 임시 키는 일반 사용자 소유·소유자만 읽기이다. 웹 컨테이너는 모든 capability를 제거하고 필요한 일부만 다시 부여하므로 root여도 다른 UID의 이 키를 읽을 수 없다. 운영 키는 root 소유라 해당 차이가 발생하지 않았다.
- 진단 사본에서 폐기되는 테스트 키의 읽기 권한만 변경해 같은 일반 사용자로 다시 실행하자 7항목 모두 통과했다. 운영 인증서·컨테이너 권한·검증 기준은 변경하지 않았다.
- 이는 격리 검사의 임시 인증서 준비 결함으로 확인했다. GitHub workflow 재실행·저장소 검사 코드 수정은 아직 하지 않았으므로 원격 CI가 통과했다고 기록하지 않는다.

## 기여·한계

최종본의 실제 실행 일치와 사용자 화면을 확인했다. 로그인·메일 실제 발송·개인 준비 기록 저장은 이번에 다시 실행하지 않았다. root 격리 검사 통과와 GitHub 일반 사용자 환경의 실패를 구분했다. 새 제품 코드가 없으므로 전체 단위·통합 검사 및 구조 지도 재생성은 반복하지 않았다.

## 발표·포트폴리오 메모

최종 소스의 운영 빌드와 실행 파일을 직접 대조해 불필요한 재시작을 피했다. 보안 검사의 기동 실패는 사용자 권한 차이를 재현하고 임시 키 권한 한 요소만 바꾼 실험으로 원인을 분리했다.

## 후속 작업

- 아래 후속 수정의 원격 CI를 확인하고 사용자가 요청한 컴퓨터 유즈로 기존 PR 본문에 결과를 반영한다.

## 사용자 후속 요청: 검사 수정과 기존 PR 갱신

사용자가 위 해결 방법 적용과 기존 PR의 컴퓨터 유즈 수정을 명시 요청했다. 기존 `verify_edge.py`에서 폐기용 키에만 `0644`를 적용했다. 상위 임시 디렉터리는 비공개이며 실제 인증서·운영 파일은 읽거나 변경하지 않는다. 컨테이너 capability, 대기 제한과 보안 단정도 유지했다.

명령 실패 시 stdout/stderr 끝부분과, 기동 실패 시 해당 임시 컨테이너의 최근 로그를 오류에 담는다. 원인을 숨기던 일반 오류 문구만의 경로를 교체했으며 새 검사 진입점·우회·의존성은 만들지 않았다.

- 수정한 실제 스크립트를 Linux 일반 사용자로 실행: 격리 7항목 통과.
- 같은 사본의 키 권한만 다시 `0600`으로 돌린 실패 실험: 종료 실패 및 `Isolated web did not start`와 `Permission denied` 동시 표시 확인. 실제 저장소 파일은 수정본을 유지했다.
- 운영 도구 `unittest discover`: 총 35개 중 31개 통과, 기존 환경 의존 4개 미실행.
- 변경 파일 Iron Laws 1회: 치명/높음 0, 중간4·낮음1. 대기 예외는 제한 횟수 후 실패하고 새 기동 로그를 표시하는 계약이므로 오류 삼키기 지적 기각. 테스트 도메인·위조 IP 3건은 격리 입력/독립 기대값으로 유지. 함수 길이1건은 단일 격리 실행·정리 책임으로 기계 분리하지 않음. 억제·기준 완화 없음. 전체 안전 증명·외부 Pro 검토를 수행했다고 주장하지 않는다.
- 운영 코드·배포 산출물은 불변이므로 jibro.live 재시작·재배포 없음. 프런트·백엔드 전체 테스트는 GitHub CI의 새 커밋 실행에서 확인할 예정이며 이 로컬 수정만으로 재실행했다고 하지 않는다.
