## 배경·문제

사용자가 내 준비 시안을 제공하고 앞선 공고 탭 이미지 작업과 같은 방식의 적용을 요청했다. 기존에 확정한 GitHub 문서의 글자·색상 규격과 실제 기능을 유지하며 393×852 모바일을 기준으로 구성한다.

## 고려한 선택지

- 홈과 공유하는 PreparationSummary/House 등의 전역 스타일을 변경하면 홈에서 확정한 간격·설명 접기 동작에 영향을 준다.
- 내 준비 표시 조합과 CSS를 분리하고 기존 수치·날짜·집·여정 로직을 재사용하면 변경 범위를 제한할 수 있다.

## 2026-11-05 · 내 준비 상단 고정

첨부된 준비 건 선택기와 개요·조건·서류·일정 탭을 공통 라우트 레이아웃으로 옮겼다. 상단은 유지하고 탭 본문만 교체·스크롤한다. 준비 건을 변경해도 현재 탭을 유지하며, 서류의 미저장 메모가 있으면 건 변경을 취소할 수 있다. 조건 질문과 질문 직후 결과는 기존 집중 화면으로 남겼다.

- 로컬 5173 서버에서 변경 모듈 응답 확인. 같은 소스의 임시 시연 서버에서 393×852·360×852·768×852를 확인했다. 393px에서 준비 선택기 상단 117.59px·탭 상단 160.59px이 네 탭 전환과 본문 스크롤 중 유지됐다. 실제 사용자 데이터는 변경하지 않았고 임시 서버는 종료했다.
- 프론트 테스트 66개·lint·타입 검사 포함 빌드 통과. 전체 포맷 검사에서는 이번에 변경하지 않은 공고 파일 두 개(NoticeCardDates.module.css, NoticePreview.tsx)가 남았다. 실기기 미검증. 화면 증거: `.tools/feature-qa/preparation-fixed-tabs.png`.

후속 조정으로 조건·서류·일정 탭의 중복 제목과 뒤로가기 줄을 제거했다. 조건 질문과 독립 결과 화면은 자체 탐색을 제공한다. 탭 전환을 포함한 앱 테스트 22개와 빌드를 확인했다.

## 2026-11-06 · 서류 완료 동작 우선 배치

사용자가 준비 완료를 주로 사용하고 상태·메모 변경은 드물게 사용한다고 설명했다. 완료 버튼 아래에 보조 편집을 접어두는 안을 제안했고 사용자가 적용을 요청했다. `DocumentEditor`의 강조 버튼을 편집 메뉴 위로 이동하고, 완료 후에는 체크 아이콘과 준비 완료를 표시한다. 상태·메모 수정은 기본 접힘이며 펼쳐야 상태 선택·메모·변경사항 저장이 나타난다. 기존 저장 API, 준비 상태 계산과 미저장 입력 보호는 유지했다. 펼침 요약의 터치 높이는 44px이다.

검증: 프론트 빌드 통과, App의 서류 관련 테스트 6개 통과(22개 제외). 기본 접힘·버튼 순서·완료 저장·상태 되돌리기·다른 서류의 미저장 입력 유지 포함. 앞서 전체 App 테스트에서 26/28 통과했으며, 서류 전환 테스트의 브라우저 API 누락은 테스트 환경 스텁으로 보완하고 재검증했다. 남은 개인 기록 조회 실패 테스트는 공고 상세의 사전 조회가 일회성 실패 mock을 먼저 소비하는 기존 경로 불일치로 확인했다. 이번 범위에서 해당 기대값이나 제품 흐름은 변경하지 않았다. 실제 모바일 기기 및 이번 배치의 브라우저 시각 검증은 하지 않았다. AI가 구현하고 독립 에이전트가 관련 테스트를 갱신했다. 원격 게시 없음.

## 2026-11-06 · 다음 중요한 일정 카드 정리

사용자 요청으로 좁은 좌우 배치와 중첩 테두리를 개선했다. `ScheduleNextCard`와 전용 CSS 모듈에 표시를 분리하고 이전 schedule-next/schedule-soon 스타일은 제거했다. 일정명·날짜와 D-day를 한 행에 배치하고 괄호 속 시각·조기 중단 안내는 별도 줄로 보존했다. 하단 알림·캘린더 버튼은 같은 크기이며, CalendarExport의 기존 팝업과 일정 선택 로직을 재사용한다. 다음 일정 계산·다운로드 대상·기록 API는 유지했다. 모바일 카드 순서와 데스크톱 카드 간격을 유지한다.

검증: 실제 공개 공고를 읽는 임시 컴포넌트 확인 화면에서 393×852와 360×852 브라우저 크기를 확인했다. 360px 버튼은 각각 143×44px, 가로 넘침 없음. 팝업 열기·닫기 확인, 원본 사용자 기록을 변경하지 않았다. 임시 파일과 탭은 제거했다. 관련 테스트 5개 및 빌드 통과. 이후 데스크톱 카드 하단 16px 간격 규칙을 추가했다. 실기기·전체 화면 회귀는 미검증. AI가 구현하고 독립 에이전트가 기존 반응형 순서를 검토하고 컴포넌트 테스트를 추가했다. 원격 게시 없음.

## 2026-11-06 · 전체 일정 세로 타임라인

사용자가 내 준비 일정의 공식 일정 제목을 전체 일정으로 바꾸고 첨부 이미지와 같은 날짜·진행선·상태 열을 요청했다. `ScheduleTimeline`과 전용 CSS에 표시를 분리하고 `scheduleTimelineModel`에서 5단계 표시 모델을 계산한다. 공고 게시, 접수 시작, 접수 마감, 서류 대상자 발표, 서류 마감의 칸은 날짜가 없어도 유지하고 확인 필요로 표시한다. 게시·접수·D-day 표시는 날짜 기준이며 개인의 기록 완료를 뜻하지 않는다. 상세 일정은 준비 안내 검수 상태와 버전 일치를 확인한 뒤 사용한다. 세부 접수 제약과 추가 일정, 출처·확인일·개인 기록은 하단 접힌 영역에 보존했다. 이전 전용 타임라인 스타일은 제거했다. 상단 준비 선택·탭 고정과 일정 기록 API는 변경하지 않았다.

검증: 모델·캘린더 테스트 8개, 탭 전환 통합 테스트 1개 통과. 타입 검사 포함 빌드 통과. 기존 실제 공개 공고를 읽는 임시 확인 화면에서 393×852/360×852를 확인했다. 5개 행, 미확인 날짜, 날짜 한 줄 표기, 출처 접기/펼치기, 가로 넘침 없음을 확인했다. 원본 사용자 기록을 수정하지 않았고 임시 파일과 탭을 제거했다. 실제 기기·전체 회귀 미검증. AI가 구현하고 독립 에이전트가 데이터 매핑·테스트를 담당했다. Windows의 대소문자 파일명 충돌은 모델 파일명을 명시적으로 분리해 해결했다. 원격 게시 없음.

### 전체 화면 로딩 복구

전체 일정 적용 후 사용자가 로딩 불가를 보고했다. 빌드가 통과했어도 장시간 실행 중인 Vite의 모듈 경로 캐시는 수정 전 ScheduleTimeline.ts를 유지하고 있었고, 실제 브라우저 로그에서 export 누락 오류가 반복됐다. 이는 이번 파일명 변경 과정에서 발생한 문제다. 기록된 PID·실행 경로·시작 시각을 대조해 프론트 서버만 종료 후 재실행했다. API health 200, 변환된 SchedulePage의 올바른 .tsx 경로, 실제 5173 홈페이지 렌더링을 확인했다. DB·사용자 기록·백엔드는 변경하지 않았다. 앞으로 파일명/확장자 분리 후에는 개별 확인 화면과 빌드뿐 아니라 실행 중인 전체 앱 진입을 검증한다.
내 신청 기록 카드도 전용 ScheduleRecord CSS 모듈로 간격·상태 행·가로 전체 기록 버튼을 정리했다. 아이콘과 상태 문구를 좌측에 나란히 두고 기록 입력의 펼침 상태를 접근성 속성으로 연결했다. 공식 신청 경로와 기존 저장·취소 동작은 보존했다. 기록 저장 후 취소 통합 테스트 1개와 빌드 통과. 이번 카드 배치의 실기기 확인은 미실행.
후속 사용자 요청으로 신청 기록의 펼침 버튼과 중복 상태 행을 제거했다. 카드에서 바로 체크/해제하며 같은 일정 ID·revision으로 저장한다. 접수 마감의 기록 문구는 신청 완료로 기록으로 간결하게 바꾸고, 다른 절차는 제목을 유지한다. 체크박스는 검정 배경과 흰 체크를 사용한다. 직접 체크 후 저장·취소 테스트와 빌드 통과.

### 2026-11-06 · 개요에서 신청 여부 팝업 기록

사용자가 일정 탭의 나의 신청 기록 카드 전체 제거 후, 개요의 신청 여부 기록을 팝업 질문으로 바꾸도록 요청했다. `ApplicationRecordDialog`로 모듈을 분리해 완료했어요/아직이에요 선택 즉시 기존 schedule API에 해당 신청 일정의 ID와 revision을 저장한다. 서류 제출 등 다른 일정은 일괄 변경하지 않는다. 닫기·Escape는 저장하지 않으며 저장 중에는 중복 동작을 막는다. 오류 시 팝업과 오류 문구를 유지하고 성공 시 캐시 갱신 후 닫는다. 안내 미제공 또는 신청 기록 대상 일정이 없으면 저장할 수 없음을 표시한다. 개요 버튼 배치와 선택한 준비 건 맥락을 유지한다.

검증: 팝업 단위 테스트 6개, 준비 건 전환 통합 테스트 1개, 타입 검사 포함 빌드 통과. 임시 화면에서 실제 공개 공고 제목으로 393×852 팝업, 360×852 가로 넘침 없음, 닫기 후 트리거 초점 복귀를 확인했다. 실제 사용자의 저장 API는 호출하지 않고 저장 성공/실패는 테스트 대역에서 검증했다. 전체 5173 홈페이지 로딩 확인, 임시 파일 제거. AI 구현 및 독립 테스트 검토. 원격 게시 없음.

## 조건 질문 단계 표시 정리 (2026-11-06)

사용자 요청에 따라 모바일의 잘린 질문명·가로 스크롤 단계 표시를 정리했다. QuestionSteps는 흰색 카드에서 질문 단계와 현재/전체 개수를 표시하고, 1023px 이하에서는 작은 분할 표시로 현재 위치를 구분한다. 긴 질문명은 아래 질문 본문에 맡기며 접근성 목록에는 유지한다. 큰 화면은 번호와 전체 질문명을 세로로 표시한다. 짧은 문항명을 새로 추측해 만들지 않았고 질문 저장·이동 로직은 수정하지 않았다. 이전 순번을 완료 체크로 표현하던 방식은 제거하여 현재 질문 위치와 실제 응답 완료를 구분했다.

빌드 통과. 실제 컴포넌트를 사용한 임시 브라우저에서 393px 첫/다음/마지막 단계(1/7, 2/7, 7/7) 표시와 현재 항목, 가로 넘침 없음을 확인했다. 360px에서 기본 글자를 32px로 확대해도 패널/단계 목록의 내용 폭이 영역 폭과 같았다. 실제 기기 및 저장 API는 이번에 재검증하지 않았고 검증 파일은 삭제했다.

사용자 후속 요청으로 조건 질문 화면의 공고 게시일, 기준일 안내, 질문 이유 본문, 계정 저장·원본 미입력 안내를 화면에서 제거했다. 기존 화면설계서의 질문 이유 표시보다 이번 명시적 표시 변경 요청을 적용했다. 질문·선택지·공식 근거와 저장 로직 및 원본 데이터는 유지한다. 사용하지 않는 공고 조회와 가져오기를 제거했고 TypeScript 검사가 통과했다.

사용자 요청에 따라 조건 질문 버튼을 `이전`·`다음`으로 바꾸고 선택 시 자동 저장 후 다음 질문으로 이동하도록 변경했다. 이는 기존 화면설계서의 '선택 즉시 다음으로 넘어가지 않는다' 규칙에 대한 명시적 사용자 개정이다. 마지막 문항은 저장 성공 후 결과로 이동한다. 상태 갱신 직전의 오래된 답변이 저장되지 않도록 선택값을 mutation 인자로 전달하고 중복 제출 잠금, 저장 실패 시 답변 유지·다음 버튼 재시도, 기존 답변 재선택 시 이동을 처리했다. 검토 중인 안내는 선택/저장을 막는다. 자동 저장·결과 이동 및 실패 재시도/이전 후 재선택 테스트 2개와 빌드가 통과했다.
