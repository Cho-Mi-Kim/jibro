# 현재 제공 공고 전체의 조건 질문·답변 개별 검토

- 기록일: 2026-11-21 (Asia/Seoul)
- 기록 상태: 근거 정리·담당자 검토 전
- 작업 상태: 해결
- 유형: 개발 / 문제 해결 / 공식 원문 대조
- 담당·검토: Codex 구현·공고별 원문 대조·독립 표시/실행 검증. 사람 관리자 검수로 기록하지 않음.
- 관련 이슈·PR·커밋: 기존 review/local-updates-20261115에서 작업, 이번 작업 commit/push/병합 없음.

## 배경·문제

기본 목록 122건 중 준비 안내를 제공하는 106건의 조건을 오산세교2·경주영천·완주삼례·포항블루밸리처럼 쉽게 읽을 수 있게 개선해 달라는 요청이다. 범위는 접수 중11·예정55·일정미확정4·종료36건이며, 목록 밖 전체 과거 공고까지 확대하지 않았다. 기존1,428질문에서 유형별 조건·서류 연결을 보완한 최종 공개 질문은1,474개다.

## 고려한 선택지

- 화면의 줄 수만 자르면 숫자 기준과 신청 대상 예외가 잘린다.
- 모든 공고를 같은 주택 유형 템플릿으로 바꾸면 지역별 순위·배점·완화 기준이 섞인다.
- 검수 상태를 임시로 해제하고 덮어쓰면 기존 안내·개인 준비·출처 검증 경계를 훼손한다.

## 결정·이유

공고별 공식 자료를 대조한 원고와 공통 표시 구성요소를 분리했다. 제목·핵심 요약·문단·목록·표·정확한 원문 쪽수를 원고에 보관하고, 질문 ID·원문 제목·설명·출처 위치·제공된 파일 지문이 일치할 때만 사용한다. 기존 네 개 수작업 모듈은 우선 보존했다. 새 표시 원고는106건을 한 번에 불러오지 않고 필요한 공고의102개 파일로 나눠 읽는다.

서류 적용 대상·선택지·질문 간 관계가 바뀌는71개 공고는 새 안내 버전으로 게시했다. 현재 공개본/원문/버전의 불변 기준과 공식 자료 재다운로드 검증을 통과한 경우만 적용했다. 개인 준비·이전 기록과 과거 공개본의 데이터 지문을 게시 전후 대조했다.

## 변경·해결 과정

- `reviewedConditionPresentation`과 `conditionOverview`가 공고 상세·비교·내 준비·질문·이전 기록·일회성 결과에 검토 원고를 전달한다. `api`, `oneTimeCheckApi`, `historyApi`는 응답에 필요한 원고만 먼저 읽는다.
- `build-reviewed-conditions.mjs`는 검토 원고를 공고별 파일/출처 색인으로 생성한다. CI의 `check:reviewed-conditions`가 생성 누락·변경 불일치를 막는다.
- 후보 유형이 구체적이지 않던 행복주택 조건, 유형별 필수 증빙, 대체 가능한 증명서의 중복 요청, 신청 유형과 가족관계 답변의 모순을 보완했다. 확인되지 않은 자격을 자동 확정하지 않는다.
- `refineConditions`는 동일 원문의 질문·서류만 보완하며 종료 공고의 상태·일정·검수 시각을 보존한다. 기존 일정/미해결항목의 지자체·마이홈 근거는 그대로 유지하고 조건 전용 검증 증명을 전체 재게시에는 사용할 수 없게 제한했다.
- 최신 첨부와 기존 안내가 섞인 정읍상동2·3, 정읍수성1은 `reconcileCurrentSources`에서 전체 현재 원문을 명시적으로 재대조했다. 최신 서류·발표 일정과 이동한 양식 쪽수를 바로잡았다. 주택관리공단 본문은 별도 한정된 출처 검증으로 재확인하며 매 요청마다 달라지는 다운로드 토큰을 파일 검증으로 오인하지 않는다.
- 정확한 쪽수 대조 중 평택송화의 우선배정 기준을 검색 표기 차이로 잘못 의심했다. PDF3쪽에서 ‘2세미만·30퍼센트’를 직접 확인해 삭제 초안을 게시 전에 철회했다. 관련37공고40항목을 다시 대조해 해당 규칙이 원문에 있음을 확인했다.
- 모바일 실제 렌더링에서 요약 두 줄 자르기가 수치·예외를 가리는 문제와 `::details-content`에 동작 줄이기가 적용되지 않는 문제를 수정했다. 기호만 남은 목록과 빈 문단도 원문에 맞게 정리했다.
- 과거 질문36개에서 선택값의 뜻이나 입력 방식이 바뀌었는데도 새 표시 원고가 맞는 것으로 인식될 수 있음을 추가로 확인했다. 생성기가 게시 원고의 입력 방식·선택값/문구/추가확인 여부·입력 제한·질문 간 의존관계를 표시 가드에 연결한다. 계약이 다른 과거 기록은 당시 설명을 유지하고 현재 질문만 새 설명을 사용한다. 개인 답변을 변환하거나 과거 공개본을 다시 쓰지 않는다.

## 검증·결과

- 실제 기본 목록은 여전히122건, 검토 대상106건·1,474질문·2,615서류다. [공고별 결과](../../reviews/2026-11-21-listed-conditions/results.json)에 버전·항목 수·남은 확인 필요를 기록했다.
- 프런트 전체 CI:82개 테스트 파일/636검사, 계층·순환 검사10개, 타입·서식·생성 원고 일치·빌드 통과.
- 백엔드 단위791개 및 출처 게시 통합42개 통과. IntelliJ Java5개 파일을 사본에서 재서식해 차이0 확인. bootJar 성공.
- 실제106공고·1,474질문·일회성 확인2,296시나리오에서 서류 ID·필수 여부·답변 보존·추가 확인 경고가 일치했다. 종료 등36건은 신규 확인을 제공하지 않는 계약에 따라 상세만 검사했다.
- 답변 의미가 바뀐 과거 질문36개는 당시 설명을 유지하고 현재 질문은 새 설명을 사용하며, 과거 입력 객체는 변경되지 않음을 확인했다. 생성기는 프로젝트 서식으로 파일을 출력하도록 정리했다.
- Edge의360/390/768px 및360px 글자125%에서106공고 접힘·펼침·본문 끝·제목·표·가로 넘침·실제 클릭을 검사했다. 정읍상동 새 PDF40쪽, 정읍수성 새 PDF3쪽이5173에서 실제 열리는 것도 화면 내용까지 확인했다. 실제 휴대폰 검사는 하지 않았다.

## 기여·한계

원문 대조와 구현은 AI 보조 작업이며 기관의 자격 확정이나 사람 관리자 승인으로 표현하지 않았다. 현재19공고의28개 확인 필요 항목은 실제 출처 차이·확인 범위를 보존한다. 공고별 검토 원고가 없는 미래 공고에 같은 세부 숫자·예외를 임의로 적용하지 않는다. 기존 준비는 새 안내를 확인하는 기존 갱신 흐름을 이용하며 답변을 강제로 바꾸지 않는다.

## 발표·포트폴리오 메모

공고별로 다른 기준을 읽기 쉬운 공통 화면에 연결하면서 원문 동일성·답변 의미·필수 서류·개인 기록을 함께 보존한 사례다. 범용 문장 치환만으로 완료를 판단하지 않고 실제 전체 목록과 답변 분기, 작은 화면의 표현을 교차 검증했다.
