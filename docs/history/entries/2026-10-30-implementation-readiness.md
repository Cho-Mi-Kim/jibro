## 배경·문제

사용자가 초기 설정과 두 브랜치 병합을 마친 뒤 바로 구현할 수 있는지, 빠뜨린 작업이 있는지, 프론트엔드와 백엔드의 구현 순서를 질문했다. 설치·검사 완료와 실제 업무 기능 구현 완료를 구분하고, 먼저 합의할 사항과 기능 개발 중 진행할 사항을 정리했다.

판단 기준은 [기획안](../../planning/project-proposal.md), [기획 세부안](../../planning/project-details.md), [화면설계서](../../design/screen-spec.md), [코딩 컨벤션](../../conventions/coding-conventions.md), [검증 기록](../../verification.md)이다. 과거 대화의 개발 경험 편중은 참고하되 현재 팀원 수·역량·담당·주당 가용 시간은 재확인이 필요하다.

## 고려한 선택지

- 프론트엔드 전체를 먼저 완성: 화면 검토를 빨리 진행할 수 있지만 실제 공고 구조·서버 상태와 맞지 않는 화면을 수정할 수 있다.
- 백엔드 전체를 먼저 완성: 데이터·API를 먼저 정리할 수 있지만 실제 사용자 흐름 검증이 늦어지고 다른 팀원이 기다릴 수 있다.
- 기능별 계약을 먼저 합의하고 양쪽 구현·연동을 반복: 초기 합의 비용은 들지만 작은 실제 흐름으로 데이터·화면·권한·저장을 함께 검증할 수 있다.

## 결정·이유

현재 환경으로 구현 착수는 가능하다는 점을 확인했다. **기능별 최소 데이터 모델과 API 계약을 먼저 정하고 프론트엔드·백엔드를 병행하는 방식**을 권고했다. 이는 아직 사용자가 채택한 개발 계획이 아니므로 기존 제품·기술 정책을 변경하지 않는다.

한 사람이 양쪽 핵심 구현을 대부분 담당하게 된다면 첫 기능의 얇은 서버 흐름을 만든 뒤 화면에 연결하고 다음 기능으로 이동하는 순서를 권고한다. 다른 팀원은 익숙한 작은 화면·테스트·공고 구조화 등 결과와 완료 기준이 분명한 작업을 맡을 수 있다. 역할은 실제 역량·학습 목표·가용 시간 확인 후 정한다.

## 변경·해결 과정

코드·환경·원격 설정을 변경하지 않고 다음 상태를 확인했다.

| 범위 | 확인 결과 | 다음 작업 권고 |
| --- | --- | --- |
| 실행·검사 기반 | React·Spring Boot·PostgreSQL, PR 검사, 기록 자동화 구성 완료 | 팀원별 clone 후 실행·hook 설치 확인 |
| 실제 업무 기능 | 프론트엔드는 연결 확인 화면, 백엔드는 health·보안·Querydsl 기반 설정. 운영 도메인·운영 SQL 없음 | 공고 목록·상세의 첫 연동 기능 구현 |
| 문제·데이터 근거 | 문서에 조사·인터뷰 계획이 있으며 저장소에서 완료 결과는 확인되지 않음 | 별도 보유 결과 확인. 없으면 인터뷰와 실제 공고·공식 API 검증을 개발과 병행 |
| 데이터 모델 | 공고·규칙·개인 준비·검수·버전 연결 방향은 합의, ERD·구체 스키마는 후속 작업 | 실제 공고를 기준으로 최소 ERD·상태 전이·Flyway 작성 |
| API | 검색 결합·페이지 크기·공통 오류 등 원칙 합의, 기능별 DTO·허용 값·정렬·상태 코드 등은 미구체화 | 첫 기능부터 요청·응답·오류·예시·권한 계약 작성 |
| 준비도·집 | 초기 완성 범위 포함은 확정. 계산 가중치·구체 단계 매핑은 미확정 | 미확인·해당 없음·재확인·필수 항목·반올림을 다루는 초안과 기대 결과 사례 작성. 서버에서 계산 |
| 인증 | 세 로그인 수단·토큰 보관/수명·권한 방향 합의. 실제 인증 기능 없음 | 회원·로그인 수단 모델, 쿠키·CSRF·실패 복원, 관리자 생성 절차를 해당 기능 전에 구체화. Google·카카오 등록/개발 redirect URI는 일찍 준비 |
| 공고 운영 | 동시 검수·공개 상태 분리·수정 시 사용자 기록 보존 방향 합의 | 첫 공개 흐름에 최소 검수 기능 포함. 자동 수집의 중복·수정 감지와 변경 영향 처리까지 후속 연동 검증 |
| 협업 통제 | main·develop의 Rulesets 응답이 빈 배열이고 기존 방식 보호 조회도 Branch not protected | PR·승인·세 CI 통과를 필수로 하는 보호 설정 권고. 이번에는 설정하지 않음 |
| Java 포맷·문서 현황 | 로컬 포맷 검증 완료, CI 필수 연결은 보류. 일부 기존 문서에 원격 CI 미확인 표현 남음 | 포맷터 CI 검증과 문서 상태 갱신은 기능 개발과 병행 |

권고한 구현 순서는 다음과 같다. 각 단계의 계약은 해당 기능을 시작할 때 구체화하며 서비스 전체 설계 완료를 기다리지 않는다.

1. 실제 공고·공식 API 제공 필드 확인과 첫 기능의 최소 ERD·API·완료 조건 합의. 첫 자동 수집 호출과 샘플 보존을 확인한다.
2. 검수한 공고의 비회원 목록·상세·복합 검색을 화면과 서버에 연결한다. 최소 검수·공개 처리를 포함하며 기본 정보 공개와 준비 안내 제공 상태를 분리한다.
3. 이메일 로그인·JWT·재발급·권한과 준비 건 저장·재조회 흐름을 연결한다. Google·카카오는 등록을 일찍 진행하고 기존 문서의 순서에 따라 구현해 세 방식을 초기 제공 범위에 유지한다.
4. 조건 질문·개인 서류·검증된 공식 발급 링크·일정·지금 할 일·준비도(%)·집 표현을 실제 서버 상태에 연결한다. 상태 변경 후 재조회와 새로고침에서도 결과가 유지되는지 확인한다.
5. 수집 재실행·수정 공고·버전별 검수·재확인과 기존 개인 기록 보존을 확장·통합 검증한다. 최종 시연 전 권한·저장 실패·미검수 안내 차단·준비도 오해 여부를 확인한다.

대표 공고 한 건으로 첫 흐름을 만드는 것은 구현 순서이며 지역·유형·수집량·전체 지원 범위의 상한으로 바꾸지 않는다. 준비도(%)·집 건축 표현은 초기 완성에서 유지한다. AWS 배포 전략 구체화, 미채택 캘린더 구현, 후순위 알림을 착수의 선행 조건으로 추가하지 않는다.

## 검증·결과

- `git status --short --branch`와 소스 목록·실제 파일을 확인했다. 작업 시작 시 develop은 미커밋 변경 없이 origin/develop과 같았으며, `git fetch origin develop` 후 fast-forward 확인도 Already up to date였다.
- `gh pr view 1`, `gh pr view 2`에서 두 PR의 MERGED 상태와 project-history·frontend·backend 3개 검사 각각 SUCCESS를 확인했다. 실행 근거는 [PR #1 검사](https://github.com/Cho-Mi-Kim/jibro/pull/1/checks), [PR #2 검사](https://github.com/Cho-Mi-Kim/jibro/pull/2/checks)다.
- 두 브랜치의 Rulesets 조회는 빈 배열, `/branches/{branch}/protection` 조회는 각각 HTTP 404·Branch not protected였다. 보호 설정이 적용되지 않은 상태로 판단했다. API 접근이 안 된 첫 시도는 읽기 전용 네트워크 접근을 허용해 재실행했으며 실제 조회에 성공했다.
- `frontend/src/app/App.tsx`는 DevelopmentPage만 연결하며, `backend/src/main/java/org/jibro/global/config/SecurityConfig.java`는 GET health만 허용하고 나머지 요청을 차단한다. 공통 fetch는 HTTP 상태를 다루는 기본 단계이며 도메인 오류 code 처리·인증 복원 등은 후속 구현이다.
- OpenAPI·Spring Security의 공식 문서를 참고했다. [OpenAPI 명세](https://spec.openapis.org/oas/v3.1)는 언어와 소스 구현에 독립적으로 API를 기술하는 근거, [Spring OAuth2 Login 설정](https://docs.spring.io/spring-security/reference/servlet/oauth2/login/advanced.html)은 등록된 redirect URI와 실제 처리 경로의 일치를 확인하는 근거다. OpenAPI 도구·라이브러리를 설치하지 않았다.
- `node scripts/project-history.mjs sync`: 기록 3건의 목록을 갱신했다. `.tools/verify-docs.mjs`: Markdown 19개·상대 링크 127개·내부 앵커 7개 확인, 원본 문서 5개·목업 10개 보존 확인, 오류 0건이었다. `git diff --check`도 통과했다.
- 업무 기능·설정 변경이 없어 기존 제품 빌드·테스트를 다시 실행하지 않았다.

## 기여·한계

Codex는 저장소·원격 상태 확인과 구현 순서 권고를 수행했다. 실제 공고 수집 성공, 인터뷰 완료, 신규 기능 구현, 사용자 효과·팀원별 기여는 확인하거나 만들어 내지 않았다. 현재 개발 인력·남은 수업 일정은 확정되지 않았으므로 기간·담당을 임의로 배정하지 않는다.

## 발표·포트폴리오 메모

초기 환경 완료와 업무 기능 착수에 필요한 설계를 구분하고, 공고 데이터·API·규칙의 구체화 항목을 확인했다. 기능별 화면·서버 연동을 통해 가설을 확인하는 개발 순서를 제안했으며, 제안의 실제 채택·실행 결과는 후속 기록으로 확인해야 한다.

## 후속 작업

- 팀 보유 인터뷰·공고 분석 결과, 현재 참여 인원·개발 역량·주당 가용 시간 확인.
- 첫 공고·데이터 수집 경로와 공고 목록·상세 API·ERD·완료 조건 구체화.
- 브랜치 보호·팀원별 실행 확인, 외부 API·소셜 제공자 등록 준비.
- 본 권고안의 채택 여부와 실제 역할·진행 일정은 팀 협의 후 갱신.
