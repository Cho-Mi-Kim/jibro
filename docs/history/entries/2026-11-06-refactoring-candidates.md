- 실제 소스 읽기, 전체 src의 호출자/import 검색, 현재 브랜치·HEAD 확인.

- 공고 스크롤과 가이드 스크롤은 동작 차이가 있으므로 즉시 범용 훅으로 합치자는 제안은 채택하지 않았다.
- 앱 소스·스타일·테스트·데이터 변경 없음. 이번에 추가한 것은 후보 기록과 작업 연결 기록뿐이며, 제거한 앱 코드는 없다.

### 동작 보존과 오류 수정 구분

- 동작 보존: 준비 계산 분리, 미사용 UI·분기 제거, NextAction 스타일 정리. DB 소유권·잠금·revision·이력 정책은 변경하지 않았다.
- 오류 수정: 시연 재확인/검수 상태 일치, 끊긴 신청 경로, 보관 초안/대상 결합, 실패 테스트 고장 주입, 공개 일정 누락 및 발표 우선순위 불일치.
- 명시적 탐색 변경: 독립 조건 결과 URL을 `/conditions/result`로 분리했다. 내 준비 `/conditions` 주소는 새로고침·직접 진입 시에도 조건 탭을 유지한다.
- 캘린더 의미 교정: 공식 자료에 확인된 `18:00` 등 시각이 있으면 종일 일정 대신 해당 시각으로 내보낸다. 날짜만 있으면 임의 시각을 추가하지 않는다.
- 준비 완료 뒤 다음 행동은 실제 화면에 맞춰 “신청 일정 확인하기”로 표시한다. 신청 여부 기록은 개요 팝업에서만 처리한다.

정적 검사는 프로젝트의 TypeScript·ESLint·빌드·Prettier를 사용했다. 첨부 자료의 Iron Laws 도구와 외부 GPT Pro 리뷰는 실행하지 않았으며, 실행했다고 주장하지 않는다. 구현하지 않은 담당자의 독립 코드 리뷰는 실제 수행했다.

최종 수정 후 독립 검토자가 공개 일정 게이트 제거·서류 대상 발표 우선순위·동일 기준에서만 기록 표시·일정 확인 현황 분리를 다시 읽어 처분을 확인했다. 해당 검토 범위에서 추가 심각한 회귀는 발견하지 않았다.

### 최종 검증

- 프론트: `npm run build`, `npm run lint`, `prettier --check src` 통과. Vitest **21개 파일 132건 통과**.
- 백엔드: `gradlew build integrationTest` 통과. XML 결과 **단위 15건 + 실제 PostgreSQL 통합 23건, 실패·오류·skip 0**.
- 계약 검출 확인: 시연 서류 가중치를 50→49로 바꾸면 계약 테스트 3건 실패; 발표 분류에서 당첨을 빼면 2건 실패; 준비 조회 오류를 빈 목록으로 삼키면 실패 경로 테스트 실패; 보관 성공 시 모든 초안을 비우면 다른 대상 초안 보존 테스트 실패. 각 변이는 원복 후 통과했다.
- 전체 실행 중 발견한 TypeScript의 Node 타입 부재와 Vite의 외부 raw fixture 로딩 제한은 테스트의 로컬 파일 읽기/타입 선언으로 바로잡았다. 제품 서버의 파일 접근 제한은 완화하지 않았다.
- 화면: 360·768·1280px에서 NextAction의 변경 전후 요소 크기·여백·글자·grid 계산값 일치. 393×852 브라우저 검증 수행. 실제 휴대전화나 글자 200% 확대 검증은 별도 수행하지 않았다.
- 실제 연결: 새 JAR 8086 + 프론트 5176 + `jibro_test.refactor_qa_20261106`의 격리 스키마에서 브라우저 검증. 검증용 가상 공고와 새 체험 계정만 사용했다. 질문 2개 저장 → 독립 결과 새로고침 → 홈 질문 응답에서 조건 탭 → 조건 탭 새로고침 → 여정 공식 신청 팝업 → 신청 완료 기록 후 새로고침 유지 → 메모 포함 보관 후 새로고침 유지 → 복원 후 답변 2/2·신청 완료 유지까지 확인. 브라우저 console error 0.
- A/B 초안 전환, 저장 중 대상 변경, 실패/재시도, 복원/메모 연결 중 다른 초안 보존은 ArchivePage의 대역 통합 3건에서 검증했다. 실제 브라우저에서는 준비 1건의 보관/복원 흐름을 확인했다.
- 실제 외부 신청·메일·소셜 로그인·수집 API를 다시 실행한 검증은 아니다. 개인 신청 기록은 공식 기관 신청을 대신하지 않는다.

### 실행 상태·산출물

자동 승인 검토가 기존 8080 백엔드 중지·재시작 작업을 차단했다. 기존 프로세스를 우회 종료하지 않았다. 5173의 프론트 소스는 갱신됐지만 연결된 백엔드는 이전 실행 빌드이며 **최신 JAR 재시작은 미반영**이다. 기존 5173 health는 UP/database UP을 확인했다. 새 백엔드는 별도 8086에서 검증했고 검증 서버 8086/5176은 종료했다.

- 검증 로그·화면: `.tools/logs/refactor-*` (로컬 검증 산출물).
- 책임 모델: `docs/models/build_code_model.py`, `docs/models/README.md`, `frontend/public/jibro-code-model.html` 갱신. SVG 5개 파싱·참조 파일 존재 확인; 다이어그램 배치는 유지.
- 연결 폴더 `.jibeuro/project.json`의 code_roots를 실제 저장소로 수정하고 생성 구조·의미 지도를 현재 구현과 정합화했다. 원본 업로드 문서는 유지했다.
- 후속 실행 항목: 사용자가 기존 로컬 백엔드를 종료한 뒤 최신 빌드를 시작하면 5173에서도 새 서버 구현을 사용할 수 있다. 검증 환경 통과를 기존 서버 교체 완료로 보고하지 않는다.

구조 개선과 결함 수정은 확인했으나 성능 개선 수치나 실제 사용자 효과를 측정한 결과로 표현하지 않는다.

### 후속 재시작 완료

같은 날 사용자 “재시작 해주고” 요청으로 기존 기록된 백엔드의 실행 경로·시작 시각·JAR 명령을 대조한 뒤 해당 프로세스만 종료했다. `Start-Local.ps1 -NoBrowser`가 최신 bootJar를 확인하고 새 8080 프로세스를 시작했다. 기존 5173 Vite와 DB는 유지했다. 새 프로세스의 시작 로그 및 5173 프록시를 통한 `/api/v1/health`에서 status/database UP을 확인했다. 앞 절의 재시작 미반영 제약은 이 후속 작업으로 해소되었다. 당시 차단과 별도 QA 결과는 이력으로 유지한다.
