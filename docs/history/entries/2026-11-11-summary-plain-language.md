# 요약의 긴 행정 표현을 짧은 말로 표시

## 배경·문제

사용자가 ‘미성년 직계비속(태아 포함) 2명 이상을 양육’ 같은 요약 표현을 앞으로 ‘2자녀 이상’ 정도로 줄여 달라고 요청했다. 기존 요약 가독성 작업의 후속 표현 개정이다.

## 선택과 결정

화면별로 문자열을 치환하거나 검수된 DB 원고를 일괄 수정하지 않고, 서버의 공통 요약 표현 함수 `NoticeSummary.concise`를 기존 공개 읽기와 미래 자동 요약 생성에서 함께 사용한다. 요약은 짧게 표현하되 실제 자격 조건과 공식 근거는 정확한 표현을 보존한다.

## 변경·해결

- 확인된 대상 문장의 해당 표현만 ‘2자녀 이상인/이며’로 줄인다. 다른 자녀 수를 2명으로 바꾸지 않으며 이하·부정문·나머지 조건은 그대로 둔다.
- `SupportSummaryCompiler`는 기존 원문 검증 후 공통 표현 함수를 사용한다. 미성년·태아 포함의 공식 근거를 확인하는 조건은 완화하지 않았다.
- 기존 공고는 공개 API에서만 짧게 표시한다. DB 원고·조건·서류·일정·검수 상태·개인 준비에 쓰기 없음. 기존 관리자/접수종료 읽기 제외 유지.
- 재시작 과정에서 이전 실행 기록의 실행 파일 경로가 null인 것을 발견했다. PID·생성 시각·실제 Java 경로·프로젝트 JAR 경로가 모두 일치하는 것을 확인한 후 메타데이터를 복구했다. 새 기록은 시작된 프로세스를 다시 조회해 경로를 남긴다.

## 검증·결과

요약 관련 단위17건 및 bootJar 통과. 현재 공개 다자녀 공고3건의 API에서 짧은 표현을 확인하고 나머지 응답 필드가 동일함을 확인했다. 비교용 신혼 공고1건은 전체 응답 동일. 종료27건·개인준비0행 지문 동일. 5173 연결 백엔드를 `backend-support-summary-concise.jar`(PID110472)로 재시작, health/DB UP 확인. 기존 Gradle 폐기 예정 기능 경고 있음.

## 기여·한계

AI가 사용자 지정 표현의 공통 처리·회귀 테스트·로컬 검증을 수행했다. 임의의 모든 행정 용어를 자동 번역하는 기능은 아니다. 이번 단계는 서버 문구 변경이므로 모바일 화면 배치 검사는 다시 수행하지 않았다. 커밋·push·외부 배포 없음.

## 발표·포트폴리오 메모

요약용 쉬운 표현과 정확한 자격 기준의 책임을 분리하고, 기존·신규 공고가 같은 표현 규칙을 사용하도록 했다.

## 후속 작업

요약은 핵심 대상·지원 중심의 짧고 익숙한 말을 사용한다. 추가 축약은 공고별 숫자·부정·예외 의미가 바뀌지 않는지 확인해 적용한다. 로컬 검증 근거는 `.tools/qa/notice-support-summary/concise/validation.json`이다.


## 지원 내용도 간결하게 표시

- 후속 사용자 요청: 거창군 신원면 예시처럼 지원 문장도 간결하게 표시. 지역·주택·비율을 남기고 ‘자격에 따라 시중시세의’는 ‘시세의’, ‘보증금과 월 임대료를 내고 거주할 수 있도록 공급’은 ‘보증금과 월 임대료로 공급’으로 줄였다.
- 같은 `NoticeSummary.concise`에서 대상과 지원 문장을 처리한다. 임대조건/임대료 범위, 숫자·소수점·비율, 부정문과 별도 보증금/재계약 설명은 보존한다. 기존 읽기와 미래 자동 생성 공용이며 DB·검수 상태·자격 기준 수정 없음.
- 검증: 요약 단위19건·bootJar 통과. 최초 테스트가 임대조건‘으로’의 조사 분기를 발견해 실제 원문의 조사까지 보존하도록 수정한 후 재통과했다. 현재 공개62건 API 대조에서9건의 요약만 변경, 나머지 모든 필드와53건 응답 동일. 요청한 거창군 문장과 정확히 일치. 종료27·개인준비0행 지문 보존. backend-support-summary-benefit.jar(PID98560) 재시작 및 health/DB UP 확인.
- 근거 `.tools/qa/notice-support-summary/benefit/validation.json`. 레이아웃 변경 없음, 이번 단계에서 시각검증을 재실행하지 않았다. 커밋·push·외부배포 없음.


## 자격과 순위 카드도 공고별로 요약

- 사용자 후속 요청: ‘자격과 순위를 구분해요’도 요약 표시. 기존 일반 설명 대신 신청 자격과 선정 순위 두 행을 기본 표시하고, 상세 예외·공식 출처·조건 탭 이동은 우상단 펼침 버튼에 모았다.
- 설계: 화면에서 업무 규칙을 해석하지 않고 `NoticeQualificationSummary` 순수 투영을 `NoticeService.view`에서 사용한다. 자격은 이미 검수한 대상 문장, 선정 방식은 출처가 있는 검수 질문에서 완결된 기준만 읽는다. 명시적 지역 우선·가구 유형별 순위는 짧게 표현하고 정확한 원고를 detail에 보존한다.
- 공통화: 기존 지원 카드와 새 자격 카드를 `NoticeSummaryCard`/전용 CSS 모듈로 통합. 기존 지원 내용 문구·서류 카드 동작 보존. 모든 검수 원고를 다시 AI로 생성하거나 데이터베이스에 쓰지 않는다.
- 검증: 백엔드26개 단위와 bootJar, 프런트15개·typecheck·변경 TS ESLint·경계10개·build 통과. 기존 번들 크기/Gradle 폐기 예정 경고 있음. 처음 프런트 테스트의 중복 출처 선택을 해당 카드로 한정했다. 실제62건 대조에서 소득 분류의 순위 언급을 발견해 순위 배정 문장의 형식 검사와 회귀 사례를 보완한 후 재검증했다.
- 실제62건 API에서 기존 필드 변경 없음. 검수 완료24건에 카드 데이터, 그중16건은 선정 방식 요약·8건은 상세 기준 확인 안내. 종료27건·개인 준비0행 지문 보존. 검수 상태 승격이나 공식 자료 재수집 없음.
- 실행: backend-support-summary-qualification.jar, PID18032, health/DB UP. 시작 직후 Get-Process.Path가 null로 남는 기존 실행 기록 문제는 PID·생성 시각·실행 파일·JAR 대조 후 복구하고 새 기록은 Win32_Process의 ExecutablePath로 확인했다.
- 브라우저393×852/360×800에서 요약 표시·세부 펼침·출처·조건 탭 이동·가로 넘침 없음 확인, viewport 복원. 실제 기기·글자 확대·다크모드는 이번 단계에서 다시 검사하지 않았다. 로컬 QA: `.tools/qa/notice-support-summary/qualification/{validation.json,mobile-393.png}`.
- AI가 요청된 요약 표현·공통 모듈·검증을 구현했다. 커밋·push·외부배포 없음. 향후 새 형식은 검증된 문맥이 확보될 때 추가하며 상세 기준 안내를 임의의 확정 순위로 바꾸지 않는다.


## 필요한 서류 확인도 핵심 서류로 요약

- 사용자 후속 요청에 따라 공통 설명을 공고별 공통 서류/해당 시 추가 요약으로 바꿨다. 각 구분은 핵심3개와 나머지 개수, 확인 필요 서류는 별도 행으로 표시한다. 공고 상세의 일정 우선 배치는 유지했다.
- 서버 `NoticeDocumentSummary`는 검수된 DocumentTemplate의 조건 연결/GuidanceIssues/출처만 사용한다. 공통 여부를 화면에서 다시 계산하거나 개인 자격/답변을 추정하지 않는다. 안정 정렬로 기본 증빙을 우선하며 표기 주체·상세 발급형식·대체 서류 의미를 보존한다.
- 프런트 `NoticeDocumentSummary`도 기존 공통 NoticeSummaryCard를 사용한다. 이전 SummaryDisclosure 구현을 삭제해 중복 경로를 정리했다. 출처·제출 기준·전체 제출서류 이동은 접기 안에 유지한다.
- 검증: backend23개(서류요약6·자격요약7·표현6·확인필요범위4) 및 bootJar, frontend17개·typecheck·변경파일 ESLint·경계10·build 통과. 기존 번들크기/Gradle 경고 유지. API62건 비교에서 새 documentSummary 외 기존 필드 보존, 검수 완료24건의 그룹/출처/개수/충돌 제외를 대조했다. 종료27건·개인준비0행 지문 동일.
- 로컬 실행: backend-support-summary-documents.jar PID105892, health/DB UP. DB·검수 상태·원고·준비 기록 변경 없음. 향후 검수 완료 공고도 동일 읽기 경로를 사용한다.
- UI: 393×852/360×800 표시·접기펼치기·원문페이지 링크·제출서류 탭 이동 확인. 360px20px 글자 확대에서 가로 넘침 없음, 고정 하단 영역과 스크롤 영역 분리 유지. 기존 사용자 축소 설정의 펼침 터치 영역32×24는 유지했다. 임시 글자 크기와 viewport 복원. 실제 기기/다크모드는 재검사하지 않음.
- 근거: `.tools/qa/notice-support-summary/documents/{validation.json,mobile-393.png}`. AI가 구현/로컬 QA를 수행했으며 커밋·push·배포 없음. 요약이 전체 제출 목록이나 모든 서류의 개인별 필수 판정으로 받아들여지지 않도록 해당 시 추가/전체 목록 경로를 함께 유지한다.

## 앞으로 수집될 공고의 자격·순위·핵심 서류 자동 요약 검증

- 사용자 요청: 미래 수집도 기존 요약 형식 자동 적용, 접수종료 제외. 별도 저장/예약 경로를 덧붙이지 않고 기존 자동 검수 게시→공개 읽기 투영을 유지했다.
- NoticeService가 AutomaticReviewEligibility.closed를 재사용하도록 변경해 시작일 누락+지난 마감, 정확한 마감 시각 및 한국시간 당일 종료, 공식 조기종료와 취소를 제외한다. 기본/안내/변경 검수 경계 보존.
- 신규 자동 발췌 통합 테스트에서 절 제목 줄이 선정 기준 인식을 막는 문제를 확인했다. 알려진 선정 절 제목만 제거하고 완결된 문장을 읽도록 수정했다. 표 행·조건부 머리말은 지우지 않으며 상세 원문 그대로 보존한다.
- 단위 요약 경계19건(공개경계5·자격8·서류6), 자동 게시/부분 검수 통합13건 통과. 같은 실행에서 가이드 관련 검증도 수행(별도 로딩 지연 이력). 현재62건 핵심 데이터/요약/버전 동일, 달라진 수집/확인 시각과 구분했다. 재시작 전후 종료 공고/준비 지문 동일.
- 로딩 지연 수정 요청을 함께 처리한 실행본 backend-guide-pagination-v2.jar에 반영했다. 실제 미래 신규 공고가 도착한 운영 관찰은 아니며 격리된 PostgreSQL 테스트의 수집→발췌→자동검수→공개 응답을 검증했다. 커밋/push없음.

공고 상세 조건 탭에서는 NoticeConditionCard가 항목별 검수 설명에서 첫 한두 문장을 보여주고 질문형 제목과 반복 안내 표현을 줄인다. 금액·날짜·소수점을 글자 수로 자르지 않고, 축약한 조건은 같은 항목에서 전체 설명·공식 근거를 제공한다. 확인 필요 조건은 확인 사유를 먼저 표시한다. 5173에서 신혼·신생아 전세임대Ⅱ의 성년·미성년 예외 항목을 360·390·768px로 확인했다.

공고 상세와 내 준비의 조건 결과가 ConditionSummary로 같은 항목별 요약·전체 조건·공식 근거를 표시한다. 내 준비의 추가 확인과 답변 완료 목록은 저장된 답변을 함께 보여준다. 입력 화면은 기존 질문과 선택지를 사용한다. 관련 테스트 61건과 빌드를 통과했고 5173 브라우저 360·390·768px에서 테스트 준비 기록의 두 그룹과 펼침 동작을 확인했다.

이전 준비 기록의 조건도 ConditionSummary를 사용하며 선택한 저장 버전의 질문·답변·검수 사유만 전달한다. 당시 조건·선택지와 근거를 한 번에 펼쳐 원래 문구와 제출 당시 선택을 확인한다. Chrome 360·390·768px에서 테스트 기록 두 버전의 요약 값이 서로 구분되고 펼침이 동작하는 것을 확인했다.
