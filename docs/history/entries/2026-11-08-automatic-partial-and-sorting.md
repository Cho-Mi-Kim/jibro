# 신규 수집 공고의 부분 준비 안내와 기본 정렬

## 요청과 결정

사용자가 앞으로 수집되는 공고에도 충돌한 항목만 확인 필요로 남기고 나머지는 자동으로 준비 안내를 제공하도록 요청했다. 기본 정렬은 접수 중·예정·종료 각각에서 정상 안내·일부 확인 필요·검수 중·미제공 순으로 지정했다. 기존 지정 4건의 수동 원문 검토와 별개로 예약 자동 검수에 이 정책을 적용한다.

## 구현

- 수집·발췌 이후 기존 `AutomaticReviewService`가 같은 `GuidanceReviewCompiler`를 호출한다. 명시 조건, 제출 목록, 선택적 일정, 서식의 확인 사안을 개별 모듈에서 판정하여 `Content.reviewIssues`에 모은다. 미해석 내용을 승인하거나 어느 한쪽의 충돌 값을 선택하지 않는다.
- 원문 구간의 소득 충돌만 별도 질문으로 분리하며, 정상 연령 등 다른 조건은 계속 응답할 수 있다. 서류 목록은 공통 항목을 유지하고 상충 항목만 확인 필요로 남긴다. 명확히 연결된 종속 서류에도 같은 상태를 적용한다. 영향을 특정할 수 없는 조건·서류 참조는 전체 보류다.
- 일정의 발표·서류 마감 충돌은 확정 일정에서 제외하고 근거로 남긴다. 접수 경계·누락 순위·알 수 없는 숫자 범위는 기존 공개 조건을 충족하지 못하면 전체 보류한다. 캘린더와 알림에 추정 날짜를 넣지 않는다.
- 같은 이름의 PDF/HWPX에서도 모든 페이지를 확인한다. 동일 규칙 값만 다른 경우 양쪽을 검수하며, 조건 추가·누락과 주변 예외의 차이를 합집합으로 확정하지 않는다.
- 자동 공개 감사에 `PARTIAL`과 당시의 확인 필요 범위를 저장하는 V31을 추가했다. 기존 수동 차단, 최신 revision·발췌 지문, 기존 개인 스냅샷 보호를 유지한다. 정책과 로컬 분석 캐시 버전을 올려 과거 HOLD를 새 정책으로 평가할 수 있게 했다.
- 기본 정렬은 DB에서 페이지 분할 전에 상태→안내 순위를 적용한다. 일정 미확인은 마지막, 조기 종료·취소는 종료 그룹이다. 명시 마감순·최신순은 유지한다. 프런트 시연 데이터에도 같은 비교 기준을 적용했다.

## 검증과 실제 실행

- 백엔드 단위 380개 통과. 통합 216개를 실행했으며 1개의 신규 테스트에서 정정 후 상태 기대값을 기존 계약인 CHANGE_REVIEW로 바로잡고 해당 7개를 재실행해 통과했다. 새 수집→발췌→자동 부분 공개→PARTIAL 감사, 중복 방지, 이전 정책 HOLD 재평가, 정상/충돌 서류 구분, 기존 개인 스냅샷 보존을 확인했다. 3접수 상태×4안내 상태의 페이지 분할 전 정렬도 실제 PostgreSQL로 확인했다.
- 프런트 281개 테스트, lint, 타입 검사와 빌드, 계층·순환 검사 10개 통과. 기존 500kB 번들 경고는 남아 있다. 모바일 브라우저 393×852·360×800에서 정렬 기본 선택, 제공/일부 확인 필요의 순서, 가로 넘침 없음·콘솔 오류 없음을 확인했다. 실제 기기 검증은 아니다.
- 백업 `.tools/backups/before-auto-partial-20261108.dump` 102,839,874bytes 생성 후 backend PID23244로 재시작했다. frontend PID52132는 유지했다. 5173 health/database UP, V31 적용 성공.
- 2026-11-08 16:56 KST 실제 API 4,657건/전체 페이지의 상태·안내 순위가 단조 순서임을 확인했다. 당시 접수 중 정상1, 접수 예정 정상9·부분4, 접수 종료 정상2, 일정 미확인 검수4639·미제공2였다. 예약 수집이 계속되므로 총건수는 이후 변할 수 있다. 일정이 확인되지 않은 공고를 종료/예정으로 추측하지 않는다.
- 실제 예약 실행에서 `official-rules-v5` BASIC PASS30/GUIDANCE HOLD29 감사 기록을 확인했다. 새로운 실제 부분 공개가 발생했다고 주장하지 않는다. 신규 부분 공개는 분리된 테스트 DB에서 확인했으며, 원문 누락·범위를 정하지 못한 기존 자료는 계속 보류된다.
- 기존 부분 제공 4건의 version2/revision3/확인 필요8건과 수동 보호 상태가 유지됐다. 작업 전후 개인 준비 스냅샷 및 기존 승인 안내 해시가 같았다. 이번 작업 시작 검증 시 개인 준비 테이블은 0행이었으며 이전 작업 당시의 2행과 구분한다.
- 근거: `.tools/qa/auto-partial/` 실행 로그·보존 비교·런타임 검증과 `docs/reviews/2026-11-08-auto-partial-runtime.json`. 테스트 자료는 분리된 DB에만 사용했고 실제 공개 가짜 공고를 추가하지 않았다. commit·push·배포 없음.
