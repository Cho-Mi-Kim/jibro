## 배경·문제

탭 이동·초기 로딩이 느려 공고/내 준비의 한꺼번에 받는 데이터를 확인해 달라는 요청이다. 공고 20개 응답에 질문·첨부·서류·요약 전체가 포함됐고 카드 미리보기에서도 상세를 다시 요청했다. 개인 준비 목록은 모든 스냅샷과 각 공고 전체를 읽어 목록을 만들었다.

## 고려한 선택지와 결정

페이지 크기를 줄이는 대신 목록/미리보기와 상세 계약을 분리했다. 20개 표시·필터·정렬은 그대로 유지하며 전송하지 않아도 되는 상세 데이터와 개인 메모를 제거한다. 준비도는 저장 시 평가된 값을 선택기에서 사용하고 최신 안내 대조는 선택한 상세 및 수정 명령에서 수행한다. 짧은 캐시로 탭 이동의 반복 조회를 줄이되 쓰기 직전 확인은 유지한다.

## 변경·해결 과정

NoticeQueryRepository의 명시적 projection → NoticeService → NoticeListItem, PreparationRepository 단일 목록 projection → PreparationListItem 경로로 변경했다. 목록에서 공고 전체/개인 전체 자료를 로딩하는 옛 경로를 제거했다. React에서 공통 목록·선택 상세 훅을 분리하고 카드 미리보기 추가 API 호출을 제거했다. 홈/세부 탭/선택기/마이/시작/보관/비교/데모 호출자를 맞췄다. 시작 시 읽기 실패를 무시하는 변경은 회귀 검증에서 발견해 제외했으며 기존 실패 시 보존 동작을 유지한다.

## 검증·결과

- 실제 공개 공고 20개: JSON 860,723 → 12,024 bytes, 98.60% 감소. 동일 ID/순서/표시 메타데이터 유지, 예약 수집에 따른 collectedAt 2건만 측정 중 변경. 첫 서버 실행 후 708ms, 이어서 132/71/95ms; 시간 측정은 동일 조건 전후 비교가 아니므로 속도 배수로 해석하지 않는다.
- 별도 테스트 DB 준비 1건: 목록 150 bytes / 상세 2,203 bytes. 소유자/보관 제외, 상세 답변·메모 보존 및 변경 검수 후 수정 거부 검증. 실제 사용자 준비 건으로 성능 수치를 측정하지 않았다.
- backend 통합 26개: ListPayload, NoticeSort, ApplicationTiming, Housing, SampleNoticeVisibility, MemberFeatures 통과. bootJar 성공.
- frontend 관련 134개 통과(19개 파일 94개 통과 후 App 40개 최종 재실행). 타입·Prettier·ESLint·경계 10개·빌드 통과. 빌드의 기존 500KB chunk 경고는 별도 범위다.
- 5173 로컬 서버에 반영. 재시작 전후 접수 종료 공고/개인 준비 지문 동일. 수집·검수 변경이나 사용자 기록 쓰기를 하지 않았다.
- Chrome 실제 CSS 393×852 / 360×800에서 공고 20개 표시·카드 펼치기·가로 넘침 없음, console error 없음. 내 준비 실제 브라우저는 비로그인으로 로그인 이동까지 확인; 로그인 후 선택/탭/저장 흐름은 자동화된 화면 테스트로 확인. 실제 휴대폰 미검증.
- 측정 자료: `.tools/qa/list-loading/validation.json`, before/after 응답 및 화면 캡처(로컬 전용).

## 기여·한계 / 발표 메모

목록 응답을 상세 응답과 분리해 실제 목록 전송량을 줄였고 개인 준비의 건수 비례 공고 조회를 제거했다. AI 구현 보조 결과이며 팀 또는 개인 성과를 대신 확정하지 않는다. 모든 로딩 지연이 해결됐다고 보증하지 않으며 외부 서비스 처리 속도·클라이언트 초기 번들 크기는 이번 변경의 대상이 아니다.
