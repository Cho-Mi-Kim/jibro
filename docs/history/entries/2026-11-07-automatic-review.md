# 자동 검수·공개와 Gemini 연결

## 배경·결정
- 사용자가 수동 검수 범위를 줄이고 자동 판단 가능한 내용의 자동 검수/공개를 요청했다. 기존 수동 전용 문서를 이 범위에서 개정하도록 승인했다.
- 최초 결정적 규칙만 적용하는 안은 복잡한 자연어 처리에 한계가 있어, 사용자 제공 Google AI Studio 키를 서버 전용 후보 생성기로 연결했다. 키는 .env에만 두며 Git 제외 여부를 확인했다. 키/요청 헤더/인증 URL을 기록하지 않는다.
- 후보의 자신감이나 complete 응답으로 공개하는 안은 채택하지 않았다. 전체 원문·정확한 인용·지원 규칙·동시성 검증기를 분리했다.

## 구현
- `AutomaticReviewService` → 순수 규칙/일정 컴파일러 → `AutomaticPublicationService`. 기본 정보 공개와 안내 공개 분리.
- 자동 이력과 입력 revision/출처·발췌 내용 해시를 기록. 관리자 편집/검수 보호, 변경 공고의 오래된 일정 회수, 개인 준비 snapshot 보존.
- 원문 전체 파싱 문맥 보존, 잘림/빈 페이지 보류. 실패 자료만 30/60초 후 최대2회 재시도, claim token으로 늦은 worker 종료 방어.
- Gemini REST 클라이언트와 구조화 후보 검증기. 공개 공식 문서만 입력, 사용자 개인정보/답변은 입력하지 않음. `gemini-3.5-flash-lite` 지정, 자동 대체 모델 없음.
- DB 기반 하루 최대10회/최소60초 간격, 입력4만자/출력4096토큰/512KiB 제한, 동일 원문+모델+정책 결과 재사용. 인증/쿼터 오류 당일 호출 중단.
- V22~V25 적용 전 로컬 DB 백업. 코드 기존 변경 보존, 커밋/push 없음.

## 검증·실제 결과
- `./backend/gradlew.bat -p backend test --console=plain`: 30개 테스트 클래스, 150 tests, failures/errors 0. `bootJar` 성공.
- 테스트는 자동 공개, 지원 규칙, 날짜 충돌, 생략된 예외/숫자·대상 변경, 관리자 편집 경합, 동일 발췌 재처리, 제한 재시도, 요청 한도/캐시, Gemini 모의 응답을 포함한다.
- Gemini 실제 모델 목록 API 조회 성공, 지정 모델의 generateContent 지원 확인. 이후 서버와 같은 GeminiReviewClient와 DB 호출 제한기를 사용한 실제 공개 원문 단편 1회 요청에서 CANDIDATE 응답 성공(input1618/output191토큰)을 확인했다. 이 연결 검증 후보로 안내를 공개하지 않았다.
- 새 서버 PID59752(당시), DB migration22~25 성공, 5173 health UP. 이전에 수집한 실제 LH16건 자동 기본 PASS를 확인. 공개 목록은 기존3건+신규16건=19건으로 확인했다.
- 실제16건의 새 전체 문맥 발췌는 대기/진행 중이었다. 안내 PASS는 아직 확인하지 않았다. 실제 Gemini 생성 성공은 위 단편 연결 검증 범위다.

## 기여·한계
- AI 보조 구현·검토·테스트 수행. 팀원의 개인 기여나 운영 품질 지표로 해석하지 않는다.
- 현재 지원하는 정형 조건과 제한된 동등 표현만 자동 승인한다. Gemini는 후보를 만들지만 임의 자연어 문서 전체의 자격 해석을 검증 없이 승인하지 않는다. 복잡한 순위·가구원·표·예외는 HOLD가 될 수 있다.
- 수치 조건은 원문 기반 자기확인 질문이다. 숫자 입력을 통한 보편적 자격 계산 엔진을 새로 구현한 것은 아니다.
- 호출 상한은 계정의 무료 등급을 보장/변경하지 않는다. Google 청구 설정과 실제 한도는 계정별이다.

## 후속
- 실제 발췌 완료 후 공고별 HOLD 사유를 확인하고, 검증 가능한 규칙/표 해석 범위를 확장한다.
- 단편 연결 성공과 별개로 전체 공고의 Gemini 후보·쿼터 및 원문 대조 결과를 확인한다.
- 실제 외부 운영/메일/OAuth/푸시 완료 여부는 이 작업과 별도다.

## 후속: 로컬 해석과 작은 쟁점 묶음

### 요청·검토·결정
- 사용자 요청: 크롤링 버전처럼 해석을 로컬에서 구현하여 API가 적은 자원으로 읽게 한다. 과거 구현 코드를 이식하지 않고 현 Java/Spring 계층에 새로 구현했다.
- 원문을 잘라 40,000자 한도에 넣거나 모든 미해석 문장을 순차 API 요청으로 만드는 방법은 선택하지 않았다. 연결된 예외가 잘릴 수 있고 한 공고가 수십~수백 요청으로 늘기 때문이다.
- 원문 구조·명시 사실은 로컬에서 보존하고, 확인할 특정 쟁점의 완전한 근거 묶음만 전달한다. 작은 요청의 성공을 원문 전체 해석 완료나 공개 승인으로 계산하지 않는다.

### 구현·수정
- `LocalRuleInterpreter`/`LocalRuleBook`: 원문 URL·SHA-256·페이지·문자 범위·정확 인용, 주체·범위·수량·AND/OR·부정·예외·참조를 연결한다. 명시적 완화, 가구별 자동차, 미성년 예외, 학적 동등표현, 선착순/순위를 한정된 사실 주석으로 읽는다. 일반 미해석 부분은 삭제하지 않는다.
- 실제 원문과 반례를 검사하면서 재계약 할증률을 신청 소득 기준으로 읽는 오류, 부정문에서 긍정 사실을 생성하는 오류를 수정했다. 명시적 긍정 술어와 같은 문장 범위를 확인하며 모호한 명사만 있는 표현은 보류한다.
- `CompactReviewPlanner`/`CompactReviewPacket`: 실제 JSON 본문 최대6,000자, 해당 자료 버전에서 최초3묶음. 문맥이 같을 때만 질문을 합치고 출처·범위가 다르면 유지한다. 맥락 누락/참조 별표 미해결/큰 의존 범위는 자르지 않고 보류한다. 누락 근거는 다른 질문의 연결 관계에서도 차단된다. 일반 미해석 내용은 로컬 대장에 남고 API로 전부 보내지 않는다.
- `LocalAnalysisService`/`Repository`, V26: 현재 발췌 내용 해시와 해석/계획 정책으로 결과 캐시, 과거 HOLD 자료 처리. 기본PASS·실제LH·정상상태·안내HOLD·수동 편집 여부·최신 발췌를 전송 전 확인하고 응답 저장 때 공고 잠금 아래 재확인한다. 일시 쿼터 대기는 결과로 굳히지 않으며 중단/영구 실패를 무한 반복하지 않는다.
- `GeminiReviewClient.reviewPacket`/`ScopedReviewSchema`/`ScopedReviewValidator`: 알려진 쟁점·근거 ID만 허용한다. NO_CONFLICT/CONFIRMED_CONFLICT/UNRESOLVED 참고 결과를 별도 저장하며 안내 공개를 변경하지 않는다. **전체 문서 요청·옛 GeminiReviewSchema/GeminiCandidateValidator·구 후보 타입은 제거**했다. 출력2048토큰/512KiB/30초, 기존10회/일·60초 제한과 모델/정책/정확자료 캐시 유지. 시스템 지침·응답스키마의 고정 비용은 6,000자 본문 한도와 별도다.
- 관리자 GET `.../reviews/{noticeId}/extractions/{extractionId}/local-analysis`는 로컬 자료 조회/생성만 한다. 일반 사용자는 접근할 수 없고 다른 공고의 발췌 ID는404. 개인 답변/메모/증빙은 요청에 포함하지 않는다.

### 검증·측정
- 최종 `./backend/gradlew.bat -p backend test integrationTest bootJar --console=plain` 성공: **단위40클래스/233개, DB통합32클래스/162개, 실패·오류·건너뜀0**. 기존 경합/공개/발췌 검사를 포함한다. 이번 변경은 백엔드만이며 프론트 검사는 다시 수행하지 않았다.

### 기여·남은 범위
- AI 보조로 모델·정책·API·저장·회귀 검사를 구현했다. 팀원의 개인 성과나 사용자 정확도 지표로 해석하지 않는다.
- 현재 명시 사실은 검토를 돕는 주석이다. 복잡한 전체 자격 계산, 미지원 표/별표 해석, 모든 보류 공고의 무인 공개를 완료한 것은 아니다. 기존 수동 안내·개인 준비·가상 공고 차단을 유지했다.
- 새 조건군이나 참조 해석을 지원할 때 반대 의미·누락·주체 경합 검사와 정책 버전을 함께 갱신해야 한다. 실제 운영 메일/OAuth/푸시 연결은 별도다. 원격 커밋/push/배포 없음.

### 발표 메모
검증된 설명: 공식 원문을 로컬에서 근거와 함께 구조화하고, 필요한 일부 쟁점만 작은 API 요청으로 검토하도록 변경했다. 전체 의미 해석 성공률이나 종전 대비 전체 비용 절감률을 측정한 것으로 발표하지 않는다.

### 실제 API 형식 호환 수정
- 첫 실제 실행에서 중첩 배열에 건수 상한을 넣은 응답 JSON 스키마가 HTTP400/INVALID_ARGUMENT로 거절되었다. 실패4회도 기존 DB 사용량 제한에 기록했으며 성공으로 저장하거나 공개하지 않았다. 진단 중 API 자동 요청만 임시 비활성화하고 사이트와 로컬 분석은 유지했다.
- 원격 스키마에서 중첩 배열 건수 제약을 제외한 뒤 같은 엄격한 로컬 개수·근거·중복 검사를 유지했다. 실제 요청 본문5,784자에서 HTTP200, 쟁점3개, 입력3,478/출력444토큰, `GEMINI_SCOPED_REVIEW_RECEIVED`와 근거 검증 통과를 확인했다. 원문의 일부 쟁점을 검토한 결과이며 전체 안내 공개는 아니다.
- 요청/캐시 정책을 `scoped-review-v2`로 구분해 이전 요청 형식의 실패 캐시를 새 형식에 적용하지 않는다. 이 버전도 로컬 파생 자료의 정책 키에 포함한다. 변경 후 전체 단위/DB통합 검사를 다시 실행한다.
- 변경 후 전체 단위233개/DB통합162개와 bootJar 재검사 성공. 최종 backendPID63732, `.tools/runtime/backend-local-analysis-v2.jar`, API 자동 요청 활성화, 5173 health/databaseUP. 실제 scheduler에서5,970자 묶음 CANDIDATE(input3599/output1029), 같은 묶음을 서비스로 재조회했을 때 추가 API attempt0을 확인했다. 기존 개인기록·공개검수·샘플차단은 그대로다.
