# 새 공고의 상황별 질문 생성과 기존 유지 12건 재확인

- 기록일: 2026-11-22 (Asia/Seoul)
- 기록 상태: 검토 완료
- 작업 상태: 지원 형식의 자동 연결 구현·5173 반영 완료 / 모든 실공고 자동 해석은 미완료
- 유형: 개발 / 문제 해결
- 담당·검토: Codex root 구현·통합, personal_schedule_scope 생성기, personal_scope_model 원문 재생·시험, applicant_final_review 독립 읽기 검토. 사용자·팀원 코드 리뷰 미실시.
- 관련 이슈·PR·커밋: 새 커밋·push·운영 배포 없음

## 배경·문제

현재 제공 공고106건의 수동 원문 검토·94건 원고 보완과, 앞으로 수집되는 공고의 자동 질문 생성은 별개였다. 기존 자동 검수는 주로 기준 확인 YES/NO를 만들었다. 사용자는 첫 질문에서 구체 상황을 선택하고 해당 질문·서류로 이어지는 동작을 새 공고에도 적용하고, 이전에 유지한12건의 이유를 물었다.

## 고려한 선택지와 결정

화면에서 공고별 문구를 바꾸거나 이미 보완한94건을 새 공고에 복사하지 않는다. 기존 자동 검수·정정 반영 결과를 소유하는 `GuidanceReviewCompiler`에서 한 번 `ApplicantSituationCompiler`를 호출한다. 원문 해석과 개인 입력 계약 변환의 책임을 구분하고, 기존 질문 범위·서류 조건 필드를 사용한다. 별도 API·화면 상태·공고ID 분기·DB 컬럼은 추가하지 않는다.

확정 유형의 이름은 공유 어휘를 읽지만, 표시용 유형 겹침을 서류 제출 의무로 확장하지 않는다. 읽지 못한 첨부를 제거하거나 원문을 짧게 바꿔 전체 검수를 통과시키는 방안은 채택하지 않았다. 수동 검수 원고를 복구하는 `VerifiedReissueFiles.restore`와 항목별 공식자료만 게시하는 `PairedPreparationItems`의 기존 책임도 유지한다.

## 변경·해결 과정

- `OfficialGuidanceItem`과 `OfficialGuidanceRows`: 명시된 유형별 자격·기준 행 및 유형/자격 표를 읽는다. 숫자·예외는 전체 값에 보존한다. 혼합된 대상이나 다른 공급 축을 단일 유형으로 간주하지 않는다.
- `ApplicantSituationCompiler`: 완전히 확인된 유형 자격 또는 성년·미성년 예외 구간을 구체 상황 선택으로 만든다. 선택한 유형의 기준에 명시 범위를 부여하고 정확한 제출 대상의 서류는 직접 연결한다.
- 제거한 입력: 완전히 대응한 자격 YES/NO는 원문 링크를 가진 참고 설명으로 전환한다. 직접 서류 연결로 대체한 자가판단 질문과 완전히 중복된 성년 질문은 참조 여부를 확인해 제거한다. 미확정·충돌·혼합 기준과 다른 참조가 있는 질문은 남긴다.
- `GuidanceReviewCompiler`: 같은 자동 생성 경계와 정책 v15를 사용한다. 로컬 분석·후속 재검수 캐시는 기존 버전 입력으로 새 정책을 구분한다. 새 질문 생성 뒤 최종 질문/서류 개수 제한을 검사한다.
- 의미 변경이다. 새 수집 원고의 입력 계약을 개선하며 기존 개인 답변·메모·과거 기록을 소급 변경하지 않는다.

## 유지한12건 재확인

포항블루밸리·인천산곡·동탄·파주운정은 기존 유형별 질문 분기가 있고, 태백장성은65세 이상 단일 모집 대상이다. 인천·부천 일반매입, 청주 다자녀매입, 창원 일반매입, 거창신원 다자녀매입, 의령화정 다자녀매입, 오산세교2 7단지, 부산2차 일반매입은 구체적인 나이/공급유형과 독립 가족·복지 상황에 따른 서류 연결이 있어 당시 원고를 유지했다.

12건 모두 파주처럼 첫 답변만으로 질문 수가 달라지는 것은 아니다. 공통 질문은 남아야 하며 일부 확인형 문구를 더 다듬을 여지도 있다. 이번 읽기 감사에서 참조 오류0, 버전 변경0이었다. 과거94건 보완을 이번 자동 생성 구현의 실적으로 중복 계산하지 않는다.

## 검증·결과

- 프런트 실제 내 준비·일회성 입력 및 결과 소비자2파일17검사 통과.
- 최종 Java 관련18클래스94검사와 실제 PostgreSQL·Spring MVC 연결5검사 통과. 시험용 원고를 테스트 DB에 게시해 저장형과 일회성에 같은 질문 범위·서류 필요도가 도달하고, 익명 응답은 no-store이며 개인 기록을 쓰지 않는 것을 확인했다. 테스트 트랜잭션은 원복하며 운영/로컬 공개 DB에 시험 공고를 게시하지 않았다.
- 생산자 연결을 제거한 변이에서 첫 상황이 없다는 통합시험 실패를 확인하고 원복했다. 검수 중 유형 보호·정정값 전파·최종102문항 차단·기존 신고접수증 범위 보존까지 최종 재통과했다.
- 실제 IntelliJ·저장소 스타일을 사용한 변경8파일 서식 적용/검사 통과. 전체 Java 파일 검사로 주장하지 않는다.
- 현재106개 전체 공식 추출 원형의 읽기 재생은 기존 첨부 판독/문서 변형 대조에서 READY0·상황 생성0이었다. 단독 공식 PDF111개의 별도 형식 지원 검사에서는 READY1·상황 생성0이었다. 단독 PDF 검사는 나머지 첨부를 제외해 현재 공고를 승인한 결과가 아니다. 후속 검수 DB에는 PASS/PARTIAL 성공 자료가 없어 성공 원형 재생 증거도 없었다.

## 기여·한계와 리뷰 처분

자동 생성 경계를 구현한 것과 모든 새 공고가 파주 수준의 질문으로 자동 공개되는 것은 구분해야 한다. 완결된 유형별 행·성년 예외 구간 밖의 자유 형식, 좌우 단이 섞인 PDF와 미판독 첨부는 여전히 자동 해석 한계다. 현재 공고를 검수 없이 재게시하거나 개인 자료를 변경하지 않았다.

독립 리뷰의 최종 개수 제한 위치 지적은 최종 생성물 검사로 이동해 수정했다. 기존 신고접수증과 새 행방불명 답변의 연결 누락은 기존 ID로 직접 연결하고 중복 자가판단 질문을 제거해 수정했다. 다른 목적·공통 서류를 잘못 축소하지 않도록 원래 제출 범위를 확인할 수 없으면 변환을 보류한다. 독립 재검토의 미처분 결함은0이다. Iron Laws·GPT Pro 도구는 세션에 없어 실행하지 않았다. 실제 서비스의 기관 자격 판정을 자동으로 확정하지 않는다.

최종 `bootJar`를 로컬 실행 파일에 반영하고5173/8080을 재시작했다. 5173 API에서 서버·DB UP, 기존 파주 공고v7과 구체 첫 질문 정상 응답을 확인했다. 이는 현재 수집 공고의 새 자동 생성 성공 증거가 아니다. 새 브라우저 크기/실제 기기 확인과 운영 사이트 배포는 하지 않았다.

## 발표·포트폴리오 메모

원문 검수 결과에서 신청자 상황 입력을 생성하고, 기존 저장형·일회성 소비자를 재사용하는 구조로 정리했다. 합성 문법 시험, 실제 DB/API 연결, 실제 원문 지원률을 별도로 관찰해 자동화 범위를 과장하지 않는다. 사람 담당자의 개인 기여는 미확인이다.

## 후속 작업

- 좌우 단·표의 구조 보존 및 서로 다른 첨부 표현의 항목별 완전성 검증이 별도 보완 대상이다. 문구 복사나 안전 경계 완화로 전체 자동화했다고 표시하지 않는다.
- 일회성 읽기 감사 결과는 `.tools/qa/automatic-applicant-situations-20261122/verification.json`에 남겼다. formatter 범위 지정 도구는 검사가 끝나 제거한다. 원문 재생 도구는 이번 결과 재현용으로만 남기며 후속 파서 개선의 재현 자료로 이관되면 제거한다. 운영 실행 경로에서는 참조하지 않는다.
