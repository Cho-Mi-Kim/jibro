## 배경·문제

사용자는 이전 원문 대조에서 남은 20개 표시 항목 중 정정본과 공식 자료로 해결할 수 있는 것은 처리하고, 기관 확인이 꼭 필요한 항목만 남겨 달라고 요청했다. 원본·정정본에 중복 표시된 항목을 포함한 12개 공고가 대상이었다. 기존 질문·서류와 개인 기록, 다른 작업의 미커밋 변경은 보존해야 했다.

후속 공지·준용 최초 공고·당시 법령이 필요한 경우가 있었고, 기존 출처 검증은 원공고에 직접 연결된 첨부만 인정했다. 정확한 종료 날짜가 없더라도 모집 충족 시 종료라는 조건이 명확한 공고와, 공식 상태가 이미 종료인 공고를 날짜 충돌과 구분해야 했다.

## 고려한 선택지

- 현재 상세의 날짜나 다수 원문의 숫자를 선택: 단계가 다른 날짜와 실제 충돌을 구분하지 못하므로 채택하지 않았다.
- 기존 모든 보류 유지: 후속 공식 공지로 해소 가능한 사항도 남게 된다.
- 명시적 추가 공식 자료 검증과 항목별 수정: 원본·정정 사실 및 계획·실제 일정을 구분하고 이전 게시 증거를 보존할 수 있어 채택했다.

## 결정·이유

범용 자동 승인의 기준을 낮추지 않고 명시적 원문 검토 경로를 보완했다. `SupplementalSourceVerifier`가 추가 자료의 허용 경로, 제목·본문·첨부 링크 목록 지문 및 선택 첨부의 연결·바이트 SHA를 검증한다. 원공고의 최신 상세·전체 첨부·발췌·revision·게시 지문 검사는 그대로 유지한다. 역사 법령의 요청 값만 믿지 않고 실제 본문 제목·시행일도 확인한다.

모집 인원 충족 등 종료 조건이 명시된 경우는 `confirmedOpenEndedPeriod`로 설명하고 날짜를 만들지 않는다. 현재 공식 상태가 접수 종료임을 확인한 경우는 `Content.applicationClosure`로 상태·필터·정렬·준비 시작을 일치시키되 실제 마감 날짜와 분리한다. 자동 게시 후보가 이 값을 임의로 추가하면 거부한다.

## 변경·해결 과정

1. 전체 DB 백업과 대상 원고·공개 API, 대상 밖 공고 및 개인 준비 기록의 비교값을 로컬에 보관했다. 이전 검토 원고와 기록은 덮어쓰지 않았다.
2. 내포·화성·성남 후속 공지, 대전 최초 모집 원문, 당시 주택공급규칙을 대조했다. 적용한 사실·출처·남은 사안은 [검토 보고서](../../reviews/2026-11-09-review-resolution-source-review.md)에 정리했다.
3. 추가 자료 검증, 조건부 종료 정책, 공식 종료 상태 투영을 각 책임 모듈에 구현했다. 일반 수집의 허용 호스트나 자동 판정 범위를 넓히지 않았다.
4. 원고 수정으로 정정 연결의 revision이 달라지면 기존 링크는 숨기고, 동일 원본·정정본을 최신 양방향 공식 근거로 다시 검증해야 복원되도록 했다. `NoticeCorrectionService.reverify`와 V32 `verification_history`가 이전 근거를 보존한다.
5. 12건의 현재 상세와 기존 첨부 32개 SHA를 다시 확인하고 최신 발췌를 기록했다. 이후 검증 영수증과 이전 게시 지문을 요구하는 `amend`로 모두 반영했다. 청주·성남 정정 연결 2쌍을 재검증했고, 역방향 근거가 없는 내포 연결은 생성하지 않았다.
6. 교차 검토에서 해결된 화성·내포 질문에 남아 있던 예전 확인 필요 이유를 정리했다. 최종 질문의 미확정 플래그는 실제 계좌 충돌 항목에만 남아 있다.

## 검증·결과

- 최종 `gradlew test integrationTest bootJar`: 단위 499개 + 별도 테스트 DB 통합 280개, 총 779개 통과. 실패·오류·건너뜀 0.
- frontend 관련 5파일 37개 검사 통과. 이번 작업은 frontend 제품 코드를 변경하지 않았다.
- 20개 표시 항목 중 14개 해결, 6개 유지. 남은 항목은 내포 계좌 2개·후속 마감 2개, 대전 계약 종료 1개, 익산 실제 조기 종료 1개로 고유 사안 4개다.
- 이전 범위 17건은 12 PASS / 4 PARTIAL / 1 UNSUPPORTED. 16건의 질문 249개·서류 템플릿 312개 및 기존 ID를 보존했다. API의 질문·서류·이슈·일정을 최종 원고와 대조했다.
- 공식 종료 관찰 5건은 CLOSED 필터에 포함되고 OPEN/UNKNOWN에서 제외된다. 12개 대상 모두 현재 접수 종료·준비 신규 시작 불가이며 확정되지 않은 과거 마감 날짜를 만들지 않았다.
- 최신 서버로 재시작 후 정정 연결 2건 200, 미검증 내포 연결 없음 204, 실제 API 17건을 재확인했다. 실행 JAR SHA256은 `bb264d84c47ee9b1f48c32b1258f7b9d6ae7cdb7b9ab45df19f12c1c347cc3df`다.
- 브라우저 393×852 / 360×800에서 성남·청주·내포의 상태, 일정, 정정 연결 및 항목별 확인 필요 안내를 확인했다. 가로 넘침·콘솔 오류 0. 실제 휴대전화 검증은 수행하지 않았다.
- 대상 밖 18,906개 공고의 내용 SHA·공개 version·안내 검수 상태는 동일했다. 전체 행이 동일한 것은 아니다. 동시 기본정보 검수 worker가 410건을 BASIC/PASS 처리하여 revision 1→2 및 기본정보 검수 상태·시각을 갱신한 것을 동일 410건 감사로 확인했다. 이번 명시적 수정과 구분하며 이를 되돌리지 않았다. 개인 준비 기록은 전후 0건·동일 지문이다.
- 근거: [적용 패키지](../../reviews/2026-11-09-review-resolution-packages.json), [적용·API·보존·모바일 검증 기록](../../reviews/2026-11-09-review-resolution-runtime.json). 비교용 5174/5184를 교체하지 않았다.

## 기여·한계

AI 보조로 공식 자료 조사, 코드·검토 원고 수정, 독립 교차 검토 및 로컬 실행 검증을 수행했다. 사람이나 기관이 승인한 것처럼 표시하지 않는다. 남은 계좌·실제 종료일 차이는 문의 또는 새 공식 정정 자료가 필요하며 기관에 메시지를 보내지는 않았다. 해결된 14개는 검토 대상 표시 항목 수이며 모든 수집 공고 자동 판정 성능을 뜻하지 않는다.

## 발표·포트폴리오 메모

날짜가 없다는 이유로 전체 준비 안내를 막거나 임의 날짜를 선택하지 않고, 종료 조건·현재 접수 상태·확정 날짜를 구분했다. 정정·후속 자료를 별도 검증하면서 원문 및 과거 게시 증거를 보존했다. 개인 기여 귀속과 사용자 효과는 담당자 확인 전 단정하지 않는다.

## 후속 작업

- 남은 4가지 고유 사안은 해당 회차의 LH 납부 안내·접수 이력·계약 종료 기록 등으로만 재검토한다.
- 내포 자동 정정 연결은 공식 역방향 ID 근거가 확인되기 전까지 생성하지 않는다.
- 이번 변경은 로컬에만 적용했다. 팀 검토·원격 게시·운영 배포는 별도 요청 범위다.
