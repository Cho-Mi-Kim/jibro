# 공개 PDF 자원 경계와 비밀번호 변경 재인증 보완

- 기록일: 2026-11-24 (Asia/Seoul)
- 기록 상태: 검증 완료
- 작업 상태: 해결 (코드·표준 검증 완료, 운영 미배포)
- 유형: 문제 해결·보안
- 담당·검토: Codex AI 보조 구현·별도 자체 검토. 인간 담당/검토자 미확인
- 관련 검토: Codex Security cbc6873a-1aeb-468a-ad7f-048647d12443, 커밋/PR 미등록

## 배경·문제

사용자가 보안 검토에서 선택한 두 항목의 수정을 요청했다. 공개 PDF 페이지 요청이 주 JVM에서 직접 PDFBox를 실행했고, 비밀번호 변경은 로그인과 달리 현재 비밀번호를 틀린 횟수를 기록하지 않았다. 원래 검토는 읽기 전용이었으며 이번 요청이 코드 보완을 승인했다. 기존 작업 트리932개 변경을 보존했다.

## 고려한 선택지

- 프록시의 IP별 요청 제한만으로는 PDF 처리의 전체 메모리·실행 시간을 제한하지 못한다.
- 컨트롤러 안에서만 용량을 잡으면 반환한 대용량 응답이 전송되는 동안 용량이 먼저 반환될 수 있다. 따라서 HTTP 응답 쓰기까지 제한한다.
- 새 PDF 실행 관리자를 만들지 않고 기존 문서 파서의 프로세스 감독을 공유한다.
- 비밀번호 변경에 새 실패 테이블을 만들지 않고 기존 DB 로그인 예산을 사용해 경로·IP를 바꾸는 추측을 제한한다.

## 결정·구현

`OfficialDocumentCapacityFilter`가 공개 파일 GET/HEAD의 다운로드 전부터 응답 쓰기까지 전역2개를 허용한다. 초과는429, 저장된 relocate와 health는 제외한다. `BoundedDocumentParser`의 공통 실행기가 `DocumentParserWorker`의 pdf-page 모드도 감독한다. 힙128MiB·메타64MiB·직접 메모리16MiB·8초·출력20MiB 제한과 실제 종료/정리를 유지한다. 직접 렌더 경로는 제거했다. 정상 PNG·원문 지문409·없는 페이지404·기존 PDF 원본을 보존한다.

`AccountService.password`는 기존 `LoginAttemptLimiter`로 예산을 별도 예약/완료한다. 새 비밀번호 형식을 먼저 검사하고 기존 비밀번호 대조·새 자격 저장은 한 트랜잭션이다. 실패 기록은 롤백돼 사라지지 않는다. 로그인/변경은 같은 계정 실패5회/15분·IP30회/15분 정책이며 요청 IP는 기존 프록시 신뢰 경계를 사용한다. 정상 변경의 이전 토큰 폐기는 유지한다. 마이그레이션은 없다.

## 검증·결과

운영 키를 제거한 별도 임시 소스 복사본과 로컬 jibro_test를 사용했다. 수정 전에는5회 실패 후 정상 비밀번호의 변경 요청이200으로 성공해 기대429와 다른 것을 재현했다. 최초 DB 미기동 실패와 이후 실제 재현을 구분한다.

수정 후 관련 단위24개·DB통합7개=31개 통과. 실제 worker jar의 서로 다른 두 페이지·기존 공식 PDF fixture·없는 페이지·자식 프로세스 시간/힙/출력 초과 후 종료·다음 정상 처리, HTTP 과부하의 다운로드 전 거부·health 응답, 비밀번호 변경 예산 공유·동시 예약·정상 자격 변경을 검사했다.

첫 전체 실행은 단위1007개 중1006통과/라이브 원문 선택 검사1개 제외, 통합445개 중3실패였다. 보안 수정6개 기존 파일을 이전 내용으로 되돌리고 새6개 파일을 제외한 복사본에서도 같은3실패를 재현했다. 기존 테스트의 계약 불일치라 프로덕션 규칙은 바꾸지 않았다.

- 첨부 재연결 fixture: 공식 첨부를 읽는 테스트의 대표 근거가 주소 없는 예시 자료였다. 실제 첨부를 대표 근거로 사용하고 HTML을 조회하지 않는지 확인한다.
- 조건 경고: 참고 안내 확인까지 미확인 조건으로 세던 기대값을 현재의 신청자 상황 질문 규칙으로 맞추고 참고 안내가 경고에 없음을 확인한다.
- 일정: 날짜와 추가 설명을 함께 허용하는 현재 계약을 검증하고 직렬화 후 둘 다 보존되는지 확인한다. 날짜 없는 잘못된 접수 마감의 거부는 유지한다.

해당3클래스32검사 통과. 변경 Java11개 및 QA3개는 공유 IntelliJ 포맷을 사용한다. 전체 포맷은 파일별 실행 비용으로 중단하고 변경 경로만 처리했다. 최종 절대 경로14개 검사에서 IS CLEAN14/IS DIRTY0 및 BUILD SUCCESSFUL을 확인했다.

최종 `test integrationTest bootJar` 전체 재검사는 성공했다. 단위1007개 중1006통과/실제 공식 사이트를 호출하는 선택 검사1개 제외, DB통합445개 전부 통과로 총1451개 통과/실패·오류0개다. 선택15개 소스는 실제 작업 폴더와 검증 복사본의 바이트 일치를 확인했다. backend-0.0.1-SNAPSHOT.jar의 SHA-256은 `7bd0f7a847d7f9e547e5f2e98a49b5b91f749e008dab13607613a2f875a5cb29`다.

봉인된 원래 검토와 별도로 Codex Security 보관소의 `artifacts/fixes/20261124-pdf-password/fix-report.md`와 `test-summary.json`에 수정 근거·검증·호환성·한계를 저장했다. 원격 remediation 상태를 임의로 변경하지 않았다.

## 기여·한계

수정·검증은 AI 보조 작업이며 사람의 보안 승인이나 실제 운영 부하 시험으로 표현하지 않는다. 원래 봉인 보고서는 보존한다. 운영 배포·외부 계정 설정·Git push는 수행하지 않는다. 이전 Nginx/인증서 배포 stage 실패는 별도 미완료 작업이다.

## 발표·포트폴리오 메모

검사 통과와 배포를 구분하고, 비밀번호 실패의 별도 커밋과 다운로드 이전의 자원 확보를 실제 회귀로 검증했다. 확인하지 않은 장애 감소율이나 개인 성과 수치는 기록하지 않는다.

## 후속 작업

코드와 표준 검증은 완료했다. 실제 운영 반영은 별도 요청에서 검증한 변경으로 수행하고 정상 PDF·비밀번호 변경을 재확인한다. 제한은 인스턴스별이며 JVM 힙128MiB는 운영체제 전체 프로세스 메모리의 단일 상한을 뜻하지 않는다.
