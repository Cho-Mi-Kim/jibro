## 배경·문제

사용자는 내 준비와 일회성 질문이 공고 조건을 읽는 화면과 다른 목적이며, 신청자 상황을 답하면 서류와 신청 준비를 개인화해야 한다고 명확히 했다. 기존 입력 화면은 공고 설명 제목을 공유하고 단순 안내 확인도 필수 질문처럼 보여 주었다.

## 고려한 선택지

공고 설명 자체를 입력용으로 변경하면 상세·비교·이전 기록의 원문 안내도 함께 달라진다. 기존 질문의 YES/ACK를 신청 방법으로 재해석하면 저장 답변과 서류 연결 의미를 바꾼다. 따라서 입력 표시만 분리하고 기존 답변 계약에 명시된 사실을 활용하기로 했다.

## 결정·이유

`applicantQuestion`이 상황 질문의 제목·도움말을, `QuestionPrompt`가 입력과 공식 참고 설명을 맡는다. `ConditionSummary`는 공고 설명을 계속 담당한다. `PersonalizedPreparationGuide`는 확인된 구체적 신청 유형·방법·대리인과 같은 버전의 서류 연결을 표시한다. 설명 확인을 온라인/현장 신청으로 추측하지 않는다.

## 변경·해결 과정

- `QuestionCriteria`를 `QuestionPrompt`로 교체하고 기존 파일·호출을 제거했다. 두 입력 화면과 단계 제목을 새 모델에 연결했다. 선택지 값·숫자·예외·출처는 유지한다.
- 순수 안내 확인은 공고 전체 참고 안내로 옮긴다. 서류 연결·답변 의존·공식 재확인이 있는 항목은 질문으로 남긴다. `QuestionAnswers`/프런트 questions와 공동 계약 자료로 Java·시연의 역할 구분을 검증한다.
- 질문 수·추가 확인·다음 할 일·진행률도 같은 역할 구분을 사용한다. 원래 질문이 있으나 모두 순수 안내라면 질문 할 일이 없는 것으로 계산하며, 원래 질문 자체가 없는 공고의 정책은 유지한다. 기존 답변을 생성하거나 삭제하지 않는다.
- 준비 목록은 경량 SQL 투영과 `PreparationRules.progress`로 현재 진행률을 계산해 상세와 일치시킨다. 질문 본문·근거·메모는 목록에 싣지 않고 N+1 조회를 추가하지 않는다. 이전 기록은 저장 당시 상태를 유지한다.
- 결과의 개인 맞춤 안내를 먼저 표시하고 `공고 전체 준비 안내 n개`는 기본 접힘으로 표시한다. 필요한 서류의 기존 제출 대상·발급 방법·공식 링크는 유지한다.
- 새로운 중복 판정 경로 대신 기존 서버 서류 필요 여부와 답변 의존 계산을 재사용한다. 임시 기능 플래그·호환 경로는 없다. 입력/진행률 의미 변경이며 단순 동작 보존 리팩토링으로 주장하지 않는다.

## 기여·한계

사용자가 질문의 제품 목적을 결정했고 Codex와 하위 에이전트가 구현·검사를 보조했다. Iron Laws 전용 도구와 GPT Pro 별도 리뷰는 실행하지 않았으며 프로젝트 정적 검사와 독립 코드 리뷰를 수행했다. 새 신청 사실을 공고에 만들거나 모든 공고의 공식 문서를 재검수한 작업은 아니다. 현재 공고·새 공고 모두 동일 표시/역할 경로를 사용하되 구조화된 답변 계약이 없는 항목은 임의로 신청 방법을 단정하지 않는다. 운영 jibro.live 배포·Git 게시·사용자 계정으로 저장하는 실사용 검증은 이번 범위에 없다.

## 발표·포트폴리오 메모

공고 설명과 사용자 입력의 책임을 분리하고, 기존 답변·서류 연결을 보존하면서 개인 맞춤 안내를 앞에 배치했다. 포항 실제 흐름에서 질문 15개가 상황 질문 7개/참고 안내 8개로 구분된 것을 확인했으며 일반적인 질문 감소율이나 사용자 만족도 수치로 확대하지 않는다.

## 후속 작업

새 입력 유형을 추가할 때 공식 선택지·숫자·예외·서류 연결 의미를 함께 정의한다. 운영 반영은 별도 요청 시 진행한다.
