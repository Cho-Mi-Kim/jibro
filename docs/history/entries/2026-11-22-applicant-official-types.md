## 문제와 결정

YES/NO로 공급계층 기준을 확인하거나 유형별 서류의 제목이 대상 유형을 드러내지 않으면, 기존 보수적 유형 추론만으로 해당 없는 질문을 제외할 수 없었다. 기본 목록 122건의 질문을 조사하고 공식 모집계층과 주택형·공급순위·가점 축을 구분했다. 단일 모집계층에는 인위적 유형 선택기를 만들지 않았다.

완주삼례·인천산곡·화성 동탄·평창장평 일반형의 혼합 확인 질문을 실제 유형 선택과 고정 의미 질문으로 교체했다. 신혼·신생아 전세임대Ⅰ·Ⅱ, 익산제3산단, 과천, 전주1산단, 담양의 기존 선택지는 보존하면서 공식 제출대상에 따른 정확 범위를 연결했다. 원고는 `data/notices/applicant-types-20261122/batch-a.json`, `batch-b.json`, `batch-c.json`이다.

## 소유 책임과 더한 것·뺀 것

- `HousingModels.Question`과 프런트 `Question`에 선택적 `applicability { questionId, answerValues }`를 둔다. 검수된 배타적 질문 범위를 표현하는 정식 데이터이며 저장 스냅샷·API·목록 projection에 전달한다. 외부 입력 검증은 유효한 선택형 부모·값·한 단계 연결을 확인한다.
- 기존 `preparationApplicability`가 명시 범위를 먼저 판단하며 미기재 자료의 제목 추론은 보수적으로 유지한다. 부모 미선택·모름·무효·공식 검수·답변 모순을 임의로 숨기지 않는다. 내 준비·일회성 입력과 조건·서류·진행률은 같은 정책을 소비한다.
- 실제 범위가 달라지는 집·차·소득·청약 질문을 새 ID로 분리하고 옛 혼합 ID를 제거한다. YES를 다른 의미로 재사용하지 않는다. 유형 선택으로 정해지는 서류의 중복 제출대상 질문은 제거하고 기존 서류 ID를 부모 답변에 연결한다. 기존 기록·메모는 기존 버전 갱신 계약으로 보존한다.
- 명시된 고정 질문은 `applicantQuestion`의 일반적인 제목 변환을 거치지 않아 본인/현재 가족/결혼 후 가족 범위가 유지된다. 옛 검수 요약이 바뀐 질문 계약을 덮지 않도록 기존 원고 guard에 applicability를 포함했다.
- UI 전용 유형 답변, 병렬 sidecar, 별도 서류 분기 화면, 새로운 DB 컬럼·주기 작업은 추가하지 않았다. 기존 SourceReviewPublicationService.refineConditions 경계를 사용하며 로컬 보조 도구의 작업 경로만 매개화했다.
