# 공고 예약 수집과 재시도

적용 기준: 사용자 2026-11-06 후속 요청 7·8번. 과거 결정표의 6시간 주기는 이 요청으로 변경한다.

2026-11-07 출시 보완 요청 1·17·18번: 최근 3개월·단일 분류 수집을 명시적 게시일 범위·복수 분류의 영속 커서로 교체한다. 과거 실제 수집 성공은 최신 코드나 운영 키의 검증 완료를 뜻하지 않는다.

## 수집 범위와 요청 계약

- `app.collection.category-codes` (`LH_COLLECTION_CATEGORY_CODES`) 기본값은 `06,13`이다. LH 임대주택과 매입·전세를 포함한 주거복지 목록을 각각 읽는다. 현재 지원한 두 분류만 허용하고 중복·빈 값·다른 코드는 시작 시 거부한다.
- `app.collection.history-start-date` (`LH_COLLECTION_HISTORY_START_DATE`) 기본값은 `2000-01-01`이다. 이는 장기 수시모집을 최근 3개월 밖으로 밀어내지 않기 위한 보수적 조회 설정이며, 공식 API가 그 날짜까지 모든 과거 공고를 제공한다는 보장은 아니다. 기관의 실제 자료 보유 범위·호출량·처리 시간을 운영 키로 확인해야 한다.
- 각 실행은 시작 때 분류 목록·게시 시작일·한국 기준 조회 종료일을 저장한다. 요청은 `UPP_AIS_TP_CD`, `PAN_ST_DT`, `PAN_ED_DT`, `PG_SZ=100`, `PAGE`로 구성한다. 마감 상태로 제한하지 않으므로 오래된 공고가 접수 종료·정정되어도 같은 기간의 다음 수집에서 다시 비교한다. API 키는 서버에서 한 번 인코딩하며 이력에 남기지 않는다.
- 공식 명세의 출처는 [LH 공고 조회 API](https://www.data.go.kr/data/15058530/openapi.do)다. `PAN_ST_DT`/`PAN_ED_DT`는 기존 실제 응답 `dsSch` 및 연동 기록과 대조한 게시일 검색 계약을 유지한다. 명세의 `PAN_NT_ST_DT`/`CLSG_DT`를 검수 없이 신청 기간으로 전용하지 않는다.
- 수집 결과는 기존처럼 HOLD/HOLD이며 자동 게시하지 않는다. 같은 출처의 반복 수집은 같은 공고를 갱신하고, 내용 변화가 없으면 새 버전을 만들지 않는다. 공식 목록에서 누락되거나 네트워크가 실패한 공고를 삭제·취소로 바꾸지 않는다.

## 실행 시간과 환경

- `Asia/Seoul` 기준 매일 **00:00, 06:00, 09:00~18:00의 매 정각**에 수집한다. 총 12회다. 호스트 운영체제 시간대와 분리한다.
- Spring 애플리케이션 내부 스케줄러로 실행한다. 별도 Codex 예약이나 Windows 작업은 만들지 않는다. 서버가 꺼져 있을 때는 실행되지 않는다.
- `app.collection.schedule-enabled` 기본값은 true다. LH_SERVICE_KEY가 없으면 자동 실행을 만들지 않고 관리자 화면에서 수집 키가 필요하다고 표시한다. 운영자가 false로 설정해도 수동 수집과 이미 요청된 작업의 재시도·복구는 사용할 수 있다.
- 기동 15초 뒤부터 30초마다 실행 대기와 재시도를 확인한다. 정각 트리거도 같은 큐를 사용한다. 재시작 시 과거 누락 시간 전체를 한꺼번에 실행하지 않고 **가장 최근 예약 한 건**만 고유 슬롯으로 등록한다.
- 관리자 `GET /api/v1/admin/collections/schedule`은 활성/키 설정 상태, 한국시간 일정, 다음 예약 등록 시각(`nextRunAt`), 공식 서버 재요청 가능 시각(`providerResumeAt`), 실행·재시도 대기 건수를 반환한다. 공급자 대기 중에도 다음 정각 슬롯은 등록할 수 있지만 실제 요청은 `providerResumeAt` 이후에만 실행한다. 대기 제한이 없으면 이 필드는 null이다. 실제 비밀값은 반환하지 않는다.

## 실행 기록·중복·복구

V12는 기존 `collection_run`에 수동/예약 구분, 예약 슬롯, 조회 기준일, 시도 횟수, 마지막 완료 페이지 다음 위치, 처리·추가 확인 건수, 다음 시도 시각, 실행 소유 토큰과 만료를 추가한다. 예약 실행자는 null(system)이며 가상 관리자 계정을 만들지 않는다. 등록 첨부 점검도 시스템 실행자를 허용한다.

- 같은 한국시간 예약 슬롯은 DB 고유 제약으로 한 번만 등록한다.
- 짧은 PostgreSQL 트랜잭션 잠금과 단일 RUNNING 고유 제약으로 여러 서버·관리자 요청에서도 한 번에 한 수집만 실행한다.
- 네트워크 요청 중 DB 잠금을 유지하지 않는다. 실행 소유권은 2분 임대이고 각 페이지·공고 처리 전후 갱신한다. 공고 저장은 소유권 확인과 같은 짧은 트랜잭션에서 수행한다.
- 실패한 페이지는 완료 처리하지 않는다. 같은 페이지를 다시 읽어도 기존 출처 식별자·해시 비교로 중복 공고나 같은 버전을 추가하지 않는다.
- 중단되어 임대가 만료된 실행은 마지막 완료 페이지 다음부터 복구한다. 늦게 돌아온 이전 실행은 새 실행의 상태나 공고 저장을 덮어쓰지 못한다. 반복 중단도 재시도 한도에 포함한다.
- 수동 요청 중 다른 작업이 진행 중이면 QUEUED로 기록하고 이후 처리한다. 한 작업 단위는 전체 분류를 합해 기본 5페이지(설정 범위 1~20)다. 남은 분류·페이지가 있으면 같은 실행을 QUEUED로 돌려 다음 단위에서 자동으로 이어간다. 정상 이어가기는 오류 재시도 횟수를 소모하지 않는다. 수동 `startPage`는 첫 분류에만 적용하며 다음 분류는 1페이지부터 시작한다.
- 수집을 시작한 한국 날짜를 조회 기준일로 고정한다. 자정을 지나 재시도·이어가기를 하더라도 조회 기간은 바뀌지 않는다. 공식 API가 같은 기간의 결과 순서를 바꾸는 경우까지 스냅샷으로 고정할 수는 없으므로 다음 정기 수집에서 처음부터 다시 확인한다.
- 분류마다 최대 500페이지이며 공식 전체 건수와 페이지 크기를 대조한다. 총건수가 없는 응답은 100건 페이지 뒤에만 이어읽고 짧은 페이지에서 끝낸다. 동일 페이지 안의 중복 출처나 이전 완료 페이지와 동일한 출처 묶음은 오류로 중단한다. 완료 페이지 식별값은 DB에 남겨 다음 청크·재시작에서도 반복을 탐지한다. 추가 페이지가 있는데 안전 한도에 도달하면 해당 범위를 미완료로 남기고 다른 분류를 계속 확인하며 최종 PARTIAL로 기록한다. 앞 작업 단위의 첨부·초안 처리 실패도 누적하여 마지막 결과를 성공으로 덮지 않는다.
- 기존 수집이 진행 중이어도 정각 예약 슬롯은 DB에 등록한다. 여러 작업은 같은 단일 실행 소유권을 순서대로 사용한다.

## 재시도 정책

| 분류 | 동작 |
| --- | --- |
| 일시적 연결/시간 초과, HTTP 429, 5xx | 최초 시도 외 최대 3회. 1분→5분→15분 뒤 재시도 |
| 유효한 Retry-After | 기본 간격보다 길면 그대로 적용. 초 또는 HTTP 날짜 지원. 48시간 등 긴 지시도 임의로 줄이지 않음 |
| 인증·권한·잘못된 요청, 응답 형식/공식 주소 검증 오류 | 자동 재시도하지 않고 FAILED |
| TLS 검증 실패·명시적 스레드 중단 | 재시도로 우회하지 않음 |
| 초안 추출·첨부 점검의 부분 실패 | 파일/초안의 별도 이력과 PARTIAL로 구분. 성공한 목록 수집을 자동 공개로 취급하지 않음 |

기다리는 동안 HTTP 요청 스레드를 몇 분씩 붙잡지 않는다. RETRY_WAIT와 다음 시각을 DB에 저장하고 작업 스레드는 반환한다. 실패 메시지에는 API 키·원문 예외·개인 데이터를 노출하지 않는다.

현재 목록 수집 공급자는 LH 하나다. V17의 `collection_provider_hold`는 실행 상태와 별개로 공식 API의 Retry-After 제한 시각과 원인 실행을 기록한다. 마지막 재시도가 FAILED로 끝나거나 실행 기록이 정리되어도 공급자 제한은 남는다. 더 짧은 후속 지시로 기존 대기 시각을 당기지 않는다.

공급자 제한과 RETRY_WAIT 작업 중 가장 늦은 대기 시각이 지나기 전에는 새 수동·예약 수집도 실행 소유권을 얻지 못한다. 새 실행 등록으로 대기를 우회하지 않으며, DB에 보존되어 서버 재시작 뒤에도 적용된다. 기한이 끝나면 자동으로 실행 가능해지며, 실패한 실행 자체를 다시 성공 상태로 바꾸지는 않는다.

`CollectionItemProcessor`는 목록 정규화 이후의 내부 초안 생성 경계다. 미검수 결과를 공개 질문·서류 규칙으로 확정하지 않는다. 첨부 본문 변경 감지는 [첨부 감지 계약](attachment-change-detection.md)을 유지한다.

## 검증

일정/재시도 단위 테스트, 실제 PostgreSQL의 동시 고유 슬롯 등록·실행 소유권 획득·재시도 시각·페이지 복구·조회 기준일 고정·자동 페이지 이어가기·횟수 제한 테스트와 관리자 표시 테스트를 제공한다. 실제 정각 장시간 대기, 기관의 429 실발생, 서버 두 대 운영 관찰은 자동 테스트와 별개의 운영 검증이다.

V20은 기존 실행의 단일 `06` 분류·조회일에서 3개월 전 시작일을 보존한다. 신규 실행에만 현재 설정을 스냅샷으로 저장하므로 배포 중 이미 요청한 작업의 의미를 바꾸지 않는다. 분류 전환 실패·두 분류의 동일 페이지 번호·과거 게시일·총건수 누락·반복 페이지·범위 한도를 새 회귀 사례로 추가했다. 외부 키가 없는 HTTP 대체 응답 검증과 실제 LH 운영 성공은 별도다.
