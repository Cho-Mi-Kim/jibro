# 로그인 시도 제한과 현재 세션 로그아웃

2026-11-06 사용자 요청 후순위 11·21번의 구현 계약이다. 기존 계정 연결·비밀번호 변경·탈퇴의 전체 인증 폐기 규칙은 유지한다.

## 로그인 요청 제한

- 이메일을 앞뒤 공백 제거·소문자로 정규화한다. 같은 계정의 실패 또는 처리 중 시도는 15분에 5회, 같은 실제 요청 IP는 15분에 30회까지 허용한다. 성공한 시도는 실패 예산을 소비하지 않는다. 실패 기록은 성공 여부와 무관하게 15분 후 제외된다.
- 없는 이메일, 비밀번호가 없는 소셜 계정, 잘못된 비밀번호, 비활성 계정은 동일한 401 메시지를 반환하고 비밀번호 해시 비교를 수행한다. 제한을 넘으면 계정 존재 여부와 무관하게 동일한 429 `LOGIN_RATE_LIMIT`을 반환한다.
- 이메일과 IP는 서버 비밀키 기반 HMAC 키로만 기록하며 비밀번호는 기록하지 않는다. 요청 접수와 결과 기록은 인증 트랜잭션과 별도로 커밋한다. 인증 실패로 기록이 사라지지 않는다.
- PostgreSQL의 순서가 고정된 두 advisory lock으로 계정·IP 예산을 예약한다. 여러 서버와 동시 요청도 같은 한도를 사용한다. 중단된 처리 중 요청은 최대 15분간 예산에 남는다. 다음 로그인 요청에서 하루 지난 기록을 최대 500개씩 정리한다.
- IP는 `HttpServletRequest.getRemoteAddr()`를 사용하며 앱이 `X-Forwarded-For`, `X-Real-IP`를 직접 신뢰하지 않는다. 직접 노출 환경은 전달 헤더 처리를 끈 기본 설정을 유지한다. 역방향 프록시 운영은 실제 신뢰 프록시만 허용하는 서버 설정·직접 백엔드 접근 차단을 함께 구성해야 한다. 임의 전달 헤더로 제한을 우회할 수 없다.

## 세션과 로그아웃

- 비밀번호·소셜·체험 진입 모두 서버 `auth_session`을 만든다. Access JWT의 `sid`는 세션 ID이며 매 로그인마다 다르다. Refresh 회전은 같은 `sid`를 유지한다.
- Access는 15분, 세션과 refresh는 마지막 발급부터 7일이다. 매 인증 요청에서 소유자, 계정 활성 상태, 체험 만료, `security_version`, 세션 만료·폐기 여부를 확인한다.
- CSRF가 확인된 로그아웃 요청은 기존 HttpOnly refresh 쿠키가 가리키는 현재 세션과 그 세션의 모든 refresh를 폐기한다. 이미 발급된 access도 즉시 거절된다. 다른 기기의 세션은 유지된다. 유효한 Bearer access만 있는 요청도 자신의 세션을 폐기할 수 있다.
- 일반 회원은 회전 직전 쿠키로도 같은 세션을 폐기할 수 있어 refresh/로그아웃 경쟁에서 새 토큰이 살아남지 않는다. 이전에 회전한 쿠키로 체험 계정 자체를 제거하지 않는 기존 체험 정책은 유지한다.
- 비밀번호 변경·로그인 수단 해제·탈퇴는 기존 `security_version` 갱신 및 refresh 제거로 모든 기기를 무효화한다.
- V13 이전 access에는 `sid`가 없으므로 허용하지 않는다. 기존 refresh는 마이그레이션에서 폐기된다. 이 버전 최초 적용 시 기존 사용자는 다시 로그인한다.
- 만료·폐기·기존 버전 refresh가 401로 거절되면 같은 경로의 HttpOnly 쿠키를 즉시 만료시킨다. 다음 로그인·새 체험에 무효 쿠키가 반복 전송되는 상태를 해소하며, 해당 토큰을 다시 허용하지는 않는다. 일시적 서버 오류에는 쿠키를 지우지 않는다.

## 검증 범위

`LoginSecurityIntegrationTest`는 PostgreSQL 커밋 경계에서 두 기기 분리, 즉시 access/refresh 폐기, refresh와 로그아웃 동시 경쟁, CSRF, 다른 소유자의 sid, 기존 sid 없는 토큰, 존재 여부 비노출, 제한 만료, 성공 예산 제외, 전달 헤더 우회, 10개 동시 요청의 5회 제한을 확인한다. 실제 운영 프록시·여러 인스턴스 배포 검증은 별도 운영 환경에서 수행한다.
