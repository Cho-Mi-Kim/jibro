# 공식 공고 자동 검수

## 변경 승인과 공개 경계

2026-11-07 사용자가 자동 판단 가능한 내용은 자동 검수·공개하고, 문서 충돌 또는 근거 확인 불가만 보류하도록 승인했다. 이 결정은 기존 모든 공고/발췌의 수동 검수 전용 정책을 해당 범위에서 개정한다. 사용자 자격에 대한 LH 최종 심사를 대체하지 않는다.

- 기본 정보: 실제 LH 수집 식별자·원문 호스트·해시·공고일·지역·유형을 검사해 PASS. 신청 기간이 없는 것은 추정하지 않는다.
- 준비 안내: 파싱된 전체 문맥과 공식 출처가 있는 지원 규칙만 질문·서류·일정으로 변환한다. 원문 누락·스캔 페이지·잘림·지원하지 않는 예외는 HOLD. 2026-11-08 개정에 따라 영향 범위가 정확히 식별되는 충돌은 해당 항목만 확인 필요로 남기고 나머지 안내를 PARTIAL로 제공한다.
- 기본 PASS와 안내 PASS는 별개다. 기본 공개만 된 공고에는 불확실한 안내를 게시하지 않는다. 변경된 공고의 이전 자동 생성 날짜·일정은 재검수 중 숨긴다.
- 관리자 원고 편집/검수와 기존 수동 안내는 자동 대체 대상에서 제외한다. 기존 사용자 준비 snapshot도 변경하지 않는다.
- notice 잠금, revision, 최신 완료 발췌 내용 해시를 모두 대조한 뒤 적용한다. 같은 결과의 반복 실행은 버전을 올리지 않는다. 같은 발췌 ID의 파일 재시도도 내용이 달라지면 다시 검사한다.
- 자동 판단은 `automatic_notice_review`에 정책 버전·입력 revision·출처/발췌 해시·사유와 함께 기록한다. PARTIAL은 미해결 항목의 ID·영역·근거·종속 서류 범위도 `review_issues`에 보존한다. 가짜 관리자 계정이나 수동 검수 기록을 만들지 않는다.

## 현재 규칙 해석 범위

`AutomaticGuidanceCompiler`와 `GuidanceRuleGrammar`는 명시된 무주택/미혼/연령, 본인 소득·자산·차량 금액 상한, 지원하는 공통/대학생/취업준비생 서류와 날짜 문장을 처리한다. 숫자 조건은 근거를 제시하는 자기확인 질문이며 입력 min/max를 자격 기준으로 오용하지 않는다. 임의의 가구원/순위/예외/백분율 표를 모두 이해하는 범용 자격 엔진은 아니다.

`AutomaticScheduleCompiler`는 명시적 연도·날짜·라벨만 사용한다. 선택적 결과발표/서류 마감이 없으면 만들지 않는다. 서류 접수 기간을 신청 접수 기간으로 바꾸지 않는다.

### 2026-11-07 보류 공고 재검사 보완 (`official-rules-v2`)

- `SourceCoveragePolicy`는 원문/첨부 URL의 완전성부터 검사한다. 단순 공고 상태·유형·공고일만 있는 HTML과 명백한 평면도·배치도·위치도만 별도로 취급한다. 파일명에 자격·소득·예외·제출 등 기준 단서가 있거나 용도가 불명확하면 필수 검수 자료로 남긴다. 매뉴얼/양식이라는 이름만으로 제외하지 않는다.
- 같은 이름의 PDF/HWPX는 공백·독립 페이지 번호를 제외한 전문이 같을 때만 중복으로 묶는다. 숫자 집합만 같거나 표 순서가 달라 동일성을 입증하지 못하면 `DOCUMENT_VARIANT_CONTEXT_UNVERIFIED`로 보류한다. 이는 실제 내용 충돌 확정과 다르다. 이 단계의 실패는 규칙 컴파일러나 Gemini 성공으로 우회할 수 없다.
- `EvidenceGuidanceCompiler`는 짧고 완결된 완화·세대별 차량 범위·순위 구간을 근거 연결 자기확인 질문으로 만들며, 조건·예외·서류 적용 대상의 원문 구간을 보존한다. 일반적인 소득/재산/자격 자동 계산 엔진은 아니다. 여러 governing 문서의 문맥이 다른 경우, 누락 근거, 이어지는 순위표, 개인 주거 준비 범위 밖의 기관 공고는 자동 승인하지 않는다.
- 페이지별 읽기 확인만 수십 개 생기는 결과는 유효한 안내 완성으로 보지 않는다. 20문항을 넘는 후보는 보류한다. 실제 장문 공고의 전체 자동해석은 아직 검증되지 않았다.
- `OfficialDetailParser`는 LH 메타데이터 상자 밖의 공급일정·기타사항도 읽고 단순 표의 제목/값을 연결한다. `ScheduleSourceReader`는 원문 전체에서 명시된 순위·인터넷/현장별 기간을 구분한다. 같은 원문 안에 명시된 연도만 축약 연도에 사용할 수 있으며 현재 연도를 추정하지 않는다.
- 전체 접수 범위와 순위별 세부 기간을 함께 보존한다. 서류 대상자 발표와 최종 결과 발표는 별개다. 병합 셀 때문에 특정 순위의 날짜를 확정하지 못하면 보류하며 다른 순위 날짜로 채우지 않는다. 일정 컴파일 성공은 준비 안내 공개 성공과 다르다.

## 로컬 우선 해석과 Gemini 선택 연결

`LocalRuleInterpreter`가 수집된 전체 발췌를 먼저 읽고, `LocalRuleBook`에 정확한 원문 구간·출처 SHA-256·페이지·파트 내 시작/끝 위치와 적용 대상·수치·부정·완화·예외·참조 관계를 보관한다. 명시된 값과 관계를 추출하는 단계이며 범용 자격 판정이나 모든 문장의 해석 완료를 뜻하지 않는다. 일반 미해석 문장은 로컬 보류 기록으로 남기고, `CompactReviewPlanner`가 특정 조건 관계를 추가로 검토할 필요가 있는 문맥만 선택한다. 필요한 예외·참조를 포함한 문맥이 누락되거나 요청 한도를 넘으면 잘라서 보내지 않는다.

원문 전체를 Gemini에 보내 규칙 후보를 받던 경로는 제거했다. 현재 `GeminiReviewClient/Service`는 `CompactReviewPacket`만 받아, 해당 질문의 일관성·충돌·미해석 여부를 보조 검토한다. 별도의 로컬 공개 검수 컴파일러가 유지되며, API 응답을 자동 공개 후보나 완전성 증명으로 사용하지 않는다.

키는 저장소 루트의 Git 제외 `.env`에 `GEMINI_API_KEY`로 둔다. `LH_SERVICE_KEY`와 별개이며 `VITE_` 환경변수에 넣지 않는다. `GEMINI_MODEL`, `GEMINI_REVIEW_ENABLED`로 명시적으로 활성화한다. 사용 가능 모델 확인과 무료 등급/청구 설정 확인은 별개다.

- 서버가 수집한 공개 공식 문서만 전달한다. 사용자 답변·소득 입력·메모·증빙은 전달하지 않는다.
- 요청 하나의 정확한 `payloadJson()`은 메타데이터·JSON 이스케이프를 포함해 최대 6,000자다. 원문 위치와 전체 해석 기록은 로컬에 유지하고, API에는 정확한 인용·출처·페이지·적용 범위와 필요한 관계를 보낸다. 시스템 지시문·응답 스키마·HTTP 포장 때문에 실제 전체 요청은 6,000자보다 크며, 문자 수는 토큰 수가 아니다.
- 공고별 첫 계획은 최대 3개 요청이다. `deferredPacketIds`와 `LOCAL_REVIEW_PENDING`은 아직 검토하지 않은 항목이며, 저장된 첫 계획을 소비한 뒤 보류분 전체를 자동 전송하거나 완료로 변경하지 않는다. 동일한 전체 근거를 가진 질문만 합치며 PDF/HWP 등 다른 출처·범위의 문장을 임의로 동등하게 취급하지 않는다.
- `SourceCoveragePolicy`의 원문·필수 첨부 누락 등은 API 보조 검토도 차단한다. 예외적으로 `DOCUMENT_VARIANT_CONTEXT_UNVERIFIED`만 남은 자료는 제한된 부분 문맥 검토를 허용하지만, 변형 파일의 동일성을 입증하거나 기존 공개 HOLD를 해제한 것으로 보지 않는다.
- 응답은 질문 ID별 `CONFIRMED_CONFLICT`, `NO_CONFLICT`, `UNRESOLVED`와 근거 문장 ID 목록이다. `ScopedReviewSchema/Validator`는 모든 요청 질문이 정확히 한 번 나타나는지, 해당 질문에 포함된 근거만 인용했는지 검사하며 충돌에는 서로 다른 근거 두 개 이상을 요구한다. `NO_CONFLICT`는 전달한 부분 문맥에만 적용되고 공고 전체의 완전성·신청 자격·안내 PASS를 뜻하지 않는다.
- 출력 최대 2,048토큰/응답512KiB·요청30초 제한, 리다이렉트/잘린 출력 거절. 요청키는 헤더에만 포함하고 로그/URL에 넣지 않는다.
- `GeminiBudgetRepository`: 서버 전체 하루 최대10회(한국시간), 최소60초 간격. DB에 호출 예약을 먼저 기록해 재시작/동시 작업도 한도를 공유한다. 정확한 요청 내용·근거 해시·정책·모델별 결과를 재사용하며 캐시 응답도 현재 질문·근거 계약으로 검증한다. 중단된 호출을 무조건 반복하지 않는다.
- 인증/쿼터 오류가 발생하면 그날 추가 호출을 중단한다. 다른 모델·유료 서비스로 자동 전환하지 않는다. 이 로컬 제한은 Google의 계정별 무료 한도 또는 청구 설정을 변경하지 않는다.

## 발췌 재시도

자료 읽기 실패는 성공 자료를 보존한 채 실패 자료만 30초/60초 후 최대2회 재시도한다. EMPTY는 성공으로 간주하지 않으며 무한 재시도하지 않는다. claim token을 대조해 중단된 옛 worker가 새 결과를 덮어쓰지 못하게 한다. 실패 원문 링크·비밀키·원문 전체를 로그에 출력하지 않는다.

첨부 하나를 읽을 때마다 `ExtractionStore.checkpoint`에 성공한 자료와 실행 심박을 남긴다. 재시작 뒤 이미 읽은 자료를 유지하고, 실행 소유권이나 공고 revision이 바뀌면 중간 저장도 거절한다.

`ExtractionText`는 HTML 파싱 전과 추출 파트 저장 전에 NUL/고립 surrogate 및 크기를 검사한다. JSONB에 저장할 수 없는 문자를 삭제해 승인하지 않고, 해당 출처를 설명이 있는 FAILED(빈 context/excerpts)로 기록한다. 따라서 오류 문자가 checkpoint와 finish를 연달아 실패시켜 RUNNING에 남는 문제를 막는다. 정상 한글·유효한 surrogate pair·개행은 변경하지 않는다.

## 실행 검증

### 2026-11-08 대기열 재사용과 지정 공고 검수

- 재수집 시 같은 공고 revision·원문 fingerprint의 READY/PARTIAL/FAILED 완료 결과를 재사용한다. 기존 55분 제한을 없앴으며, 시간이 지났다는 이유로 검수 결과를 새 대기 작업으로 대체하거나 실패 재시도 횟수를 초기화하지 않는다.
- 원고·첨부 변경으로 revision/fingerprint가 달라지거나 명시적 재발췌를 요청하면 새 작업을 만든다. 첨부 해시 변경 감지 경로는 유지한다. 원격 자료가 조용히 변경된 경우에는 해당 변경 감지 또는 명시적 재발췌가 필요하다.
- 현재 원문과 다른 대기 작업은 다운로드 없이 SUPERSEDED로 종료한다. 기본 검수 PASS 공고의 자료를 내부 HOLD 공고보다 먼저 처리하며, 큐 우선순위가 안내 공개 상태를 변경하지 않는다.
- `ExtractionStore.claim(UUID)`와 `NoticeExtractionService.runNext(UUID)`는 지정 공고만 회수·정리·처리한다. 일반 예약 작업은 기존 전체 큐 진입점을 사용한다. 실패 자료 30/60초·최대2회 재시도와 작업 소유 토큰 검증은 유지한다.
- 사용자가 선택한 기존 보류18건의 실제 재검수 결과는 2026-11-08 기록을 따른다. 파일 읽기 완료와 개인별 준비 안내 PASS를 구분하며, 자료 누락·파일 변형본 대조·복잡한 조건 미해석을 임의 해제하지 않았다.

구현/테스트/실제 연동 결과는 `docs/history/entries/2026-11-07-automatic-review.md`에 별도로 기록한다. Gemini 모의 테스트 성공은 실제 API 성공이나 임의 LH 문서의 해석 정확도 보장이 아니다.
## 2026-11-08 유형별 검토 초안과 원문 내부 불일치

`GuidanceReviewCompiler`가 자동 공개 검사와 관리자 미리보기에 동일한 판정을 제공합니다. 공개 조건을 충족하지 못하더라도 근거에 연결된 후보는 읽기 전용으로 확인할 수 있습니다. 미리보기 GET은 공개 원고, 검수 상태, 개인 준비 기록, Gemini 사용량을 변경하지 않습니다.

- `NationalRentalGuidancePreview`는 소득·총자산 배제/선착순/현장접수 국민임대 중 검증된 문장 범위를 만족하는 자료를 14개 주제 질문과 조건별 서류 후보로 묶습니다. 공고 ID·도시명·날짜를 하드코딩하지 않습니다. 일반 소득표를 재활성화하거나 거주지 순위를 만들지 않습니다. 인감 대리와 본인서명 대리의 서류는 대안으로 구분합니다.
- 이 유형별 후보는 범용 자격 판정이나 기존 전체 문맥 검사를 대체하지 않습니다. 기존 전체 규칙 컴파일러, 원문 충족 여부, 일정, 내부 충돌 검사가 모두 통과해야 공개할 수 있습니다. 후보의 문항 수가 적다는 이유로 PASS하지 않습니다.
- `OfficialFormConsistency`는 공식 목록/첫 페이지 공고일과 첨부 서식의 명시적 '해당 공고에 따른 입주자' 날짜를 비교합니다. 자격 본문 없이 검증된 목록 필드만 있어 EMPTY로 저장된 페이지도 날짜 근거로 읽습니다. 실패·미확인·그 밖의 EMPTY 본문이나 과거 법령·예시 날짜는 모집공고일로 전용하지 않습니다.
- `NationalRentalScopeReview`는 소득배제와 소득가구원용 임신·입양 서류, 배점 무관 선착순과 가산점용 가족서류의 미확정 적용관계를 개별 근거와 함께 남깁니다. 자동으로 필요/불필요를 확정하지 않습니다.
- `SourceCoveragePolicy`는 날짜만 있는 공식 목록 본문을 별도 자격 원문으로 중복 계산하지 않으며, 그 날짜는 일정 대조에서 보존합니다. `DocumentVariantComparison`은 공백·Unicode 조합·명시적으로 완전한 페이지 순서만 정규화합니다. 단어/글자 집합이 같거나 표 셀 순서가 다르면 의미 동일성을 추정하지 않습니다.
- HWPX 구조 추출은 [표 구조 계약](../architecture/hwpx-structure.md)을 따릅니다. PDF의 복잡한 표와 HWPX의 의미 일치를 자동으로 증명한 것은 아닙니다.
- 관리자 GET `/api/v1/admin/reviews/{noticeId}/extractions/{extractionId}/guidance-preview`는 최신 revision/발췌 내용 지문을 검사하며 이전/미완료/재발췌된 자료는409, 다른 공고의 발췌는404로 거절합니다.
- `official-rules-v4`로 공개 감사 정책을 구분하며 로컬 분석 캐시에 `source-review-v4`를 포함합니다. 확인된 내부 충돌·서류 적용관계 미확정은 추가 모델 요청으로 해제하지 않으며, 해당 자료의 자동 API 요청을 차단하여 불필요한 호출을 줄입니다.
- 서류 적용범위 검사는 PDF 전용 초안 여부와 관계없이 모든 출처에 공통으로 적용합니다. 같은 내용이어도 다른 출처의 근거는 보존하며 같은 근거만 중복 제거합니다. 다른 해석 경로를 사용하더라도 기존 출처 무결성·규칙 모순 등의 오류를 없애지 않습니다.
- 일정의 최종 검사에서 단일 모집의 대상자/결과 발표가 접수 마감보다 앞서면 보류합니다. 양쪽 시각이 있을 때만 같은 날의 시각 순서도 비교합니다. 순위별 접수나 조기 마감으로 설명될 가능성이 있어도 어느 모집 대상인지 추정하지 않고 범위 확인 대상으로 남깁니다. 서류 마감과 최종 결과 발표 순서는 일률적으로 강제하지 않습니다. `서류 마감`과 `서류 제출 마감`을 모두 명시된 일정으로 읽습니다.


## 2026-11-08 지정 18건의 원문 대조 패키지

사용자의 “18건 해결해줘” 요청에 따라, 범용 자동 문법으로 미해석된 지정 공고를 실제 공식 자료별로 다시 읽고 준비 안내 원고를 작성한다. 이 경로는 예약 자동 검수와 구분되며, 자동 문법의 문서 누락/충돌 검사를 완화하지 않는다.

- `SourceReviewVerifier`는 원고·현재 notice revision·완료 extraction을 묶고 공식 상세 페이지와 현재 첨부를 다시 조회한다. 상세 본문은 저장된 HTML SHA와 검토 패키지가 일치해야 하고, 새 조회의 추출 문맥 전체도 저장 문맥과 같아야 한다. 첨부는 원본 파일 SHA가 정확히 같아야 한다. 새 첨부, 달라진 파일, 누락된 출처는 PASS/UNSUPPORTED 적용을 막는다.
- 기존 발췌에 포함된 출처와 현재 공식 첨부 모두가 검토 목록에 있어야 한다. 파일 읽기가 실패했다는 이유로 출처를 제외하는 기능은 두지 않는다.
- `SourceReviewPublicationService`는 verifier만 만들 수 있는 짧은 수명의 검증 결과와 패키지 전체 해시를 대조하고, notice 잠금 안에서 현재 revision·최신 extraction fingerprint를 다시 확인한다. 같은 패키지는 재적용하지 않는다. 기존 PASS 원고와 개인 준비 기록은 수정하지 않는다.
- 공개 원고에는 공고별 자기확인 질문·모름/추가확인·해당자 서류·순위별 날짜와 출처를 보존한다. 최종 신청 자격이나 선정 가능성을 판정하는 것은 아니다. 조건이 복잡하다는 이유만으로 확인되지 않은 기준을 필수 조건으로 만들지 않는다.
- 초기 적용에서는 실제 기관 문서 충돌이 남으면 공고 전체를 HOLD로 기록했다. 아래의 사용자 확정 개정 이후, 영향 범위를 원문으로 특정할 수 있는 검토 패키지는 PARTIAL로 적용할 수 있다. 개인 입주가 아닌 기업체 공급·어린이집 운영자 모집은 근거와 함께 UNSUPPORTED로 분류한다.
- V27 `notice_source_review`에 `AI_ASSISTED_SOURCE_REVIEW`와 전체 검토 패키지, 원문 지문, 적용 전후 revision을 기록한다. 관리자 계정·사람 검토 이력을 만들지 않는다. `automatic_notice_review`의 범용 자동 승인으로도 표시하지 않는다.
- 이 경로에는 공개 HTTP API·예약 작업을 추가하지 않는다. 현재 자료를 읽은 검토 패키지를 명시적으로 적용할 때만 사용한다. 새로운 공고가 모두 자동 해석 가능해졌다는 뜻이 아니다.
- 큰 첨부의 명시적 대조는 기존 허용 호스트·공인 주소·리다이렉트 차단을 그대로 적용한 100MiB/60초 스트리밍 해시 검증을 사용한다. 메모리로 파일 전체를 받거나 압축을 모두 푸는 경로가 아니다. 자동 다운로드/문서 파서의 기존 20MiB/24MiB 한도는 유지한다.

### 읽기 실패 보완

- HWPX는 검증된 컨테이너의 mimetype/section XML만 읽는다. 본문 크기·항목·문자 한도와 CRC를 검사하며 삽입 그림의 글자까지 읽었다고 주장하지 않는다.
- PDF의 NUL은 embedded 폰트의 실제 빈 glyph·양의 가로 전진폭·비결손 glyph가 증명된 공백에 한해서만 복원한다. 불명확하거나 실제 윤곽이 있는 글자는 기존 실패 판정을 유지한다.
- 공식 HTML의 접수처 안내도 문맥에 포함한다. 정형 일정과 접수처 자유문구가 다르면 한쪽을 무시하지 않는다.

## 2026-11-08 사용자 확정: 충돌 항목만 확인 필요

사용자가 “충돌하는 부분만 확인 필요로 표시하고, 나머지 조건이랑 서류는 준비 안내 제공”하도록 기존 전체 HOLD 정책을 개정했다. 확인된 조건·서류는 이용 가능하게 하고, 기관 자료의 불일치 자체는 해결되었다고 표시하지 않는다.

- `Content.reviewIssues`가 충돌 ID, 영역(CONDITION/DOCUMENT/SCHEDULE), 제목·이유·공식 근거, 영향받는 질문/서류 ID를 보존한다. 질문에 종속된 서류도 같은 확인 범위에 포함한다. 존재하지 않는 ID, 근거 누락, 중복 ID는 거절한다.
- 출처 검토 결과 `PARTIAL`은 기존 AVAILABLE 게이트를 열되 원고·공개 공고·개인 준비 스냅샷에 확인 필요 항목을 유지한다. V29의 감사 결과는 PARTIAL로 보존하며 일반 PASS 검토로 기록하지 않는다. 모든 미해결 finding이 reviewIssues와 정확히 대응해야 적용된다.
- 공식 확인이 필요한 질문은 사용자 답변과 관계없이 추가 확인으로 남는다. 관련 서류 필요 여부는 UNKNOWN이며 준비 완료 기록을 허용하지 않는다. 다른 질문의 답변과 서류 준비 완료 기록은 정상 제공한다. 준비도 100%로 숨기지 않고, 다음 행동은 우선 처리 가능한 항목으로 연결한다.
- 확정하지 못한 일정은 확정 schedules에서 제외하고 SCHEDULE 이슈에 이유와 상충 근거를 표시한다. 날짜를 추정해서 캘린더·기한 알림에 보내지 않는다. 확인된 나머지 일정은 유지한다.
- 공식 미확정 질문/서류를 일반 FAQ로 재가공하지 않는다. 확인할 내용은 해당 공고의 근거와 함께 제시한다.
- 기존 전체 출처 대조, 최신 revision·발췌 해시·파일 해시 검증, 기존 PASS 원고와 개인 준비 기록 보호는 유지한다. 이 변경이 예약 자동 검수의 미해석 항목을 모두 안전하게 분리할 수 있다는 의미는 아니다. 출처 누락이나 영향 범위를 특정하지 못한 경우는 전체 HOLD를 유지한다.

## 2026-11-08 예약 자동 검수에 부분 제공 적용

사용자가 앞으로 수집할 공고에도 같은 원칙을 적용하도록 요청했다. 자동 검수는 전체 보류 사유와 원고의 `reviewIssues`를 분리한다. 지원하는 규칙과 근거로 영향받는 항목을 특정한 경우에만 부분 제공하며, 미해석 문장을 일괄 승인하거나 외부 모델 응답을 완전성 증거로 사용하지 않는다.

- `AutomaticPublicationService`는 전체 보류 사유가 하나라도 있으면 유효한 부분 후보도 공개하지 않는다. 내용 검증에서 `GuidanceIssues.validate`로 존재하는 질문·서류 ID, 종속 서류, 근거와 질문의 확인 필요 상태를 대조한다. 신청 시작·마감은 해당 일자의 확정 일정이 모두 존재해야 한다.
- 안전한 부분 후보는 이용 가능 상태로 공개하되 감사에는 PASS 대신 PARTIAL을 기록한다. V31은 GUIDANCE/PARTIAL과 비어 있지 않은 `review_issues`의 조합만 허용한다. BASIC/PASS/HOLD의 확인 범위는 빈 배열이다. 이후 정정 원고가 이전 원고를 대체해도 당시의 미확정 범위가 감사에서 사라지지 않는다.
- 발행 정책 `official-rules-v5`와 컴파일 정책 `source-review-v5-scoped`는 이전 전체 보류 결정·로컬 분석 캐시와 구분한다. 기존 수동 차단 원고·이미 공개된 안내를 무조건 재작성하지 않는다. 기존 HOLD도 현재 발췌가 유효하면 새 정책으로 재검사될 수 있지만 과거 결과 자체를 변경하지 않는다.
- 새 출처가 수집되면 이전 자동 안내의 공개 날짜·질문·서류를 내려 재검사하고, 기존 개인 준비 스냅샷은 유지한다. 같은 발췌의 동일 지문·정책은 중복 발행하지 않으며, 발췌 교체·revision 변경·수동 편집 이후 늦게 도착한 자동 결과는 거절한다.
- 선택적 일정에서 충돌한 날짜는 확정 일정·캘린더·기한 알림에 섞지 않는다. 나머지 확인된 접수 기간과 일정은 유지한다. 접수 경계 자체나 알 수 없는 범위가 남아 공개 기준을 충족하지 못하면 전체 HOLD를 유지한다.

이는 지원 범위의 충돌을 자동으로 분리하는 계약이다. 스캔 누락, 읽기 실패, 동일성을 입증하지 못한 변형 파일, 범위가 불명확한 다중 문서, 지원하지 않는 복잡한 예외까지 자동 해결되었다는 뜻은 아니다. 검증 결과와 실제 실행 범위는 이번 작업 기록을 따른다.

### 범위 판정과 기본 정렬

- `AutomaticGuidanceCompiler.compileScoped`는 같은 조건의 상충 값과 제출 대상별 문서 목록을 각각 묶는다. 서류 목록 교집합은 그대로 제공하고 차집합·제출 대상이 상충한 문서만 확인 필요로 남긴다.
- `EvidenceGuidanceCompiler.compileScoped`는 완전한 공식 구간을 확인 질문으로 보존한다. 정확하게 식별된 상충 문장은 별도 질문으로 분리하여 같은 구간의 정상 조건까지 묶이지 않게 한다. 다른 원문 사이의 차이가 이 규칙들만으로 모두 설명되지 않으면 전체 보류한다. 충돌 조건을 서류가 참조하지만 영향 범위를 확정하지 못하면 보류한다.
- `SourceCoveragePolicy.assessScoped`는 모든 변형 파일의 페이지·텍스트·지문을 먼저 확인한다. 같은 이름의 PDF/HWPX 차이가 동일 종류·주제의 명시 규칙 값에만 있을 때 양쪽 자료를 검수에 전달한다. 조건 추가·누락, 주변 예외 변경, 빈 페이지는 정상본과 합치거나 제외하지 않는다.
- `ScopedFindingGuidance`는 양식의 공고일·소득배제 관련 서류·가산점용 가족서류의 발견 사항을 실제 존재하는 문서와 질문에 연결한다. 영향을 받는 문서가 후보에 없거나 근거 위치를 연결하지 못하면 전체 보류 사유로 남긴다.
- 기본 정렬 `active`: 접수 중 → 접수 예정 → 접수 종료(조기 종료·취소 포함) → 일정 미확인. 각 상태 안에서는 정상 준비 안내 → 일부 확인 필요 → 검수 중(변경 검수 포함) → 미제공 순이다. 서버가 페이지를 나누기 전에 이 순서를 적용한다. 동률은 마감일 오름차순, 공고일 내림차순, ID 오름차순이며, 명시적으로 고르는 마감순·최신순은 유지한다.

## 2026-11-08 검수 중 공고의 읽기 전용 원문 표시

사용자가 검수 중인 공고에서도 표시 가능한 부분을 요청하여, 공식 원문 열람을 발췌 카드로 확장한다. 이는 검수되지 않은 개인별 해석·조건 질문·서류 목록을 공개하는 기능과 구분한다.

- 상세 전용 `GET /api/v1/notices/{id}/source-information`은 기본 공개를 통과한 실제 공고만 읽는다. 목록 DTO와 기존 `Notice`의 안내 상태·질문·서류·일정·`canStart` 값은 변경하지 않는다.
- 응답의 `state=AVAILABLE`은 열람할 원문 구간이 있다는 뜻이며 안내 승인과 관계없다. `sections`는 CONDITION/DOCUMENT/SCHEDULE 범주의 원문 구간과 출처·위치·자료 확인 시점만 포함한다. 개인별 답변·필요 서류·준비 상태·판정 결과는 포함하지 않는다.
- 실제 EXTRACTED 자료의 문맥을 보존하여 표시하며, 실패한 자료나 후보 해석·모델 응답으로 문장을 보충하지 않는다. 일부 구간만 표시할 수 있으므로 전체 규칙이 확인되었다는 의미로 사용하지 않는다. `pendingAreas`는 표시할 구간이 없는 영역이며 승인 여부가 아니다.
- 현재 공고 revision·원문 지문과 최신 발췌 작업·내용 지문을 전후 대조한다. 새로운 대기/실행 작업이 있으면 이전 완료 자료로 대체하지 않는다. 공개에서 내려간 공고와 로컬 예시는 조회할 수 없다.
- 조회는 네트워크 수집·외부 모델 요청·자동 승인·개인 기록·감사 저장을 실행하지 않는다. `Cache-Control: no-store`를 사용하며 화면도 새 원문을 조회하는 동안 이전 발췌를 숨긴다.
- 화면은 `공식 원문에서 확인한 내용`과 `원문 발췌 · 검수 중`을 구분해 표시한다. 확정 일정·캘린더·기한 알림에는 원문 발췌의 날짜를 추가하지 않는다. 검수 완료 안내 화면은 기존 개인별 준비 계약을 사용한다.

## 2026-11-08 읽기 실패 복구와 최신 공고 대기 순서

- XLS/XLSX 첨부도 기존 별도 문서 작업 프로세스에서 읽는다. 시트·셀 좌표·병합 범위·숨김 여부·셀 표시 형식을 보존하고 수식은 재계산하지 않는다. 수식의 저장값은 그 사실을 명시하며 외부 연결이나 매크로를 실행하지 않는다. 직접 엑셀 첨부 링크도 기존 공식 호스트 제한을 적용한다.
- 읽을 수 있는 본문이 있으면 `EXTRACTED`, 본문이 비어 있으면 `EMPTY`다. 조건/서류/일정 키워드가 없는 주택 목록을 읽기 실패로 분류하지 않는다. `excerpts`가 비어 있어도 전체 문맥은 별도 보존한다. 이 상태는 안내 승인과 관계없으며 모든 출처·변형본·범위 검사는 그대로 적용한다.
- XLSX의 전체 압축 항목·실제 해제 크기·CRC를 셀 객체 생성 전에 검사한다. 기존 24MiB/300항목/200파트/100만자 및 별도 프로세스 메모리·시간 제한을 유지한다. 시트의 행/열/셀/병합 수에도 상한을 둔다. 스캔 PDF는 빈 텍스트를 임의로 보충하지 않는다.
- 공개 기본 정보가 확인됐지만 안내가 보류된 공고를 먼저 읽는다. 이어읽기는 최초 대기 위치를 유지하고 `next_attempt_at`은 재시도 가능 시각만 제한한다. 최근 30일 공고는 대기 시각을 최대 24시간 앞당겨 평가하므로 최근 공고를 먼저 보면서도 오래 대기한 과거 공고가 계속 밀리지 않는다.
- 명시 날짜 뒤 쉼표와 시각, 단일 `[현장접수]` 표기를 읽을 수 있도록 일정 문법을 보완한다. 여러 방식의 접수가 하나의 날짜를 공유하는지 불명확하거나 연도가 근거로 연결되지 않으면 기존 보류를 유지한다.
- 재검수 정책은 `official-rules-v6` / `source-review-v6-scoped`다. 이전 감사는 보존하며 최신 발췌·revision·정책이 일치할 때만 새 결정을 기록한다. 이미 승인된 안내·수동 차단·개인 준비 기록을 이번 읽기 복구로 다시 작성하지 않는다.

### 명시적 원문 검토와 정정

- 자동 정책의 전체 범위 검증을 통과하지 못한 최신 공고는 모든 본문·서식·동일 내용의 다른 형식을 대조한 원고를 기존 `SourceReviewVerifier`로 다시 확인한다. 현재 revision, 최신 발췌 지문, 공식 HTML의 전체 추출 문맥, 모든 첨부의 실제 SHA를 재검증한 경우에만 적용한다. 사람의 관리자 승인 기록을 만들지 않고 `AI_ASSISTED_SOURCE_REVIEW`로 기록한다.
- 검토한 안내의 오류를 명시적으로 정정할 때는 `amend`를 사용한다. 현재 revision의 새로운 원문 검증과 정확한 이전 게시 지문·게시 revision·현재 content JSON 일치가 모두 필요하다. 중간 편집이나 사람의 검수 이력이 있으면 거부한다. 기존 감사는 수정하지 않고 새 감사와 버전을 추가하며 개인 준비 스냅샷은 바꾸지 않는다. 예약 작업과 HTTP 쓰기 API에서는 호출하지 않는다.
- 정정 공고 연결은 제목 유사도가 아니라 공식 상세의 현재/원본 공고 ID와 양방향 연결·정정사유를 확인한다. LH의 리터럴 변수 형식과 `curr`/`otxt` 리터럴 분기 형식을 읽되 원격 JavaScript를 실행하지 않는다. 원본의 내용을 최신 정정 내용으로 덮어쓰지 않는다.
- 과거 공식 공고의 30자리 숫자 ID도 선행 0을 제거하지 않고 그대로 대조한다. 실제 확인된 `GoCrc`의 빈 원본 ID 기본값·빈 대체 분기 형식은 전체 정적 블록과 공식 제출 경로가 맞을 때만 인식한다. 동적 대입, 추가 덮어쓰기, 다른 제출 주소, 중복 함수 및 양방향 근거 없는 관계는 거부한다. 기본값이 있다고 역방향 공고 ID를 추정하지 않는다.

### 기존 공개 원고의 첫 목록 연결

- 과거 작성한 공개 원고는 목록 수집 지문·수집시각이 둘 다 비어 있을 수 있다. 최초 연결의 null→지문 설정을 원문 변경으로 간주하지 않는다.
- 기존 BASIC PASS·GUIDE PASS/UNSUPPORTED, 자동 덮어쓰기 차단, 변경 검토 아님, 정상 lifecycle, 정확히 같은 LH 원문 URL·URL 기반 sourceKey·제목·유효 공고일, 유효 원고를 모두 요구한다. 제공 중 원고는 기존 검수 계약의 질문·서류·일정·신청기간 완전성을 지키며 존재하는 접수 경계 일정의 날짜가 기간과 충돌하면 보존 경로를 거부한다.
- 감사가 있는 경우 최신 감사의 revision과 결정이 현재 상태와 일치해야 한다. 감사가 없는 기존 원고에 관리자 기록이나 확인시각을 만들지 않는다. 이 조건을 충족하면 수집 지문·수집시각만 최초 설정하고 기존 상세 지역/유형·내용·결정·확인시각·버전을 보존한다. 새로 승인하는 경로가 아니다.
- 이미 지문/수집시각이 있거나 위 조건이 다르면 기존 변경 검토를 따른다. 최초 연결 뒤 실제 지문 변경 역시 기존대로 HOLD와 새 버전으로 처리한다.

### 2026-11-08 원문 대조 후 신청 기간만 미확정인 준비 안내

사용자는 OCR 오독을 공식 원문과 대조하고, 확인된 조건·서류를 제공하도록 요청했다. 공식 상세와 첨부의 접수 기간이 다르더라도 검토가 끝난 준비 항목을 함께 숨기지 않는다.

- `SourceReviewModels.Package.applicationPeriodIssueId`는 명시적 `PARTIAL` 검토에서만 허용한다. 실제 `SCHEDULE` 이슈 및 `unresolvedFindings`와 연결되어야 하며 조건·서류 ID를 대신 연결할 수 없다.
- `ReviewedApplicationPeriod`는 알려진 경계마다 같은 날짜의 기본 접수 시작/마감 일정을 요구한다. 모르는 경계는 날짜·시각을 비우고 기본 경계 일정도 넣지 않는다. 확인된 단지별·순위별 일정은 별도로 보존한다. 두 경계가 모두 확정된 경우 이 예외 필드는 사용할 수 없다.

### 명시적 후속 공식자료 재검토 (2026-11-09)

2026-11-09의 후속 사용자 요청으로 신규 수집 공고의 자동 대조 경로를 별도로 추가했다. 아래 명시적 검토 경로와 구분하며, 자동 발견·관계·재검토·게시 계약은 [정정·후속 공식 자료 자동 대조](automatic-followup-review.md)를 따른다.

- 원공고의 정정본·후속 공지·명시적으로 준용한 최초 공고·당시 시행 법령은 `supplementalReferences`로 별도 선언한다. 원공고 자체의 최신 발췌 지문, 전체 문맥, 현재 첨부 전부의 SHA 검사를 대체하지 않는다.
- `SupplementalSourceVerifier`는 LH의 지정된 상세/공지 경로 또는 국가법령정보센터의 정확한 역사 버전만 허용한다. 검토한 제목·본문·모든 직접 첨부 링크의 지문을 현재 응답과 대조한다. 선택한 첨부는 실제 부모 페이지에 연결되어 있어야 하며, 원바이트 SHA도 같아야 한다. HTML 첨부의 별도 읽기 경로는 이 명시적 검토에만 사용한다.
- 역사법령은 요청 식별자·숨김 버전 값과 실제 본문 제목·시행일을 함께 대조한다. 본문의 법령번호·개정 메타정보도 지문에 포함한다. 현재 법령을 과거 공고에 소급 적용하지 않는다.
- 날짜가 정해지지 않고 모집인원 충족 등 종료 조건이 명시된 경우 `confirmedOpenEndedPeriod`로 그 조건과 근거를 기록할 수 있다. 시작일은 확정되어야 하고 종료일은 비워야 하며, 동일 설명이 공개 요약에 포함되어야 한다. 이 경우 기관 확인 이슈를 인위적으로 만들지 않는다. 종료 조건조차 충돌하거나 모르는 경우에는 기존 부분 검토 이슈를 유지한다.
- 정확한 과거 종료일을 몰라도 현재 공식 공고상태가 접수마감으로 확인된 경우 `Content.applicationClosure`로 설명과 근거를 기록한다. 공개 상태·필터·정렬·준비 시작은 CLOSED로 일치시키되 날짜·D-day·캘린더 일정을 생성하지 않는다. 자동게시 후보가 이 값을 임의 선언하면 거부한다. 확인된 조건·서류 열람과 기존 개인 준비 기록은 보존한다.
- 이미 게시한 원고의 수정은 기존 게시 내용·지문·revision이 일치하는 `amend` 경로로만 적용한다. 정정 관계의 revision이 바뀌면 기존 링크를 숨기는 원칙을 유지하고, 같은 원본/정정본 쌍을 최신 공식 양방향 근거로 `reverify`한 경우에만 복원한다. 이전 관계 근거는 `notice_correction.verification_history`에 보존한다. 단방향 정정 연결의 자동 허용 범위는 넓히지 않는다.
- 이 경로는 명시적 검토 작업이며 예약 수집의 자동 승인 정책을 대신하지 않는다. 후속 정정 내용과 원본 당시 값, 예정 일정과 실제 마감 공지를 구분해 기록한다.
- 미확정 경계를 `접수 종료` 같은 일반 별칭으로 바꾸거나 `확인 필요·미정·미확정` 제목과 날짜를 함께 넣어 확정 일정으로 우회할 수 없다. 별도 단지·순위의 확정 접수와 서류·계약 절차의 날짜는 전체 신청 경계와 구분한다.
- 신청 기간을 비운 안내는 기간 미확인 상태로 제공한다. 임의의 마지막 접수일, 다른 순위의 날짜, 현재 연도, `9999.12.31` 등의 대체값으로 마감일·알림·캘린더를 만들지 않는다.
- 조건·서류 원고 검증, 모든 공식 첨부·상세 재조회, 원문 SHA·전체 문맥·최신 revision·검토 영수증·개인 기록 보존 검사는 그대로 적용한다. 범용 OCR 결과와 예약 자동 검수의 승인 조건은 완화하지 않는다.
- 검토 이력에는 원문 대조한 페이지·표·동일 내용의 다른 형식·도면 범위를 남긴다. 오독 교정은 출처가 연결된 안내 원고에 반영하며 원시 OCR을 신뢰 가능한 원문으로 바꿔치기하지 않는다. 실제 문서 내부 불일치는 해당 항목에만 남긴다.
- 자격·서류가 없는 접수 종료 안내문은 `UNSUPPORTED`로 설명과 확인된 공개 일정만 제공한다. 다른 공고의 자격·서류를 가져와 개인별 안내를 생성하지 않는다.

### 개별 결과 발표 자동 안내 (2026-11-10)

- 사용자 요청에 따라 `AutomaticScheduleCompiler`가 검증된 공식 원문에서 개별 결과 발표 설명을 함께 컴파일한다. `IndividualAnnouncementCompiler`는 공고별 신청일부터의 최소 주/개월, 소득·자산 확인 조건, 기간 단축·연기 예외, 문자·이메일 안내 문구를 출처에 묶는다. 전 공고에 동일한 10주 설명을 넣지 않는다.
- 명시적인 결과/당첨자/예비입주자 발표 문장 및 선정안내+결과 통지 문맥을 대상으로 한다. 계약·입주 개별 안내, 부적격 소명, 부정문, 원문 없는 짧은 발췌는 결과 발표로 바꾸지 않는다.
- 구조가 검증된 HWPX 표는 기존 `HwpxContextReader`의 좌표를 공유해 최종 발표 열과 값의 관계를 확인한다. PDF에서 평탄화된 여러 열을 가까운 글자끼리 이어 붙이지 않는다. `2027.1월예정`은 설명이며 임의 날짜로 변환하지 않는다.
- 설명은 `결과 발표 · 개별 안내`, 빈 `date`, `timingDescription`, 공식 근거로 저장한다. 기존 화면의 개별 안내 설명창을 사용하고 알림·캘린더에는 예상 날짜를 만들지 않는다.
- 서로 다른 설명/기간, 고정 최종 발표일 또는 기존 미확정 결과와의 충돌은 결과 발표 항목의 검토 이슈로 분리한다. 일치하는 설명은 하나로 합치며, 해당하지 않는 조건·서류·일정은 기존 검수 기준을 유지한다.
- 접수종료는 기존 작업 대기열·실행·게시 잠금 단계에서 제외하며, 새로 추출한 접수 종료일까지 확인한다. 컴파일러도 확인일 이전에 종료된 공고에 새 개별 발표 일정을 추가하지 않는다. 이미 수동 검수·게시한 원고를 정책 변경만으로 덮어쓰지 않는다.
- 지원 문법 밖의 원문, 읽지 못한 자료, 구조가 불명확한 표를 모두 자동 해결했다고 간주하지 않는다. 전체 원문·지문·최신 revision·공식 자료 검증과 부분 확인 필요 정책은 그대로 적용한다.
- 캐시 정책은 `source-review-v8`, `official-rules-v8`. 상세한 미종료 공고 수동 반영 기록과 미래 자동 검수 구현을 구분한다.

2026-11-10 기존 수집 공고 누락 점검에서 신청일부터 3개월 이후 발표 예상·적격자 개별 문자 통보 문법을 추가했다. 설명의 검증 일정 변동 조건도 보존한다. 현재 정책은 `source-review-v9`, `official-rules-v9`이며 기존 수집 공고의 일정 한정 수정은 [점검 기록](../history/entries/2026-11-10-current-individual-announcement-audit.md)에서 자동 검수와 구분한다.

### 첨부 신청기간 독립 반영 (2026-11-11 사용자 요청)

- `ApplicationPeriodReviewWorker`는 기존 자동 검수 활성 설정과 주기를 사용한다. `ApplicationPeriodCompiler`의 `application-period-v1`은 조건·서류 검수 승인과 별개로 공식 원문의 확정된 신청 시작·마감만 평가한다. 별도 AI 호출을 추가하지 않는다.
- 최신 발췌 revision/원천 지문/내용 지문, 공식 출처 바인딩, 문서 전체 범위, PDF/HWP 변형본 일치가 필요하다. 변형본 문맥 차이는 모든 변형본의 일정을 비교해 일치할 때만 허용하며 읽기 실패·누락·부분 페이지·미검증 OCR은 통과시키지 않는다.
- `ApplicationTableReader`는 신청일시/신청일자/접수일시/접수일자 뒤 신청방법·신청장소가 연결되는 명시적 표만 읽는다. 명시 연도·순서가 검증되지 않은 날짜, 다른 열, 누락된 순위 날짜를 임의 보충하지 않는다.
- 상시·공급 종료 시까지·도착순/선착순 계약 등 종료가 미정인 후속 절차가 있으면 초기 접수일만으로 종료하지 않는다. 법령의 분양권 소유 정의와 사무소 운영기간은 후속 모집으로 취급하지 않는다.
- `ApplicationPeriodReviewService`는 잠금 안에서 최신성·수동 검수·차단·기존 종료 여부를 재검사한다. 확정된 기존 날짜/시각과 충돌하면 HOLD다. 두 신청 경계 외 일정, 요약, 조건, 서류, 준비 안내 검수 상태, 개인 준비 기록은 보존한다. 신청기간 저장은 준비 안내 승인이 아니다.
- V36 `application_period_review`에 발췌 ID·내용 지문·정책별 결정을 기록하고 같은 입력을 중복 반영하지 않는다. 원천 `source_closed`는 LH 응답을 나타내므로 첨부 종료 판정으로 변경하지 않는다. 실제 접수 상태는 기존 `ApplicationPeriod`가 계산한다.
- LH 공고중 재수집으로 확인된 기간을 지우지 않는다. 종료 공고는 일반 첨부 작업 등록/선점 및 기간 검수에서 제외한다. 사용자가 지정한 명시적 단건 발췌·검토 경로는 유지한다.
- 현재 자료 반영과 자동 문법의 범위는 [실행 기록](../history/entries/2026-11-11-attachment-closure.md)을 따른다. 복잡한 표를 명시 검토로 반영한 사실을 일반 자동 해석 성공으로 계산하지 않는다.
