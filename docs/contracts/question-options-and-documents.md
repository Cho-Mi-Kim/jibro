# 질문별 선택지와 준비 대상 서류 계약

최초 적용일: 2026-11-01. 2026-11-06 사용자 요청(#13)에 따라 숫자·날짜·다중 선택을 지원하도록 입력 계약을 확장했다. 현재 검수 공고의 질문과 기존 단일 선택 답변은 그대로 유지한다. 근거가 없는 질문이나 생년월일·주민등록번호 등 개인정보 입력 항목을 자동 추가하지 않는다.

## 질문·답변

- `Question.options`: `{ value, label, requiresFollowUp? }[]`. 선택지 코드는 대문자·숫자·밑줄 1~50자이며 질문 안에서 고유하다. 2~20개, UNKNOWN 필수.
- `value`가 서버 저장값, `label`이 질문과 결과 화면에 보이는 답변이다. 결과 화면에서 모든 응답을 ‘해당 없음’으로 재해석하지 않는다.
- `requiresFollowUp=true`는 ‘아직 확인할 내용이 남음’, ‘추가 문의 필요’ 같은 답변이다. 모름·미응답과 함께 추가 확인으로 남기며 준비도에서 확인 완료로 계산하지 않는다. 이는 자격 탈락/승인 자동 판정이 아니다.
- `PUT /api/v1/preparations/{id}/answers`: `revision`, `answers: Record<questionId, string | number | string[]>`의 전체 응답 맵을 보낸다. 서버는 스냅샷에 없는 질문 ID·선택값·null·형식이 다른 값을 거절한다. 잘못된 입력은 저장 답변·서류 상태·리비전을 변경하지 않는다.
- 구버전 질문에 options가 없으면 기존 YES/NO/UNKNOWN 계약을 읽는다. 새 안내의 질문별 선택지는 구버전의 응답을 임의 변환하지 않는다.

### 입력 종류와 검증 (2026-11-06)

`Question.inputKind`를 생략하거나 null로 보내면 `SINGLE`이다. `constraints`도 선택 사항이다. 데이터베이스는 기존 JSON 스냅샷을 사용하므로 데이터 마이그레이션 없이 이전 문자열 답변을 읽는다.

| inputKind | 저장 값 | 입력 제약 |
| --- | --- | --- |
| `SINGLE` | 선택 코드 문자열 | 기존 `options` 계약 그대로 |
| `MULTIPLE` | 중복 없는 선택 코드 배열 | `maxSelections`: 1~19, 실제 선택지 수 이내. 생략 시 UNKNOWN을 제외한 전체 선택지. 서버가 선택지 순서로 정렬 |
| `NUMBER` | JSON 숫자 | `min`, `max`, 양수 `step`(기본 1), 선택 단위 `unit`(1~20자). 소수 6자리 이내, 절댓값 9,007,199,254,740,991 이내. `min` 또는 0을 기준으로 step 배수 |
| `DATE` | `YYYY-MM-DD` 문자열 | 실제 달력 날짜, 연도 0001~9999, `minDate`/`maxDate` 포함 범위 |

- 모든 종류에서 모름은 단일 문자열 `"UNKNOWN"`이다. 다중 선택 배열에는 UNKNOWN을 섞거나 단독 배열로 넣지 않는다. 숫자·날짜의 options는 생략/빈 배열이며 모름 선택은 공통 입력 UI가 제공한다.
- 숫자처럼 보이는 문자열을 숫자로 바꾸거나 존재하지 않는 날짜를 보정해서 저장하지 않는다. 잘못된 제약 범위·다른 종류의 제약을 검수 공고에 저장하지 못한다.
- 숫자·날짜 범위는 입력 유효성만 검증한다. 유효한 값은 ‘답변 완료’로 집계하며 신청 자격·선정 순위 충족을 뜻하지 않는다. 숫자/날짜를 이용한 조건부 서류 비교 규칙은 허용하지 않는다. 검수된 비교 연산 계약 없이 임의 임계값으로 필요 서류를 판정하지 않는다.
- 단일 선택만 선택 즉시 저장·다음 질문으로 이동한다. 다중 선택·숫자·날짜는 ‘다음’으로 저장한다. 오류 시 입력을 유지하고, 이전 질문을 저장해도 다른 질문의 미완성 입력을 지우지 않는다.
- 조건 결과·이전 안내 기록은 저장된 질문의 선택지 이름, 숫자 단위, 날짜를 읽기 전용으로 표시한다. 과거 답변을 현재 입력 계약에 맞춰 변환하지 않는다.

## 조건부 서류

- `DocumentTemplate.conditionQuestionId`와 `conditionAnswerValues`로 필요한 선택값을 지정한다. 구버전은 `['YES']`를 기본으로 읽는다.
- 문항 미응답/UNKNOWN → UNKNOWN, 지정값 → CONDITIONAL, 그 밖의 답변 → NOT_APPLICABLE. 다중 선택은 선택한 코드 중 지정값과 하나라도 정확히 일치하면 CONDITIONAL이다.
- 조건이 없으면 REQUIRED다. 일치값은 해당 질문에 존재해야 하며 UNKNOWN을 필요 조건으로 지정하지 못한다.
- 준비 스냅샷은 `rules`와 `ruleValues`를 보관하여 원본 공고의 후속 편집과 분리한다.
- 실제 준비 목록과 선택된 서류 상세는 REQUIRED/CONDITIONAL만 렌더링한다. 준비 완료한 대상 서류도 진행 기록으로 계속 표시한다.
- UNKNOWN은 별도의 ‘해당 여부 추가 확인’ 안내에 모아 조건 답변 링크를 제공한다. NOT_APPLICABLE은 목록에서 숨긴다. 데이터 자체는 삭제하지 않아 답변 변경 시 다시 표시할 수 있다.
- 선택했던 서류가 더 이상 대상이 아니면 첫 준비 대상 서류로 선택을 옮긴다. 대상이 0개이면 빈 목록 안내를 표시한다.
- 이미 완료한 서류의 조건이 바뀌면 RECHECK로 전환하며, 모름/해당 없음 상태에서는 완료 저장을 차단한다.

## 기존 준비 기록의 새 안내 적용

`POST /api/v1/preparations/{id}/refresh`는 `{ revision, version }`을 받는다. 소유자·현재 리비전·최신 안내 버전·안내 공개 상태를 확인한다. 화면에서 사용자가 ‘새 안내로 질문 다시 확인하기’를 눌렀을 때만 수행한다.

1. 이전 전체 스냅샷을 `preparation_history`에 보관한다(V5 마이그레이션).
2. 질문 계약 전체(문구·근거·선택지·입력 종류·입력 제약)가 동일한 답변만 이어받는다. 바뀐 질문은 미응답으로 두며 이전 값은 이력에 보존한다.
3. 같은 서류 ID의 메모는 유지한다. 완료 상태는 재확인으로 돌린다.
4. ID·제목·날짜가 동일한 일정 기록만 유지한다.
5. 같은 준비 ID를 유지하고 버전·리비전을 갱신한다. 트랜잭션 실패 시 보관과 갱신 모두 취소한다.

아카이브는 해당 준비 기록의 소유 관계를 따른다. 공개 API로 노출하지 않으며 로그나 Git에 개인 답변을 남기지 않는다.

### 이전 안내·답변 조회 (2026-11-06 사용자 요청 반영)

- `GET /api/v1/preparations/{id}/history`는 소유자의 저장 버전·저장 시각 목록을 최신 버전부터 반환한다. `GET /api/v1/preparations/{id}/history/{version}`은 해당 원본 준비 스냅샷만 반환한다.
- 진행 중 준비와 보관한 여정 모두 같은 소유자에게만 조회를 허용한다. 타인 준비와 없는 준비·버전은 모두 404이며 익명 요청은 401이다.
- 화면은 안내 버전과 저장 시각(한국 시각), 과거 참고 기록임을 표시하고 원래 질문·선택지·답변·서류 상태·메모·일정 기록을 읽기 전용으로 보여 준다. 현재 공고의 공개 상태나 규칙으로 과거 기록을 재계산하지 않는다.
- 저장은 기존 새 안내 적용 시점에만 발생한다. 빈 기록을 위해 가상의 항목을 만들지 않으며 과거 스냅샷 복원·수정은 제공하지 않는다. 로컬 데모에는 갱신 이력이 없어 빈 상태를 표시한다.

## 로컬 적용

백엔드 새 빌드와 V5 적용 후 다음 명령으로 v2 원문 검수 자료가 일치하는 전세임대 1건만 v3로 바꾼다. 기존 준비 기록은 자동 변경하지 않는다.

```powershell
node scripts/apply-guidance-review.mjs --question-options
node scripts/apply-guidance-review.mjs --question-options --apply
```

최초 검수와 동일하게 충돌 시 중단, 동일 결과 재실행 시 건너뛰기, 공개 공고 적용 전후 로컬 백업을 적용한다.
