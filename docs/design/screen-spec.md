## 1. 설계 기준과 적용 우선순위

### 1.1 서비스의 중심 가치

사용자는 선택한 공고에 대해 **무엇을 확인해야 하는지, 어떤 서류가 필요한지, 언제까지 무엇을 해야 하는지**를 알 수 있어야 한다. 홈에서 다음 행동을 찾고, 필요한 상세 안내와 공식 근거를 확인한 뒤, 준비 상태를 기록하는 흐름을 우선한다.

핵심 가치는 다음 세 요소의 결합이다.

1. 사용자 답변에 따라 달라지는 조건과 제출서류의 개인화.
2. 조건·서류·일정 안내와 공식 공고 근거의 연결.
3. 현재 단계, 준비 상태, 다음 행동을 보여주는 신청 여정.

### 1.2 유지하는 9월 21일 결정

- 사용자 화면 10종: 홈, 공고 목록, 공고 상세, 조건 확인, 조건 확인 결과, 내 준비, 서류 체크리스트, 신청 일정, 가이드, 마이페이지.
- 하단 내비게이션: **홈 · 공고 · 내 준비 · 가이드 · 마이**.
- 공고 탐색과 개인별 신청 준비를 구분한다. 신청 일정은 `내 준비`의 하위 화면이다.
- `가이드`는 제도·용어·발급 방법·공식 문의처를 설명한다. 별도 `주거정보` 탭은 두지 않는다.
- 강준님 시안의 정보 배치·공식 근거·행동 안내와 영록님 시안의 집·벽돌 표현을 결합한다.
- 캐릭터·사람·마스코트를 사용하지 않는다. 집·벽돌·문서 일러스트를 사용한다.
- 불필요한 응원 문구, 손글씨 문구, 밑줄 장식, 요란한 배경, 반복되는 큰 일러스트를 줄인다.
- 조건 안내 결과와 준비 진행률을 서로 다른 영역에 표시한다.

### 1.3 반영하는 10월 5일 결정

- 핵심 브랜드 색상은 차분하고 짙은 벽돌색 `#B64A32`로 확정한다.
- 연한 벽돌색 `#F3E3DA`, 화면 배경 `#FAF8F5`, 카드 `#FFFFFF`, 본문 `#262626`을 적용한다.
- 벽돌색은 주요 행동·선택 상태·현재 단계·준비 진행률에 사용한다.
- 초록·황색·오류색은 의미가 있는 상태에만 보조적으로 사용한다.
- 집과 벽돌의 성장 표현은 신청 준비 행동의 진행을 나타낸다.
- **SEED Design 스킬을 후속 화면 설계와 구현에서도 사용한다.** 적용 절차는 11절을 따른다.
- 검증된 공식 발급 링크는 초기 준비 흐름에 실제 연결한다. 캘린더 파일 내보내기는 푸시와 분리해 일정 정확성·대상 기기 가져오기 사용성을 검증한 뒤 실제 구현 범위를 결정한다.
- 준비도(%)와 집 건축 표현은 초기 완성에 포함한다. 상태별 목록·필수 미확인 표시만 먼저 제공하고 두 요소를 후도입하는 제안은 기각한다.
- 푸시·이메일 알림은 후순위로 유지한다. 알림 및 아직 구현 범위가 확정되지 않은 캘린더 등의 진입점은 준비 중 안내를 제공하며 실제 예약·발송·파일 생성을 한 것으로 표시하지 않는다.

### 1.4 최신 기획안과의 연결

기능과 운영 정책은 [최신 기획안](../planning/project-proposal.md), 구현 계약은 [코드 및 기술 규칙](../conventions/coding-conventions.md)을 참고한다.

- 공개 공고 목록·상세는 비회원도 조회한다. 개인 답변·준비 상태 저장에는 로그인한다.
- 이메일·비밀번호, Google, 카카오 로그인 진입을 지원한다.
- 기본 정보 검증·공개 완료 공고를 일반 사용자 목록·상세에 표시한다. 준비 안내 검수·보완 중이나 미지원 공고도 기본 정보를 공개할 수 있으며 준비 안내 제공 상태를 구분한다.
- 자동 수집량과 정밀 준비 안내 검증 표본 수를 구분한다. 한 기관을 우선 조사하되 지역·유형은 미리 제한하지 않고 공통 구조·추가 준비 규칙·검수 작업량으로 초기 범위를 정한다. 표본 수를 화면의 상한으로 두지 않는다.
- 준비도와 조건 안내는 서버가 제공한 결과를 표시한다. 화면이 독자적인 자격 판정이나 가중치 계산을 하지 않는다.
- 수정 공고의 영향을 받은 항목은 재확인 상태로 연결한다.

이 문서는 **화면 표현의 기준**이다. 공고별 질문, 필요 서류, 기한, 진행도 가중치, 문의처의 실제 값은 공고 분석과 검수로 확정한다. 이미지 속 기관·날짜·서류·페이지 번호를 실제 규칙으로 사용하지 않는다.

### 1.5 공고 정보·준비 안내 동시 검수와 공개

관리자는 하나의 검수 작업에서 공고 기본 정보와 준비 규칙을 함께 원문 대조하고 결과·보완 사유·공개 상태는 영역별로 기록한다. 최초 검수 전 자동 수집 결과는 공개하지 않는다. 두 영역 모두 통과해야만 공고 목록에 표시하는 방식은 사용하지 않는다.

| 검수·제공 상태 | 목록·기본 상세 | 준비 기능과 사용자 안내 |
| --- | --- | --- |
| 기본 정보·준비 규칙 모두 통과·공개 | 표시 | `준비 안내 제공 중`, 신규 `내 조건 확인하기` 또는 기존 `준비 계속하기` |
| 기본 정보 통과·준비 규칙 검수/보완 중 | 표시 | `준비 안내 검수 중`, 원문 확인 경로. 신규 개인 준비 기능 보류 |
| 기본 정보 통과·준비 안내 미지원 | 표시 | `준비 안내 미제공`, 원문 확인 경로. 신규 개인 준비 기능 미제공 |
| 기본 정보 검증 실패·미공개 | 일반 조회 대상에서 제외 | 신규 안내·준비 시작 중지. 기존 개인 기록은 권한·버전 정책에 따라 별도 보존·조회 |
| 수정 공고로 준비 규칙 영향 검토 중 | 해당 기본 정보 검증 후 표시·갱신 | `준비 안내 변경 검토 중`, 영향 항목·버전 차이 안내. 해당 신규 안내·시작 보류, 과거 개인 기록 보존 |

- 공식 접수 상태, 집으로 준비 안내 제공 상태, 사용자의 개인 준비 진행 상태를 별도 라벨로 표현한다. 하나의 `검증 완료` 배지로 합치지 않는다.
- `준비 안내 검수 중`은 집으로의 안내를 확인 중이라는 뜻이다. 기관의 공식 공고 검토 상태나 사용자의 신청 자격을 뜻하지 않는다. `미제공`도 신청 불가를 뜻하지 않는다.
- 공고 기본 정보 확인일·버전과 준비 안내 확인일·기준 버전을 구분한다. 미확인 값은 확인 필요로 표시하고 기간·조건·준비도를 추측하지 않는다.
- 미제공 상태는 이번 MVP의 공고별 데이터·규칙 검수 상태이며, 알림·캘린더 등의 후순위 기능 `준비 중` 안내와 구분한다. 개인화 기능 대신 공식 원문 경로와 구체적인 상태 설명을 제공한다.
- 서버가 제공한 신규 준비 시작 가능 여부·버전과 상태를 따른다. 버튼 숨김만으로 제한하지 않으며 직접 주소 진입·요청과 조회 후 상태 변경도 서버 검사를 거친다.
- 준비 안내 미제공 공고는 조회만으로 개인 준비 건·질문·서류·준비도를 생성하지 않는다. 공고 즐겨찾기는 기존 후순위 기능 상태를 유지한다.

### 1.6 발급 링크·캘린더·초기 완성 표현의 우선순위

- 공식 발급 링크는 해당 서류·발급 대상·발급 방식·공식 경로·확인일을 검수한 뒤 제공한다. 직접 신청 경로가 불안정하면 안정적인 공식 안내 페이지를 사용한다. 모든 링크의 확보를 기다리지 않고 확인한 것부터 연결한다.
- 발급 안내를 읽거나 외부 발급처로 이동하는 것은 서류 준비 완료가 아니다. 사용자가 실제 발급 여부를 기록한 뒤 서버 결과로 준비도(%)·집 단계를 갱신한다.
- 캘린더 파일 내보내기의 실제 기능은 아직 미확정이며 별도 검증 대상이다. 파일 생성·가져오기·외부 등록·알림 예약을 서로 구분하고 공고 변경의 자동 동기화를 약속하지 않는다.
- 준비도(%)·집 건축 표현의 초기 포함은 확정이다. 가중치·집 단계 매핑·구체적 배치는 검증으로 개선하되 상태별 목록만 제공하는 것으로 초기 완성을 대체하지 않는다. 필수 미확인·재확인 안내는 %·집과 함께 표시한다.

## 2. 정보 구조와 내비게이션

### 2.1 상위 메뉴

| 탭 | 사용자 질문 | 보여줄 내용 | 주요 이동 |
| --- | --- | --- | --- |
| 홈 | 지금 무엇을 해야 하나요? | 대표 준비 건, 준비도, 지금 할 일, 가까운 기한, 조건·서류 요약 | 관련 준비 항목으로 바로 이동 |
| 공고 | 어떤 공고를 살펴볼까요? | 지역·유형·마감 상태·키워드 검색, 공고 목록, 준비 안내 제공 상태, 공식 공고 상세 | 공고 상세 → 원문 확인 / 검수 완료 시 조건 확인 시작 |
| 내 준비 | 어디까지 준비했나요? | 준비 건 목록, 선택한 건의 조건·서류·일정·여정 | 조건, 서류, 일정 상세 |
| 가이드 | 이 표현과 절차는 무엇인가요? | 제도 설명, 용어, 발급 안내, 신청 절차, 공식 문의처 | 가이드 상세 또는 공식 자료 |
| 마이 | 내 계정과 기록을 어떻게 관리하나요? | 로그인 상태, 계정 요약, 준비 건 바로가기, 서비스 안내, 로그아웃 | 로그인 또는 관련 관리 화면 |

**탭 이름과 순서는 모든 루트 화면에서 고정한다.** `공고`를 `신청 일정`으로 바꾸거나 화면마다 `준비`와 `내 준비`를 혼용하지 않는다.

### 2.2 화면 계층

```text
홈
  └ 지금 할 일 → 해당 준비 건의 조건·서류·일정 상세
공고
  └ 공고 상세 → 로그인 필요 시 인증 → 조건 확인 → 결과 → 준비 건
내 준비
  └ 선택한 준비 건 개요
       ├ 조건 확인 / 조건 결과
       ├ 서류 체크리스트 → 서류 준비 안내
       ├ 신청 일정
       └ 신청 여정 / 후속 절차 기록
가이드
  └ 제도·용어·서류·절차·공식 문의처의 상세 콘텐츠
마이
  └ 로그인 / 계정 요약 / 준비 기록 바로가기 / 서비스 안내
```

### 2.3 내비게이션 표시 규칙

- 홈·공고 목록·내 준비·가이드·마이페이지에는 하단 내비게이션을 표시한다.
- 공고 상세에는 `공고`, 준비 건 개요·서류·일정에는 `내 준비`를 선택 상태로 표시한다.
- 조건 질문과 직후 결과 화면은 집중 작업 흐름으로 하단 내비게이션을 숨기고, 뒤로가기와 명확한 종료 동작을 제공한다.
- 공고 상세의 탭은 `핵심 요약 · 조건 · 제출서류 · 일정`이다. 공고 자체의 정보를 보여준다.
- 개인 준비 건의 탭은 `개요 · 조건 · 서류 · 일정`이다. 사용자의 답변과 준비 상태를 보여준다.
- 지역·유형·접수 상태 필터는 메뉴가 아니다. 개인 준비 건의 일정 탭과 구분한다.
- 뒤로가기는 진입 경로로 돌아간다. 공고 목록의 필터·페이지·스크롤 위치를 복원한다.
- 알림·설정 등 계획된 후순위 기능의 진입점을 표시하고 선택하면 준비 중 안내로 연결한다. 의미 없는 장식 아이콘이나 반응 없는 버튼은 두지 않는다. 세부 규칙은 7.1절을 따른다.

## 4. 집·벽돌·진행도 표현

### 4.1 일러스트 규칙

- 간결한 평면 벡터 형태의 집·벽돌·문서를 사용한다.
- 캐릭터, 사람, 얼굴이 달린 집, 마스코트를 사용하지 않는다.
- 완성된 벽돌은 벽돌색, 미완료 부분은 중립색·윤곽선으로 구분한다.
- 집은 홈의 대표 준비 건과 내 준비의 선택한 건에서 중심적으로 사용한다.
- 공고 목록에는 작은 유형 아이콘을 사용한다. 카드마다 큰 집·아파트 그림을 반복하지 않는다.
- 가이드는 제목 옆의 작은 집·문서 그림 정도로 제한한다. 큰 배너가 첫 안내 목록을 밀어내지 않게 한다.
- 조건 질문에는 작은 단계 표시만 둔다. 설명과 집이 반복되어 입력 영역을 밀어내지 않게 한다.
- 이미지 속 텍스트 대신 실제 UI 텍스트를 사용한다. 장식 이미지와 진행 상태의 대체 설명을 구분한다.

### 4.2 신청 여정

> 공고 확인 → 조건 확인 → 서류 준비 → 공식 신청 → 후속 절차

| 여정 | 집 표현 예시 | 완료 기록의 의미 |
| --- | --- | --- |
| 공고 확인 | 집터 | 주요 내용과 신청 기간을 확인한 기록 |
| 조건 확인 | 기초 | 필요한 질문·확인 작업을 수행한 기록 |
| 서류 준비 | 벽·지붕 | 해당 서류 준비 작업의 기록 |
| 공식 신청 | 문·창문 또는 작은 열쇠 아이콘 | 사용자가 공식 사이트에서 신청했다고 기록 |
| 후속 절차 | 완성 상태 옆 문서 확인 아이콘 | 해당 공고의 서류 제출·보완·결과 확인 작업 기록 |

집의 정확한 단계 전환은 서버의 진행 단계와 연결한다. 위 형태는 일러스트 설계 예시이며, 조건 질문을 끝냈다는 이유로 자격 충족을 표시하지 않는다. 집 완성이나 열쇠가 주택 확보·선정·실제 입주를 의미하지 않게 한다.

### 4.3 준비도와 개수의 구분

- 전체 준비도는 조건 확인·기한 확인·필수 작업 등을 반영한 서버 결과다. 가중치는 별도 업무 규칙으로 확정한다.
- `서류 3/5`는 현재 해당하는 서류 중 준비 완료로 기록한 개수다.
- 전체 준비도와 서류 개수는 분모·의미가 다르므로 별도 이름과 영역으로 표시한다.
- 서류만의 진행 바를 표시한다면 `3/5`와 같은 비율을 사용한다. 전체 준비도를 그대로 복사하지 않는다.
- 준비도 산정 결과가 없으면 `준비도 확인 중`으로 표시한다. 임의의 65%를 기본값으로 넣지 않는다.
- 조건부 서류의 해당 여부가 미확인이면 `추가 확인 1개`로 따로 표시한다. 필요 여부가 확정되기 전 완료 분모를 임의로 늘리거나 줄이지 않는다.
- 필수 미확인·재확인은 높은 준비도와 함께 보여준다. 진행 바만 보고 문제가 없다고 해석하지 않게 한다.
- 신청 기간 종료와 사용자의 준비 완료는 별도 상태다. 기간이 지났다고 작업 완료로 바꾸지 않는다.

준비도 가까이에 다음 문구를 표시한다.

> 준비도는 서비스에 기록한 준비 항목의 진행 상태입니다. 실제 신청 자격이나 선정 가능성을 의미하지 않습니다.

일러스트 변화는 저장 성공 후 짧게 제공한다. 출석 보상, 랭킹, 집 퇴화, 실패 벌점은 사용하지 않는다. 동작 줄이기 설정에서는 정적인 결과만 표시한다.

## 5. 조건·서류·일정 상태 체계

### 5.1 조건 안내

| 상태 | 표시 예시 | 의미 / 다음 행동 |
| --- | --- | --- |
| 입력 기준 충족 | 체크 + `입력 기준 충족` | 입력한 내용과 해당 명시 조건이 맞음. 공식 근거 확인 가능 |
| 불일치 가능 | 주의 아이콘 + `불일치 가능` | 해당 조건과 맞지 않을 가능성. 답변 수정·원문 확인 |
| 추가 확인 필요 | 물음표 + `추가 확인 필요` | 모름, 정보 부족, 예외 조건 등. 확인 질문으로 이동 |
| 기관 문의 권장 | 전화 아이콘 + `기관 문의 권장` | 서비스 안내만으로 해석하기 어려운 예외. 공식 문의처 안내 |

`확인 가능`은 원문을 볼 수 있다는 뜻과 혼동될 수 있으므로 사용자 화면에서는 `입력 기준 충족`처럼 의미를 구체화한다. 이는 기존 상태의 표시 문구를 정돈한 것이며 최종 자격 판정이 아니다. 전체 결과 제목은 `내 조건 확인 결과`로 하고 `신청 가능`, `적합도`, `당첨 가능성`은 사용하지 않는다.

질문을 완료한 개수와 충족한 조건 개수도 구분한다. `질문 6/7 응답`을 `조건 6/7 충족`으로 표시하지 않는다.

| 미확인 | 중립 아이콘·문구 | 필요 여부와 안내 확인 |
| 발급 필요 | 문서 아이콘·문구 | 발급 안내 보기 |
| 준비 중 | 진행 아이콘·문구 | 메모·준비 상태 수정 |
| 준비 완료 | 체크·문구 | 사용자 기록 유지, 필요하면 되돌리기 |
| 재확인 | 주의 아이콘·문구 | 변경된 공고 근거와 영향 확인 |

서류의 **필요 여부**(`공통 필수 / 해당 조건부 / 해당 여부 미확인 / 해당 없음`)와 **준비 상태**를 별도 속성으로 둔다. `조건부`를 준비 완료 여부와 같은 상태 배지로 취급하지 않는다.

### 5.3 일정

- 공식 일정: 접수 시작·마감, 대상자 발표, 서류 제출, 보완, 결과 확인 등 공고가 제공하는 단계.
- 사용자 기록: 신청함, 제출함, 결과를 확인함 등 사용자가 직접 남긴 완료 상태.
- 날짜가 지났다는 이유로 사용자가 신청했다고 표시하지 않는다.
- 기한은 단계명·날짜·시간을 함께 표시한다. 시간이 명시되지 않은 날짜에는 `23:59`를 임의로 붙이지 않는다.
- 확정일, 예정일, 추후 공지를 구분한다. 수정 공고로 바뀐 일정에는 변경 표시와 근거를 제공한다.
- 실제 시각은 한국 시간대 `Asia/Seoul`로 표시한다. 날짜만 있는 값은 시각과 구분한다.
- 서류 제출 대상 여부를 아직 모르면 `대상자 여부 확인 필요`를 먼저 표시한다.

### H01. 홈

**목적:** 사용자가 다음 준비 행동과 가까운 기한을 빠르게 찾는다.

**위에서 아래로 배치한다.**

1. `집으로`와 간결한 화면 설명. 마이 바로가기.
2. 대표 준비 건: 공고명, 기관·지역, 현재 단계, 이름이 붙은 기한, 준비도, 작은 집.
3. **지금 할 일:** 한 가지 핵심 행동, 선정 이유, 관련 기한, `준비 방법 보기`.
4. 여정 5단계의 축약 표시.
5. 조건 응답·서류 준비·다음 일정 요약. 각 상세로 이동.
6. 하단 내비게이션.

- 대표 건 선택 기준은 마지막에 열어본 진행 중 준비 건을 우선하는 설계안이다. 여러 건이면 명시적인 전환 동작을 둔다.
- 지금 할 일의 우선순위는 서버가 제공한다. 변경 영향·필수 미확인·기한 등 이유를 짧게 보여준다.
- 비회원에게 개인 준비도와 가짜 준비 건을 보여주지 않는다. `공고 둘러보기`를 주요 행동으로 제공한다.
- 로그인했으나 준비 건이 없으면 `첫 신청 준비를 시작해 보세요.`와 공고 진입을 제공한다.
- 수정 공고 영향이 있으면 대표 건에 `재확인 필요`와 관련 항목으로 가는 동작을 둔다. 준비 안내가 변경 검토 중이면 과거 기록의 기준 버전을 표시하고 미검수 최신 규칙을 지금 할 일·준비도에 적용하지 않는다.
- 상단 알림 아이콘은 선택할 수 있게 구현하고 준비 중 안내를 표시한다. 실제 읽지 않은 알림이 없으면 숫자나 빨간 점을 붙이지 않는다.
- 홈의 집·준비도는 요약이다. 상세 목록과 긴 발급 설명을 모두 펼쳐 넣지 않는다.

**수용 기준:** 홈에서 한 번의 선택으로 지금 할 일의 안내에 도달한다. 기한이 신청 마감인지 서류 제출 마감인지 구분한다.

### N01. 공고 목록

**목적:** 기본 정보가 검증·공개된 공고를 검색하고 원문을 확인하며, 준비 안내 제공 여부를 구분해 상세로 진입한다.

**구성:** `공고 찾기` → 검색 입력 → 지역·지원 유형·접수 상태 필터 → 적용한 필터 → 결과 수·정렬 → 목록 → 페이지 이동.

- 설명: `청년 주거지원 공고를 찾아보세요.`
- 카드: 공고명, 기관, 지역·유형, 공식 접수 상태, 단계가 명시된 신청 기간, 준비 안내 제공 상태, 상세 진입. `접수 중`과 `준비 안내 검수 중`을 같은 상태로 표현하지 않는다.
- 지역·유형·상태 간에는 AND, 한 필터 안의 복수 값은 OR로 연결한다.
- 적용한 필터와 결과 페이지를 URL에 유지한다. 비어 있는 결과도 정상 화면으로 처리한다.
- 초기 필터 선택값은 실제 공개 데이터에서 제공한다. 확인하지 않은 기관·유형을 시연용으로 추가하지 않는다.
- 카드 전체 또는 제목을 상세 진입 대상으로 하고 카드마다 진한 벽돌색 버튼을 반복하지 않는다.
- 개인 정보를 이용한 추천 순위·적합도·신청 가능 공고 수를 표시하지 않는다.
- 즐겨찾기 아이콘은 표시하고, 실제 저장 기능을 연결하기 전에는 선택 시 준비 중 안내를 제공한다. 아이콘을 선택됨으로 바꾸거나 저장 완료 메시지를 표시하지 않는다. 핵심 행동은 공고 상세·원문 확인이며 준비 안내 검수·공개 완료 공고에만 `준비 시작`을 연결한다.
- 기본 정렬·동률 처리는 API 설계에서 확정한다. 목업의 임박순을 확정된 서버 계약으로 간주하지 않는다.
- 결과 없음: 적용 필터를 유지하고 `검색 조건 바꾸기` 또는 `필터 초기화`를 제공한다.

**수용 기준:** 새로고침과 뒤로가기 후 검색 조건이 유지되고, 공식 접수 상태와 준비 안내 제공 상태를 색 없이도 구분한다. 기본 정보가 공개된 검수 중·미제공 공고도 조회되며 미검수 조건 안내는 노출되지 않는다.

### N02. 공고 상세

**목적:** 공고의 검증된 기본 정보·공식 원문을 확인하고, 준비 규칙이 검수·공개된 경우 개인별 준비를 시작한다.

**구성:** 뒤로가기·제목 → 기관·공고명·공고일·지역·지원 유형 → 검증된 공식 신청 기간·원문·첨부 → 준비 안내 제공 상태와 기본 정보 확인일 → 제공 상태에 따른 내부 탭·본문 → 가능한 주요 행동.

| 상세 탭 | 내용 |
| --- | --- |
| 핵심 요약 | 검증된 기본 정보와 공식 기간·원문·첨부, 준비 안내 상태. 조건 해석·주의사항 요약은 준비 안내 검수 완료 시 표시 |
| 조건 | 준비 규칙 검수·공개 완료 시 신청 자격·선정 순위·예외 설명과 원문 근거 제공 |
| 제출서류 | 준비 규칙 검수·공개 완료 시 공통·조건부 서류, 제출 단계·근거 제공 |
| 일정 | 기본 정보 검증을 마친 공식 신청 기간은 표시. 세부 준비 단계·서류 기한은 해당 안내 검수 완료 후 표시. 개인 완료 기록은 표시하지 않음 |

- 준비 안내 제공 중이며 서버가 신규 시작 가능으로 응답하면 주요 버튼은 `내 조건 확인하기`다. 저장할 개인 준비 흐름이므로 비회원이면 먼저 로그인한다. 로그인 복귀 후에도 현재 제공 상태를 재확인한다.
- 준비 안내 제공 중의 보조 동작은 `공식 공고 보기`와 첨부 문서 열기다. `준비 시작`과 경쟁하는 진한 버튼을 반복하지 않는다.
- 준비 안내 검수 중·미제공이면 주요 행동을 `공식 공고 보기`로 바꾸고 상태별 설명을 제공한다. 준비 시작·조건 질문·개인별 서류 목록은 연결하지 않으며 검수 완료 시점이나 지원 예정일을 약속하지 않는다.
- 미검수 조건·서류·예외 본문은 표시하지 않는다. 기존 조건·제출서류 탭 위치에는 준비 안내 상태 설명과 원문 경로를 제공해 내용이 없는 이유를 설명한다. 기본 정보 검증 완료를 개인별 안내 검증 완료처럼 표시하지 않는다.
- 이미 준비 건이 있고 해당 안내를 계속 사용할 수 있으면 `준비 계속하기`로 연결한다. 변경 검토 중이면 `기존 준비 기록 보기`로 연결해 기준 버전·영향 항목을 표시하고 미검수 최신 규칙에 따른 행동은 제한한다. 같은 공고에 중복 준비 건을 의도 없이 만들지 않는다.
- 근거는 `공고문 4쪽 · 신청 자격`처럼 문서와 위치를 함께 표시한다.
- 원문 링크가 정확한 위치로 열리지 않으면 공식 문서를 열고 찾아야 할 페이지·제목을 안내한다.
- 기본 정보 버전·확인일과 준비 안내 기준 버전·확인일·변경 여부를 구분해 확인 가능한 위치에 둔다. 기본 정보가 최신 버전이고 개인 준비 기록은 과거 버전이면 차이와 변경 검토 상태를 설명한다.
- 모집 종료 후에도 과거 공고와 기록은 읽을 수 있게 하되 종료 상태와 당시 일정임을 명시한다.

**수용 기준:** 기본 정보만 공개된 공고에서도 원문을 확인할 수 있다. 검수된 안내에서 원문·신청 자격·선정 순위를 구분하며, 미검수 준비 규칙과 신규 개인 준비 기능은 제공하지 않는다. 조건부 서류를 모두에게 필수로 안내하지 않는다.

### C01. 조건 확인

**목적:** 검수·공개된 준비 규칙의 조건을 답할 수 있는 질문으로 나누고 모르는 항목을 보존한다.

- 직접 경로 진입과 저장·결과 요청 시 서버가 준비 규칙의 제공 상태·버전·사용자 권한을 확인한다. 미제공·검수 중이면 신규 질문을 만들지 않고 공고 상세·원문 확인으로 연결한다. 기존 기록은 과거 기준 버전으로 보존하며 변경 검토 중의 영향받는 최신 안내를 생성하지 않는다.

**구성:** 뒤로가기·`조건 확인` → 선택 공고 → 질문 단계 → 질문·이유·선택지 → 공식 근거 → 이전·저장 후 다음 단계.

- 질문 묶음 예시: 기본정보 → 거주지 → 소득 → 자산 → 기타. 공고 규칙에 따라 질문과 단계 수를 바꾼다.
- `2/5`는 질문 단계다. 전체 준비도와 별개이며 같은 진행 바를 재사용하지 않는다.
- 각 질문에 왜 필요한지 설명한다. 거주지는 생활상 거주지·주민등록상 거주지·공고 기준일을 구분한다.
- 단일 선택은 세로 Radio 목록, 복수 선택은 Checkbox 계열로 설계한다.
- **첫 질문의 실제 사용자 답변은 기본 선택하지 않는다.** 기존 저장 답변만 복원한다. `잘 모르겠어요`를 지원한다.
- 미입력과 모름은 서로 다른 상태다. 모름을 선택해도 진행할 수 있고 결과에서 추가 확인으로 남긴다.
- 필요한 범위·사실만 묻고 주민등록번호·증빙 원본·불필요한 정확한 소득액을 요구하지 않는다.
- `이 기기에만 저장됩니다`라는 문구를 쓰지 않는다. 현재 정책에 맞게 `답변과 준비 상태를 계정에 저장합니다`라고 안내한다.
- 단계 이동 시 저장 성공 후 다음 단계로 간다. 실패하면 답변을 유지하고 재시도를 제공한다.
- 선택 즉시 다음으로 넘어가지 않는다. 검토할 기회를 준다.
- 마지막 버튼은 `조건 결과 보기`. 완료 여부는 답변 저장과 결과 요청 성공을 기준으로 처리한다.

**수용 기준:** 모름·미입력이 충족으로 처리되지 않고, 뒤로가기·재진입 시 저장한 응답이 복원된다.

### C02. 조건 확인 결과

**목적:** 확인된 항목과 아직 해결해야 할 질문을 구분하고 준비 목록으로 연결한다.

**구성:** `내 조건 확인 결과` → 선택 공고·기준 버전 → 상태별 개수 → 조건 카드 → 추가 확인 행동 → 서류 요약 → `내 준비 목록 보기`.

- 첫 요약은 `입력 기준 충족 3개 · 추가 확인 2개`처럼 상태별 개수로 표현한다.
- 조건 카드에는 입력 요약, 해당 조건, 상태, 이유, 근거, 답변 수정 동작을 연결한다.
- 불일치 가능·추가 확인·기관 문의 항목은 다음 행동과 함께 우선 노출한다.
- 기관 문의 권장은 공고의 공식 연락처와 확인해야 할 질문을 제공한다. 서비스 내 상담을 약속하지 않는다.
- 조건 결과에 적합도 백분율이나 큰 완성 집을 넣지 않는다. 질문 완료와 자격 충족을 혼동시키지 않는다.
- 서류 요약은 `확인된 제출서류`와 `해당 여부 추가 확인`을 나눈다.
- 일부 답변을 모르는 상태에서도 준비 건을 유지한다. 미확인 항목을 숨기거나 완료 처리하지 않는다.
- 입력 기준 충족 상태에도 최종 심사·자격 확정과 구분하는 안내를 제공한다.

**수용 기준:** 사용자가 추가 확인할 항목과 그 이유를 설명하고, 다음 행동을 선택할 수 있다.

### P01. 내 준비

**목적:** 준비 건을 선택하고 조건·서류·일정·여정을 한곳에서 관리한다.

- `/preparations`: 진행 중 준비 건 목록과 사용자가 완료로 기록한 건을 구분한다.
- 준비 건이 하나면 목록에서 개요로 바로 이어지는 구성을 허용하되 다른 준비 건으로 돌아가는 진입점을 유지한다.
- `/preparations/:preparationId`: 공고명·기관·현재 단계 → 이름 있는 기한 → 준비도와 작은 집 → 지금 할 일 → 조건·서류·일정 바로가기 → 여정·후속 기록.
- 홈은 지금 할 일의 요약, 내 준비는 준비 건의 관리 중심으로 역할을 구분한다.
- 집을 포함한 큰 요약 카드는 한 번만 사용한다. 같은 화면의 다른 카드에 완성 집을 반복하지 않는다.
- 조건 요약은 `질문 6/7 응답`과 `추가 확인 1개`, 서류는 `3/5 준비 완료`처럼 의미를 명시한다.
- 공식 신청 단계에는 `공식 신청 사이트 열기`와 별도의 `신청 여부 기록` 동작을 둔다.
- 외부 링크를 눌렀다는 이유로 신청 완료를 기록하지 않는다.
- 후속 절차는 해당 공고에 존재하는 실제 단계만 표시한다.
- 기본 정보가 최신이고 기존 준비 건이 과거 버전이면 각각의 기준을 표시한다. 변경 검토 중에는 기존 답변·서류 상태를 보존하고 검수 완료 전 새 조건 충족·새 준비도로 바꾸지 않는다.
- 완료 기록과 모집 종료를 구분한다. 준비 기록 보관·정리 메뉴를 먼저 설계하는 경우 정책과 실제 기능을 확정하기 전에는 준비 중 안내로 연결하며 기록을 변경하지 않는다.

**수용 기준:** 다른 공고의 진행도·기한·서류가 섞이지 않고, 선택한 준비 건이 모든 하위 화면에서 드러난다.

### P02. 서류 체크리스트

**목적:** 개인별 필요 서류와 준비 방법을 확인하고 상태를 기록한다.

**구성:** 공고명·제출 단계 → 개인 준비 내부 탭 → `필수 서류 5개 중 3개 준비 완료` → 공통 필수·해당 조건부 목록 → 해당 여부 미확인 → 서류 준비 안내.

서류 행의 기본 표시는 **서류명 · 필요 여부 · 준비 상태 · 상세 진입**이다. 펼친 안내에는 다음 정보를 제공한다.

| 정보 | 표시 원칙 |
| --- | --- |
| 왜 필요한가 | 해당 조건과 제출 단계 연결 |
| 발급 대상 | 본인·가구원 등 공고에 명시된 제출 대상 |
| 발급처 | 공식 발급기관 이름 |
| 발급 기준 | 공고 기준일·문서 종류·상세 여부 등 원문에 있는 조건 |
| 제출 방법 | 온라인·우편·방문 등 공고별 실제 절차 |
| 형식·용량 | 원문이 요구하는 경우에만 표시 |
| 기한 | 이 서류가 필요한 단계의 기한 |
| 공식 근거 | 문서·페이지·항목·버전 |
| 준비 기록 | 상태 선택, 메모, 저장 결과 |

- 목록의 펼침은 Accordion을 활용한다. 여러 항목 비교를 위해 필요하면 복수 펼침을 허용한다.
- 한 항목만 접고 펼치는 독립 상세는 Accordion 목록과 구분한다.
- `소득 증빙서류`는 가능한 상위 분류다. 모든 사용자에게 소득금액증명·원천징수영수증·자격득실확인서가 모두 필요하다고 일괄 안내하지 않는다.
- `공고일 이후 발급`, `주민등록번호 전체 표시`, `PDF`, `3MB` 같은 조건을 전 공고의 기본값으로 사용하지 않는다.
- 준비 완료는 사용자가 해당 서류의 상태를 기록한 것이다. 서비스의 원본 검증·접수 완료 의미가 아니다.
- 행의 펼침과 상태 변경은 별도 동작이다. 체크 영역 선택으로 안내만 열리거나, 펼침 선택으로 완료가 바뀌지 않게 한다.
- 전체 목록 하단에 모호한 `준비 완료로 표시` 버튼을 두지 않는다. 선택한 서류 상세에서 `이 서류 준비 완료로 기록` 등 대상을 명시한다.
- 수정 공고로 영향을 받은 서류는 이전 완료 기록을 보존하면서 `재확인`을 표시한다. 자동으로 새 조건을 충족했다고 보지 않는다.
- 사용자 서류 원본 업로드·다운로드·파일함은 제공하지 않는다.

공식 발급처 **안내와 검증된 링크 연결을 초기 구현에 포함**한다. `발급 방법 보기`는 서비스 내 안내, `공식 발급처 열기`는 확인된 공식 경로로 연결하며 기관명·외부 이동을 명시한다. 이동 전 서류 종류·발급 대상·기준 등 검수된 확인사항을 보여준다. 링크가 미검증·오류이면 `발급 경로 확인 필요` 또는 `방문 발급 안내`처럼 해당 상황을 설명하고 발급 방법·공식 기관 확인 경로를 제공한다. 링크 미확보를 기능 전체의 후순위 `준비 중`으로 표현하지 않으며 임의 주소나 개인 서류 내용을 전송하지 않는다. 외부 이동만으로 준비 완료·준비도·집 단계를 바꾸지 않는다.

**수용 기준:** 공통·조건부·해당 여부 미확인이 구분되고 개별 상태 변경과 목록 요약이 저장 후 일치한다. 검증된 공식 링크는 실제 경로로 연결되며 미검증/오류 경로는 대체 안내를 제공한다. 외부 이동 자체는 준비 완료가 아니다.

### P03. 신청 일정

**목적:** 공식 기한과 사용자의 완료 기록을 구분하고 다음 일정에 대응한다.

**구성:** 선택 공고 → 다음 중요한 일정 → 공식 일정 타임라인 → 사용자의 신청·제출 기록 → 해당 단계의 남은 작업 → 공식 사이트 열기.

- 진입: 내 준비의 `일정`, 홈의 다음 일정. 하단 탭은 `내 준비`다.
- 초기 화면은 타임라인·목록으로 제공한다. 캘린더 형식은 목록을 가리거나 별도 전역 탭을 만들지 않는다.
- 일정 행: 단계명, 날짜·시간, 예정 여부, 출처, 관련 작업, 사용자의 기록 여부.
- 공식 일정이 지나면 `일정 경과`로 표시한다. 사용자 체크와 같은 초록 완료 표시를 자동 부여하지 않는다.
- 대상자 발표는 `대상자 여부 확인하기`로 공식 경로에 연결한다. 개인 대상자 상태는 직접 기록한다.
- 제출 준비 요약에는 해당 단계의 서류만 포함한다.
- 외부 신청 버튼에는 기관명과 외부 이동 표시를 제공한다. 돌아온 사용자에게는 완료 여부를 직접 기록할 선택지를 제공한다.
- `알림 설정`은 후순위 진입점으로 준비 중 안내를 제공한다. `캘린더 파일 내보내기`는 푸시와 분리한 검증 대상으로 관리하고 실제 범위 확정 전에는 준비 중 안내를 제공한다. 이 상태에서 실제 예약·설정 저장·파일 생성·외부 등록 완료를 표시하지 않는다.
- 캘린더 평가에서는 사용자가 선택한 검증 일정의 .ics 생성·가져오기 흐름을 확인한다. 기본 정보에서 검증된 공식 신청 일정과 준비 규칙 검수가 필요한 개인별 서류 기한을 구분한다. 날짜만 있는 일정에 마감 시각을 추측해 넣지 않는다.
- 실제 내보내기 채택 시 단계명·날짜/시각·공식 원문·기준 버전·생성 시점을 포함하고 개인 답변·민감정보는 제외한다. 파일 생성 성공 메시지는 `일정 파일을 내려받았어요`이며 외부 등록·알림 설정 완료로 표현하지 않는다. 자동 동기화되지 않는 복사본임과 공고 수정 후 일정 재확인 필요를 안내한다. 대상 기기의 다운로드·가져오기·중복/갱신 동작 검증 결과로 기능 범위를 확정한다.
- 마감일 변경이 있으면 이전·새 기한과 공식 변경 근거를 안내한다.

**수용 기준:** 사용자가 날짜 경과와 신청 완료를 구분하고, 다음 기한에 필요한 작업으로 이동한다.

### G01. 가이드

**목적:** 신청을 막는 용어·절차·서류 질문을 공식 자료 기반으로 설명한다.

**구성:** `가이드` → 주제 분류 → 자주 확인하는 질문 → 상세 안내 → 공식 자료·문의처.

| 분류 | 내용 예시 |
| --- | --- |
| 지원제도 | 초기 지원 유형의 목적·절차·기관 역할 |
| 조건과 용어 | 신청 자격과 선정 순위, 가구원 범위, 기준일 |
| 서류 발급 안내 | 서류의 용도, 발급기관, 공고별로 확인할 사항 |
| 신청 절차 | 공식 신청·서류 제출·보완·결과 확인 |
| 공식 문의처 | 공고별 문의기관·연락처·확인할 질문 |

- 제도별 차이를 설명하고 일반 안내를 특정 공고의 확정 조건처럼 보여주지 않는다.
- 공고 상세·조건 질문·서류 안내에서 관련 가이드로 바로 연결하고, 돌아올 때 원래 맥락을 유지한다.
- 가이드 상세에는 적용 대상, 기준 시점, 공식 출처를 제공한다.
- FAQ는 Accordion으로 설계한다. 답변 내부를 별도 작은 스크롤 영역으로 만들지 않는다.
- 기존 목업의 가이드 검색 진입점도 표시한다. 검색 기능 연결 전에는 입력값을 받는 검색창 대신 `가이드 검색 · 준비 중` 버튼을 두고 선택 시 준비 중 안내를 제공한다. 주제·FAQ 탐색은 실제로 동작한다.
- 별도 주거정보 탭이나 부동산 매물 추천·시세 정보·지역 커뮤니티로 확대하지 않는다.

**수용 기준:** 일반 설명과 선택 공고의 조건을 구분하고 관련 공식 근거를 찾을 수 있다.

### M01. 마이페이지

**목적:** 계정 상태와 개인 기록의 진입점을 제공한다.

**구성:** `마이` → 계정 요약 → 내 준비 바로가기 → 서비스 이용 안내 → 로그아웃.

- 프로필은 계정 이름 또는 이니셜·단순 계정 아이콘으로 표현한다. 캐릭터 프로필·옷장·레벨을 넣지 않는다.
- 비회원에게는 로그인 동작과 공개 공고 진입을 제공한다.
- 로그인 수단은 이메일·Google·카카오를 지원한다. 제공자별 브랜딩은 실제 구현 시 공식 지침으로 확인한다.
- 서비스가 기관의 공식 신청 시스템과 별개라는 점, 준비도와 사용자 기록의 의미를 안내한다.
- 관심 공고·알림 설정 등 계획된 후순위 메뉴는 `준비 중` 배지와 함께 노출하고 공통 안내로 연결한다. 계정 연결·탈퇴 등 정책 미확정 메뉴를 설계하는 경우에도 안내만 표시하며 계정이나 데이터를 변경하지 않는다. 문의 내역처럼 별도 서비스 제공 여부가 정해지지 않은 새 기능은 자동으로 추가하지 않는다.
- 로그아웃 시 개인 데이터가 다음 사용자에게 남아 보이지 않도록 로그인 상태와 개인 화면을 갱신한다.

**수용 기준:** 비회원과 회원 상태가 명확하고, 핵심 관리 동작은 실제 화면으로, 후순위 메뉴는 준비 중 안내로 연결되며 개인 준비 기록에 접근할 수 있다.

## 7. 보조 화면과 공통 인터랙션

다음은 핵심 10개 화면을 연결하는 필요한 보조 화면·상태다. 모두 별도 최상위 탭으로 만들지 않는다.

| 보조 요소 | 진입 / 목적 | 표시·동작 |
| --- | --- | --- |
| 로그인·회원가입 | 개인 준비 시작·마이 | 이메일·비밀번호·Google·카카오 진입. 인증 후 원래 공고·준비 화면 복귀 |
| 공고 필터 선택 | 공고 목록 | 모바일 선택 시트. 적용·초기화·닫기, 기존 적용값 유지 |
| 서류 준비 안내 | 서류 행·지금 할 일 | 서류명·공고·발급 방법·근거·개별 상태 기록 |
| 근거 보기 | 조건·서류·일정 | 공식 문서, 페이지·문단, 버전·확인일, 원문 열기 |
| 가이드 상세 | FAQ·관련 도움말 | 적용 범위·출처·기준 시점, 원래 화면 복귀 |
| 변경 공고 안내 | 홈·내 준비·항목 | 변경 항목·새 근거·재확인 행동, 과거 기록 유지 |
| 후속 절차 기록 | 내 준비·일정 | 사용자 확인 여부·메모·기록 시점. 공식 조회와 구분 |
| 후순위 기능 안내 | 알림·캘린더 등 진입점 | 기능명과 준비 중 메시지, 현재 사용할 수 있는 대체 경로, 닫기 |
| 관리자 화면 | 별도 관리자 경로 | 수집 실행·실패, 공고 정보·준비 안내 동시 검수, 영역별 통과·보완 사유·공개 결정, 근거·버전·확인일·변경 영향 관리 |

관리자 화면은 일반 하단 내비게이션에 넣지 않는다. 작업용 표와 공고·원문 버전별 하나의 상세 검수 화면에서 기본 정보와 준비 안내를 함께 대조한다. 공통 출처·기간은 같은 근거를 사용하고 영역별 검수 결과·보완 사유·미지원 여부·검토자·확인일·공개 이력을 남긴다. 기본 정보 실패 시 양쪽 공개를 차단하고 기본 정보 통과·준비 안내 보완 시 목록만 공개할 수 있어야 한다. 관리자 역할을 서버에서 검사하며 자동 수집 성공을 검수·공개 완료로 표시하지 않는다.

저장이 필요한 필터·질문·상태 동작의 버튼에는 처리 중 상태를 제공하고 중복 제출을 막는다. 저장 결과가 실패했으면 완료 표시·준비도·집 단계가 먼저 바뀌지 않게 한다.

### 7.1 후순위 기능을 화면에 먼저 반영하는 규칙 — 사용자 결정

후순위 기능도 **메뉴·버튼·아이콘과 안내 동작까지 구현**한다. 실제 API·외부 연동·데이터 저장·발송·예약은 구현 우선순위에 따라 이후 연결한다. 화면 시연에서 핵심 기능과 후순위 기능의 상태가 구분되어야 한다.

| 기능 | 화면 위치 | 선택 시 안내 / 현재 대체 경로 |
| --- | --- | --- |
| 알림 확인 | 홈·내 준비 등 상단 알림 아이콘 | 알림 기능 준비 중 / 신청 일정 보기 |
| 기한 알림 설정 | 신청 일정·마이 | 기한 알림 준비 중 / 서비스 내 기한 확인 |
| 캘린더 파일 내보내기 | 신청 일정 | 파일 내보내기 준비 중 / 일정 목록 확인. 푸시와 별도 검증 후 범위 확정 |
| 관심 공고 저장·조회 | 공고 카드·상세·마이 | 관심 공고 기능 준비 중 / 현재 공고 보기 |
| 공고 비교 | 공고 목록·상세의 보조 동작 | 비교 기능 준비 중 / 개별 공고 상세 확인 |
| 수정 공고 전후 비교 | 변경 안내·공고 상세 | 비교 화면 준비 중 / 현재 공식 근거와 재확인 항목 보기 |
| 가이드 검색 | 가이드 | 검색 기능 준비 중 / 주제·FAQ 탐색 |
| 완료 여정 보관·경험 재사용 | 내 준비·마이의 후순위 메뉴 | 기록 관리 기능 준비 중 / 기존 준비 건 확인 |

위 항목은 현재 기획·목업에 있는 후순위·별도 평가 진입점의 화면 배치 기준이다. 검증된 공식 발급처 열기는 초기 기능이므로 이 표와 공통 준비 중 안내를 적용하지 않는다. 다국어·계정 관리 등 추가 후순위 화면을 설계할 때도 같은 안내 규칙을 따른다. 모든 버튼을 한 화면에 몰아넣지 않고 각 기능이 필요한 맥락의 보조 영역에 배치한다.

**공통 안내 다이얼로그**

- 제목: `아직 준비 중인 기능입니다`
- 본문 예시: `캘린더 파일 내보내기는 아직 제공하지 않아요. 현재는 신청 일정 화면에서 기한을 확인해 주세요.`
- 주요 버튼: `확인` — 안내를 닫고 원래 화면을 유지한다.
- 대체 경로가 있다면 보조 버튼: `신청 일정 보기` 등 실제로 동작하는 화면으로 연결한다.
- 출시일·지원 예정 기관·알림 발송 시점을 확정하지 않았다면 임의의 약속을 쓰지 않는다.

**상호작용 기준**

1. 메뉴·텍스트 버튼에는 가능하면 `준비 중` 배지를 표시한다. 라벨이 없는 아이콘에는 `알림 — 준비 중`처럼 접근 가능한 이름을 제공하고 선택 시 안내한다.
2. 준비 중 진입점은 클릭·터치·키보드로 선택 가능하게 둔다. disabled 버튼으로 만들어 안내를 볼 수 없게 하지 않는다.
3. 잠금·경고·오류처럼 표현하지 않고 중립적인 서비스 안내로 보여준다.
4. 클릭해도 실제 설정값·즐겨찾기·계정·캘린더·알림 예약·준비 상태를 바꾸지 않는다. 성공 토스트·완료 체크·가짜 알림 개수를 만들지 않는다.
5. 준비 중 안내를 보기 위해 로그인부터 요구하지 않는다. 해당 기능이 구현된 뒤 실제 기능의 인증 정책을 적용한다.
6. 확인·닫기·바깥 영역 선택·Escape로 닫을 수 있도록 설계하고, 닫은 뒤 원래 버튼으로 포커스를 돌린다.
7. 같은 기능의 진입점은 동일한 기능명과 메시지를 사용한다. 새로고침 후에도 가짜 선택 상태가 남지 않게 한다.
8. 실제 기능 연결 시 준비 중 배지·안내를 제거하고 정상·오류·저장 결과 상태로 전환한다.

**수용 기준:** 모든 계획된 후순위 진입점에 반응이 있고, 사용자가 아직 제공되지 않는 기능임을 이해하며 안내 전후로 실제 사용자 데이터가 바뀌지 않는다.

## 8. 공통 상태와 사용자 피드백

| 상태 | 화면 기준 |

| 변경 공고 | 영향 항목·버전·재확인 안내. 과거 완료를 새 조건 충족으로 바꾸지 않음 |
| 임박·마감 | 공고별 기준으로 표시. 날짜·시간·단계명과 신청 완료 기록은 분리 |
| 후순위 기능 준비 중 | 클릭 가능한 진입점 → 공통 안내 → 원래 화면 또는 실제 대체 경로. 데이터 변경·성공 메시지 없음 |

확인 모달은 실제로 저장하지 않은 수정 내용이 사라지거나 중요한 기록을 변경하는 경우에 사용한다. 저장한 질문에서 단순 뒤로가기를 할 때 반복 경고를 띄우지 않는다.

## 9. 화면에 필요한 데이터

이 표는 화면에 필요한 정보의 개념 목록이다. API DTO·필드명을 확정한 명세가 아니다.

| 정보 영역 | 필요한 값 | 표시 원칙 |
| --- | --- | --- |
| 공고 | 식별자, 기관, 제목, 지역·유형, 기본 정보 검증·공개 상태·버전·확인일, 공고일, 공식 신청 기간, 원문·첨부 | 기본 정보 검증·공개 완료 공고 표시. 미검수 조건 요약은 제외 |
| 준비 안내 제공 | 검수·제공 상태, 기준 버전·확인일, 신규 준비 시작 가능 여부, 사용자용 안내 사유 | 공고 기본 정보와 구분. 내부 초안·검수 코멘트는 노출하지 않고 서버 상태로 화면 분기 |
| 근거 | 문서명, 위치, 원문 URL, 공고 버전, 확인일 | 값이 없으면 근거 확보 상태로 처리하고 추측 금지 |
| 질문 | 질문 ID, 단계, 문구, 선택지, 질문 이유, 조건 기준·공식 근거 | 해당 준비 규칙이 검수·공개되고 접근 허용된 경우 제공 |
| 조건 결과 | 상태, 입력 요약, 판단 근거, 부족 정보·다음 행동 | UI의 임의 자격 판정 금지 |
| 서류 | 이름, 필요 여부·조건, 대상, 발급처·검증된 공식 URL·링크 상태·확인일·발급 방식, 기준, 제출 단계, 기한 | 필요 여부·준비 상태·링크 제공 여부 분리. 확인된 공식 URL만 실제 이동 |
| 준비 건 | 사용자·공고·버전, 현재 단계, 답변, 서류 상태, 기록 | 공고·사용자·준비 건 맥락 유지 |
| 준비도·집 건축 | 서버의 준비도(%), 계산 기준 버전, 집 단계 매핑 기준, 필수 미확인·재확인 | 초기 완성에 함께 포함. 개수와 가중 진행률 구분, %·집·여정의 같은 준비 상태 사용 |
| 지금 할 일 | 대상 항목, 이유, 관련 기한, 행동·이동 대상 | 다음 행동 한 가지를 우선 |
| 일정 | 단계, 날짜 또는 실제 시각, 예정 여부, 출처, 변경 여부 | 날짜·시각·예정 구분 |
| 변경 영향 | 이전·현재 버전, 변경된 조건·서류·기한, 확인 기록 | 영향 항목의 재확인 유도 |

화면 설계용 예시 데이터는 `시연용 예시`라고 표시한다. 과거 공고의 기한을 현재 접수 중처럼 표현하지 않는다. 같은 준비 건을 표시하는 화면의 공고명·기관·버전·기한·개수는 같은 기준 데이터에 맞춘다. 공고 기본 상세는 검증된 최신 버전, 개인 기록은 과거 기준 버전을 표시할 수 있으며 이 차이를 숨기거나 최신 기한으로 과거 기록을 자동 덮어쓰지 않는다.

## 10. 접근성과 사용성 검토

- 탭·버튼·링크는 키보드로 접근하고 포커스 위치가 보이게 한다.
- 하단 탭은 아이콘과 라벨을 함께 제공한다. 활성 상태의 색과 선택 의미를 보조 기술에도 전달한다.
- SEED Bottom Navigation 기준에 따라 탭 아이콘을 Fill 스타일로 통일한다. 기존 목업의 Line/Fill 혼합은 새 시안에서 정리한다.
- 단일 질문 그룹에는 질문명과 선택값이 연결된다. 선택지의 전체 행을 터치할 수 있게 한다.
- 화면의 클릭 영역은 모바일에서 44px 이상을 프로젝트 목표로 검토하며 작은 근거 링크도 여유를 확보한다.
- 작은 회색 안내, 근거 링크, 비활성 상태까지 실제 대비를 확인한다.
- 화면 폭·글자 크기가 커지면 버튼을 세로로 전환하고 중요한 설명을 자르지 않는다.
- 준비도에는 읽을 수 있는 진행 값과 의미를 제공한다. 장식용 집은 중복 낭독을 피하고, 정보용 집은 텍스트로 동일 의미를 제공한다.
- 색·집 모양만으로 조건 상태, 필수 여부, 기한을 전달하지 않는다.
- 고정 요소는 안전 영역과 키보드를 고려하여 배치한다. 시스템 영역과 겹친 버튼이 없게 한다.
- 동작 줄이기 환경에서는 집 변화와 진행 애니메이션을 정적인 결과로 바꾼다.
- 폰트 확대 시 하단 탭에서 읽기 어려움이 생기는지 별도 확인한다. SEED 기본 동작을 그대로 사용했다고 검증 완료로 간주하지 않는다.

## 11. SEED Design 스킬 적용 지침

### 11.1 Codex에서 SEED Design 스킬 설치·사용하기

팀원 모두 Codex에서 `seed-design` 스킬을 사용한다. 아직 설치하지 않은 팀원은 다음 절차로 설치한다. 이미 Codex가 스킬을 인식하는 환경에서는 다시 설치하지 않아도 된다.

1. Node.js와 npm이 설치된 환경에서 프로젝트 폴더를 Codex로 연다.
2. Codex의 터미널에서 **프로젝트 루트**를 작업 위치로 두고 다음 명령을 실행한다. Codex 채팅에 아래 명령으로 스킬을 설치해 달라고 요청해도 된다.

   ```shell
   npx skills add https://github.com/daangn/seed-design --skill seed-design --agent codex --copy
   ```

3. 설치 후 프로젝트의 `.agents/skills/seed-design/SKILL.md`와 참조 파일들이 함께 설치되었는지 확인한다. `--agent codex`는 Codex용 설치를 지정하고, `--copy`는 심볼릭 링크 대신 파일을 복사한다.
4. Codex에서 `seed-design` 스킬이 인식되는지 확인한다. 보이지 않으면 Codex를 재시작하고 프로젝트를 다시 연다.
5. 화면설계서를 첨부하거나 경로로 지정하고, **`$seed-design`을 명시하여** 설계·구현을 요청한다. 예: “`$seed-design`을 사용해 docs/design/screen-spec.md의 홈 화면을 설계해 줘.” 자세한 지시문은 11.6절을 사용한다.

설치 근거: [SEED Design 공식 스킬 설치 안내](https://seed-design.io/ai-integration/skill), [skills CLI의 Codex·복사 옵션 안내](https://github.com/vercel-labs/skills), [OpenAI의 스킬 인식·사용 안내](https://learn.chatgpt.com/docs/build-skills).

이 절차는 **Codex용 스킬 설치**이며 React 컴포넌트 라이브러리를 프로젝트에 설치하는 절차와는 별개다. 설치 후 프로젝트 루트의 `.agents/skills/seed-design/SKILL.md`를 읽고 적용한다. 단순히 당근과 비슷한 주황색 화면을 만드는 의미가 아니라, 공식 Foundations와 공통 컴포넌트의 구조·상태·사용 지침을 확인하여 화면에 대응하는 작업이다.

이번 문서는 **공통 컴포넌트 스펙·Foundations 기반 화면 설계**로 분류했다. 라이브러리 설치·테마 API 적용·코드 생성은 수행하지 않았다. 최신 기획의 구현 플랫폼은 React이며, 실제 코드 작성 단계에서는 스킬의 플랫폼 판별 절차와 React 문서를 이어서 적용한다.

### 11.2 적용 순서

1. 사용자 합의 사항과 본 화면 설계서를 먼저 확인한다.
2. [전체 문서 인덱스](https://seed-design.io/llms.txt)를 읽고 관련 Foundations·Components·Patterns 문서를 찾는다.
3. 인덱스가 제공한 실제 문서에서 컴포넌트 구조·상태·규칙을 확인한다. 기억으로 존재하지 않는 API나 토큰을 만들지 않는다.
4. 브랜드·표면·본문·상태 역할을 나누고 집으로의 다섯 확정 색상에 대응한다.
5. 아래 컴포넌트 매핑으로 10개 화면을 구성한다.
6. enabled·pressed·loading·disabled·selected·error 등 해당 상호작용 상태를 함께 설계한다.
7. 집·벽돌·여정·준비도는 제품 전용 요소로 설계한다. 같은 이름의 공식 컴포넌트가 있다고 가정하지 않는다.
8. 디자인 단계의 수치와 공식 컴포넌트의 실제 규격·토큰 대응을 기록한다.
9. 구현 요청에서는 대상 워크스페이스의 `seed-design.json.framework` 및 직접 의존성을 확인하고 [React 문서 인덱스](https://seed-design.io/react/llms.txt)를 읽는다. Lynx 문서를 React에 혼용하지 않는다.
10. 최종 화면에서 공식 근거·색상 대비·기한·상태·다음 행동을 점검한다.

브랜드 팔레트와 프로젝트 토큰 이름은 서비스 설계값이다. 설치한 SEED 버전의 공개 토큰·테마 지원을 확인하기 전에 임의의 SEED CSS 변수명·Props·설정 파일을 작성하지 않는다. 구조·기본 동작·접근성은 공식 컴포넌트를 우선 검토하되 실제 적용과 변경 범위는 구현 단계에서 확인한다.

### 11.3 컴포넌트 대응

| 화면 요소 | SEED 참조 | 집으로 적용 |
| --- | --- | --- |
| 하단 5개 탭 | Bottom Navigation | 순서 고정, Fill 아이콘, 선택 탭 벽돌색, 짧은 라벨 |
| 주요 행동 | Action Button | 고강조 행동 하나, 처리 중·비활성화 상태, 구체적 행동 문구 |
| 조건 입력 | Field + Radio / Checkbox 후보 | 레이블·설명·오류·근거, 선택 행 전체 터치 |
| 서류·FAQ 설명 | Accordion | 펼침과 상태 기록 분리, 페이지 단위 스크롤 |
| 주의·근거 안내 | Callout | 메시지 의미에 맞는 톤, 짧은 제목, 일관된 확인 행동 |
| 상세 내부 탭 | Tabs 후보 | 공고 정보 탭과 개인 준비 탭 구분 |
| 공고 상태 | Badge 후보 | 공식 접수 상태·집으로 준비 안내 제공 상태·사용자 준비 상태 구분 |
| 검색 필터 | Chip / Bottom Sheet / Select 후보 | 실제 데이터에 맞는 선택, 필터 적용·복원 |
| 오류·빈 결과 | Result Section / Skeleton 후보 | 원인·다음 행동·재시도와 일관된 로딩 |
| 계정 화면 | Text Input / Field 후보 | 라벨·오류와 로그인 상태 명시 |
| 후순위 안내 | Dialog 후보 | 준비 중 메시지·닫기·대체 경로, 포커스 복귀. 경고형 Alert Dialog로 과장하지 않음 |
| 집 성장·여정·준비 바 | 제품 전용 설계 | 서버의 준비 상태만 시각화, 자격·선정 가능성과 분리 |

`후보` 항목은 이번 작업에서 개별 상세 문서를 모두 검토한 컴포넌트가 아니다. 실제 사용 전에 인덱스에서 공식 상세 문서와 React 지원을 확인한다.

### 11.4 공식 지침을 적용하는 구체적 규칙

- 색상: 브랜드·중립·긍정·주의·오류 역할을 분리한다. 프로젝트 팔레트는 기본 SEED 브랜드색으로 되돌리지 않는다.
- Action Button: 고강조 주요 행동은 하나로 제한한다. Solid 버튼과 보조 버튼을 나란히 둘 때는 Neutral Weak 조합을 우선 검토한다. 모호한 `다음`은 구체적인 동작으로 바꾼다.
- Bottom Navigation: 5개를 넘기지 않고 탭 아이콘의 Fill 스타일을 통일한다. 웹의 내부 컨테이너는 최대 480px을 기준으로 대응한다.
- Field: 질문명·입력·도움말·오류를 묶는다. 저장하지 않은 변경을 버릴 때만 이탈 안내를 제공한다.
- Radio: 한 가지 답변일 때 사용하며 세로 배치를 기본으로 한다. 사용자 사실을 추측해 기본 선택하지 않는 제품 예외를 적용한다.
- Accordion: 두 개 이상 항목의 설명 목록에 사용한다. 개별 패널에 작은 내부 스크롤을 만들지 않는다.
- Callout: 표시·행동형을 구분한다. 전체가 누를 수 있는 메시지에 별도의 중복 링크를 얹지 않는다. 메시지의 의미에 맞는 톤을 사용한다.
- Safe Area: 배경과 조작·읽기 영역을 구분하고 고정 바·버튼·텍스트가 시스템 영역에 가려지지 않게 한다.

### 11.5 SEED 일반 지침과 제품의 예외

| 항목 | 일반 지침 / 대응 | 집으로의 결정과 이유 |
| --- | --- | --- |
| Radio 기본 선택 | 빈번한 선택지를 기본으로 제안하는 일반 지침 | 연령·거주·무주택·소득 등 사실 확인에서는 무선택 시작. 잘못된 조건 결과 방지 |
| 브랜드색 | 역할 토큰으로 관리 | 다섯 HEX 값은 사용자 합의값 유지. 기본 당근색으로 교체하지 않음 |
| 고강조 버튼 | 중요 행동 하나 | 카드마다 진한 버튼을 반복하지 않고 지금 할 일·준비 시작·저장에 집중 |
| 전용 여정·집 | 공통 컴포넌트만으로 의미를 결정하지 않음 | 준비 작업 기록의 은유로 설계. 조건 안내 결과의 점수처럼 사용하지 않음 |

### 11.6 후속 디자인 작업에 사용할 지시문

```text
$seed-design
docs/design/screen-spec.md를 기준으로 화면을 설계한다.
seed-design 스킬을 읽고 전체 공식 문서 인덱스에서 Foundations와
해당 컴포넌트의 공통 스펙을 확인한 뒤 적용한다.
브랜드는 #B64A32, 약한 배경은 #F3E3DA, 화면은 #FAF8F5,
카드는 #FFFFFF, 본문은 #262626으로 유지한다.
홈·공고·내 준비·가이드·마이의 다섯 메뉴와 핵심 10개 화면을 유지한다.
캐릭터를 제외하고 집·벽돌·문서로 준비 작업의 진행을 표현한다.
조건 상태·서류 상태·공식 일정·사용자 기록을 구분한다.
공식 근거와 다음 행동을 우선하며 불필요한 응원 문구·큰 반복 일러스트를 제거한다.
모름은 허용하고 사용자 사실을 묻는 Radio 답변은 기본 선택하지 않는다.
정상·로딩·빈 상태·오류·저장 실패·수정 공고의 상태까지 설계한다.
검증된 공식 발급 링크는 초기 준비 흐름에 실제 연결한다.
준비도(%)·집 건축 표현은 초기 완성에 포함하고 필수 미확인 표시를 함께 제공한다.
알림 및 범위 확정 전 캘린더 파일 내보내기 등의 진입점은 준비 중 안내를 제공한다.
선택하면 '아직 준비 중인 기능입니다'라는 공통 안내를 표시하고,
실제 데이터 변경·발송·예약·외부 연동·가짜 완료 표현은 하지 않는다.
실제 기능 구현은 본 문서의 MVP와 후순위 구분을 유지한다.
실제 React 코드 구현을 요청받으면 대상 플랫폼과 설치 버전을 확인하고
React 공식 문서의 공개 API·토큰·테마 계약에 맞춰 연결한다.
```

### 11.7 React 구현·백엔드 연동 시 작업 원칙

- 하나의 모노레포 안에서 React·TypeScript는 `frontend/`, Spring Boot는 `backend/`, API·개발 문서는 `docs/`로 관리한다. 프론트엔드는 VS Code·npm, 백엔드는 IntelliJ IDEA·Gradle Wrapper를 사용하고 실행·검사·빌드는 각각 수행한다.
- 각 폴더의 README에 실행·검사·빌드 방법을 기록하고 루트 README에 전체 실행 순서·API 연결 확인 방법을 연결한다. 초기에는 별도 모노레포 관리 도구를 추가하지 않는다.
- 기존 `main`·`develop` 정책 아래 기능·수정 단위 브랜치와 PR을 사용한다. 화면·API·문서의 연동 변경은 함께 검토하고 큰 작업은 연결된 PR로 나눠 선행 작업·호환성·통합 확인 순서를 적는다. 공통 설정·같은 파일 변경은 관련 작업자와 먼저 조율한다.
- 프론트·백엔드별 PR 검사 작업을 구성하고 초기에는 양쪽을 모두 실행한다. 개별 검사·빌드 통과와 실제 화면·API 연결 확인을 구분하며, 목업 데이터만으로 서버 저장·권한·오류 처리를 검증했다고 기록하지 않는다.
- 배포 산출물·버전·적용·복구 절차를 각각 관리하고 변경 없는 쪽의 재빌드·재시작을 필수로 묶지 않는다. API·DB 변경이 있으면 호환성·적용 순서·통합 확인·복구 제약을 함께 검토한다. 기존 EC2 1대의 Nginx·Spring Boot 구성을 유지할 수 있으며 구체적인 배포·복구 절차와 자동화는 후속 설계에서 정한다.

상세 기준은 [코드 및 기술 규칙의 모노레포 운영 원칙](../conventions/coding-conventions.md#모노레포-운영-원칙--20261020-확정)을 따른다. 이 원칙은 개발 작업 기준이며 화면 구성이나 MVP 범위를 변경하지 않는다. 로컬 기본 환경·API 연동은 검증했으며 원격 CI 실행·도메인 기능·배포 완료 여부는 별도로 확인한다.

## 12. 디자인·구현 검토 체크리스트

- [ ] 핵심 10개 화면과 하단 5개 메뉴의 역할이 일치한다.
- [ ] 벽돌색 팔레트 다섯 값이 바뀌지 않았고 브랜드색을 경고색으로 혼용하지 않았다.
- [ ] 연한 벽돌색 위 작은 글자는 본문색으로 읽을 수 있다.
- [ ] 캐릭터·손글씨 응원·반복 대형 집·강한 배경 장식이 없다.
- [ ] 홈에서 지금 할 일의 안내로 한 번에 이동한다.
- [ ] 공고와 개인 준비 건의 내부 탭·내용이 구분된다.
- [ ] 기본 정보 검증·공개 완료와 준비 안내 검수·제공 상태를 구분하며 동시 검수가 양쪽 통과를 강제하지 않는다.
- [ ] 기본 정보 공개·준비 안내 검수 중/미제공 공고도 목록·상세·원문을 조회하고 미검수 조건·서류·준비도를 노출하지 않는다.
- [ ] 공식 접수 상태와 준비 안내 상태가 구분되고 상태 설명은 기관의 검토·신청 가능 판단으로 오해되지 않는다.
- [ ] 준비 안내 제공 여부에 따라 시작 버튼·상세 탭·원문 행동이 달라지고 직접 경로·로그인 복귀·저장 요청도 서버 상태를 확인한다.
- [ ] 관리자 한 화면에서 영역별 검수 결과·보완 사유·버전·확인일·공개 이력을 기록하고 기본 정보 실패 시 양쪽 제공을 막는다.
- [ ] 질문은 공고별 규칙에 연결되고 실제 사용자 답변을 미리 선택하지 않는다.
- [ ] 모름·미입력·불일치 가능·문의 권장이 구분된다.
- [ ] 질문 진행, 조건 결과, 서류 개수, 전체 준비도가 서로 다른 의미로 표시된다.
- [ ] 초기 완성에서 준비도(%)·집 건축 표현이 실제 서버 상태와 연결되고 계산 기준·집 단계 매핑·미확인/재확인 안내가 일치한다.
- [ ] 공식 발급 링크가 초기 흐름에서 실제 동작하고 미검증·오류 링크는 발급 방법·확인 경로로 안내한다.
- [ ] 발급처 이동·일정 파일 다운로드를 준비 완료·외부 캘린더 등록·알림 예약 완료로 처리하지 않는다.
- [ ] 캘린더는 푸시와 분리해 정확성·대상 기기 가져오기·변경/중복 처리를 평가하고 범위 확정 전 준비 중 상태를 유지한다.
- [ ] 서류 필요 여부와 준비 상태가 분리되어 있다.
- [ ] 서류 원본 업로드가 없으며 공고별 발급 기준·형식·용량을 추측하지 않는다.
- [ ] 공식 일정과 사용자 완료 기록이 구분된다.
- [ ] 외부 신청 사이트 방문을 접수 완료로 처리하지 않는다.
- [ ] 같은 기준 버전을 사용하는 화면의 공고·기관·날짜·개수가 일치한다. 기본 상세의 최신 버전과 기존 개인 기록의 과거 버전 차이는 설명한다.
- [ ] 수정 공고의 영향 항목에 재확인 안내가 연결된다.
- [ ] 비회원 공고 조회와 개인 저장 전 로그인 흐름이 연결된다.
- [ ] 저장 실패 시 입력·기록·진행률이 사실과 맞게 유지된다.
- [ ] 알림·캘린더 등 계획된 후순위 기능의 진입점과 `준비 중` 표시가 있다.
- [ ] 후순위 기능 선택 시 공통 안내와 닫기·대체 경로가 동작한다.
- [ ] 안내만 표시한 후 사용자 데이터·설정·준비도·즐겨찾기 상태가 바뀌지 않는다.
- [ ] 가짜 알림 개수·예약 완료·저장 성공 메시지가 없다.
- [ ] 준비도 안내가 가까이 있고 자격·선정 확률로 오해되는 표현이 없다.
- [ ] SEED 공식 스펙·버전·제품 예외·전용 요소를 구분했다.
- [ ] 키보드·글자 확대·좁은 폭·안전 영역·동작 줄이기에서 핵심 동작을 확인했다.
