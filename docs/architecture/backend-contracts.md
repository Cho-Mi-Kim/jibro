- 초기 기준일: 2026-10-30. 최종 대조일: 2026-11-10. PR #24 (`e288a99`)의 코드 기준이며 아직 develop/main 배포 완료를 뜻하지 않는다.
- 기준: [프론트엔드 기능 계약](frontend-contracts.md), 구현 DTO `HousingModels`, 인증 DTO `AuthController`
- 구현 범위: 이메일·비밀번호 로그인, Google·카카오 OAuth 연결, 공고 검색, 개인 준비 기록, 서버 준비도 계산, 관리자 검수·구조화 편집, LH 목록 자동 수집, 관심 공고·알림·보관함·계정 관리·공개본 이력. 새 API·발송 환경·시연 제한은 [회원 기능 계약](../contracts/member-features.md)을 따른다.

## 인증·권한

회원가입은 이름 2~30자, 이메일 최대 254자, 비밀번호 10자 이상이며 BCrypt의 UTF-8 72바이트 제한을 적용한다. 이메일은 소문자로 정규화한다. 중복 이메일은 409다. 이메일 소유 확인, 현재 비밀번호를 이용한 변경, 메일 링크 재설정·탈퇴 및 프로필 수정은 구현했다. 이메일 확인을 회원가입·로그인 전체의 선행 조건으로 강제하지는 않으며 이메일 알림 활성화에는 확인이 필요하다. 기존 계정과 소셜 계정을 연결·해제하는 기능은 미구현이다.

접근 토큰은 HS256, issuer `jibro`, audience `jibro-web`, 15분 만료다. `JWT_SECRET`은 최소 32바이트이며 저장소에 넣지 않는다. 갱신 토큰은 임의 32바이트 값을 발급하고 DB에는 SHA-256 해시만 보관한다. 7일 만료, 행 잠금으로 단일 회전을 보장한다. 요청마다 DB의 계정 활성 여부·체험 만료·`security_version`과 JWT `sv`를 대조한다. 비밀번호 변경·재설정·탈퇴는 security_version을 올리고 갱신 토큰을 삭제해 기존 접근 토큰도 차단한다. 일반 로그아웃은 현재 갱신 토큰만 폐기하므로 이미 발급한 접근 토큰은 최대 15분 동안 유효하다. 체험 종료는 계정과 기록을 삭제하므로 해당 접근 토큰도 즉시 거절한다.

쿠키 `jibro_refresh`는 HttpOnly, SameSite=Lax, Path=/api/v1/auth다. Secure 기본값은 true이며 로컬 HTTP에만 `AUTH_SECURE_COOKIE=false`를 사용한다. 실제 배포는 HTTPS·동일 출처 역방향 프록시가 전제다. `GET /auth/csrf`의 마스킹된 토큰을 `X-CSRF-TOKEN` 헤더로 보낸다. JWT와 CSRF 토큰을 URL·로그·localStorage에 기록하지 않는다.

소셜 로그인은 제공자별 CLIENT_ID와 CLIENT_SECRET이 모두 있을 때 활성화된다. `/auth/providers`가 활성 목록을 반환한다. 제공자+subject로 사용자를 식별하고 검증된 이메일을 사용한다. 같은 이메일의 기존 계정으로 자동 연결하지 않으며 충돌은 가입/연결 오류로 처리한다. OAuth state/OIDC 검증은 Spring Security를 사용한다. 성공 시 갱신 쿠키를 설정하고 고정된 `FRONTEND_URL/auth/callback`으로 이동한다. 접근 토큰은 URL에 포함하지 않는다.

관리자 권한은 서버에서 확인한다. 일반 회원가입은 USER만 생성한다. 최초 관리자는 운영자가 가입된 계정을 확인하고 DB에서 승격한다. 공개 관리자 비밀번호나 자동 관리자 계정은 제공하지 않는다. OAuth 키와 메일 발송 환경, 로그인 요청 제한은 배포 전 설정·보완 대상이다. 메일 확인 링크는 계정·용도별 1분 내 중복 발급을 생략하지만 이를 로그인·가입·체험 전체의 요청 제한으로 간주하지 않는다.

`local-sample`에서만 `POST /auth/trial`을 제공한다. 임시 계정의 JWT 권한은 TRIAL이며 생성 후 24시간 만료다. 기존 일반 계정의 유효한 갱신 쿠키가 있으면 409, 체험 계정의 유효 쿠키가 있으면 재사용·회전한다. 체험은 관리자, 외부 발송 채널, 이메일 확인·비밀번호 변경·탈퇴 링크 API를 사용할 수 없다. 정리 작업은 1분 간격으로 만료 계정을 최대 200개씩 삭제한다. 정적 Pages 시연은 이 서버 체험과 다르다.

## 저장·동시 수정

- 공고: 검색 필드는 관계형 컬럼과 인덱스, 가변 질문·서류·일정은 JSONB로 저장한다. Querydsl로 필터 내부 OR, 필터 사이 AND를 적용한다.
- 준비: 사용자+공고 유일 제약, 소유자 조건 조회, 공고 당시 스냅샷과 조건부 서류 규칙을 저장한다. 다른 사용자의 ID는 404다.
- revision: 수정 요청과 현재 revision이 다르면 409. 사용자 기록과 공고 잠금으로 검수/기록 변경의 경쟁을 막는다.
- 공고 내용 수정: 공고 version과 검수 revision을 올리고 기본·안내 모두 HOLD로 돌린다. 기존 준비 기록은 원래 내용을 보존하고 수정은 막는다. 현행 `POST /preparations/{id}/refresh`는 사용자 요청과 revision·새 AVAILABLE 버전을 확인한 뒤 이전 스냅샷을 이력에 보존한다. 동일한 질문 계약의 답변과 동일한 ID·제목·날짜의 일정 기록만 이어받고, 기존 완료 서류는 재확인으로 전환한다.
- 준비도: 조건 30%, 적용 서류 50%, 일정 기록 20%. 모름·미입력·해당 여부 불명은 완료 점수를 주지 않는다. 해당 없는 서류는 분모에서 제외한다. 분모가 0인 영역은 0점이다. 정수 반올림 결과가 100이어도 미확인 답변·미완료 서류·미기록 일정이 하나라도 남으면 99%로 제한한다. 조건부 서류의 해당 여부가 바뀌면 완료 표시를 재확인으로 돌린다.
- DB migration: 기존 테스트용 V1을 보존하고 운영 스키마는 V2부터 시작한다. 테스트 DB에는 운영 migration과 테스트용 migration을 함께 적용한다.

`PreparationRules`는 서류 필요 여부와 준비도·집 단계·경고·다음 행동을 계산하는 순수 규칙이다. DB에 접근하거나 전달받은 준비 기록을 수정하지 않는다. `PreparationService`는 소유권·잠금·revision·입력 검증·트랜잭션·기준 갱신을 유지하고 규칙 결과를 저장한다. 생성·답변 변경·기준 갱신이 동일한 필요 여부 계산을 사용한다. 시연 계산과의 기대값 공유 및 실제 서버 검증의 경계는 [프론트엔드 개인 준비 계약](frontend-contracts.md#개인-준비)을 따른다.

## 관리자 구조화 계약

`GET /admin/reviews/{id}/draft`로 기본 정보와 구조화 원고를 읽고 `PUT`으로 `{revision, draft}`를 저장한다. draft는 title, agency, region, type, startDate, endDate, publishedDate, content를 갖는다. 날짜가 확인되지 않으면 null이다.

content는 summary, evidence, attachments, questions, documents, schedules다. 질문별 `options`의 value·label·requiresFollowUp을 사용한다. 서류의 conditionQuestionId가 null이면 필수이며, 질문 ID가 있으면 그 답변이 `conditionAnswerValues`에 포함될 때 조건부 제출이다. 다른 유효 답변은 해당 없음, UNKNOWN/미입력은 미확인이다. 이전 자료에서 conditionAnswerValues가 없으면 YES를 기본값으로 사용한다. 세부 검증·전이는 [질문·서류 계약](../contracts/question-options-and-documents.md)을 따른다. 여러 질문의 AND/OR 등 현재 표현으로 다룰 수 없는 복잡한 예외는 임의로 판정하지 않고 HOLD 또는 UNSUPPORTED로 둔다.

질문·서류·일정 ID는 공백 없는 영문·숫자·하이픈·밑줄, 최대 64자이며 영역 내 중복을 금지한다. 질문·서류·일정 각각 최대 100개, 첨부 50개, 메모·검수 사유 최대 2,000자다. 외부 링크는 HTTPS만 허용하며 운영자가 공식 발급·공고 링크를 검증한다. `PATCH /admin/reviews/{id}`는 기본·안내 결과를 함께 기록한다. 준비 안내 PASS에는 질문·서류·일정이 필요하다.

## 공식 수집의 범위와 한계

출처: [공공데이터포털 LH 분양임대공고문 조회 API](https://www.data.go.kr/data/15058530/openapi.do). `LH_SERVICE_KEY`에는 URL 인코딩 전 Decoding 키를 넣는다. 서버가 HTTPS 공식 엔드포인트에 키를 한 번 인코딩하여 보낸다. Encoding 키를 넣으면 이중 인코딩되어 `SERVICE_KEY_IS_NOT_REGISTERED_ERROR`가 발생할 수 있다. 2026-10-31 실제 API 및 관리자 수집 API로 276건 저장과 재수집 시 중복 없음, 전건 HOLD/HOLD를 확인했다. 자동 테스트는 외부 키 없이 합성 자료를 사용하며 실제 응답의 `dsSch`·`dsList`·`resHeader` 구조를 반영한다.

관리자가 수집 버튼을 누르면 한국 날짜 기준 최근 3개월의 LH 임대주택 목록을 자동 요청·정규화한다. 게시일 검색에는 `PAN_ST_DT`와 `PAN_ED_DT`를 `yyyyMMdd` 형식으로 사용한다. `PAN_NT_ST_DT`와 `CLSG_DT`는 응답 필드이며 검색 범위로 사용하지 않는다. 100개씩 기본 5페이지, 설정으로 최대 20페이지까지 처리한다. 이는 호출시간·트래픽 보호 장치이며 제품의 공고 수 상한이 아니다. 한도에 닿으면 PARTIAL, 키 없음은 NOT_CONFIGURED, 외부 오류는 FAILED로 실제 실행 결과를 저장한다. 성공으로 가장하지 않는다. 주기 예약 수집과 대규모 작업 큐는 아직 적용하지 않았다.

동일 공식 상세 URL은 동일 출처로 취급한다. 목록 순번·전체 건수·응답 시각을 제외한 원본 목록 필드의 해시가 바뀌면 공고를 재검수한다. PDF·첨부 본문만 변경되고 목록 값이 그대로면 자동 감지하지 못하므로 원문 대조가 필요하다. 원문을 임의 추론하여 질문이나 지원 자격을 생성하지 않는다. 신규 수집 자료는 기본·안내 모두 HOLD이며 검수 후 기본만 공개하거나 안내까지 제공할 수 있다. 목록의 게시일·마감일을 실제 신청 기간으로 자동 전용하지 않는다.

## 로컬 샘플과 운영 자료

2026-11-01: 기본 공고 검색 및 필터는 `source_key`가 `local-sample-`로 시작하는 예시 공고를 제외한다. `GET /notices?includeSamples=true`는 개발 검증용으로 예시를 함께 조회하며 기본 검수 PASS 조건은 동일하다. 기존 예시 상세와 개인 준비 기록은 보존한다. 운영은 별도 DB를 사용한다.

공식 초기 자료와 로컬 적용 방법은 [공식 공고 대조 자료](../../data/notices/README.md)를 따른다. 자동 수집 전체 결과를 일괄 공개하지 않는다.

`local-sample` 프로필에서만 가상 공고 3건과 샘플 가이드를 추가한다. 공고 제목·출처에 샘플임을 표시한다. 서버 저장은 실제 PostgreSQL이므로 새로고침 후에도 개인 기록이 유지된다. 샘플을 켠 DB를 그대로 운영 데이터로 사용하지 않는다. 프로필을 끄면 샘플을 자동 삭제하지 않으며 운영은 별도 DB를 사용한다.

`GET /guides`는 현재 공개된 실제 공고를 읽어 요약·공식 문의 경로를 만들고, 준비 안내 PASS이며 변경 검수 중이 아닌 공고의 질문·서류·일정을 가이드로 추가한다. 샘플 공고는 실제 가이드 생성에서 제외하고 local-sample에서는 별도 샘플 절차 안내 한 건을 추가한다. 별도의 편집형 가이드 CMS는 없으며 실제 데이터가 없으면 빈 목록일 수 있다. 검색·카테고리 필터는 내려받은 자료에 대해 프론트에서 수행한다.

운영 배포·도메인·HTTPS·관리자 지정·외부 키·실제 공고 사람 검수·메일/푸시 실발송·주기 공고 수집은 별도 설정/후속 검증 대상이다. 알림 발송 스케줄러 구현과 LH 예약 수집 미구현을 구분한다. PR #24는 V6~V9 마이그레이션을 추가하므로 운영 적용 전 백업·업그레이드·복구 검증이 필요하다.

수집 재개: POST /admin/collections?startPage=6 처럼 시작 페이지를 지정할 수 있다. 기본값은 1이며 1~9999를 허용한다. 같은 페이지를 다시 요청해도 동일 출처를 중복 생성하지 않는다.

## 공개 일정

공개 Notice DTO의 `schedules: ScheduleTemplate[]`는 기본 정보 검수 후 공개되는 공식 일정이며, 준비 안내 HOLD 상태에서도 노출한다. 개인별 질문·서류와 준비 시작 제한은 유지한다. 프론트엔드의 대상자 발표는 서류제출대상자 발표를 먼저 선택하고, 해당 일정이 없으면 다른 발표 일정을 사용한다. 날짜만 존재할 때 임의 시각을 표시하지 않는다. 이는 기존 공개 계약이며 개인 준비 계산 분리로 변경하지 않는다.

`NoticeSchedules`는 알림용 공개 일정 선택과 기본 접수 일정의 중복 정리를 담당하고 `AlertService`는 회원별 알림 조회·읽음 처리를 담당한다. 같은 날의 기본 마감과 시각이 보완된 동등한 마감은 하나로 취급하되 기존 `end` 식별자를 보존한다. 다른 지역·별도 시각·서류 마감 등 서로 다른 일정은 유지한다. 공개 일정의 대표 날짜·시각과 캘린더 반영, 개인 스냅샷의 완료 기록을 현재 일정에 연결하는 조건은 [프론트엔드 일정 계약](frontend-contracts.md#일정-해석내보내기-현행-2026-11-06)을 따른다. 새 API 필드나 DB 일정 종류를 추가하지 않는다.
