# 백엔드 구현 계약과 운영 설정

- 기준일: 2026-10-30
- 기준: [프론트엔드 기능 계약](frontend-contracts.md), 구현 DTO `HousingModels`, 인증 DTO `AuthController`
- 구현 범위: 이메일 인증, Google·카카오 OAuth 연결, 공고 검색, 개인 준비 기록, 서버 준비도 계산, 관리자 검수·구조화 편집, LH 목록 자동 수집

## 인증·권한

회원가입은 이름 2~30자, 이메일 최대 254자, 비밀번호 10자 이상이며 BCrypt의 UTF-8 72바이트 제한을 적용한다. 이메일은 소문자로 정규화한다. 중복 이메일은 409다. 이메일 소유 확인·비밀번호 재설정·계정 연결·탈퇴는 아직 구현하지 않았다.

접근 토큰은 HS256, issuer `jibro`, audience `jibro-web`, 15분 만료다. `JWT_SECRET`은 최소 32바이트이며 저장소에 넣지 않는다. 갱신 토큰은 임의 32바이트 값을 발급하고 DB에는 SHA-256 해시만 보관한다. 7일 만료, 행 잠금으로 단일 회전을 보장한다. 로그아웃은 현재 갱신 토큰을 폐기한다. 이미 발급한 접근 토큰은 최대 15분 동안 유효하다.

쿠키 `jibro_refresh`는 HttpOnly, SameSite=Lax, Path=/api/v1/auth다. Secure 기본값은 true이며 로컬 HTTP에만 `AUTH_SECURE_COOKIE=false`를 사용한다. 실제 배포는 HTTPS·동일 출처 역방향 프록시가 전제다. `GET /auth/csrf`의 마스킹된 토큰을 `X-CSRF-TOKEN` 헤더로 보낸다. JWT와 CSRF 토큰을 URL·로그·localStorage에 기록하지 않는다.

소셜 로그인은 제공자별 CLIENT_ID와 CLIENT_SECRET이 모두 있을 때 활성화된다. `/auth/providers`가 활성 목록을 반환한다. 제공자+subject로 사용자를 식별하고 검증된 이메일을 사용한다. 같은 이메일의 기존 계정으로 자동 연결하지 않으며 충돌은 가입/연결 오류로 처리한다. OAuth state/OIDC 검증은 Spring Security를 사용한다. 성공 시 갱신 쿠키를 설정하고 고정된 `FRONTEND_URL/auth/callback`으로 이동한다. 접근 토큰은 URL에 포함하지 않는다.

관리자 권한은 서버에서 확인한다. 일반 회원가입은 USER만 생성한다. 최초 관리자는 운영자가 가입된 계정을 확인하고 DB에서 승격한다. 공개 관리자 비밀번호나 자동 관리자 계정은 제공하지 않는다. OAuth 키, 이메일 인증과 로그인 요청 제한은 배포 전 설정·보완 대상이다.

## 저장·동시 수정

- 공고: 검색 필드는 관계형 컬럼과 인덱스, 가변 질문·서류·일정은 JSONB로 저장한다. Querydsl로 필터 내부 OR, 필터 사이 AND를 적용한다.
- 준비: 사용자+공고 유일 제약, 소유자 조건 조회, 공고 당시 스냅샷과 조건부 서류 규칙을 저장한다. 다른 사용자의 ID는 404다.
- revision: 수정 요청과 현재 revision이 다르면 409. 사용자 기록과 공고 잠금으로 검수/기록 변경의 경쟁을 막는다.
- 공고 내용 수정: 공고 version과 검수 revision을 올리고 기본·안내 모두 HOLD로 돌린다. 기존 준비 기록은 원래 내용을 보존하고 수정은 막는다. 새 버전으로 기록을 이관하는 UI/API는 후속 작업이다.
- 준비도: 조건 30%, 적용 서류 50%, 일정 기록 20%. 모름·미입력·해당 여부 불명은 완료 점수를 주지 않는다. 해당 없는 서류는 분모에서 제외한다. 분모가 0인 영역은 0점이다. 조건부 서류의 해당 여부가 바뀌면 완료 표시를 재확인으로 돌린다.
- DB migration: 기존 테스트용 V1을 보존하고 운영 스키마는 V2부터 시작한다. 테스트 DB에는 운영 migration과 테스트용 migration을 함께 적용한다.

## 관리자 구조화 계약

`GET /admin/reviews/{id}/draft`로 기본 정보와 구조화 원고를 읽고 `PUT`으로 `{revision, draft}`를 저장한다. draft는 title, agency, region, type, startDate, endDate, publishedDate, content를 갖는다. 날짜가 확인되지 않으면 null이다.

content는 summary, evidence, attachments, questions, documents, schedules다. 서류의 conditionQuestionId가 null이면 필수, 질문 ID면 YES 시 조건부 제출·NO 시 해당 없음·UNKNOWN/미입력 시 미확인이다. 이 단순 규칙으로 표현할 수 없는 복잡한 자격·예외는 자동 판단하지 말고 준비 안내 HOLD 또는 UNSUPPORTED로 둔다. 질문은 이 규칙에 맞는 의미로 작성해야 한다.

질문·서류·일정 ID는 공백 없는 영문·숫자·하이픈·밑줄, 최대 64자이며 영역 내 중복을 금지한다. 질문·서류·일정 각각 최대 100개, 첨부 50개, 메모·검수 사유 최대 2,000자다. 외부 링크는 HTTPS만 허용하며 운영자가 공식 발급·공고 링크를 검증한다. `PATCH /admin/reviews/{id}`는 기본·안내 결과를 함께 기록한다. 준비 안내 PASS에는 질문·서류·일정이 필요하다.

## 공식 수집의 범위와 한계

출처: [공공데이터포털 LH 분양임대공고문 조회 API](https://www.data.go.kr/data/15058530/openapi.do). `LH_SERVICE_KEY`에는 URL 인코딩 전 키를 넣는다. 서버가 HTTPS 공식 엔드포인트에 키를 인코딩하여 보낸다. 실제 키·외부 승인 계정이 없어 이번 구현에서는 실서비스 응답을 호출 검증하지 못했다. 파서 테스트 자료는 명세 필드에 맞춘 합성 자료다.

관리자가 수집 버튼을 누르면 최근 3개월의 LH 임대주택 목록을 자동 요청·정규화한다. 100개씩 기본 5페이지, 설정으로 최대 20페이지까지 처리한다. 이는 호출시간·트래픽 보호 장치이며 제품의 공고 수 상한이 아니다. 한도에 닿으면 PARTIAL, 키 없음은 NOT_CONFIGURED, 외부 오류는 FAILED로 실제 실행 결과를 저장한다. 성공으로 가장하지 않는다. 주기 예약 수집과 대규모 작업 큐는 아직 적용하지 않았다.

동일 공식 상세 URL은 동일 출처로 취급한다. 목록 순번·전체 건수·응답 시각을 제외한 원본 목록 필드의 해시가 바뀌면 공고를 재검수한다. PDF·첨부 본문만 변경되고 목록 값이 그대로면 자동 감지하지 못하므로 원문 대조가 필요하다. 원문을 임의 추론하여 질문이나 지원 자격을 생성하지 않는다. 신규 수집 자료는 기본·안내 모두 HOLD이며 검수 후 기본만 공개하거나 안내까지 제공할 수 있다. 목록의 게시일·마감일을 실제 신청 기간으로 자동 전용하지 않는다.

## 로컬 샘플과 운영 자료

`local-sample` 프로필에서만 가상 공고 3건과 샘플 가이드를 제공한다. 공고 제목·출처에 샘플임을 표시한다. 서버 저장은 실제 PostgreSQL이므로 새로고침 후에도 개인 기록이 유지된다. 샘플을 켠 DB를 그대로 운영 데이터로 사용하지 않는다. 프로필을 끄면 샘플을 자동 삭제하지 않으며 운영은 별도 DB를 사용한다. 운영 가이드 자료는 아직 등록되지 않아 `/guides`가 빈 목록을 반환한다.

운영 배포·도메인·HTTPS·관리자 지정·외부 키·실제 공고 검수·메일 발송·주기 수집은 별도 설정/후속 검증 대상이다.

수집 재개: POST /admin/collections?startPage=6 처럼 시작 페이지를 지정할 수 있다. 기본값은 1이며 1~9999를 허용한다. 같은 페이지를 다시 요청해도 동일 출처를 중복 생성하지 않는다.
