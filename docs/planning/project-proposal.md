## 1. 핵심 타깃

### 주요 타깃

청년 대상 공공임대주택이나 주거비 지원사업에 처음 신청하며, 공고문 해석과 서류 준비에 어려움을 겪는 대학생·취업 준비생·사회초년생.

### 초기 타깃 및 지원 범위 선정

**한 기관을 우선 조사하되 지역·지원 유형은 미리 제한하지 않는다.** 후보 기관의 여러 지역·유형 공고를 처음부터 비교하고, 공통 데이터 구조·규칙 재사용성·추가 준비 규칙·검수 및 사용자 검증 작업량을 기준으로 초기 범위를 선정한다. 지역이나 유형명이 다르다는 이유만으로 제외하지 않으며, 공통 구조로 처리되고 검증 작업량을 감당할 수 있는 공고는 함께 포함한다. 수집한 공고의 준비 안내는 원문 대조·검수를 완료한 범위에 적용한다.

대표 공고 한 건으로 수집→검수→준비 목록→저장 흐름을 먼저 구현하는 순서는 서비스 지원 범위와 구분한다. 실제 공고와 API를 비교하기 전에는 여러 지역·유형의 수집·구조화가 어렵거나 추가 작업량이 작다고 단정하지 않는다.

초기 지원 범위는 다음 기준으로 선정한다.

- 실제 공고와 첨부 문서를 충분히 확보할 수 있는가?
- 신청 경험자 또는 신청을 고려한 사람을 인터뷰할 수 있는가?
- 조건과 제출 서류가 일정한 구조를 가지고 있는가?
- 학기 중 사용자 테스트가 가능한 신청 일정인가?
- 공통 규칙과 주요 조건·서류·절차·예외 차이를 대표하는 표본을 구성할 수 있는가? 대표 1건과 추가 2∼3건은 시작점이며 필요한 차이가 빠지면 보완한다.
- 지역·유형별 차이가 기존 값·설정으로 표현되는가, 새 질문·조건부 서류·예외·신청 단계가 필요한가? 추가 구현·검수 작업량을 학기 중 감당할 수 있는가?
- 공식 API·원문·첨부파일을 확보하고 신규·수정 공고를 자동 수집할 수 있는가?

후보로는 한 기관의 **청년 매입임대**와 **청년 임대주택** 등 여러 지역·유형 공고를 비교한다. 수도권은 인터뷰 대상 확보를 위한 조사 출발점으로 활용할 수 있으나 데이터 지원 지역의 상한으로 삼지 않는다. 구체적인 기관과 지원 범위는 공고 분석·추가 작업량 및 인터뷰 대상 확보 결과로 확정한다.

### 구체적인 사용 상황

- 관심 있는 공고를 찾았지만 자신에게 해당하는 조건을 파악하기 어려운 경우
- 신청 자격과 선정 순위의 차이를 이해하기 어려운 경우
- 공통 서류와 자신에게만 필요한 조건부 서류를 구분하기 어려운 경우
- 공고문, 첨부파일, 메모, 캘린더, 서류 발급 사이트를 반복해서 오가는 경우
- 신청 이후의 서류 제출이나 보완 요청 일정을 놓칠까 걱정되는 경우
- 전체 신청 과정 중 자신이 어디까지 준비했는지 알기 어려운 경우

### 초기 핵심 사용자 페르소나

> 수도권에서 독립을 준비하는 만 24세 취업 준비생. 청년 매입임대 공고를 발견했지만 소득 기준, 가구원 범위, 순위 조건을 정확히 이해하지 못했다. 블로그와 공식 공고를 함께 확인하며 별도의 메모에 서류 목록을 정리하고 있지만, 빠뜨린 서류가 없는지 확신하지 못한다.

## 2. 해결하려는 문제 가설

> 청년 주거지원에 처음 신청하는 사람은 공고를 발견한 이후에도 자신의 상황과 공고의 조건·서류·일정을 연결하기 어렵다. 이로 인해 여러 자료를 반복해서 확인하고, 필요한 항목을 놓치거나 신청을 중단할 수 있다.
> 

| 세부 가설 | 확인할 실제 경험 |
| --- | --- |
| 공고의 조건을 해석하기 어렵다 | 용어 또는 예외 조건을 이해하지 못해 기관에 문의하거나 신청을 망설였는가? |
| 자격과 선정 순위를 혼동한다 | 신청할 수 있는 조건과 우선적으로 선정되는 조건을 동일하게 이해했는가? |
| 자신에게 필요한 서류를 구분하기 어렵다 | 공통 서류와 해당자만 제출하는 서류를 혼동했는가? |
| 다음 행동을 결정하기 어렵다 | 공고를 읽은 뒤 무엇부터 확인하거나 발급해야 할지 몰랐는가? |
| 신청 단계별 일정을 놓친다 | 최초 신청 이후 서류 제출, 보완 요청, 결과 확인 일정을 놓친 경험이 있는가? |
| 준비 상태가 여러 도구에 흩어진다 | 공고·메모·캘린더·발급 사이트를 오가며 반복 확인했는가? |
| 현재 준비 상태를 알기 어렵다 | 몇 가지 항목을 완료했지만 신청 가능한 상태인지 확신하지 못했는가? |
| 준비 과정에서 피로와 불안을 느낀다 | 절차가 복잡하거나 끝이 보이지 않아 준비를 미룬 적이 있는가? |

### 근본 문제

공고가 길다는 사실 자체보다 **공고 발견 이후 실제 신청까지 이어지는 실행 과정이 개인별로 정리되지 않는 것**을 핵심 문제로 본다.

```
공고 발견
  ↓
내 조건 확인
  ↓
필요 서류 구분
  ↓
발급 순서 결정
  ↓
기한 관리
  ↓
공식 신청
```

기존 정보가 각 단계별로 제공되더라도, 사용자가 이를 자신의 상황에 맞는 하나의 준비 계획으로 다시 구성해야 한다는 가설이다.

### 아직 확인되지 않은 점

- 이러한 문제가 실제 신청자에게 얼마나 자주 발생하는가?
- 가장 어려운 지점은 조건 해석, 서류 준비, 일정 관리 중 무엇인가?
- 기존 공식 안내와 상담으로 해결되지 않는 부분은 무엇인가?
- 사용자가 신청 준비를 위해 새로운 서비스를 사용할 의사가 있는가?
- 준비 과정을 여정으로 시각화하는 것이 실제 이해와 실행에 도움이 되는가?
- 집 완성 과정과 진행도 표현이 동기를 주는가, 중요한 신청 절차를 가볍게 보이게 하는가?

## 3. 사용자가 이 서비스를 선택할 이유

### 핵심 가치

이 서비스는 새로운 지원사업을 추천하는 데 집중하지 않는다. 사용자가 이미 관심 공고를 찾은 이후, **공식 신청까지 필요한 행동을 개인별로 정리하는 실행 도구**를 지향한다.

사용자는 서비스를 통해 다음 질문에 답할 수 있어야 한다.

- 내 상황에서 확인해야 할 조건은 무엇인가?
- 확인된 조건과 아직 판단할 수 없는 조건은 무엇인가?
- 어떤 서류가 모든 신청자에게 필요하고, 어떤 서류가 나에게만 필요한가?
- 각 서류는 어디에서 발급하고 언제까지 준비해야 하는가?
- 공고의 어느 부분을 근거로 안내한 것인가?
- 현재 준비 상태는 어디까지인가?
- 지금 가장 먼저 해야 할 한 가지 행동은 무엇인가?

### 핵심 차별화

> **공고를 찾는 서비스가 아니라, 선택한 공고를 실제로 준비하고 신청할 수 있도록 개인별 실행 계획을 만드는 서비스**
> 

공고 내용을 다음과 같이 연결한다.

```
공식 공고
  ↓
개인별 조건 질문
  ↓
확인·불일치 가능·추가 확인 상태 구분
  ↓
맞춤 서류 목록
  ↓
기한과 발급 순서
  ↓
지금 할 일
  ↓
공식 신청 경로
```

### 게이미피케이션의 역할

게이미피케이션은 별도의 재미 요소를 추가하기보다, 복잡한 신청 절차를 이해하고 끝까지 준비하도록 돕는 **진행도 시각화 수단**으로 사용한다.

#### 신청 여정 지도

```
공고 확인
  → 조건 확인
  → 서류 준비
  → 신청하기
  → 후속 절차
```

사용자가 중요한 준비 행동을 완료하면 벽돌집이 단계적으로 완성된다.

- 공고 주요 내용 확인 → 집터 확인
- 조건 질문 완료 → 기초 공사 완료
- 필수 서류 확인 → 벽과 지붕 완성
- 신청 준비 완료 → 문과 창문 완성
- 공식 신청 기록 → 열쇠 획득

#### 게이미피케이션 원칙

- 실제 신청에 필요한 행동에만 진행도를 부여한다.
- 단순 로그인이나 출석에는 보상을 주지 않는다.
- 매일 접속해야 유지되는 연속 기록을 사용하지 않는다.
- 사용자 간 준비도 랭킹을 제공하지 않는다.
- 자격 여부나 당첨 가능성을 점수화하지 않는다.
- 집 완성은 준비 행동을 표현할 뿐 신청 성공을 의미하지 않는다.
- 사용자의 불안감을 높이는 실패·벌점·집 퇴화 요소를 사용하지 않는다.

### 준비도와 자격의 구분

화면의 ‘준비도 65%’는 **준비 작업의 진행률**이다.

다음을 의미하지 않는다.

- 신청 자격 65% 충족
- 선정 가능성 65%
- 당첨 확률 65%
- 제출 서류의 적정성 65%

화면에서 다음 문구를 함께 제공한다.

> 준비도는 서비스에 기록한 준비 항목의 진행 상태입니다. 실제 신청 자격이나 선정 가능성을 의미하지 않습니다.
> 

### 사용자가 계속 이용할 이유

이 서비스는 장기간 매일 사용하는 서비스보다, 신청 기간에 집중적으로 활용하는 도구다. 따라서 일반적인 리텐션보다 다음 가치를 제공해야 한다.

- 공고를 다시 읽지 않아도 현재 준비 상태를 확인할 수 있음
- 접속할 때마다 지금 해야 할 다음 행동을 확인할 수 있음
- 서류와 기한을 한 화면에서 관리할 수 있음
- 수정 공고가 발생하면 영향을 받는 항목을 재확인할 수 있음
- 이후 다른 공고에 신청할 때 과거 준비 경험을 참고할 수 있음

## 4. 대표 사용 시나리오

1. 사용자가 관심 있는 청년 주거지원 공고를 선택한다.
2. 공고의 대상, 주요 일정, 신청 단계와 공식 원문을 확인한다.
3. 서비스가 신청 준비에 필요한 조건별 질문을 제시한다.
4. 사용자는 자신의 상황에 맞게 답하거나 ‘모름’을 선택한다.
5. 서비스는 답변 결과를 다음과 같이 구분한다.
    - 입력 내용으로 확인 가능한 항목
    - 명시 조건과 맞지 않을 가능성이 있는 항목
    - 추가 정보나 기관 확인이 필요한 항목
6. 답변에 따라 공통·조건부 제출 서류 목록이 구성된다.
7. 사용자는 각 서류의 발급처, 준비 방법, 유효기간과 공고 근거를 확인하고 검증된 공식 발급 링크로 이동한다. 방문 등 다른 방식이 필요하면 그 방법을 안내한다. 외부 이동은 발급 완료로 기록하지 않는다.
8. 서비스는 마감일과 준비 상태를 바탕으로 ‘지금 할 일’을 한 가지씩 제시한다.
9. 사용자가 준비 행동을 완료하면 신청 여정에 따라 집이 단계적으로 완성된다.
10. 사용자는 공식 신청 사이트로 이동해 직접 신청한다.
11. 실제 신청 여부와 이후 서류 제출·보완 상태는 사용자가 직접 기록한다.
12. 신청이 끝나면 준비 과정과 확인한 항목을 요약해서 볼 수 있다.

### 화면 예시

```
주거지원 준비 여정
준비도 65% · 신청 마감 D-5

지금 할 일
소득 증빙서류의 발급 기준 확인하기

확인이 필요한 조건
가구원 수에 따라 소득 기준이 달라질 수 있습니다.
공고 8페이지에서 근거 확인

서류 준비
필수 서류 5개 중 3개 준비
추가 확인 필요 1개
```

공식 시스템과 연동하지 않는 한 신청 완료나 심사 결과를 자동으로 확인하지 않는다.

공개 공고 목록·상세는 비회원도 열람할 수 있다. 개인별 답변과 준비 상태를 계정에 저장·관리할 때는 로그인이 필요하다. 이메일·비밀번호, Google, 카카오 로그인을 모두 제공한다.

### 채택한 기능 우선순위와 초기 완성 기준

| 항목 | 채택한 방향 | 완료·판단 기준 |
| --- | --- | --- |
| 공식 발급 링크 | 검증된 링크를 초기 준비 흐름에 포함 | 서류·대상·발급 방식과 맞는 공식 경로 확인. 확인된 링크부터 제공 |
| 캘린더 파일 내보내기 | 푸시와 분리해 일정 정확성·가져오기 사용성을 검증한 뒤 구현 범위 별도 확정 | 검증된 일정의 .ics 생성, 실제 대상 기기의 가져오기·변경·중복 처리 확인. 기능 구현 자체는 아직 미확정 |
| 푸시·이메일 기한 알림 | 후순위로 유지하고 수요·운영 부담을 별도 판단 | 권한·구독·예약·발송·실패·기한 변경 및 취소 처리 검토 |
| 준비도(%)·집 건축 표현 | 초기 완성 범위에 포함 | 계산·집 단계 매핑·미확인/재확인 표시·저장 결과 일치와 사용자 이해도 검증 |

준비도와 집 건축 표현의 단계적 후도입 제안은 기각한다. 상태별 목록·필수 미확인 표시는 %·집 표현을 대체하는 단계가 아니라 함께 제공할 정보다. 사용자 검증은 표현의 의미·가중치·단계 매핑을 개선하기 위한 절차이며 두 요소를 초기 완성에서 제외하는 근거로 자동 적용하지 않는다. 구현은 작은 흐름부터 순차적으로 진행할 수 있으나 초기 완료·시연에는 두 요소가 실제 준비 상태와 연결돼 있어야 한다.

### 공식 발급 링크 검수·제공 기준

- 공식 기관의 경로인지, 안내하는 서류·발급 대상·온라인/방문 등 발급 방식과 맞는지 준비 안내 검수에서 함께 확인한다.
- 사용자가 선택해야 할 문서 종류·공고 기준 등 확인된 발급 조건을 이동 전에 안내한다. 직접 신청 주소가 로그인이나 세션에 종속되면 안정적인 공식 안내 페이지를 사용한다.
- 모든 서류의 링크 확보를 기다리지 않고 검증된 링크부터 제공한다. 미검증 링크나 온라인 발급 불가 상황은 발급 방법·공식 기관 확인 경로로 안내하며 임의의 주소를 생성하지 않는다.
- 링크·공식 기관·검증일·적용 서류·근거를 기록하고 오류·변경 시 해당 링크 제공을 보류한다. 발급처 방문을 서류 준비 완료나 준비도 증가로 처리하지 않는다.

### 캘린더 내보내기와 푸시의 별도 평가

캘린더 파일 내보내기는 선택한 검증 일정의 복사본을 제공하는 기능이다. 기본 정보 검증을 마친 공식 신청 일정은 준비 안내 검수 중에도 후보로 다룰 수 있으며, 개인별 조건부 서류 기한은 관련 준비 규칙 검수 완료 후 다룬다. 일정 제목·단계·날짜/시각·공식 원문·기준 버전·파일 생성 시점을 포함하고 개인 답변·민감정보는 넣지 않는다. 날짜만 있는 값에 임의의 마감 시각을 부여하지 않는다.

.ics 파일 생성 성공과 외부 캘린더 등록 성공을 구분한다. 파일 가져오기는 공고 변경의 자동 동기화가 아니며, 재가져오기의 중복·갱신 동작과 모바일 다운로드·가져오기 흐름을 실제 대상 앱에서 확인한다. 변경 공고에는 이미 내보낸 파일의 기준이 달라졌음을 안내하고 기존 일정의 확인·갱신 방법을 제공해야 한다. [Google Calendar 파일 가져오기 안내](https://support.google.com/calendar/answer/37118?hl=ko)

검증 후 캘린더 구현 범위를 별도로 결정한다. 그 전까지 진입점은 기능 준비 중 안내로 유지한다. 푸시는 캘린더 내보내기의 전제나 묶음 기능이 아니며, 현재 기한 기록 도구·놓친 이유·알림 수요와 운영 부담을 조사한 뒤 별도 판단한다.

### 준비도 계산 원칙

단순히 체크된 항목 수만으로 준비도를 계산하지 않는다.

예를 들어 다음 요소를 반영한다.

- 핵심 조건 확인 여부
- 필수 서류 확인 여부
- 조건부 서류 해당 여부 확인
- 주요 기한 확인 여부
- 제출 전 확인 항목 완료 여부

필수 항목이 미확인 상태라면 일반 준비 항목을 많이 완료했더라도 이를 별도로 경고한다.

```
준비도 80%

주의
필수 조건 1개가 아직 확인되지 않았습니다.
```

정확한 가중치는 실제 공고 분석과 사용자 테스트를 거쳐 결정한다.

### 초기 운영 범위와 유지할 제외 항목

- 한 기관의 공고 자동 수집부터 시작하며 지역·유형을 미리 제한하지 않음. 여러 공고의 공통 구조·새 준비 규칙·검수 및 사용자 검증 작업량으로 초기 정밀 안내 범위를 선정
- 첫 구현용 대표 공고 1건과 추가 2∼3건을 시작점으로 차이를 대표하는 표본 구성. 표본 수는 전체 수집량·지역·유형의 상한이 아니며 주요 차이가 빠지면 보완
- 반복 항목은 추출을 자동화하고 조건·서류·예외·기한은 공식 원문 대조 후 공개
- 모바일 중심 반응형 웹으로 구현
- 사용자 증빙서류는 업로드하지 않고 상태만 관리. 공식 공고 첨부파일의 확보·분석은 허용
- 주민등록번호, 계좌번호, 소득 증빙 원본 등 민감정보를 저장하지 않음
- 실제 신청은 공식 기관 사이트에서 진행
- 실시간 알림 대신 서비스 내 마감일 표시를 우선 구현
- 사용자 요구로 확정한 복합 검색과 이메일·Google·카카오 로그인은 포함하되, 기술 시연을 위한 추가 기능이나 파일 업로드는 포함하지 않음
- 검색 필터의 선택값은 실제 공개 데이터에 맞춤. 필터 시연만을 위해 미검증 기관·유형의 준비 규칙을 추가하지 않으며 같은 규칙의 적용 범위는 검증 후 확대 검토

### 후순위 기능

캘린더 파일 내보내기는 위 별도 평가 대상으로 관리한다. 실제 구현 범위 확정 전에는 준비 중 진입점을 유지하며 푸시·이메일 알림과 묶어 채택하지 않는다.

- 선택한 공고의 조건·서류·일정 비교
- 이메일 또는 푸시 기한 알림
- 다른 공고에서 재사용할 수 있는 준비 경험 기록
- 수정 공고 전후 비교
- 완료된 신청 여정 보관
- 사용자 피드백 기반의 공고 설명 개선
- 접근성 옵션과 다국어 안내

### 초기 범위에서 제외

- 전국 모든 주거정책 통합
- 자동 청약 또는 신청
- 당첨 확률 예측
- 최종 자격 판정
- 주민등록·소득·재산 정보 자동 조회
- 사용자 증빙서류 원본 업로드 및 판독
- 모든 공고의 조건·예외를 검수 없이 자동 해석해 확정 안내 제공
- 상담기관을 대체하는 법적·행정적 판단
- 사용자 간 준비도 랭킹
- 매일 출석하거나 연속 접속해야 하는 기능

| 제출 서류 | 공식 안내에서 추출한 후보를 원문과 대조 | 공통·조건부·추가 요청 서류, 발급 기준·제출 대상 구분 |
| 발급 정보 | 공식 발급기관 안내 확인 | 비공식 블로그를 최종 근거로 사용하지 않음 |
| 단계별 일정 | 공고와 후속 공식 안내 확인 | 수정 공고와 변경 여부 관리 |
| 사용자 답변 | 조건 확인에 필요한 최소 항목만 직접 입력 | 모름·확인 필요 선택 제공 |
| 준비 상태 | 사용자가 직접 기록 | 서류 적정성 및 공식 접수 완료와 구분 |
| 수정 이력 | 신규·수정 자동 감지 후 기존 버전과 원문 대조 | 영향 항목·재확인 필요·검수 및 적용 이력 기록 |
| 회원 식별·인증 정보 | 확정한 가입·로그인 방식에 따라 확보 | 준비 건의 소유자 식별, 계정과 관리자 권한 분리. 비밀번호 사용 시 평문 저장 금지 |

### 데이터 구조

```
기관
 ├ 수집 실행 기록
 └ 공고 (외부 식별자·출처 연결)
    ├ 수집 원본·첨부 정보
    ├ 구조화 초안·동시 검수 기록
    ├ 기본 정보 검증·공개 상태·기준 버전·확인일
    ├ 준비 안내 검수·제공 상태·기준 버전·확인일
    ├ 공고 버전
    ├ 신청 단계
    ├ 조건
    │  ├ 질문
    │  ├ 예외
    │  └ 공식 근거
    ├ 제출 서류
    │  ├ 공통 서류
    │  ├ 조건부 서류
    │  └ 발급 정보
    └ 일정
```

사용자 데이터는 다음과 같이 연결한다.

```
사용자
 └ 신청 준비 건
    ├ 선택한 공고 버전
    ├ 조건별 답변
    ├ 조건 확인 상태
    ├ 개인별 서류 목록
    ├ 서류 준비 상태
    ├ 일정 확인 상태
    └ 신청 여정 진행 상태
```

### 데이터 확보 전략

**한 기관의 공고 자동 수집 + 소수 공고로 규칙 검증 + 검수 후 준비 안내 공개**를 채택한다. 수집과 조건 해석을 구분하며 대표 표본으로 정한 데이터 구조·정답을 자동화의 검증 기준으로 사용한다.

| 항목 | 확정 방향 | 적용 범위 |
| --- | --- | --- |
| 수집 | 한 기관의 공식 API 우선 자동 수집 | 신규 공고·기본 정보·원문 및 첨부 링크. 실제 제공 항목을 먼저 확인 |
| 검증 표본 | 첫 구현용 대표 공고 1건과 차이를 대표하는 추가 표본 | 추가 2∼3건은 시작점이며 조건·서류·절차·예외 차이를 검증할 수 있도록 조정. 수집량·지역·유형의 상한이 아님 |
| 구조화 | 반복 항목부터 추출 자동화, 사람이 조건·서류·예외 검토 | 사용자 질문·개인별 준비 규칙으로 변환하는 정확성 확인 |
| 검수·공개 | 공고 정보와 준비 안내를 동일 검수 과정에서 확인하되 결과·공개 상태는 구분 | 기본 정보 검증·공개 완료 공고는 검색·상세 제공. 개인별 준비 안내는 해당 규칙 검수·공개 완료 후 제공 |
| 수정 공고 | 변경 자동 감지 후 영향 검토 | 기존 공개 규칙·사용자 준비 상태를 자동으로 덮어쓰지 않음 |
| 초기 범위·확장 | 한 기관을 우선 조사하되 지역·지원 유형은 미리 제한하지 않음 | 공통 데이터 구조·규칙 재사용성·추가 준비 규칙·검수 및 사용자 검증 작업량으로 초기 범위 선정. 다른 기관 도입은 별도 평가 |

#### 초기 범위 비교 기록

| 비교 항목 | 공고별 기록 내용 | 범위 선정 기준 |
| --- | --- | --- |
| 수집 경로·형식 | API·원문·첨부 경로, 식별자, 필드와 수정 형식 | 같은 경로·매핑으로 처리되는지, 별도 수집 구현이 필요한지 |
| 공통 데이터 구조 | 조건·서류·일정·단계·근거를 기존 구조로 표현 가능한지 | 지역·유형명만 다르면 제외하지 않음. 구조 변경은 실제 차이로 판단 |
| 준비 규칙 | 새 질문, 답변 분기, 조건부 서류, 예외, 신청 단계 | 값·설정 차이와 새 업무 규칙을 구분해 추가 구현량 기록 |
| 검수·운영 | 원문 대조 시간, 오류·확인 필요 항목, 수정 영향 | 자동 수집 성공과 준비 안내 정확성을 구분하고 학기 중 운영 가능한지 평가 |
| 사용자 검증 | 공통 준비 문제, 유형별 여정·화면 이해 차이, 경험자 확보 | 주요 차이를 검증할 인터뷰·테스트를 계획할 수 있는지 |
| 포함 판단 | 공통 처리 가능 / 추가 규칙 필요 / 후순위와 근거 | 공통 처리되고 검증 가능한 공고는 함께 포함. 새 규칙은 추가 작업량 확인 후 판단 |

표본은 비슷한 공고 수를 채우기보다 공통 규칙과 주요 차이를 대표하도록 선정한다. 지역·유형 수나 표본 수만으로 완료를 판단하지 않으며, 범위 선정 근거·남은 미검증 사례·담당 작업을 회의 기록에 남긴다. 이번 결정은 범위 선정 기준의 채택이며, 특정 기관·지역·유형의 지원 확정이나 실제 API 검증 완료를 뜻하지 않는다.

#### 수집·검수 흐름

```text
공식 API·원문·첨부에서 자동 수집
→ 출처·외부 식별자·원본 및 변경 근거 기록
→ 기본 필드 매핑·반복 항목 추출·구조화 초안
→ 공고 정보와 준비 안내를 동일 작업에서 원문·근거 대조
→ 기본 정보·준비 안내 결과 및 공개 상태 각각 결정
→ 신규·수정 감지 및 영향 검토·재확인 처리
```

1. 후보 기관의 여러 지역·유형 공고를 비교하고, 첫 구현용 대표 공고 1건을 직접 분석해 조건·질문·서류·기한·근거의 구조와 정답 사례를 만든다.
2. 인터뷰와 병행해 한 기관의 공식 API를 연동하고 신규 공고·기본 정보를 자동 수집한다.
3. 추가 공고 2∼3건을 시작점으로 공통 규칙·주요 예외·형식 차이를 대표하는 표본을 구성하고 반복 항목부터 추출을 자동화한다. 차이가 빠지면 표본을 보완하며 추가 구현·검수 작업량으로 초기 범위를 선정한다.
4. 구조화 담당자와 별도 검토자가 같은 작업에서 공고 정보·준비 안내를 원문 대조하고 각 결과·보완 사유를 기록한다. 기본 정보 통과 후 목록 공개, 준비 규칙 통과 후 개인별 안내를 제공한다.
5. 수정 공고는 새 검수 버전으로 기록하고 변경 영향·사용자 재확인 항목을 확인한 뒤 적용한다.

수집 성공이 검수 성공을 뜻하지 않는다. 최초 동시 검수를 시작하기 전에는 공고 기본 정보도 공개하지 않는다. 일반 검색은 기본 정보 검증·공개 완료 공고를 제공하며, 미검수 원본 응답·구조화 초안·준비 규칙은 내부 작업 대상으로 관리한다. 기본 정보와 준비 안내를 동시에 검수하지만 두 영역이 모두 통과해야만 목록에 공개하는 방식은 사용하지 않는다.

#### 동시 검수와 공개 정책

공고·원문 버전별 하나의 작업에서 공통 출처·식별·최신 버전 확인 → 기본 정보 확인 → 준비 안내 확인 → 영역별 결과 기록 순서로 진행한다. 검수 담당자는 같은 원문을 활용하고 공식 기간 등 공통 값을 공유해 중복 입력을 줄인다. 검수 결과·보완 사유·검토자·확인 시각·기준 버전과 공개 이력은 두 영역별로 남긴다.

| 동일 검수의 결과 | 공고 목록·기본 상세 | 개인별 준비 안내 |
| --- | --- | --- |
| 기본 정보·준비 안내 모두 통과 | 공개 | 제공 |
| 기본 정보 통과·준비 안내 보완 필요 | 공개 | 보완 완료까지 제공 보류 |
| 기본 정보 통과·준비 안내 미지원 | 공개 | 미제공 표시 |
| 공고 식별·출처 등 기본 정보 검증 실패 | 공개 보류 | 제공 보류 |

- 기본 정보 검증: 공식 출처·공고 식별, 제목·기관, 지역의 의미와 유형, 신청 단계가 명시된 공식 기간, 원문·첨부 링크를 대조한다. 값이 없으면 확인 필요로 남기며 임의 조건 요약·신청 가능 판단을 넣지 않는다.
- 준비 안내 검수: 조건별 질문·예외·공통 및 조건부 서류·신청 단계·기한과 공식 근거를 대조한다. 준비 안내 미지원은 공식 공고가 잘못됐거나 신청할 수 없다는 뜻이 아니다.
- 사용자 상태 표시: `준비 안내 제공 중`, `준비 안내 검수 중`, `준비 안내 미제공`, `준비 안내 변경 검토 중`을 구분한다. `검수 중`은 집으로 안내의 검토 상태이며 기관의 공고 검토 상태가 아니다.
- 준비 시작: 기본 정보 공개와 적용 준비 규칙의 검수·공개·버전 유효성이 확인된 경우에 제공한다. 안내가 없으면 원문 확인 경로를 제공하고 질문·서류·준비도를 추측해 생성하지 않는다. 서버가 직접 요청도 검사한다.
- 수정 공고: 동일 작업에서 양쪽을 확인하되 기본 정보는 해당 검증을 마친 뒤 갱신할 수 있다. 영향받는 준비 안내는 변경 검토 중으로 표시하고 해당 신규 안내·시작을 보류한다. 기존 답변·준비 상태는 과거 기준 버전과 함께 보존하며 최신 안내와 구분한다. 영향이 없다고 확인한 범위는 검토 근거와 함께 유지할 수 있다.
- 확인 시점: 공고 기본 정보 확인일과 준비 안내 확인일·버전을 구분한다. 기본 상세의 최신 정보와 과거 개인 준비 기록의 값이 다른 경우 변경 이유·기준 시점을 설명한다.

이 정책은 첫 검수 전부터 공고를 자동 공개하는 방식이 아니다. 동시 검수로 업무를 묶되 준비 안내의 보완이 정확한 기본 정보의 공개를 계속 막지 않도록 한다. 목록의 출처·기간·최신성 검증과 준비 안내의 규칙 정확성·사용성 평가는 별도로 수행한다.

#### 데이터 제공 경로와 후속 확인

[LH 공고 조회 API](https://www.data.go.kr/data/15058530/openapi.do)는 공고 기본 정보와 상세 URL 등을 제공하며, [LH 공고별 공급정보 API](https://www.data.go.kr/data/15056765/openapi.do)는 공고별 공급정보를 제공한다. 이는 공식 API 후보이고 LH를 대상 기관으로 확정하거나 실제 호출을 완료했다는 뜻은 아니다. 필요한 세부 조건·서류·예외와 첨부 확보 가능 여부는 실제 응답·공식 원문을 대조해 확인한다.

기관·지원 유형을 정한 뒤 제공 필드·첨부 형식·갱신 주기·요청 한도·활용 조건·보관 정책을 확인한다. API에 없는 항목은 공식 홈페이지의 제공 방식에 맞춰 확보한다. 원본 비교에 필요한 정보와 확인 이력을 보존하며 공식 공고 첨부의 저장 위치·기간·용량은 배포 설계에서 결정한다. 사용자 증빙 원본 업로드 제외는 유지한다. 추출 자동화의 도구·AI 사용 여부는 별도 검토하며 MVP의 준비 안내는 검수된 규칙으로 실행한다.

### 조건 안내 상태

- **확인됨:** 입력 내용과 공고의 명시 조건을 연결할 수 있음
- **불일치 가능:** 입력 내용이 명시 조건과 맞지 않을 가능성이 있음
- **추가 확인 필요:** 정보가 부족하거나 예외 조건이 있어 판단할 수 없음
- **기관 문의 권장:** 공식 상담을 통해 확인해야 함

‘지원 가능’, ‘자격 확정’, ‘당첨 가능’처럼 최종 판단으로 오해될 표현은 사용하지 않는다.

## 7. 인터뷰 대상 및 질문

### 1차 탐색 인터뷰 대상

- 최근 청년 공공임대 또는 주거지원 사업에 처음 신청한 사람
- 공고를 확인했지만 신청하지 않은 사람
- 신청을 시작했지만 중단한 사람
- 가족이나 친구의 신청 준비를 도운 사람
- 가능하다면 동일 유형의 공고를 두 번 이상 신청한 사람
- 해당 사업의 상담 또는 안내 경험자

공고 비교로 확인한 공통 신청 여정을 기준으로 경험자를 모집하되, 초기 포함 후보에 준비 절차가 다른 유형이 있으면 해당 경험자도 인터뷰한다. 동일·유사 유형에서 발견한 문제를 다른 유형에도 그대로 적용한다고 가정하지 않고, 공통 어려움과 유형별 차이를 구분한다.

### 초기 모집 규모

신청·중단 경험자 5∼8명을 대상으로 탐색한다. 전체 신청자를 대표하는 통계보다 반복해서 나타나는 행동과 어려움을 발견하는 데 목적을 둔다.

### 초기 정량 목표안

사용성 테스트 기준값을 확보한 후 조정하되, 초기 목표는 다음과 같이 설정할 수 있다.

- 지원하는 공고의 핵심 조건·서류·기한에 공식 근거 연결률 100%
- 사용자 과제 수행 중 치명적인 조건·서류 오안내 0건
- 테스트 참여자의 80% 이상이 도움 없이 ‘지금 할 일’을 찾음
- 테스트 참여자의 80% 이상이 준비도와 신청 자격을 구분함
- 공고 원문만 이용할 때보다 준비 목록 누락 수 감소
- 공고 원문만 이용할 때보다 신청 준비 과제 완료 시간 감소
- 여정 표현을 불필요하거나 부적절하다고 느끼는 사용자가 반복적으로 나타나지 않음

소규모 테스트 결과를 전체 청년 신청자에게 일반화하지 않는다.

### 평가 설계 시 유의점

- 필요한 조건과 서류의 정답은 공식 공고를 근거로 사전에 작성한다.
- 수집률은 같은 기관·기간·유형의 공식 목록을 기준으로 계산한다. API 호출 성공률만으로 공고 누락이 없다고 판단하지 않는다.
- 추출 누락·예외 누락과 검수 소요 시간을 분리해 기록하며 자동 추출 결과의 정확성과 검수 후 공개 정확성을 구분한다.
- 같은 공고를 반복 사용해 생기는 학습 효과를 줄이기 위해 과제 순서를 조정한다.
- 실험용 과거 공고는 현재 신청 가능한 공고와 명확히 구분한다.
- 당첨 여부는 외부 요인이 크므로 서비스 성과로 사용하지 않는다.
- 준비도 상승 자체보다 올바른 준비 행동과 누락 감소를 평가한다.
- 집 이미지 선호도와 서비스 효용을 별도의 질문으로 측정한다.

## 10. 주의할 점과 주제 중단·축소 기준

### 정보 정확성

- 비슷한 이름의 사업이라도 조건·일정·서류를 동일하게 적용하지 않는다.
- 공고와 첨부 문서의 버전을 함께 관리한다. 주소가 같아도 내용이 바뀔 수 있어 첨부 해시·식별자 또는 원문 비교로 확인한다.
- 신규·수정 공고는 자동 감지하고 영향을 받는 항목을 검수한다. 검토 중인 변경을 확정된 규칙처럼 자동 반영하지 않는다.
- 모든 안내에 공식 근거와 확인일을 표시한다.
- 조건을 구조화한 팀원과 검토한 팀원을 분리한다.

### 과도한 판단 방지

- 사용자 입력만으로 최종 자격을 확정하지 않는다.
- 선정 가능성이나 당첨 확률을 제공하지 않는다.
- 준비 완료가 서류의 공식 적정성을 의미하지 않음을 안내한다.
- 판단할 수 없는 조건은 ‘추가 확인 필요’로 남긴다.
- 공식 상담이 필요한 사항은 문의 경로를 안내한다.

### 게이미피케이션 주의점

- 집 완성이 당첨이나 입주 성공으로 오해되지 않게 한다.
- 준비도가 자격 충족도처럼 보이지 않게 한다.
- 행정 절차의 긴장감을 지나치게 가볍게 만들지 않도록 한다.
- 마감일을 놓친 사용자에게 벌점이나 집 파괴를 적용하지 않는다.
- 사용자를 조급하게 만드는 과도한 경고와 연속 접속 기능을 사용하지 않는다.
- 접근성을 위해 집과 색상 없이도 진행 상태를 이해할 수 있게 한다.

### 개인정보

- 주민등록번호, 계좌번호, 사용자 증빙서류 원본을 저장하지 않는다. 기관이 공개한 공식 공고·첨부 문서의 수집·분석·보관은 별도로 관리한다.
- 소득·재산의 정확한 금액보다 조건 확인에 필요한 최소 정보만 입력받는다.
- 민감한 답변의 저장 여부를 사용자가 선택할 수 있게 한다.
- 테스트 과정에서도 실제 서류 원본을 수집하지 않는다.
- 개인별 답변·메모·준비 상태는 서버에서 소유자를 확인한 뒤 조회·수정한다.
- 로그인 수단은 이메일·비밀번호, Google, 카카오로 확정했다. 입력 답변의 저장 범위와 계정·준비 건 삭제 방침은 후속 기획에서 확정한다.
- JWT·쿠키·비밀번호·개인 조건 답변을 로그나 공유 기록에 남기지 않는다.

### 기술 도입과 구현 부담

- 채택한 도구·버전 계열과 실제 설치·검증 완료를 구분한다. 패치 버전·의존성 조합은 초기 빌드에서 확인하고 고정한다.
- Access JWT는 15분·메모리 보관, Refresh는 불투명 난수 토큰 7일·보안 쿠키·서버 해시 저장·재발급 시 교체로 확정한다. 쿠키·CSRF의 구체 설정은 실제 주소 구성에 맞춘다.
- Spring Data JPA·OpenFeign 계열 Querydsl·Flyway를 채택한다. 설정·검색·인증 작업을 작은 단계로 나눠 팀의 학습 부담과 담당자 집중을 관리한다.
- Querydsl은 선택 조건이 결합되는 데이터 조회에 사용한다. 공고의 자격 조건 해석과 준비도 계산은 별도의 업무 규칙으로 구현한다.
- 초기부터 지역·지원 유형·마감 상태·키워드 복합 검색이 필요하므로 Querydsl을 도입한다. 공고 수가 적다는 이유로 확정한 검색 요구를 제외하지 않는다.
- 새 라이브러리를 채택할 때 Q 클래스 생성·실제 조회 등 작은 기능으로 호환성을 먼저 확인한다.
- AWS 무료 이용 목표는 계정 플랜·기간·크레딧 조건 확인 전에는 달성을 확정할 수 없다. 배포 상세와 비용 검토는 추후 진행한다.

### AI 사용

- AI가 생성한 해석을 검토 없이 사용자에게 제공하지 않는다.
- 공고 요약에 AI를 사용하더라도 공식 원문과 사람의 검토를 거친다.
- AI의 답변을 자격 판정 근거로 사용하지 않는다.
- MVP에서는 규칙 기반 조건 안내를 우선한다.

### 주제 축소 또는 재검토 기준

- 신청 경험자에게 조건·서류·일정 문제가 반복해서 나타나지 않음
- 기존 공식 서비스가 개인별 준비 목록과 상태 관리를 충분히 제공함
- 사용자가 새로운 서비스보다 공식 상담만 선호함
- 하나의 공고를 구조화하고 검토하는 작업량이 지나치게 큼
- 공고 변경을 학기 중 안정적으로 관리하기 어려움
- 사용자들이 준비도를 자격 또는 당첨 가능성으로 계속 오해함
- 집 이미지와 여정 표현이 문제 해결에 도움이 되지 않거나 부적절하다는 반응이 반복됨
- 초기 포함 후보의 공통 신청 여정과 주요 유형별 차이를 검증할 경험자를 충분히 확보하지 못함

실제 추가 구현·검수 부담이 감당하기 어려운 경우에만 다음 순서로 범위를 조정한다. 지역·유형 수 자체를 축소 기준으로 삼지 않으며, 공통 구조로 처리되는 공고는 유지한다.

```
수집 경로·준비 규칙·검수 작업량 비교
→ 새 수집 경로와 독립적인 준비 규칙이 많은 범위를 후순위로 조정
→ 공통 구조·규칙을 재사용할 수 있는 공고군 우선
→ 검증하기 어려운 예외 안내는 확인 필요로 처리
→ 필요 시 대표 공고 한 건의 완성도 높은 신청 여정부터 검증
```

## 11. 팀 회의에서 결정할 사항

### 서비스 범위

- 어느 기관을 우선 조사하고, 여러 지역·유형 중 어떤 공고가 공통 구조·규칙으로 처리되는가?
- 추가 질문·조건부 서류·예외·신청 단계와 검수·사용자 검증 작업량을 비교했을 때 함께 포함할 초기 범위는 어디까지인가?
- 현재 공고와 과거 공고 중 무엇을 테스트에 사용할 것인가?
- 첫 구현용 대표 1건과 차이를 대표하는 추가 표본으로 주요 규칙·예외를 검증하고 한 기관의 자동 수집·검수 흐름을 학기 안에 운영할 수 있는가?
- 실제 신청 시기와 사용자 테스트 일정을 맞출 수 있는가?

### 문제 검증

- 동일 유형의 신청·중단 경험자 5명 이상을 모집할 수 있는가?
- 인터뷰 참여자를 어떤 경로로 모집할 것인가?
- 조건 이해, 서류 준비, 일정 관리 중 우선 해결할 문제는 무엇인가?
- 인터뷰 이전에 시안을 보여주지 않고 과거 경험부터 확인할 수 있는가?

### 데이터 관리

- 누가 자동 수집을 구현하고 누가 정답 사례·구조화 초안·교차 검토를 담당할 것인가?
- 대상 API의 제공 필드·첨부 형식·갱신 동작·요청 한도는 무엇인가?
- 공고의 페이지·문단 근거를 어떤 형식으로 저장할 것인가?
- 신규·수정 감지의 주기·중복 방지·재시도와 변경 검토·공개 적용을 어떻게 구현할 것인가?
- 공식 원문·첨부의 보관 위치·기간·용량과 기존 준비 건의 재확인 정책은 무엇인가?
- 관리자 화면을 어느 수준까지 구현할 것인가?

### 준비도와 신청 여정

- 준비도에 포함할 항목과 가중치는 무엇인가?
- 필수 항목 미확인 상태를 어떻게 경고할 것인가?
- 집 건축 단계를 몇 단계로 구성할 것인가?
- 신청 여정이 당첨 과정으로 오해되지 않게 어떻게 표현할 것인가?
- 준비도와 자격 조건 상태를 화면에서 어떻게 분리할 것인가?

### MVP 기능

- 확정한 이메일·비밀번호·Google·카카오 로그인과 비회원 공고 조회를 화면에 어떻게 연결할 것인가?
- 이메일 인증·비밀번호 재설정·계정 연결·해제 정책을 어떻게 정할 것인가?
- 개인 준비 상태를 저장하기 전에 로그인을 요구하는 화면 흐름은 무엇인가?
- 확정한 JWT·Refresh 정책으로 만료·재발급·로그아웃·새로고침 복원 화면을 어떻게 구현할 것인가?
- 검증된 공식 발급 링크의 서류별 적용 범위·담당자·완료 조건은 무엇인가?

- 푸시·이메일 알림의 실제 수요와 예약·발송·실패·수정 처리 부담은 어떤가?
- 공고 비교 기능을 후순위로 둘 수 있는가?
- 서류 발급 사이트 연결을 어디까지 제공할 것인가?
- 사용자 메모와 준비 상태를 어떤 단위로 저장할 것인가?
- 계정·준비 건 삭제와 민감한 답변의 저장 선택을 어떤 방식으로 제공할 것인가?

### 기술 설정·검증

- 공통 개발 환경·잠금 파일·Gradle Wrapper·Spotless·CI를 누가 구성하고 검토할 것인가?

- 인증·조건 안내·준비도·공고 데이터 검수 작업을 어떻게 분담할 것인가?
- 소셜 앱 등록·쿠키·CSRF·계정 관리 세부 정책은 누가 명세할 것인가?
- AWS 기본 구성은 채택했으며 실제 사양·비용·배포 절차는 후속 회의에서 별도 논의한다.

### 기능과 기술의 연결

### 확정 검색·API 계약

| 항목 | 확정 계약 |
| --- | --- |
| 초기 검색 조건 | 지역·지원 유형·마감 상태·키워드 |
| 조건 결합 | 서로 다른 필터는 AND, 동일 필터의 여러 선택값은 OR |
| 공개 대상 | 기본 정보 검증·공개 완료 공고를 일반 검색에 포함. 준비 안내 보완·미지원 공고도 포함하며 개인별 준비 기능은 별도 검수·공개 상태로 제한 |
| 검색 상태 | URL query parameter에 보관해 새로고침·뒤로가기 시 복원 |
| 페이지네이션 | page는 0부터 시작, size 기본 20·최대 100 |
| 성공 응답 | 응답 DTO 직접 반환, 공통 성공 래퍼 사용 안 함 |
| 빈 검색 결과 | 정상 성공 응답(200), 목록 필드는 빈 배열 |
| 오류 응답 | code, message, fieldErrors, timestamp의 공통 형식 |
| 실제 시각 | UTC로 저장·전송, 한국 시간대(Asia/Seoul)로 화면 표시 |
| 날짜만 있는 값 | 시각과 분리해 날짜로 표현. 공식 공고의 마감 기준·포함 여부 명시 |

필터별 허용 값, 키워드 검색 대상 필드, 정렬의 기준·동률 처리, 페이지 응답 DTO의 필드 명세는 공식 공고 구조화와 API 설계에서 구체화한다. 검증 표본 수는 전체 수집량의 상한이 아니며, 검색 필터만을 위해 미검증 기관·유형의 준비 규칙을 추가하지 않는다. 동일한 규칙의 적용 범위는 검증 후 확대를 검토한다.

Querydsl은 별도의 조회 Repository에 사용하며 단순 CRUD 전체를 전환하지 않는다. 자격 조건 안내·준비도 계산은 검색과 구분한 업무 규칙으로 구현한다. 선택한 JDK·Spring Boot·Hibernate·Jakarta JPA 조합에서 OpenFeign Querydsl 7.7의 Q 클래스 생성과 테스트 DB 복합 조회를 검증했다. 실제 공고 검색 검증은 후속 작업이다. 원본 Querydsl과 OpenFeign 포크 의존성은 혼용하지 않는다. [공식 Querydsl 안내](https://docs.spring.io/spring-data/jpa/reference/repositories/core-extensions.html)

### 확정 로그인·토큰 정책

| 항목 | 확정 정책 |
| --- | --- |
| 로그인 수단 | 이메일·비밀번호 + Google + 카카오 |
| 인증 구성 | Spring Security + JWT, 소셜 로그인은 Spring Security OAuth2 Login |
| 서비스 토큰 | 세 로그인 경로 모두 자체 Access Token·Refresh Token 발급 |
| Access Token | JWT, 유효기간 15분 |
| Access Token 보관·전송 | React 메모리 보관, Authorization: Bearer 헤더로 전송 |
| Refresh Token | 불투명한 난수 토큰, 유효기간 7일, HttpOnly·Secure 쿠키 |
| Refresh Token 서버 관리 | PostgreSQL에 해시·만료 시각·폐기 상태 저장, 재발급 시 교체 |
| 비밀번호 | Spring Security PasswordEncoder로 단방향 해시 저장 |
| 로그아웃 | Refresh Token 폐기, 쿠키 삭제, 메모리 Access Token·개인 데이터 캐시 제거 |
| 비회원 | 공개 공고 목록·상세 조회 가능 |
| 회원 | 개인 답변·준비 건·준비 상태 저장에는 로그인 필요 |
| 관리자 | 별도 역할로 서버에서 검사. 공개 회원가입 요청으로 관리자 권한 부여 불가 |
| 계정 식별·연결 | 사용자와 로그인 수단을 분리. 이메일이 같아도 자동 병합하지 않으며 기존 계정 인증 후 연결 |
| JWT 검증 | Spring Security Resource Server JWT 기능 활용 |

- Google·카카오는 Spring Security OAuth2 Login으로 연동하며 세 로그인 경로 모두 자체 서비스 토큰을 발급한다. 소셜 제공자 토큰을 자체 API 인증에 사용하지 않는다.
- 새로고침 시 메모리 Access Token이 사라지면 유효한 Refresh Token으로 재발급한다. 실패 시 비로그인 상태로 전환한다.
- 쿠키를 사용하는 재발급·로그아웃 요청에 CSRF 대응을 포함한다. SameSite·Path·Domain, 개발 환경과 소셜 앱 설정은 후속 구현에서 구체화한다.
- 이메일 인증·비밀번호 재설정·계정 연결·해제·탈퇴·데이터 삭제·관리자 생성 절차는 별도 정책으로 정한다.
- 로그아웃 후 이미 발급된 Access Token은 만료까지 유효할 수 있다. 이 제약과 Refresh Token 재사용 차단을 검증 사례에 기록한다.

### 모노레포의 실행·빌드·배포 및 협업 원칙

저장소는 하나로 유지하고 프론트엔드·백엔드는 별도 프로젝트로 실행·빌드·배포한다. 소규모 팀에서 화면·API·관련 문서의 연동 변경을 함께 검토하고 이슈·진행 상황을 한곳에서 확인하기 위한 선택이다.

- 프론트엔드는 `frontend/`에서 VS Code·npm, 백엔드는 `backend/`에서 IntelliJ IDEA·Gradle Wrapper를 사용한다. 의존성·설정·실행·빌드 산출물을 각각 관리한다.
- 각 프로젝트의 README에 설치·실행·검사·빌드 방법을 기록하고 루트 README에서 전체 실행 순서·API 연동 확인 방법을 연결한다. 초기에는 별도 모노레포 관리 도구를 추가하지 않는다.
- 기능·수정 단위 브랜치와 PR을 사용하고 기존 `main`·`develop` 정책을 유지한다. 필요한 프론트·백엔드·API 문서 변경은 함께 검토하며 큰 작업은 연결된 PR로 나눠 의존 관계와 통합 확인 순서를 명시한다. 공통 설정·같은 파일 변경은 먼저 조율한다.
- PR 검사는 프론트·백엔드별 작업으로 구성하고 초기에는 양쪽을 모두 실행한다. 개별 검사·빌드 통과와 실제 사용자 흐름의 연동 완료를 별도로 확인한다.
- 배포 산출물·버전·적용·복구 절차는 각각 관리하고 변경 없는 쪽의 재빌드·재시작을 필수로 묶지 않는다. API·DB 변경이 있으면 호환성·적용 순서·통합 확인·복구 제약을 함께 계획한다.
- 실행·빌드·배포 분리는 EC2 대수 증가나 서로 다른 도메인 사용을 뜻하지 않는다. 기존 EC2 1대의 Nginx·Spring Boot·`/api/` 구성을 유지하며 실제 배포·복구 절차와 자동화는 후속 설계에서 정한다.

상세 운영 기준은 [코드 및 기술 규칙의 모노레포 운영 원칙](../conventions/coding-conventions.md#모노레포-운영-원칙--20261020-확정)을 따른다. 운영 원칙과 초기 설정 현황을 반영했다. 로컬 실행·빌드·연동은 검증했으며 원격 CI 실행·실제 기능·배포 구현은 별도 후속 작업이다.

### 첫 구현 흐름과 검증

문제 조사와 공고 분석 중에도 자동 수집의 작은 연동·구조화·개발 환경 검증을 병행할 수 있다. 본격 사용자 기능 구현은 검증 결과를 바탕으로 검수한 공고 한 건의 다음 흐름부터 연결한다.

1. 백엔드 IntelliJ IDEA의 JDK 17·Gradle JVM·Wrapper·Java 스타일, 프론트엔드 VS Code의 Prettier·ESLint 설정과 각 프로젝트의 독립 실행·빌드 및 API 연결 확인
2. 공고 한 건 조회 API와 React 상세 화면 연결
3. 로그인·JWT 검증과 개인 준비 건 접근 권한 연결
4. 준비 항목 한 건 저장 후 새로고침·재로그인 시 유지 확인
5. 조건 안내·조건부 서류·준비도와 수정 공고 처리로 확장

우선 검증 사례는 다른 사용자의 준비 건 접근 차단, 만료·잘못된 토큰, 재발급·로그아웃, 미확인 조건, 조건부 서류, 공고 버전 변경, 저장 상태 유지다. 실제 지원 공고의 정답·근거 검수와 기술 테스트를 함께 수행한다.

## 다음 단계

### 1단계: 초기 범위 결정

- 후보 기관과 주거지원 유형 2∼3개 수집
- 공고와 첨부파일 확보
- 여러 지역·유형의 기본 필드·조건·질문·서류·신청 단계·예외·일정 및 수정 공고 형식 비교
- 인터뷰 대상 확보 가능성 확인
- 지역·유형 수를 미리 고정하지 않고 공통 구조·추가 준비 규칙·검수 및 사용자 검증 작업량으로 초기 지원 범위 선정

### 2단계: 문제 검증

- 신청·중단 경험자 5∼8명 인터뷰
- 실제 사용했던 공고, 메모 방법, 준비 과정을 확인
- 반복되는 문제를 조건·서류·일정·진행 상태로 분류
- 해결 우선순위 결정

### 3단계: 공고 구조화·자동 수집 실험

- 대표 공고 1건을 조건·질문·서류·일정·근거로 분석하고 정답 사례 작성
- 인터뷰와 병행해 한 기관의 공식 API·원문·첨부 제공 방식 확인 및 자동 수집 구현
- 추가 공고 2∼3건을 시작점으로 주요 규칙·예외·형식 차이·필드 누락을 대표하는 표본 구성. 검증되지 않은 차이가 있으면 보완
- 반복 항목 추출 자동화와 원문 교차 검토, 수집·구조화·검수 소요 시간 기록
- 중복 방지·실패 기록·수정 및 첨부 변경 감지·기존 버전 보존 검증
- 규칙으로 표현하기 어려운 예외는 확인 필요로 남김

### 4단계: 프로토타입 검증

- 공고 선택
- 조건별 질문
- 개인별 준비 목록
- 지금 할 일
- 신청 여정과 준비도

위 다섯 화면을 우선 제작한다. 실제 공고를 이용해 원문 방식과 프로토타입 방식을 비교한다.

### 5단계: 본격 MVP 구현 범위 확정

자동 수집·데이터 구조·개발 환경의 작은 실험은 앞 단계와 병행한다. 다음 세 조건을 근거로 본격 사용자 기능의 구현 범위와 우선순위를 결정한다.

1. 신청 경험자에게 반복되는 준비 문제가 존재한다.
2. 서비스 이용 시 누락이나 준비 시간이 감소한다.
3. 공고 한 유형을 학기 내 정확하게 관리할 수 있다.

### 6단계: 채택한 기술 설정과 첫 기능 연결

- 백엔드 IntelliJ IDEA·프론트엔드 VS Code 공통 설정과 잠금 파일·Gradle Wrapper 구성
- Java 공유 스타일 XML·Spotless idea()·Prettier·ESLint의 로컬 검증 결과를 유지하고, 원격 Actions 실행과 CI IntelliJ 환경·필수 검사 연결 확인
- 초기 버전·JPA·Flyway·Q 클래스·테스트 DB 복합 조회 검증 결과를 기준으로 실제 공고 모델·운영 마이그레이션·검색 API 검증 확장
- 이메일·비밀번호 + JWT → Google → 카카오 순으로 연결하고 계정 관리 정책 구체화
- 검색 필터 값·정렬·DTO, 쿠키·CSRF 등 후속 API·인증 설정 명세
- 자동 수집·구조화 초안·관리자 동시 검수·영역별 공개·수정 감지와 공고 조회·복합 검색 연결
- 기본 정보 공개와 준비 안내 제공의 결과별 화면·서버 접근 제한, 변경 검토 및 과거 기록 보존 검증
- 로그인·개인 준비 상태 저장의 작은 흐름 구현
- 준비도(%)·집 건축 표현은 초기 완성 범위로 구현하고 가중치·단계 매핑·공고 변경·관리자 세부 규칙은 공고 분석과 사용자 검증으로 확정
- 검증된 공식 발급 링크 연결 및 미검증·오류 경로 안내 구현, 외부 이동이 완료·준비도를 바꾸지 않는지 확인
- 캘린더 .ics와 푸시를 분리해 기술·사용성 검증 및 구현 범위 결정
- AWS 실제 사양·계정 조건·비용·배포 절차의 구체화는 후속 작업으로 진행

## 범위 제한 재검토와 개선 방향

자동 수집과 관련된 모순·과도한 상한은 이번 개정에 반영했다. 아래 추가 제안은 승인된 MVP 기능을 자동으로 확대하지 않으며, 다음 회의에서 사용자 가치·추가 작업량·검증 가능성으로 판단한다.

| 기존 제한·해석 | 문제 | 개선 방향 | 상태 |
| --- | --- | --- | --- |
| 공고 2∼3건만 수작업으로 관리 | 수집량과 검증 표본을 혼동해 자동화·확장을 막음 | 대표 1건과 차이를 대표하는추가 표본으로 규칙 검증, 추가 2∼3건은 시작점이며 필요 시 보완. 한 기관의 수집은 자동화 | 반영 완료 |
| 서류 업로드 제외이므로 공고 첨부 수집·파일 보관도 제외 | 사용자 증빙과 공개 원문은 목적·취급이 다름 | 사용자 증빙 업로드는 제외, 공식 원문 확보는 허용. 보관 방식은 별도 설계 | 반영 완료 |

| 한 지역·한 지원 유형을 초기 검증 범위로 미리 고정 | 실제 구조·규칙·검수 부담을 확인하기 전에 지원 범위를 좁힘 | 한 기관을 우선 조사하되 여러 지역·유형을 처음부터 비교. 공통 구조·새 준비 규칙·검수 및 사용자 검증 작업량으로 초기 범위 선정 | 채택·반영 완료 |

최종 자격·당첨 판단 제외, 사용자 증빙 원본 업로드 제외, 미확인 조건의 확인 필요 표시, 검수 후 준비 안내 공개는 유지한다. 수집 규모가 늘어도 근거·버전·소유자 권한 검증을 생략하지 않는다.
