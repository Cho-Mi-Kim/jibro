## 1. 과제 개요

본 과제는 청년 주거지원에 처음 신청하는 사용자가 복잡한 공고문을 이해하고, 자신의 상황에 필요한 조건·서류·일정을 빠짐없이 준비하도록 돕는 개인 맞춤형 반응형 웹 서비스를 개발하는 것을 목표로 한다.

기존 주거복지 서비스가 지원정책 탐색, 자가진단 및 공식 신청 기능을 중심으로 제공된다면, 본 서비스는 사용자가 관심 공고를 발견한 이후부터 실제 신청에 이르기까지 필요한 준비 행동을 개인별로 구성하고 관리하는 데 초점을 둔다.

## 2. 문제 정의 및 사전 조사 결과

### 2.1 핵심 문제 정의

청년 주거지원에 처음 신청하는 사용자는 관심 공고를 발견한 이후에도 자신의 상황과 공고의 조건·서류·일정을 연결하기 어렵다. 이로 인해 여러 문서와 사이트를 반복해서 확인하거나 필요한 항목을 놓치고, 경우에 따라 신청을 중단할 수 있다.

본 과제에서는 단순히 공고문이 길고 어렵다는 점보다, 공고에서 얻은 정보를 사용자가 자신의 상황에 맞는 실행계획으로 다시 구성해야 한다는 점을 핵심 문제로 정의한다.

> 청년 주거지원 신청자는 공고를 발견한 뒤에도 자신의 조건을 확인하고, 필요한 서류를 구분하며, 단계별 기한에 맞춰 준비하는 과정을 통합적으로 관리하기 어렵다.

### 2.2 공식 공고 분석

2026년 LH 서울지역본부 청년 매입임대 공고는 3월 31일 공고 후 4월 15일부터 17일까지 신청을 받았다. 신청자는 비교적 짧은 접수 기간에 공고 본문과 첨부자료를 확인하고 자신의 조건과 제출서류를 판단해야 했다.

경기남부 청년 매입임대 공고 페이지에는 모집공고문뿐만 아니라 공급주택 목록, 자주 묻는 질문 등의 자료가 별도 파일로 제공되었으며, 수정 공고가 발생하면 변경 내용을 다시 확인해야 했다. 최초 신청 이후에도 서류 제출 대상자 발표, 서류 접수, 소득·자산 검증과 대상자 선정 등 후속 단계가 이어진다.

따라서 신청자는 하나의 공고문만 읽는 것이 아니라 여러 첨부자료, 변경된 공고, 단계별 기한과 준비 상태를 지속해서 관리해야 한다.

### 2.3 온라인 사용자 피드백 조사

공개된 온라인 질문을 조사한 결과 다음과 같은 혼동 사례가 반복적으로 나타났다.

- 부모가 이혼했거나 연락이 끊긴 경우 소득 산정 범위
- 부모의 무주택 여부와 가점 적용 여부
- 신청 순위에 따른 소득·자산 검증 대상
- 형제자매 등 가구원의 포함 범위
- 다른 청년주택 또는 주거지원 사업과의 중복 신청 가능 여부
- 공통 서류와 특정 신청자만 제출하는 조건부 서류의 구분

일부 질문에는 서로 다른 답변이 제시되어 비공식 정보만으로는 정확한 판단이 어려울 가능성도 확인했다. 온라인 질문은 전체 신청자를 대표하는 통계가 아니므로, 초기 문제 가설을 수립하고 향후 인터뷰에서 확인할 항목을 도출하는 사례 자료로 활용한다.

### 2.4 유사 서비스 조사

마이홈은 주거복지 정보 탐색과 청년·신혼부부 대상 자가진단을 제공하고, LH·GH 등 운영기관은 공식 공고 확인, 청약 신청, 서류 제출과 결과 조회 기능을 제공한다.

그러나 사전 조사 범위에서는 사용자가 선택한 특정 공고를 기준으로 개인 상황에 필요한 조건·서류·기한을 구성하고, 현재 준비 상태와 다음 행동을 하나의 흐름으로 관리하는 기능을 확인하기 어려웠다.

이에 본 과제는 정책을 새롭게 추천하는 서비스보다, 사용자가 이미 선택한 공고를 실제 신청 행동으로 연결하는 준비 관리 도구를 제안한다.

## 3. 서비스 해결방안

### 3.1 핵심 해결방안

준비 규칙의 검수·공개가 완료된 관심 공고를 사용자가 선택하고 연령, 거주지, 가구 구성, 소득·자산 등 공고별 질문에 답하면 공식 공고를 구조화한 기준에 따라 다음과 같이 안내한다.

1. 입력 내용으로 확인할 수 있는 조건
2. 공고의 명시 조건과 맞지 않을 가능성이 있는 조건
3. 정보가 부족하거나 예외가 있어 추가 확인이 필요한 조건
4. 공식 기관에 문의해야 하는 조건

조건 확인 이후에는 사용자 응답에 따라 필요한 제출서류와 준비 일정을 개인화하여 제공한다. 각 항목에는 공식 공고의 근거, 발급처, 준비 상태와 마감일을 연결하고, 사용자가 현재 해야 할 다음 행동을 확인할 수 있도록 한다.

### 3.2 사용자 이용 흐름

> 기본 정보가 검증·공개된 공고 탐색 → 준비 안내 제공 상태 확인 → 검수 완료 공고의 개인 상황 입력 → 조건별 확인 → 개인 맞춤형 서류 목록 생성 → 기한 및 준비 상태 관리 → 다음 행동 확인 → 공식 신청 사이트 이동 → 후속 절차 기록

준비 안내가 검수·보완 중이거나 미지원인 공고는 검증된 기본 정보·공식 원문·첨부를 조회할 수 있다. 해당 규칙 검수가 끝나기 전에는 개인별 준비 건·질문·서류 목록을 생성하지 않는다.

실제 청약과 신청은 운영기관의 공식 사이트에서 진행한다. 공식 시스템과 연동하지 않는 한 접수 완료 여부나 심사 결과를 자동으로 확인하지 않고 사용자가 직접 기록하도록 한다.

### 3.3 핵심 기능

| 기능         | 구현 내용                                 |
| ---------- | ------------------------------------- |
| 공고 목록 및 상세 | 기본 정보 검증·공개 완료 공고의 제목·기관·지역·유형·공식 기간·원문·첨부와 준비 안내 상태 제공. 조건·서류 해석은 준비 규칙 검수 완료 후 제공 |
| 조건별 질문     | 복잡한 공고 조건을 사용자가 답할 수 있는 질문으로 구성       |

| 단계별 일정     | 신청, 서류 제출, 보완, 결과 확인 등 주요 기한 제공       |

| 공식 발급처 연결 | 서류·발급 대상·방식을 확인한 공식 링크부터 초기 준비 흐름에 실제 연결, 미검증 경로는 안내 |
| 공고 관리      | 공고 정보·준비 안내를 한 작업에서 검수하고 영역별 결과·보완 사유·공개 상태·버전·확인일과 수정 이력 관리 |

### 3.4 신청 여정 시각화

복잡하고 긴 신청 과정을 쉽게 이해하도록 다음과 같은 단계별 여정으로 표현한다.

> 공고 확인 → 조건 확인 → 서류 준비 → 공식 신청 → 후속 절차

사용자가 중요한 준비 행동을 완료하면 준비도(%)와 집 건축 단계·완성 상태가 실제 준비 기록에 맞춰 변하도록 구성한다. 두 요소는 초기 완성 범위에 포함하며 상태별 목록만 먼저 제공하고 %·집 표현을 후도입하는 제안은 기각한다. 가중치·집 단계 매핑·사용자 이해도는 검증으로 개선하고 필수 미확인·재확인 표시도 함께 제공한다. 이러한 요소는 단순한 흥미 유발보다 사용자가 현재 위치와 남은 준비 사항을 이해하도록 돕는 진행도 시각화 수단으로 활용한다.

서비스가 표시하는 준비도는 사용자가 기록한 준비 작업의 진행률을 의미한다. 신청 자격 충족도, 선정 가능성 또는 당첨 확률로 오해되지 않도록 다음 안내를 함께 제공한다.

> 준비도는 서비스에 기록한 준비 항목의 진행 상태입니다. 실제 신청 자격이나 선정 가능성을 의미하지 않습니다.

※ 이 위치에 기존에 제작한 ‘게이미피케이션 기반 주거지원 신청 준비 서비스’ 메인 화면 시안을 삽입할 수 있음.

## 4. 기존 서비스와의 차별성

본 서비스의 핵심 차별점은 공고 탐색이나 단순 자가진단에서 끝나지 않고, 선택한 공고를 개인별 신청 준비 행동으로 전환한다는 점이다.

| 비교 대상            | 기존 해결 방식                | 본 서비스의 차별점                   |
| ---------------- | ----------------------- | ---------------------------- |
| 마이홈 등 주거복지 포털    | 주거지원 정책 탐색과 자가진단        | 선택한 공고를 기준으로 개인별 준비 행동 구성    |
| LH·SH·GH 등 공식 채널 | 공고 제공, 신청, 서류 제출과 결과 조회 | 흩어진 조건·서류·기한을 하나의 준비 여정으로 연결 |
| 블로그·영상·커뮤니티      | 경험자의 해설과 신청 후기 제공       | 안내 내용마다 공식 공고 근거와 확인 시점 제공   |
| 메모·캘린더·엑셀        | 사용자가 직접 일정과 목록 작성       | 사용자 응답에 따라 조건부 서류와 다음 행동 구성  |
| 일반 할 일 관리 서비스    | 사용자가 모든 할 일을 직접 입력      | 구조화된 공고를 바탕으로 신청 준비 작업 제공    |
| 단순 체크리스트         | 모든 사용자에게 동일한 목록 제공      | 개인 상황에 따라 필요한 조건과 서류를 구분     |

차별성은 다음 세 요소의 결합으로 구현한다.

- 사용자 상황에 따라 달라지는 조건과 제출서류의 개인화
- 모든 안내와 공식 공고 근거의 연결
- 현재 단계, 준비 상태와 다음 행동을 보여주는 신청 여정

집 건축 표현 자체를 핵심 차별점으로 주장하지 않고, 개인화된 신청 준비 과정을 이해하기 쉽게 보여주는 보조 수단으로 사용한다.

## 5. MVP 구현 범위

### 5.1 필수 구현 범위

- 한 기관을 우선 조사하되 지역·지원 유형을 미리 제한하지 않고 공통 구조·추가 준비 규칙·검수 및 사용자 검증 작업량으로 초기 범위 선정
- 공식 API 우선 자동 수집, 첫 구현용 대표 1건과 주요 차이를 대표하는 추가 표본으로 규칙 검증. 추가 2\~3건은 시작점이며 수집량·지원 범위의 상한이 아님
- 모바일 중심의 반응형 웹 구현
- 기본 정보 검증·공개 완료 공고의 목록·상세 조회, 준비 안내 제공 상태 구분
- 조건별 질문과 조건 확인 상태 제공
- 개인별 제출서류 체크리스트 생성
- 주요 기한과 준비 상태 저장
- 현재 해야 할 다음 행동 제공
- 준비도(%)·집 건축 표현과 신청 여정을 초기 완성에 포함
- 검증된 공식 발급 링크를 초기 준비 흐름에 연결. 미검증·오류 경로는 발급 방법·확인 필요 사항 안내
- 관리자용 공고 및 수정 이력 관리

### 5.2 기능별 우선순위 결정

| 항목 | 채택한 방향 | 완료·판단 기준 |
| --- | --- | --- |
| 공식 발급 링크 | 검증된 링크를 초기 준비 흐름에 포함 | 서류·대상·발급 방식과 맞는 공식 경로 확인. 확인된 링크부터 제공 |
| 캘린더 파일 내보내기 | 푸시와 분리해 일정 정확성·가져오기 사용성을 검증한 뒤 구현 범위 별도 확정 | 검증된 일정의 .ics 생성, 실제 대상 기기의 가져오기·변경·중복 처리 확인. 기능 구현 자체는 아직 미확정 |
| 푸시·이메일 기한 알림 | 후순위로 유지하고 수요·운영 부담을 별도 판단 | 권한·구독·예약·발송·실패·기한 변경 및 취소 처리 검토 |
| 준비도(%)·집 건축 표현 | 초기 완성 범위에 포함 | 계산·집 단계 매핑·미확인/재확인 표시·저장 결과 일치와 사용자 이해도 검증 |

공식 발급 링크는 해당 서류·발급 대상·방식·공식 경로를 준비 안내 검수에서 확인하고 링크·기관·확인일·근거를 기록한다. 직접 신청 주소가 로그인·세션에 종속되면 안정적인 공식 안내 경로를 연결한다. 모든 링크 확보를 기다리지 않고 검증된 경로부터 제공하며 외부 이동을 발급 완료나 준비도 증가로 처리하지 않는다.

캘린더 파일 내보내기는 검증된 선택 일정의 .ics 생성·대상 기기 가져오기·수정/중복 처리를 확인한 뒤 실제 구현 범위를 결정한다. 날짜만 있는 일정에 시각을 추정하지 않고 기준 버전·생성 시점·공식 원문을 포함한다. 개인별 서류 기한은 관련 규칙 검수 후 사용하고 개인 답변·민감정보는 내보내지 않는다. 파일 다운로드는 외부 등록·알림 예약 완료가 아니며 공고 수정의 자동 동기화를 약속하지 않는다. [Google Calendar 가져오기 안내](https://support.google.com/calendar/answer/37118?hl=ko)

푸시·이메일 알림은 현재 기한 기록 도구·놓친 이유·알림 수요와 예약·권한·발송·실패·수정 처리 부담으로 별도 판단한다. 검증 전 캘린더와 알림 진입점은 준비 중 안내를 유지하고 실제 성공처럼 시연하지 않는다.

### 5.3 초기 범위에서 제외하는 기능

- 전국의 모든 주거지원 정책 통합
- 최종 신청 자격 판정
- 당첨 가능성 또는 경쟁률 기반 확률 예측
- 공식 사이트를 대신하는 자동 신청
- 주민등록·소득·재산 정보의 자동 조회
- 주민등록번호, 계좌번호 및 증빙서류 원본 저장
- 모든 공고의 AI 자동 해석
- 사용자 간 준비도 순위와 경쟁 기능
- 캐릭터 아이템 상점 등 문제 해결과 직접 관련 없는 기능

### 5.4 정보 정확성 관리

공고 정보를 구조화하는 팀원과 검토하는 팀원을 구분한다. 같은 공고·원문 버전에 대해 하나의 검수 작업에서 출처·식별·기본 정보와 조건·서류·기한을 함께 대조하되 결과·보완 사유·공개 상태는 영역별로 기록한다. 공통 출처·공식 기간 등은 같은 검증 값을 공유하고 기본 정보와 준비 안내의 기준 버전·확인일·공개 이력을 구분한다.

| 동일 검수의 결과 | 공고 목록·기본 상세 | 개인별 준비 안내 |
| --- | --- | --- |
| 기본 정보·준비 안내 모두 통과 | 공개 | 제공 |
| 기본 정보 통과·준비 안내 보완 필요 | 공개 | 보완 완료까지 제공 보류 |
| 기본 정보 통과·준비 안내 미지원 | 공개 | 미제공 표시 |
| 공고 식별·출처 등 기본 정보 검증 실패 | 공개 보류 | 제공 보류 |

기본 정보 검증에서는 공식 출처·공고 식별·기관·제목·지역과 유형의 의미·신청 단계별 공식 기간·원문 및 첨부 링크를 확인한다. 준비 안내 검수에서는 조건별 질문·예외·공통 및 조건부 서류·신청 단계·기한과 근거를 확인한다. 최초 검수 전 수집 결과는 공개하지 않는다.

사용자에게는 `준비 안내 제공 중`, `준비 안내 검수 중`, `준비 안내 미제공`, `준비 안내 변경 검토 중`을 구분해 표시한다. 집으로의 검수 상태를 기관의 공고 검토 상태·신청 자격으로 표현하지 않는다. 개인별 준비 기능의 접근 조건은 서버가 검사한다.

수정 공고도 같은 작업에서 검수하되 기본 정보는 해당 검증을 마친 뒤 갱신할 수 있다. 영향받는 준비 규칙은 변경 검토 중으로 표시하고 해당 신규 안내·시작을 보류한다. 기존 사용자 기록은 과거 기준 버전과 함께 보존·조회하며 새 규칙이나 준비 상태로 자동 덮어쓰지 않는다.

생성형 AI나 OCR은 공고문 문자 추출과 쉬운 설명의 초안을 만드는 보조 수단으로만 활용한다. 사용자에게 제공되는 조건과 서류 정보는 팀이 공식 공고와 대조한 후 등록하며, AI가 생성한 내용을 최종 자격 판단의 근거로 사용하지 않는다.

### 개발 구조와 운영 원칙

GitHub 저장소 하나에 `frontend/`·`backend/`·`docs/`를 두는 모노레포를 유지한다. 프론트엔드와 백엔드는 각각 실행·검사·빌드·배포하고, 화면·API·문서의 연동 변경은 함께 검토한다.

- React·TypeScript는 `frontend/`의 VS Code·npm, Spring Boot·JDK 17은 `backend/`의 IntelliJ IDEA·Gradle Wrapper를 사용하며 의존성을 각각 관리한다.
- 각 폴더의 README에 설치·실행·검사·빌드 방법을 작성하고 루트 README에 전체 실행 순서와 API 연결 확인 방법을 연결한다. 초기에는 별도 모노레포 관리 도구를 추가하지 않는다.
- 기존 `main`·`develop`을 유지하고 기능·수정 단위 브랜치와 PR을 사용한다. 필요한 양쪽 변경·API 문서는 같은 PR에서 검토할 수 있으며 큰 작업은 연결된 PR로 나눠 선행 작업·호환성·통합 확인 순서를 기록한다. 공통 설정·같은 파일 변경은 관련 담당자와 먼저 조율한다.
- PR 자동 검사는 프론트·백엔드별 작업으로 구성하고 초기에는 양쪽을 모두 실행한다. 각 프로젝트의 검사·빌드 통과와 실제 화면·API 연동 검증을 구분한다.
- 배포 산출물·버전·적용·복구 절차를 각각 관리하고 변경 없는 쪽의 재빌드·재시작을 필수로 묶지 않는다. API·DB 변경 시 호환성과 적용 순서·통합 확인·복구 제약을 함께 검토한다. 기존 EC2 1대 구성은 유지하고 실제 배포·복구 절차와 자동화는 후속 설계에서 정한다.

상세 기준은 [코드 및 기술 규칙의 모노레포 운영 원칙](../conventions/coding-conventions.md#모노레포-운영-원칙--20261020-확정)을 따른다. 위 내용은 채택한 운영 원칙이다. 로컬 초기 환경·연동은 검증했으며 원격 CI 실행·실제 기능·배포 완료와는 구분한다.

## 7. 사용자 검증 방법

### 7.1 조사 대상

- 최근 청년 공공임대 또는 주거지원 사업에 처음 신청한 사람
- 공고를 확인했지만 신청하지 않은 사람
- 신청 준비 중 중단한 사람
- 가족이나 지인의 신청 준비를 도운 사람

초기에는 공통 신청 여정과 주요 유형별 차이를 검증할 경험자 5\~8명을 대상으로 탐색한다. 준비 절차가 다른 초기 포함 후보가 있으면 해당 경험자도 모집한다. 인터뷰 결과를 전체 청년 신청자에게 일반화하지 않고 반복되는 문제와 실제 준비 과정을 파악하는 데 활용한다.

### 7.2 검증 방법과 판단 기준

| 검증 항목  | 방법                        | 확인 기준                                  |
| ------ | ------------------------- | -------------------------------------- |
| 문제 검증  | 신청·중단 경험 인터뷰              | 조건 혼동, 반복 확인, 준비 누락 문제가 여러 참여자에게 반복되는가 |
| 기본 정보 정확성 | 공식 공고와 목록·기본 상세 대조 | 출처·공고 식별·공식 기간·링크·기준 버전이 정확한가 |
| 준비 안내 정확성 | 질문·규칙·서류·기한과 공식 근거 이중 대조 | 중대한 조건·서류·기한 오류 및 미검수 안내 노출이 없는가 |
| 공개 상태 구분 | 동시 검수 결과별 목록·준비 기능 확인 | 기본 정보만 통과한 공고도 조회되고 미검수 신규 준비 기능은 차단되는가 |
| 사용성    | 실제 공고와 가상 신청자로 과제 수행      | 사용자가 도움 없이 현재 단계와 다음 행동을 찾을 수 있는가      |
| 비교 효용  | 공고 원문 이용 방식과 서비스 이용 방식 비교 | 준비 목록 누락과 수행 시간이 감소하는가                 |
| 근거 확인  | 안내 내용의 원문 찾기              | 사용자가 안내의 공식 근거를 쉽게 확인할 수 있는가           |
| 준비도·집 이해 | %·집 단계와 필수 미확인 상태 해석 질문 | 초기 구현의 계산·표현이 일치하고 자격·당첨 가능성으로 오해되지 않는가 |
| 공식 발급 링크 | 서류별 링크·발급 방식 확인과 사용자 이동 과제 | 정확한 공식 경로로 이동하며 미검증 경로와 발급 완료를 구분하는가 |
| 캘린더 별도 평가 | .ics 날짜·시각·버전 검증과 실제 기기 가져오기 | 다운로드와 등록이 구분되고 변경·중복 처리 및 사용성이 확인되는가 |
| 지속 사용  | 모의 신청 기간 동안 사용            | 준비 상태 확인과 수정을 위해 다시 방문하는가              |

초기 목표는 지원 공고의 핵심 조건·서류·기한에 공식 근거를 모두 연결하고, 사용자 테스트 과정에서 치명적인 조건 또는 서류 오안내가 발생하지 않도록 하는 것이다. 구체적인 시간 단축률과 누락 감소 목표는 초기 테스트에서 기준값을 확보한 후 설정한다.

## 8. 실현 가능성 및 역할 분담

한 기관을 우선 조사하되 여러 지역·유형 공고를 비교하고 공통 구조·규칙을 재사용할 수 있는 범위를 함께 다룬다. 추가 질문·조건부 서류·예외·신청 단계 및 검수·사용자 검증 작업량을 기록해 학기 중 감당 가능한 초기 범위를 정한다. 대표 한 건으로 첫 흐름을 구현하는 순서와 서비스 지원 범위는 구분하며, 표본 수 자체를 한 학기 내 실현 가능성의 근거로 삼지 않는다.

개발 경험이 적은 팀원이 공고 조사, 정책 데이터 구조화, 콘텐츠 검수, 사용자 조사와 테스트를 담당하고, 개발 담당자는 공고 데이터 모델, 조건 규칙, 사용자 준비 상태 저장 및 화면 구현을 중심으로 맡는 방식으로 업무를 분담한다.

| 역할        | 주요 업무                                 |
| --------- | ------------------------------------- |
| 기획 및 PM   | 문제 정의, 요구사항, 일정과 구현 범위 관리             |
| 공고 데이터 담당 | 공고 수집, 조건·서류·일정 구조화와 출처 관리            |
| UI·UX 담당  | 사용자 흐름, 조건 상태, 체크리스트와 신청 여정 설계        |
| 개발 담당     | 반응형 화면, 서버, 데이터베이스, 사용자 상태와 관리자 기능 구현 |
| 공동 검수     | 공식 공고 대조, 사용성 테스트와 오류 기록              |

역할은 팀원의 역량과 학습 목표를 고려해 중복 배정하며, 공고 검수와 사용자 테스트는 모든 팀원이 공동으로 수행한다.

## 9. 기대효과 및 확장 방향

사용자는 관심 공고를 반복해서 읽거나 별도의 메모와 캘린더를 직접 구성하는 부담을 줄이고, 자신의 상황에서 확인할 조건과 필요한 서류, 현재 준비 상태와 다음 행동을 한곳에서 관리할 수 있다.

프로젝트 측면에서는 공공정보를 단순히 제공하는 데 그치지 않고, 사용자의 상황과 행동 단계에 맞게 재구성하는 개인화 서비스의 설계·개발 과정을 경험할 수 있다.

공통 구조와 규칙으로 처리 가능한 여러 지역·유형은 초기 범위에 함께 포함할 수 있다. MVP 검증 이후에는 새 수집 경로·독립적인 준비 규칙이 필요한 범위나 다른 기관의 공고 추가, 수정 공고 전후 비교 등으로 확장할 수 있다. 검증된 공식 발급 링크는 초기 구현에 포함하며 캘린더 파일 내보내기는 일정 정확성·가져오기 사용성 검증 후 실제 범위를 정하고 푸시·이메일 알림은 수요·운영 부담을 별도 평가한다. 다만 공고 범위를 확대하기 전에 정보 검수와 수정 이력 관리가 지속 가능한지 우선 확인한다.

## 10. 지원금 활용과 개발 결과물의 연계

지원금은 서비스 개발과 시연에 필요한 클라우드 환경, 공고문 처리 API, 결과물 제작과 팀 회의에 사용한다.

- AWS 서버·데이터베이스·스토리지: 웹 서비스 배포와 사용자 테스트
- OCR 및 생성형 AI API: 공고문 문자 추출과 쉬운 설명 초안 생성
- 기타 외부 API: 알림 등 외부 기능 연동 및 검증
- 도메인과 인쇄물: 사용자 테스트 주소 운영 및 결과물 시연
- 회의비: 공고 구조화 검토, 기능 기획과 개발 진행 회의

세부 금액은 기술 구성과 사업단의 인정 항목을 확인하여 최종 예산서에 반영한다.
