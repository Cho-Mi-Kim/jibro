# 프로젝트 문서 안내

최종 수정일: 2026-10-29

## 읽는 순서

프론트엔드 업무 API와 판단한 세부 정책은 [프론트엔드 구현 계약](architecture/frontend-contracts.md)을 확인합니다. 백엔드 미구현 계약과 실제 동작 검증 범위를 구분합니다.

1. 새 팀원은 [개발 시작 안내](getting-started.md)에 따라 환경을 준비하고 프론트·API·DB 연결을 확인합니다.
2. 작업 전 [팀 컨벤션](conventions/team-conventions.md)과 [코딩 컨벤션](conventions/coding-conventions.md)을 확인합니다.
3. 기능별로 [기획안](planning/project-proposal.md)과 [화면설계서](design/screen-spec.md)를 함께 보고 구현합니다.
4. 구현 완료 판단은 문서의 계획과 [실제 검증 기록](verification.md)을 구분해 확인합니다. 초기 환경 검증이 로그인·실제 공고·준비 관리·배포 구현 완료를 뜻하지 않습니다.
5. 변경의 배경과 해결 과정을 찾거나 발표·포트폴리오를 준비할 때는 [프로젝트 작업 기록](history/README.md)을 확인합니다. 자동 수집 기록의 보완 상태와 개인 기여를 검토한 뒤 사용합니다.

## 수정·동기화 규칙

- 확정된 제품 정책은 기획안, 화면 상태는 화면설계서, 기술 계약은 코딩 컨벤션에서 관리합니다. 다른 문서에는 필요한 요약과 상대 링크를 둡니다. 문서가 충돌하면 임의로 한쪽을 바꾸지 않고 담당자와 합의를 확인합니다.
- 실행 명령·환경 변수·IDE 설정은 개발 시작 안내와 각 프로젝트 README를 기준으로 관리합니다. 정확한 패치 버전은 버전 기록과 실제 설정을 함께 갱신합니다.
- 확정된 규칙의 본문은 `docs/`에서 수정합니다. Notion은 회의록·작업·근거 자료를 관리하고 해당 문서를 링크합니다. 확정 문서를 별도 사본으로 반복 수정하지 않습니다.
- 기능·API·DB·공통 설정 변경 PR에는 영향을 받는 문서를 함께 갱신합니다. 기획 세부안도 같은 정책을 유지하고 제출 시점의 버전은 Git 커밋으로 식별합니다.
- 의미 있는 작업은 [작업 기록](history/README.md)에 이유·대안·검증·기여·한계를 남깁니다. 현재 기준 문서와 과거의 판단 과정을 구분하고 같은 기록을 발표 원고처럼 과장하지 않습니다.
- 파일명에 날짜를 계속 붙이거나 매번 복제하지 않습니다. 변경된 파일의 최종 수정일을 갱신하고 PR에서 이유·영향·확인 결과를 설명합니다.
- 링크와 이미지는 저장소 내부 상대 경로로 작성합니다. 개인 PC 절대 경로·비밀값·개인정보 원본을 넣지 않습니다. 이미지는 실제로 참조하는 파일만 `docs/assets/`에 추가합니다.
