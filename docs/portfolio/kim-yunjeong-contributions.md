## 1. 역할과 프로젝트 요약

**권장 역할명: 팀장 | 서비스 기획·AI 보조 풀스택 개발·통합 관리**

개발 직무 이력서의 역할란이 짧다면 **“팀장 / 풀스택 개발·서비스 기획”**으로 적고, 본문에 AI 활용 범위를 함께 밝힌다. “단독 개발”, “전체 코드 직접 구현”, “테크 리드”는 현재 기록만으로 확정하지 않는다.

## 3. 이력서에 사용할 문안

### 개발 직무용 기본 문안

**집으로 | 팀장 · 서비스 기획 및 풀스택 개발**\
청년 주거지원 공고의 조건·서류·일정을 개인별 신청 준비 과정으로 연결하는 4인 캡스톤 프로젝트

- React·TypeScript와 Spring Boot·Java 17·PostgreSQL 기반 초기 웹 서비스의 기획·기술 선택 및 AI 보조 풀스택 개발을 진행하고, 공고 탐색부터 개인 준비 기록 저장까지 연동.
- 질문별 답변 형식과 제출서류 노출 기준을 구체화하여, 사용자 조건에 따른 준비 대상 서류와 추가 확인 항목을 구분하는 흐름으로 개선.
- Google·카카오 인증 설정 및 실제 로그인 확인에 참여하고, 카카오 호출 허용 IP를 공인 IP로 수정. Google 로그인 후 새로고침 유지·로그아웃을 Edge에서 직접 확인.
- 브랜치별 PR·의존 순서·CI 확인 후 병합 원칙을 정하고, 팀원 변경의 계약 대조·수정·회귀 검증·통합을 AI 보조로 진행.
- 인수인계 전 데이터 처리와 계약의 일치 여부를 우려해 구현 검토를 요청. AI가 발견·수정한 메모 덮어쓰기 문제를 두 탭에서 직접 재현·재검증하고 수정 코드를 읽어 검토.
- 비개발 팀원의 화면 확인을 위한 GitHub Pages 시연 방식을 결정하고, 실제 서버 모드와 분리한 시연 배포 및 실행·인수인계 문서 정리를 진행.

**AI 활용:** Codex를 코드·테스트·문서 작성과 오류 조사에 활용했으며, 요구사항·기술 선택·UX 수정 방향·확인 절차를 결정하고 일부 외부 설정 및 실제 사용 흐름을 직접 확인했다.

이력서 분량이 부족하면 위 항목 중 지원 직무에 맞는 3개를 선택한다. 프론트엔드 지원은 질문·서류 흐름과 반응형 UI를, 백엔드·풀스택 지원은 인증·데이터 저장·통합 검증을 앞에 둔다.

### 역할 한 문장

> 청년 주거지원 신청 준비 서비스의 팀장으로서 요구사항·기술 선택·UX 개선을 이끌고, AI 보조 풀스택 개발과 팀원 변경 통합, 실제 연동 확인 및 시연 배포를 진행했습니다.

### 짧은 프로젝트 소개

> 집으로는 청년 주거지원 공고를 찾은 사용자가 개인 조건에 맞는 서류와 준비 행동을 확인하고 진행 상태를 기록하는 반응형 웹 서비스입니다. 공고 검색에서 끝나지 않고 조건 질문, 준비 대상 서류, 공식 근거·발급처·기한, 준비 기록을 하나의 흐름으로 연결했습니다. 신청 자격이나 선정 여부를 확정하는 서비스는 아닙니다.

## 4. 포트폴리오 본문과 대표 사례

### 프로젝트에서 맡은 역할

> 팀장으로서 청년 주거지원 공고를 ‘찾는 과정’과 실제 ‘준비하는 과정’ 사이의 연결을 핵심 과제로 정했습니다. 기술 스택과 구현 범위를 결정하고, 질문별 답변 방식·서류 목록·준비도 시각화·반응형 화면에 관한 개선 요구를 구체화했습니다. 개발에는 Codex를 활용했으며, 외부 인증 설정과 일부 실제 사용 흐름을 직접 확인했습니다. 이후 팀원이 확장한 기능은 별도 기여로 구분하고, 계약 문서 대조와 회귀 검증을 거쳐 통합하도록 진행했습니다.

### 사례 1. 질문을 마치면 준비할 서류가 분명하게 보이도록 개선

**문제:** 서로 다른 의미의 질문에 동일한 답변 형식을 적용하고, 본인에게 해당하지 않는 서류까지 보여주면 답변과 실제 준비 행동의 관계가 불명확해진다.

**본인의 판단:** 질문에 적합한 답변을 받고, 답변 이후 서류 목록에는 준비 대상 서류만 보여주도록 요구했다. 단순 화면 장식보다 사용자가 무엇을 준비해야 하는지를 우선했다.

**AI 보조 구현:** 질문별 값·선택지·추가 확인 여부를 정의하고 서버에서도 허용 답변을 검사했다. REQUIRED·CONDITIONAL은 준비 목록에, UNKNOWN은 추가 확인 영역에 표시하고 NOT_APPLICABLE은 목록에서 숨겼다. 안내가 바뀌면 명시적으로 갱신하도록 하고 기존 메모·이전 기록을 보존했다.

**당시 확인 결과:** 2026-11-01의 실제 공고·검증 계정 사례에서 질문 7개에 답한 후 공통 서류 4개와 학생 서류 1개가 보이고, 비대상 서류 4개는 숨겨졌다. 기존 계정의 준비 기록 7건도 보존됨을 확인했다. 이 사례는 당시 조건 조합의 결과이며 현재 모든 공고가 5개 서류를 요구한다는 뜻은 아니다.

**기여 경계:** 요구사항·노출 정책은 본인의 명시적 판단으로 확인된다. 코드 작성과 자동·브라우저 검증은 AI 보조 기록이다. 후속 PR #24·#26의 모든 질문 유형·규칙 확장을 본인 단독 성과로 포함하지 않는다.

### 사례 2. 실제 로그인과 공고 수집을 설정·요청·저장 단계로 나누어 확인

**문제:** 소셜 로그인 동의 이후 멈춤, 카카오 호출 제한, LH 수집 실패가 발생했다. 회원 미가입 때문에 생긴 문제인지도 확인이 필요했다.

**본인의 실행:** 외부 키와 환경 설정을 진행하고, 안내에 따라 카카오 호출 허용 IP를 사설 IP에서 공인 IP로 변경했다. 카카오·Google 로그인 성공을 직접 보고했으며, Google은 Edge에서 새로고침 후 로그인 유지 및 로그아웃 후 보호 화면의 로그인 이동을 확인했다.

**AI 보조 조사·수정:** 카카오 IP 제한 응답, OAuth 진단 정보, LH 서비스 키 인코딩과 검색 인자 문제를 분리했다. LH 요청은 응답 필드가 아닌 검색 필드 PAN_ST_DT·PAN_ED_DT와 yyyyMMdd 형식을 사용하도록 수정하고 한국 날짜 기준을 적용했다. 인증 비밀값을 남기지 않는 진단 방식도 보완했다.

**당시 확인 결과:** 2026-10-31 LH 수집을 두 번 실행해 각 276건 처리, DB 공고 수는 0 → 276 → 276으로 유지되었다. 이 실행에서는 반복 수집 시 중복 증가가 없었으며 수집 자료는 HOLD 상태로 남았다. 서버 기록에서도 두 로그인 제공자의 로그아웃 후 refresh token 폐기와 유효 토큰 0건을 확인했다.

**기여 경계:** 공인 IP 변경·계정 선택·일부 브라우저 확인은 본인 수행, 요청 분석·코드 수정·DB 확인은 AI 보조다. Google Chrome의 인증 화면 대기는 완전 해결로 쓰지 않는다. 276건을 “검수 완료 공고 수”나 “사용자 수”로 쓰지 않는다.

근거: [PR #12](https://github.com/Cho-Mi-Kim/jibro/pull/12), [외부 연동 검증 기록](../history/entries/2026-10-31-external-integration-verification.md)

### 사례 3. 실제 서버와 분리한 시연으로 팀원의 확인 경로 마련

**문제:** 개발을 담당하지 않는 팀원이 프로젝트를 보려면 개발 도구·DB·서버를 준비해야 했다. 정적 호스팅만으로 Spring Boot 서버를 함께 실행할 수는 없었다.

**본인의 판단:** 실제 계정이나 서버 저장 대신 가상 데이터로 핵심 화면을 체험하는 GitHub Pages 시연을 선택했다.

**AI 보조 구현:** pages-demo 빌드, 가상 API 어댑터, /jibro/ 경로와 해시 라우팅, 배포 자동화를 구성했다. 시연에서는 실제 로그인 입력과 소셜 인증을 숨기고 임시 저장·새로고침 초기화를 안내했다. 일반 빌드는 실제 서버 모드를 유지했다.

**확인 결과:** 초기 시연의 공고 → 질문 → 서류 완료 → 신청 기록 → 홈 진행률 흐름을 검증했다. 2026-11-16 후속 배포에서도 공고 4건, 질문 2건, 대상 서류 2건, 1건 완료 시 50% 표시, 상세 경로 새로고침을 확인한 기록이 있다. 개발 환경 없이 접근할 수 있는 공유 경로를 확보했다.

**기여 경계:** “팀원 모두가 테스트했다”, “피드백 시간이 줄었다”는 결과는 측정하지 않았다. Pages 공개는 실제 서버 운영 배포와 구분한다.

근거: [PR #20](https://github.com/Cho-Mi-Kim/jibro/pull/20), [시연 구현 기록](../history/entries/2026-11-01-github-pages-demo.md), [후속 배포 기록](../history/entries/2026-11-16-main-pages-release.md)

### 사례 4. 팀원 기능 확장을 계약·회귀 검증과 함께 통합

**문제:** PR #24·#26에서 기능과 구조가 크게 확장되며 기존 계약·보호 동작·검증 코드가 최신 구현과 어긋났다.

**본인의 판단과 진행:** 인수인계 전 미병합 구현과 계약 문서를 확인하려 했으며, 데이터 처리 과정이 제대로 구현됐는지와 계약에 어긋난 부분이 없는지도 우려해 PR #24 검토를 요청했다. 이 동기는 당시 요청에 구체적으로 적힌 내용이 아니라 사용자가 이후 직접 설명한 내용이다. AI가 검토 중 발견한 두 문제의 수정·테스트·공유를 요청했고, 별도로 병합을 보류해 디자인을 먼저 확인한 뒤 재개했다. PR #26에서는 충돌·중복 테스트 해결, 검사, 해결 코멘트 공유와 순서에 따른 병합을 요청했다.

**직접 수행한 재검증:** 사용자의 후속 설명에 따르면, 수정 후 직접 두 탭을 열어 메모 덮어쓰기 상황을 재현·재검증한 뒤 수정 코드를 읽고 검토했다. AI의 통과 보고 확인과 본인의 화면·코드 검토를 별개로 기록한다. 당시 직접 입력한 메모 값이나 상세 클릭 순서는 확인되지 않아 추가하지 않는다.

**AI 보조 해결:**

- PR #24: 두 탭의 오래된 보관 요청이 앞선 메모를 덮어쓰는 문제를 재현했다. 이미 보관된 상태와 오래된 revision을 거절하고 DB·JSON 스냅샷의 revision을 함께 갱신했다. 로그인 복귀 테스트는 인위적인 시연 지연만 테스트에서 제외했다.
- PR #26: 새 Repository 구조를 유지하면서 기존 보관 보호와 시연 테스트 경계를 보존했다. 자동 병합된 파일의 중복 helper·회귀 테스트를 정리했다. Linux에서만 드러난 OCR 테스트의 종료 경합은 제품 코드가 아닌 테스트 worker에서 수정했다.
- PR #29: UTC DB 날짜와 한국 서비스 날짜가 달라지는 테스트 실패를 한국 날짜 기반 fixture로 수정했다. 제품의 상태 판정을 완화하지 않았다.

**확인 결과:** PR #24의 후속 수정은 프론트엔드 134건·백엔드 단위 15건·DB 통합 25건과 CI 통과 기록이 있다. PR #26은 후속 수정 head의 CI 4개 작업 통과 후 병합되었다. 이 숫자는 당시 팀 코드 전체의 검사 범위이며 본인이 직접 작성한 테스트 수가 아니다.

**기여 경계:** PR #24·#26 작성자는 kangjoonkim이다. 전체 기능 확장을 본인의 신규 구현으로 표기하지 않는다. 검토 필요성 판단·수정 요청·두 탭 직접 재검증·수정 코드 검토는 본인의 역할이며, 버그 최초 발견·원인 분석·구체적인 revision 수정안·회귀 테스트 작성은 AI 보조 범위다. 사용자가 revision 설계를 처음 제안하거나 직접 코드를 작성했다고 확대하지 않는다.

근거: [PR #24 후속 수정 코멘트](https://github.com/Cho-Mi-Kim/jibro/pull/24#issuecomment-6760142110), [PR #26 해결 코멘트](https://github.com/Cho-Mi-Kim/jibro/pull/26#issuecomment-6896119283), [PR #29](https://github.com/Cho-Mi-Kim/jibro/pull/29)

### 인턴 지원서용 문제 해결 문안

> 팀장으로서 개발 인수인계 전 데이터 처리 흐름이 기능 계약과 일치하는지 확인할 필요가 있다고 판단해 Codex에 미병합 구현 검토를 요청했습니다. 검토 중 AI가 두 탭의 오래된 보관 요청이 앞서 저장한 메모를 덮어쓸 수 있는 문제를 발견했습니다. 저는 수정과 회귀 검증을 요청하고, 수정 후 직접 두 탭을 열어 같은 상황을 재현·재검증한 뒤 수정 코드를 읽어 검토했습니다. 원인 분석과 코드·테스트 작성에는 AI를 활용하되, 검토가 필요한 이유를 정하고 실제 동작과 수정 내용을 직접 확인하는 역할을 맡았습니다.

## 7. 면접에서 설명할 준비

1. **왜 Querydsl을 선택했는가?** 초기부터 지역·지원 유형·마감 상태·키워드를 조합하는 검색이 필요했다는 실제 선택 근거를 설명한다. 성능 우위 실험을 했다고 말하지 않는다.
2. **답변과 서류는 어떻게 연결되는가?** 질문 값·추가 확인·서류 적용 상태와 표시 정책을 설명한다. 미확인 항목을 비대상으로 숨기지 않는 이유도 구분한다.
3. **중복 저장을 왜 막아야 하는가?** 행 잠금과 revision 검사의 역할, DB와 스냅샷을 함께 갱신해야 하는 이유를 설명한다. AI의 최초 조사·수정과 본인의 두 탭 직접 재검증·수정 코드 검토를 구분한다.
4. **시연과 운영은 무엇이 다른가?** 실제 인증·서버 영속 저장·외부 호출 여부, 빌드 모드·라우팅·초기화 안내 차이를 설명한다.
5. **AI를 어떻게 활용했는가?** 요구사항과 판단 기준을 제공하고, 구현·오류 조사·검사를 맡긴 범위와 본인이 직접 설정·확인한 범위를 나눈다.
6. **팀원의 기여는 무엇인가?** PR #24·#26의 대규모 기능 확장과 본인의 후속 통합 범위를 구분한다. PR 작성자 계정만으로 팀원의 수작업 코드 비율을 추정하지 않는다.

기록만으로 특정 함수의 수작업 작성자를 확정할 수 없어 직접 코딩 기능 목록은 만들지 않았다. 제출 직전에 실제로 설명·수정할 수 있는 사례를 골라 문안을 압축하면 된다. 추후 직접 구현 근거가 생기면 해당 파일·커밋과 함께 추가한다.
